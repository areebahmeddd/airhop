Localization

Thirty five languages, three of them right to left, with no i18n library and no network. This chapter is why localization sits in the protocol spec rather than in a style guide, and where getting it wrong is a correctness bug rather than a cosmetic one.

In plain words

Explain it to a ten year old

The app knows how to say everything in thirty five languages, and it carries all of them inside itself rather than downloading them, because it has to work when there is no internet. Some languages count differently: English has one and many, Arabic has six ways. Some are written right to left, so the whole screen has to flip. And if you put an Arabic name in an English sentence, the punctuation jumps to the wrong side unless you tell it not to.

Why this is in the spec

ARCHITECTURE.md puts localization in section 10, beside the threat model, and that placement is an argument rather than an accident.

The app is scoped to blackouts, protests and disasters. The languages spoken there are Persian, Arabic, Urdu, Hindi, Bengali, Punjabi, Tamil, Indonesian, Filipino, Nepali, Ukrainian and Russian. An English-only UI during a shutdown in Tehran or Dhaka does not reach the person it was built for.

Three of those read right to left, and several are written in scripts with rendering rules the code has to know about. So this is a correctness concern, not a presentation one:

Three silent failures

  • A mention that never fires. If the word-boundary check uses an ASCII punctuation class, "@name。" does not count as a mention, so it passes no mute and raises no notification. Nothing looks broken. The feature simply does not work.
  • A name that reorders the punctuation around it. Without bidi isolation, an Arabic name in an English sentence drags the comma to the wrong side.
  • A row frozen in last week's language. A translated string written into storage keeps the language of the day it was stored, forever.

The decisions

DecisionRationale
Catalogs bundled, never fetched A translation download is a network call and a fingerprint, and it would fail in exactly the conditions this app exists for. 1,535 strings and 27 plural keys per language, compiled into the bundle, byte-identical on every device.
No i18n library i18next and react-intl bring namespaces, lazy network backends and untyped runtime keys, none of which suits an offline-first app with a bundled catalog.
Completeness enforced by tsc Every locale is Record<TranslationKey, string> derived from en.ts, so a partial locale does not compile. No coverage threshold, no partial state, no runtime fallback.
Plural rules hand-written Hermes has no Intl.PluralRules. 35 languages reduce to nine CLDR rule shapes, so plurals.ts is nine functions rather than a dependency plus a locale-data module per language plus a patched global.
Device language read through Intl Intl.DateTimeFormat().resolvedOptions().locale is present on Hermes on both platforms. expo-localization would mean a config plugin against native trees that must never see prebuild.
Translation at display, never at storage A t() result written into MMKV freezes in the language of the day it was stored. Persisted rows keep a systemKey and translate on render.
An RTL switch waits for the next launch React Native fixes layout direction at process start and iOS has no sanctioned self-restart. Both facts it depends on are read rather than assumed: I18nManager.isRTL for the direction in force, frameLanguage for the language it belongs to.
Every substituted value is bidi-isolated One wrap in interpolate covers every key. See below.
Word boundaries are Unicode, not ASCII A closing [\s.,!?;:] is the punctuation of a third of these languages. Comparisons normalise to NFC, since two keyboards spell the same accented character differently.
One digit system, locale grouping Every number the app renders uses Latin digits, prose counts included, and catalog.test.ts forbids a catalog its own. Grouping still follows the locale, which is the half that helps: Hindi and Tamil group by lakh.
Strings the OS renders stay where it reads them Passing them through the app would mean a native shim on both platforms for a permission dialog and a notification. npm run i18n:native holds them to the shipped set instead.

Plural rules, by hand

English has two forms. Russian has four. Arabic has six. CLDR defines six categories (zero, one, two, few, many, other) and every language uses a subset with its own selection rule. 

  THE NINE SHAPES

  otherOnly        no inflection for number at all. One boat and five
                   boats are the same word.       zh, ja, ko, th, vi, id, ms...

  oneIsOne         singular is exactly 1.         en, de, es, nl, sv, sw...

  oneIsZeroOrOne   zero takes the singular too. This is the difference
                   that makes "0 messages" wrong in Hindi and right in
                   English.                        hi, bn, fa, mg...

  filipino         the LAST DIGIT decides rather than the magnitude, so
                   4, 6 and 9 take the plural and 24 and 25 differ.

  frenchLike       zero is singular, and `many` exists only for round
                   millions, where the language says "million" rather
                   than the digits.

  spanishLike      as above but zero is PLURAL. The single point where
                   pt-PT parts company with pt-BR.

  polish           four categories chosen by the last digit, with a hole
                   punched in it for the teens, which are `many`
                   regardless of how they end.

  russianLike      similar shape, different holes.  ru, uk

  arabic           six categories, the full set.

Two implementation choices worth knowing

Which language takes which rule is a table at the bottom, not a comment on each function. So adding a language never edits a rule.

Integers only. CLDR's fractional rules key off the number of visible decimal places, which is a property of the formatting rather than the value, and every count here is a countable thing. A fraction returns other, which CLDR guarantees in every language.

And the verification: Node ships full ICU, so plurals.test.ts checks every rule against Intl.PluralRules itself. Nine hand-written functions are only defensible because they are tested against the reference implementation.

Right to left

Three shipped languages read right to left: Arabic, Persian and Urdu. RTL is not a text property, it is a layout direction: the entire interface mirrors. Back arrows point the other way, list rows flip, sheets slide from the other side, progress fills the other direction. 

  LTR                                RTL

  ┌────────────────────────┐        ┌────────────────────────┐
  │ ←  Chat name        ⋮  │        │  ⋮        Chat name  → │
  ├────────────────────────┤        ├────────────────────────┤
  │ [them]                 │        │                 [them] │
  │                 [me]   │        │   [me]                 │
  ├────────────────────────┤        ├────────────────────────┤
  │ Type a message     ➤   │        │   ➤     Type a message │
  └────────────────────────┘        └────────────────────────┘

Why switching to Arabic needs a relaunch

React Native fixes I18nManager.isRTL at process start. Changing it mid-session leaves half the tree laid out one way and half the other, and iOS has no sanctioned way for an app to restart itself. So the preference is stored and applied on the next launch, and the UI says so.

The implementation reads both facts rather than assuming them: I18nManager.isRTL for the direction currently in force, and frameLanguage for the language that direction belongs to. Assuming either produces a screen that is mirrored for the wrong language.

Layout uses logical properties (start and end rather than left and right) plus the helpers in src/i18n/layout.ts, so most components need no direction-specific code at all.

Bidi isolation

The most subtle problem in the whole chapter, and the one that is invisible until somebody with an Arabic name uses the app. 

  THE PROBLEM

  Template:  "{name} joined the channel."
  Name:      an Arabic string, which reads right to left

  Without isolation, the Unicode bidirectional algorithm resolves the
  punctuation NEXT TO the placeholder against the direction of whatever
  text landed in it. The full stop attaches to the Arabic run and
  renders on the WRONG SIDE:

      .‏محمد‎ joined the channel

  THE FIX

  Wrap every substituted value in isolation marks:

      U+2068  FIRST STRONG ISOLATE   (FSI)
      ...the value...
      U+2069  POP DIRECTIONAL ISOLATE (PDI)

  The algorithm now treats the value as one opaque neutral unit and
  leaves the surrounding punctuation alone.

The important design point: this is done once, in interpolate, so every key gets it. Doing it per call site would mean remembering it 1,535 times, and the failure is invisible to anyone testing in English.

Word boundaries and normalisation

Mentions

A mention is @name followed by a word boundary. The naive implementation closes on [\s.,!?;:], which is the punctuation of a third of these languages. A Japanese full stop is 。, an Arabic comma is ،, a Devanagari danda is ।. With an ASCII class, "@name。" is not a mention, so it passes no mute filter and raises no notification, silently.

So boundaries use Unicode property escapes rather than an ASCII class.

Normalisation

The same visible string has more than one encoding. "José" is either U+00E9 or U+0065 followed by the combining acute U+0301. They render identically and compare unequal.

Two keyboards genuinely produce different forms, so every comparison normalises to NFC. This applies at the wire boundary too: nicknames in ANNOUNCE TLV 0x01 are normalised on both encode and decode, so everything downstream compares one form. Without it, an accented name typed on one platform and announced from another fails to match: an at-mention never fires, and one person occupies two rows of a participant list.

That is a local canonicalisation, not a wire change. The packet still carries whatever bytes the sender chose, peer IDs derive from keys rather than names, and no signature covers the normalised form, so a peer that normalises differently stays fully interoperable.

Truncation

The nickname budget is 32 UTF-8 bytes, and truncation drops whole code points. Counting UTF-16 units is wrong twice over: 32 emoji is 128 bytes, four times the budget, and a slice can land inside a surrogate pair and emit a lone half that decodes to a replacement character on the far side.

The cut also backs off past a trailing combining mark or zero-width joiner, so a name never ends in a mark rendered on a dotted circle or half a split emoji. 32 bytes is about ten Devanagari characters, so the budget is reached most often in exactly the scripts that write with marks.

Which language each surface follows

Both platforms offer a per-app language of their own: Android 13's picker, which res/xml/locales_config.xml opts into, and iOS's, which appears once a bundle carries more than one localization. Airhop ships its own as well, because neither exists below Android 13 and because changing a system setting is not something to ask of somebody using this app under duress.

SurfaceFollows
Everything rendered by React NativeThe in-app picker
iOS permission dialogs, Android's foreground noticeThe OS per-app value
Reverse-geocoded place namesThe OS per-app value

On the default "system" preference the two agree, because the device language is re-sampled on every foreground edge. Android needs that: it recreates the Activity for a language change while keeping the JavaScript context alive.

Picking a language explicitly pins the app and leaves the OS-rendered strings on the system value. Writing through to LocaleManager.setApplicationLocales would close that gap and is deliberately not done: it recreates the Activity underneath a live mesh, in-flight transfers and possibly live voice, for five notification strings.

What never gets translated

Some strings cross the wire or derive an identity, so a translated variant is an interop bug rather than a cosmetic one. catalog.test.ts enforces the full list.

StringWhy
The username word lists (src/utils/username.ts)A generated name must resolve identically on every device, and in bitchat. Translating them would mean the same key produced a different name on a French phone.
The transmitted /hug and /slap textbitchat-iOS recognises an incoming emote by matching the English substrings. A translated emote is a plain message on their side.
Protocol constants, channel names, geohashesThey are identifiers.
Terms of Service and Privacy PolicyEnglish is the authoritative version, with the reader chrome around them translated.

Nothing on the wire carries a language

No locale, no script, no language tag appears in any packet. A Persian reader and an English one are indistinguishable at the protocol layer, and a courier holding sealed mail for either cannot tell them apart. That is a privacy property, and it is why localization belongs in the spec: a naive implementation that sent a locale header would leak something about who you are to every relay you cross.

What varies between devices

Text is identical everywhere because it is compiled in. Three things are not.

VariesHandling
Intl date and number output, per OS and OEM Centralised in src/utils/format.ts, formatted in the app's language rather than the device's, with cached formatters and Latin digits throughout.
Font glyph coverage for non-Latin scripts JetBrains Mono covers Latin, Greek and Cyrillic and none of the other ten scripts shipped. So the monospace face is reserved for machine data: a value from a formatter or a constant may use it, a value that came through a catalog key is prose and uses the system face.
Cached reverse-geocoded place names The OS geocoder answers in the device's language. Both native APIs accept a locale and expo-location exposes neither, and a native shim for a room-header label is not worth it, so place-names-store.ts keys its cache on that language and re-resolves.

The pseudolocale

A generated locale, qps-ploc, available in debug builds only. It accents every string, brackets it, and pads it past the longest real translation of the same key. 

  en:        "Send"
  qps-ploc:  "[Šéñð ‥‥‥‥‥‥]"

Three bugs it catches in one pass, without reading any language:

  • Hardcoded strings. Anything that does not change is not going through the catalog.
  • Layouts that break on longer text. German and Finnish routinely run 30 to 50 percent longer than English. Padding past the longest real translation proves the layout against all 35 at once.
  • Concatenation. A string assembled from fragments shows its seams immediately.

Drills

  • Why are translations bundled rather than downloaded? Because a translation download is a network call, which is both a fingerprint and a dependency that fails in exactly the conditions this app exists for. A user in a blackout would get an English interface at the moment they most need their own language. The cost is bundle size, 1,535 strings times 35 languages, which is a few hundred kilobytes of text and entirely affordable.
  • Why write plural rules by hand instead of using a polyfill? Hermes has no Intl.PluralRules, so something has to provide it. The usual answer, FormatJS, brings a dependency, a locale-data module per language, a patched global Intl, and a documented Android startup cost. The 35 shipped languages reduce to nine distinct rule shapes, so nine small functions replace all of that. It is only defensible because plurals.test.ts checks every rule against Node's full-ICU Intl.PluralRules, which is the reference implementation.
  • What is bidi isolation and why is it done in one place? A placeholder holds text of unknown direction. Without isolation, the Unicode bidirectional algorithm resolves the punctuation around it against whichever way that text reads, so an Arabic name in an English sentence drags the full stop to the wrong side. Wrapping every substituted value in FSI and PDI marks makes it one opaque neutral unit. It is done once in interpolate so every key gets it, because doing it per call site means remembering it 1,535 times and the failure is invisible to anyone testing in English.
  • Why is a translated string never written to storage? Because it freezes in the language of the day it was stored. A user who switches from English to Arabic would find their old system rows still in English forever, and there is no way to tell which stored strings came from a catalog. Persisted rows keep a systemKey instead and translate on render, so the whole history changes language with the setting.
  • Why does the mention parser matter for security or correctness? Because a mention drives muting and notifications. If the closing boundary is an ASCII punctuation class, then "@name。" in Japanese, "@name،" in Arabic, or "@name।" in Hindi is not recognised as a mention. The user is not notified, their mute rules do not apply, and nothing looks broken. It is a feature that silently does not work for a third of the shipped languages, which is exactly the kind of failure that never gets reported as a bug.
  • Why is the monospace font restricted to "machine data"? Because JetBrains Mono covers Latin, Greek and Cyrillic and none of the other ten scripts shipped. Setting it on prose means a Bengali or Amharic user gets fallback glyphs or tofu boxes. The rule that follows is mechanical: a value from a formatter or a constant may use the mono face, a value that came through a catalog key is prose and uses the system face.
  • Someone proposes sending a locale tag in the announce so peers can localise system messages. Respond. No. Nothing on the wire carries a language today, which means a Persian reader and an English one are indistinguishable at the protocol layer, and a courier holding sealed mail for either cannot tell them apart. A locale tag would be a persistent identifying attribute broadcast to every device in radio range and every relay, narrowing who someone is in exactly the situations where that matters most. System messages are rendered from a key locally, which achieves the same result with no wire change.
