The verdict, up front

Doable

Yes, and largely done. The protocol work is real, correct against a vendored reference, and tested to an unusually high standard for a project of this size. The parts that are not done are known and mostly not hard.

Makes sense

Yes. The mission is coherent, the architecture follows from it, and the wire-compatibility decision is the single smartest strategic choice in the project.

Worth it

Yes, with one condition. The engineering deserves the credibility it is building. Right now the documentation overstates what ships in several places, and that is the fastest way to lose that credibility with exactly the audience that matters.

The one thing to fix first

Close the gap between the README and the code. Four features are presented as shipped and are not. A reviewer who finds one assumes the rest of the claims are equally soft, including the security ones, which are in fact sound.

Is it doable

Mostly the question is already answered by the code existing. So the useful version is: what is the residual technical risk.

AreaAssessment
The protocol core solid 200k lines of TypeScript with no native dependencies in src/core/, which means the wire format, both Noise patterns, the ratchet, gossip sync, the courier and the routing all run under jest with no device. The comments are unusually good: most non-obvious lines carry the reason, and several carry the bug that motivated them.
Cryptographic composition sound, unaudited Correct primitives (@noble, Cure53 audited), correct constructions, and the two most dangerous mistakes already found and fixed: seeding the ratchet from the public handshake hash, and accepting unsigned announces. Nothing in the composition looks wrong to me. That is not the same as an audit, and the project says so.
The single-codebase bet paying off bitchat's two native codebases drifted until an Android fragment size mismatch broke cross-platform messaging for months. Airhop has one implementation, so a protocol bug exists on both platforms or neither. The cost, a JavaScript bridge in the hot path, is not the bottleneck: the radio is.
Native layer minimal and correct Five modules, none of which knows what a packet is. The reconciler pattern in both radio controllers is the right shape and eliminates a whole class of one-shot-start bugs.
Testing exceptional See below. This is the strongest part of the project.
Scale above the low tens unknown 25 phones converge. 200 is untested, and the mitigation is documented and absent.
Hardware behaviour unproven BLE timing, MTU on real silicon, OEM battery managers, relay hardware, real Tor circuits. All modelled from documentation.
iOS release pipeline manual CI compiles an unsigned Release build, but distribution credentials do not exist, so the shipped .ipa is produced by hand from Xcode. Android is automated end to end.
Maintainer bus factor one Independently built and maintained by one person. This is the largest non-technical risk by some distance.

Does it make sense

QuestionAnswer
Is the problem real? Yes. National internet shutdowns, disaster infrastructure failure and congested cells during mass gatherings are all routine. Every mainstream messenger has an invisible dependency on a company's servers, an ISP's network and DNS, and all three are removed regularly.
Is the architecture the right shape for it? Yes. Offline first with the internet as an extension is the correct direction of dependency, and it is enforced by design rather than intended. The one rule, that layer 3 enhances layer 2 and never enables it, resolves most design arguments.
Is flooding the right routing? Yes. Every routing protocol assumes the topology can be modelled and kept current. When the nodes are people turning around and putting phones in pockets, that assumption fails, and a route table is also an attack surface and a privacy leak. Controlled flooding gives up optimality for robustness, which is the right trade here.
Is bitchat compatibility worth its constraints? Emphatically yes, and it is the smartest decision in the project. The honest weakness of any phone mesh is user density, and sharing a wire protocol doubles the effective user base at zero cost. It constrains the file caps, the courier expiry, the Nostr cipher, the packet registry and the padding rules, and every one of those constraints is worth accepting for that.
Does the payment feature belong? Yes, though it is the most debatable. Settling a bill in a dead zone is a real need and Cashu is the only mechanism that works offline. It also brings a third-party library, a trusted party, bearer secrets on disk, and an entire class of "did the money move" states. It is correctly marked optional.
Does live voice belong? Yes. At 2 KiB/s it is 11 percent of one link, so it is nearly free, and in the target scenarios (a march, a disaster site) push-to-talk is more useful than typing.
Do the social bridges belong? not yet Airhop already has an internet layer that is strictly better on every privacy axis. The bridge buys distribution rather than capability. Chapter 48.
Does the AI assistant belong? questionable On-device inference with nothing leaving the phone is philosophically consistent, and a 1 to 3 billion parameter model on a phone in a disaster is of genuinely marginal use. It is a large amount of work and bundle for a feature nobody in the target scenario is asking for.

Is it worth it

Worth it to whom, and against what. Three framings, because they give different answers.

FramingVerdict
As a product conditional The addressable moment is narrow: it is used when everything else fails. Retention in normal conditions will be poor, because in normal conditions Signal is better. That is fine if the goal is to be installed before it is needed, and it makes distribution the hardest problem, not engineering.
As infrastructure clearly yes Every additional compatible node makes the whole mesh better, including bitchat's. Two implementations of one protocol is healthier than one, and the conformance harness is a contribution to both.
As an engineering artefact yes The multi-device simulation, the reasoning density in the comments, and the willingness to document a project's own flaws are all above the norm for this class of project. It is a credible portfolio of judgement, not just of code.

The one condition

This project's currency is credibility. It is asking people to trust it in situations where being wrong has real consequences, without an external audit, on the strength of its own documentation. That documentation is unusually honest in the places that are hard (the courier tag is not unlinkable, Tor use is visible, peer IDs do not rotate) and overstates in places that are easy to check (four features presented as shipped that are not).

A reviewer who finds one overstatement discounts everything else, including the security claims, which are sound. Fixing this costs an afternoon and is the highest return work available.

What is genuinely excellent

  1. The multi-device simulation. Twenty isolated copies of the app in one process via jest.isolateModules, on a single fake clock, with a radio fabric that models discovery latency and the backgrounded-iPhone asymmetry, asserting properties rather than outcomes. Nothing in production code had to change to allow it. I have seen commercial teams with far more resources ship a mesh product with nothing comparable.
  2. The bitchat actor. A node written to the other project's rules, whose job is to disagree when Airhop is wrong. This is the difference between claiming compatibility and testing it, and it caught at least four silent interop failures.
  3. Conformance tests that parse the vendored source. Reading maxPayloadBytes out of bitchat's Swift and failing if Airhop's caps stop fitting, and failing if their packet type allocation comes within 16 of Airhop's range. That turns "remember to check" into a red build.
  4. The reasoning density in comments. Most non-obvious lines carry the reason, and many carry the specific bug that motivated them. The panic wipe, the courier store, the fragment manager and the packet codec read like design documents. This is the single biggest factor in how quickly a new maintainer becomes productive.
  5. Honesty as an engineering practice. ChannelSendResult represents "reached nobody". PanicWipeResult reports whether the keys actually went. Offline ecash is stored as unverified. DLEQ reports "unchecked" rather than "valid". The Tor banner never over-claims. These are type signatures, not copy, and that is what makes them hold.
  6. Ordering as a security property. Several defences are correct only because of the order they run in: the group creator pin checked before the removal branch, LEAVE verified before the relay decision, the fragment size check before the assembly table is touched, the Tor gate closed before the claim is lowered. Someone thought carefully about each.
  7. The i18n work. Bidi isolation done once in interpolate, Unicode word boundaries for mentions, NFC normalisation at the wire boundary, nine hand-written plural rules verified against Node's ICU, and the rule that nothing on the wire carries a language. Most products treat localisation as a presentation concern; this treats it as correctness, correctly.

Finding class 2: engineering gaps

#GapImpactEffortSeverity
G1 Full fanout instead of subsetting. Every node relays to every non-ingress link. Transmissions per message grow with the number of edges. Fine at 25 phones, unknown at 200, and the failure is silent: writes get refused, fragments drop, delivery probability falls with nothing logging. Gossip sync already provides the repair mechanism that makes subsetting safe. Medium. bitchat's algorithm is known and the sync safety net exists. high
G2 Prekey bundles not reconciled through gossip sync (bit 9). A device arriving after a bundle has flooded cannot pull one, so courier envelopes silently fall back to sealing against the long-lived static key. Forward secrecy is lost with nothing in the UI to say so. The README specifically advertises courier mail as "sealed to a one-time prekey for forward secrecy". Low. The bit exists in bitchat, the store exists here, the sync framework exists here. high
G3 No Tor bridges or pluggable transports. In a country that blocks Tor the feature does not work at all; in one that monitors, enabling it is itself a signal. This is the largest privacy gap against the stated threat model. bitchat has it too. High. Needs pluggable transport support in the vendored Arti build plus a bridge acquisition path. medium
G4 Android depends on Orbot rather than embedding Arti. closed Resolved. Arti is now embedded on both platforms from one Rust crate, with one lifecycle, one status word and one set of return codes. The Orbot detection path is gone. Chapter 25. Medium to high. A native integration, but there is a working reference. medium
G5 Nostr DMs have no forward secrecy. Static ECDH between two long-lived identities: compromise either key and every archived gift wrap between them is readable. Inherited from NIP-17 and bitchat's cipher and not fixable unilaterally, but "end to end encrypted" reads stronger than it is. Not fixable alone. Documentable today. medium
G6 Private channel keys never rotate and cannot be revoked. One symmetric key travels in the invite link with no roster and no member cap. Anyone who ever obtains it reads everything they can get hold of, and there is no way to remove someone. This is a deliberate trade for unbounded membership, and it is not stated as plainly as the courier tag flaw is. Medium. Epoch rotation exists for groups and could be adapted. medium
G7 No key rotation or revocation anywhere. A compromised identity can only be abandoned. There is no "this key is retired" message, so contacts keep a dead pin with no signal. High. It interacts with TOFU pinning, courier tags, the outbox and contact storage. medium
G8 Scheduled relays are not cancelled when a duplicate arrives. The timer map exists but the receive path drops duplicates before reaching cancellation, so the relay fires anyway. Wasted airtime in exactly the dense case where jitter is deliberately long. bitchat cancels. Low. The machinery is already there. medium Best effort-to-value ratio on this list.
G9 WiFi Aware shares the Bluetooth paced queue. A 250 Mbps path runs at 18 KiB/s. The 25 ms pacing is a Bluetooth requirement, not a protocol one, so the fast path currently buys link diversity rather than speed. Low to medium. medium
G10 The mesh bridge covers one geohash-6 cell only. Two islands a few hundred metres apart on opposite sides of a cell boundary never meet, and boundaries do not follow streets. Documented as a follow-up. Low. Subscribe to the eight neighbouring cells. low
G11 Relay hardware never run against hardware. Simulated against a bare repeater only. A v1.3.0 roadmap item. Low, once a node exists. low
G12 Compression parity unverified against Apple's encoder. Verified against zlib 1.3.1, which matches Android. If Apple's differs, signature verification of Airhop packets on iOS bitchat could fail. The mitigation (reusing the received wire form) means it would only affect locally originated packets. Low, and needs Apple hardware. low
G13 Gateway recovery time is unbounded and unasserted. N04 records the recovery leg but does not bound it, so how long a gateway takes to become useful again after losing signal is unmeasured. Low. low
G14 mesh-service.ts is 6,349 lines. Defensible as a composition root, and it is the file most in need of a second pass. Twenty packet handlers, two radios and six subsystems in one class is a lot of surface for one person to hold, and it is the biggest onboarding cost for a second maintainer. Medium, and risky. I would not do it without a reason. low
G15 No 100+ node scenario. The honest answer to "does it work in a crowd of 200" is currently "we do not know". Adding the scenario turns that into a number and gives G1 a before-and-after measurement. Low. The harness supports it. medium

Real blockers, and imagined ones

Genuinely impossible

  • Cross-platform high bandwidth. Android WiFi Aware and Apple's AWDL are different protocols with no bridge. Apple's iOS 26 Wi-Fi Aware framework could change this, at the cost of an iOS 26 floor.
  • Live video. An order of magnitude over the BLE link budget, and no cross-platform fast path to fall back on. Packet type 0x30 was specified and retired.
  • Offline double-spend prevention. Only the mint knows whether a proof is spent, and only over the network.
  • Discovering a backgrounded iPhone from Android. CoreBluetooth moves the UUID into the overflow area. No application-side fix exists.
  • Push notifications without a push server. And a push server is a party that knows who is messaged and when.
  • Raising the file cap. bitchat-iOS refuses silently past ~1.13 MiB, and Android allows 10 MiB, so there is no cross-platform number.
  • Hiding that Tor is in use, without bridges.
  • Making a mesh work with nobody in it. Hardware is the only answer.

Hard but not blocked

  • Peer ID rotation. Breaks the direct-link rule, courier tags, contact pinning and the outbox at once. bitchat has a design document and has not shipped it. Solvable with coordination.
  • An unlinkable courier tag. Needs a v2 tag keyed on a shared secret, agreed across implementations. Purely a coordination problem.
  • Forward secrecy for Nostr DMs. Needs a NIP or a bitchat-side change.
  • The LAN transport. Genuinely straightforward, and the highest-value unshipped transport work: cross-platform, needs no radio the phone might lack, carries the whole protocol.
  • Arti on Android. There is now a working reference.
  • Fanout subsetting. A known algorithm with the safety net already running.

What I would tell a new maintainer on day one

  1. Read the comments. They are not decoration. Most non-obvious lines carry the reason, and many carry the bug that motivated them. Changing a line whose comment explains why it is that way is how a fixed bug returns.
  2. The wire format is not yours. Every shared constant is a contract with two other implementations. Every silent interoperability failure in this project's history came from changing one in good faith for a defensible local reason.
  3. Never run npx expo prebuild. It deletes every native module.
  4. Never rename a keychain item, an HKDF separator, or an MMKV partition id. They are addresses, not labels. Renaming orphans user data and, for a keychain item, leaves a secret the panic wipe can no longer reach.
  5. Assume every packet is hostile. Anything reachable from the receive path is attacker-controlled. Every collection needs a cap, every length needs a bounds check, and a malformed frame must return null rather than throw.
  6. Never claim more than you know. If a new state can be uncertain, make the type say so. That principle is why the delivery states, the wipe result and the DLEQ result are shaped the way they are.
  7. Run the simulation before and after any protocol change. And if a scenario cannot be written against the device control surface, that is a finding about the app rather than a gap in the harness.
  8. When in doubt, do what bitchat does. Principle 7 exists because it has been right every time so far.

Closing

This is a serious piece of engineering built by one person in their spare time, on top of a well-chosen foundation, with a level of testing and self-documentation that most funded teams do not reach. The protocol work is correct, the security reasoning is sound, and the places where it is weak are almost all places where it says so first.

The gap between what the code does and what the README says it does is the only thing in this review that is both easy to fix and actively costing the project something. Fix that, ship the four small gaps, get the audit, and this stands on its own.
