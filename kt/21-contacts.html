In plain words

Explain it to a ten year old

A contact card is like a business card with a secret lock printed on it. Anyone who has your card can lock a box that only you can open. Your phone can show that card as a square pattern on the screen, and a friend's phone can read it with the camera. If they read it off your actual screen, standing next to you, their phone knows it really came from you. If somebody forwarded them the card in a message instead, the lock still works, but nobody can be sure who sent it. Airhop keeps those two facts separate, forever, because they are not the same fact.

Two questions, two fields

The distinction the whole chapter rests on

"How did these keys get onto my phone?" and "Has a human confirmed they are the right keys?" are different questions. They are stored in different fields and they change under opposite rules.

FieldAnswersValuesMay it be lowered?
source How the keys arrived qr, link, manual Never lowered, but may be raised by a later write
verification Whether a human checked them in-person, fingerprint, or absent Never removed once earned; only a write carrying one may set it

They are independent. A contact whose keys arrived through a link can be verified later on a phone call, and that verification is exactly as strong as a camera scan. What differs is what each one is allowed to do, which the merge policy below spells out.

Why source alone was not enough

Older records predate the verification field. The reader isVerified() falls back to source === "qr" for those, because at the time a qr source could only have come from the camera. That fallback is why no migration was needed, and it is also why source could not simply be reused: today a card can reach the app through a link and still be verified, and a card can reach it through the camera as the first step of two.

The three code formats

The add-contact screen accepts three things. They are unambiguous, so the parse order is about cost rather than precedence.

FormatCarriesSigned?Expires?Who emits it
airhop:v1/<base64url> Peer ID, Noise key, signing key, nickname, Nostr key No No Airhop, from the Profile screen
bitchat://verify?... Noise key, signing key, nickname, optional npub Yes, Ed25519 Yes, 5 minutes bitchat, from its verification sheet
airhop://peer/<16 hex> A peer ID and nothing else No No Deep links, and typed by hand

The weakest of the three, and why the share button avoids it

airhop://peer/<id> is the one artifact that cannot reach the person it names. A peer ID is a hash of the Noise key and carries no keys at all, so the recipient can label the contact but cannot encrypt to it, and can only message back from inside Bluetooth range once an announce has been heard. "Share QR" therefore shares the image, which carries the whole card. The bare link appears only as a text fallback when the share sheet itself is unavailable.

The contact card, byte by byte

src/core/crypto/contact-exchange.ts. Fixed header, variable nickname, trailing Nostr key. There is exactly one version, because Airhop had no install base when it was designed and a versioned pair costs a branch on every read forever. 

  offset  size   field
  ──────  ────   ─────────────────────────────────────────────────
   [0]     1     version, always 1
   [1]     8     peerID          first 8 bytes of SHA-256(noisePub)
   [9]    32     Noise static    X25519 public key
   [41]   32     signing         Ed25519 public key
   [73]    1     nickname length 0 to 32
   [74]    n     nickname        UTF-8, truncated at 32 BYTES
   [74+n] 32     Nostr pubkey    secp256k1 x-only

  total = 106 + n bytes,  106 to 138

  then:  "airhop:v1/" + base64url(bytes)
         141 to 184 characters, comfortably inside a QR code

Three keys travel together, and each earns its place:

  • The Noise key is what a session opens against. A contact without one is a peer ID and nothing more, which is why hasKeys() tests this key and not the signing key.
  • The signing key is not decoration. When a LEAVE arrives after a restart the live registry holds no pin, and leaveIsAuthentic falls back to this stored copy. It is also half of the safety number.
  • The Nostr key is what makes a contact met only by QR reachable over the internet, having never been in Bluetooth range. The registry forgets a peer's npub 60 seconds after their radio disappears; a contact keeps it for good.

The nickname is truncated at 32 bytes, not characters, matching the announce path exactly. Encoding never throws for an over-long name, because the wire format already silently truncates and two different behaviours for one field is how formats drift.

Reading a bitchat verification QR

src/core/crypto/bitchat-verify-qr.ts. This is the only way an Airhop user can pick up a bitchat user's identity in person: our format is unreadable to them, and theirs was unreadable to us. 

  bitchat://verify?v=1
                  &noise=<64 hex>
                  &sign=<64 hex>
                  &nick=<utf8>
                  &ts=<unix seconds>
                  &nonce=<base64url>
                  &sig=<128 hex>
                  [&npub=<bech32>]

  signature covers, each field length-prefixed:

     "bitchat-verify-v1"   domain separator, byte identical to theirs
     v, noise, sign, npub, nick, ts, nonce

  checks, in this order:
     1. is it a bitchat verify URL at all?     no  -> keep scanning
     2. all required params present, hex OK?   no  -> "tampered"
     3. |now - ts| <= 5 minutes ?              no  -> "expired"
     4. Ed25519 verify with the key in `sign`  no  -> "tampered"
     5. peerID = SHA-256(noise)[0:8]           recomputed, never trusted

Freshness is checked before the signature, on purpose

A stale code is by far the likelier case: a screenshot, a photo of a screen, a code left open on a desk. It is also the one the user can act on, because "ask them to show it again" is a fix. Through a viewfinder an expired code looks identical to an unreadable one, so the two outcomes are reported separately rather than both becoming a silent non-scan.

This interop is one way, and the UI must not pretend otherwise

On bitchat's side that QR names a peer they are already connected to, and the real proof is a nonce challenge sent over the live Noise session afterwards. Airhop does not answer their challenge protocol. So the bitchat user learns nothing, sees no verification on their side, and the Airhop user has read the card for what it carries rather than for what it means to them.

The five minute window is the one security property bitchat's format has that ours does not. It is symmetric on purpose, both past and future: a future-dated stamp must not buy a QR a longer life than a fresh one gets. Our own cards carry no expiry, which is the honest trade for a card that is meant to be saved, shared and used later.

The binding check

Every card, from every route, faces one test before anything is written: 

  SHA-256(card.noisePubKey)[0:8]  ==  card.peerID   ?

  no  -> reject the card entirely, return false
  yes -> the peer ID and the Noise key belong together

This is the whole reason a peer ID means anything. A card is attacker-shaped input: whoever we are talking to chose every byte of it. Without this check a forged QR could claim somebody else's peer ID while supplying attacker-controlled keys, and every DM the user then believed they were sending to that contact would be encrypted to the attacker instead. bitchat-iOS rejects announces on exactly this check, under the name senderMismatch.

The attack the binding check does not catch

A peer ID is SHA-256 of the Noise key, and that key is public. So an attacker can build a card carrying a victim's real peer ID and real Noise key, passing the binding check cleanly, while substituting their own signing key. Announce-level pinning refuses that. A card trusted merely because it arrived would have waved it through. This is precisely why inPerson exists, and why the safety number covers both keys rather than the peer ID.

Five ways a contact arrives

RouteWhat arrivessourceMay re-pin?Verified?
Camera scan of their live screen Full card qr yes Yes, in-person
Card picked from the photo roll Full card link no No
Contact code pasted from a message Full card link no No
Card sent inside a geohash DM Full card link no No
Peer ID typed or deep-linked ID only manual no No

Two things vary independently: what arrived, and where it came from. The photo roll and the camera can carry byte-identical payloads. Only the camera saw the other phone, so only the camera earns inPerson. That flag is captured at the moment of the read, because by the confirm step every route looks identical.

All routes converge on the same confirmation step, showing the avatar, the username and the peer ID before anything is saved, so identity is double-checked however it arrived. There is a sixth path that is not user-initiated: saveIfAbsent, which keeps anyone you message as an unverified contact. That is Signal's behaviour, and it is the single entry point for it so that every conversation-starting path stays consistent.

The merge policy

Four screens can write a contact. A rule that several callers have to remember is not a rule, so the policy lives in one pure function, mergeContact(), and is tested on its own. 

  SOURCE_RANK:   manual 0  <  link 1  <  qr 2

  field            rule on a re-write
  ───────────────  ────────────────────────────────────────────────
  source           max(prior, next). Never decreases.
  verification     kept once earned. Only a write carrying one sets it.
  addedAtMs        min(prior, next). A re-add is not a new acquaintance.
  verifiedAtMs     kept once set.
  nickname         a name already on file WINS over one arriving now.
  localNickname    kept unless the caller supplies one.
  nostrPubkeyHex   first key wins. A new npub for a known peer is
                   suspect, not authoritative.
  noisePubKeyHex   filled when absent; replaced ONLY by source === "qr"
  signingPubKeyHex filled when absent; replaced ONLY by source === "qr"

The property that holds across all of it: a write can never lower a contact's standing. That is what makes it safe for the geohash card path to state source: "link" flatly, even for somebody already verified in person.

Why "a name already on file wins"

Re-adding somebody must never replace what they called themselves at first contact. If it did, an attacker who could get a card in front of the user could rewrite a familiar display name to something misleading, and the user's own memory of the first exchange would be the only thing contradicting the screen.

Three narrower writers exist beside addContact, each deliberately unable to do what the others do:

WriterSetsCannotWhy it exists
setProvenKeys Noise and signing keys, together Replace keys already held; grant verification saveIfAbsent reaches only what the registry held at that instant, so a messaged contact often carries no keys. A safety number needs both, which is why they travel together. Only an authenticated peer state qualifies as proof, because that rides inside a completed Noise session and a session completes only when the remote static key hashes to the claimed peer ID.
setNostrPubkey The Nostr key, once Overwrite a stored key; create a contact An announce claiming a new npub for a known peer is treated as suspect. It never manufactures a contact for a stranger just because we heard them.
markVerified verification: "fingerprint" Touch any key at all Confirms what is already stored. A substituted key would have produced words that did not match, so there is nothing to import and no re-pinning power to gate. Refused for a contact with no keys, since there would have been nothing to compare.

Why the local nickname is a separate field

Writing your own label over nickname would destroy the only copy of what the peer claims to be called. The contact sheet shows both, so "who they say they are" stays checkable after you have renamed them to something you recognise. The label is gated on holding their keys rather than on verification, matching bitchat's canEditLocalAlias: it is typed against one specific peer ID and never transmitted, so no attacker can cause one, but a label on an identity the app cannot address is a label on nothing.

A contact is a known identity; a peer is a reachable one. This store never forgets; the peer store is rebuilt from live announces and forgets on restart. Chapter 14 is the long version.

The safety number

src/core/crypto/fingerprint.ts. Six words, identical on both phones, read aloud over a channel the two people already trust: a call, a radio, another app. The strength comes from that channel, not from the app. 

  per identity:

    fp = SHA-256( "airhop-fingerprint-v1" || noisePub || signingPub )

  the pair, on BOTH phones:

    ours, theirs  ->  sort byte-wise, lower first
    sn = SHA-256( "airhop-safety-number-v1" || first || second )

  words:

    take 6 x 7 bits from sn, most significant bit first
    index into a 128 word list
    ->  6 words,  42 bits

Four decisions in that diagram are load-bearing:

  • It covers both keys. A peer ID is SHA-256 of the Noise key alone, so reading a peer ID aloud would not catch the attack that matters: a forged card that keeps the victim's real peer ID and Noise key and substitutes the attacker's signing key.
  • The inputs are sorted. Neither side has to know who is who. Without sorting, each side derives a different string and the exchange doubles in length.
  • Two domain separators. The pair hash takes the peer hash's output as its input, so without distinct prefixes one could be substituted for the other.
  • It imports nothing. A match sets a flag, a mismatch tells the user to stop. Neither writes a key, so unlike the scan path there is no re-pinning power to gate.

Why six words and not eight

42 bits is sized against the attack, not to a round number. Forging a match means grinding key pairs until the pair hash lands on the same six words: 242 work for one targeted pair, and it has to be finished before those two people speak. Every extra word is another word to read over a bad line, and a code nobody finishes reading protects nothing. Signal uses 60 digits for a similar reason arrived at differently: theirs is designed to be compared visually side by side, ours to be spoken.

Sharing your own code

The Profile screen renders encodeQRContent(getContactCard()) as a QR image, with the same string shown underneath as copyable text. They are the same bytes, which is why one warning sentence covers both. 

  Profile -> QR
     ├─ image  : the full card, scannable
     ├─ text   : "airhop:v1/..." , tap to copy
     └─ Share  : writes a PNG to cache, opens the share sheet
                 fallback if sharing is unavailable:
                 a message containing airhop://peer/<id>
                 (the weak form, and only as a last resort)

If the mesh service is not up yet the QR falls back to the bare peer ID, which older scanners also still accept. The photo-library "add" permission exists partly for this: saving your own QR to the camera roll is a supported way to hand it over later.

What breaks it

  • A forwarded card allowed to re-pin. The whole reason inPerson defaults to false. Without it, anyone who could get a link in front of the user could overwrite the signing key of a contact verified face to face, and the binding check would not notice because the peer ID and Noise key would be genuine.
  • An expired bitchat QR reported as unreadable. Not a security failure, a usability one, and it was worth code to fix: the two look identical through a viewfinder and only one has an obvious remedy.
  • A nickname truncated differently from the announce path. Byte truncation, not character truncation, in both places. Get it wrong and one person renders two ways in one app.
  • A safety number compared over the wrong channel. The code's strength is entirely the channel's strength. Reading it to each other inside Airhop proves nothing, because that is the channel under suspicion. The interface has to make the out-of-band requirement obvious, and this is the failure most likely to happen in practice.
  • A card whose peer ID does not derive from its Noise key. Refused outright. This is the check that makes peer IDs meaningful, and it applies to every route including the geohash DM path.

If you removed it

The mesh would still work, and it would be strictly worse in three ways. Nothing would survive a restart: peers are learned from announces and forgotten, so every conversation would need the other person in radio range to begin. Nobody could be reached over the internet without having first met on Bluetooth, because the npub would only ever live in the 60 second registry window. And there would be no way to detect an impersonation at all, because detecting one requires having pinned what the identity looked like before. Contacts are what turn a proximity chat into an address book.

Alternatives

ApproachHow it worksWhy not here
Phone number directory Signal's model: a server maps numbers to keys Requires a server, an identifier tied to a legal identity, and a phone network. Airhop's entire premise is that none of the three is available.
Web of trust PGP: contacts sign each other's keys, trust is transitive Nobody ever understood the trust calculus, and it leaks the social graph by design, which for this threat model is the exact thing being protected.
Key transparency log An append-only log of key bindings, auditable by clients The right answer for a system with servers, and genuinely strong. It needs an always-online log and a gossip protocol to detect a split view, neither of which survives being offline in a field.
Numeric safety number Signal's 60 digits, compared visually Fine on a screen, poor over a bad phone line. Words survive being spoken, which is the channel this design assumes.
Challenge-response verification bitchat's model: a nonce over the live session after the scan Stronger against a replayed QR, and it is why their code carries an expiry. It also requires the peer to be connected at that moment, which rules out verifying a contact you have not met yet. Airhop reads their QR but does not answer the challenge.

Drills

  • Someone sends you an Airhop contact code in a chat app and you paste it in. Are those keys usable? Are they trustworthy? Usable, yes. The card is self-consistent and the peer ID is checked against SHA-256 of its own Noise key, so encryption to that identity works and a DM route can be opened immediately. Trustworthy, no. Nothing about the delivery proves who sent it, because a card forwards as easily as a URL. It is stored with source: "link", carries no verification, and is specifically not allowed to replace keys already bound to that peer ID. The fix is a safety number comparison over a channel you trust, which upgrades the record to verification: "fingerprint" without touching a single key.
  • The binding check passes. Why is that not enough? Because a peer ID is SHA-256 of the Noise key, and the Noise key is public. An attacker can take a victim's real peer ID and real Noise key, both of which they can hear off the air, and build a card that passes the binding check while carrying their own Ed25519 signing key. That gets them the ability to forge signed announces and LEAVEs for the victim's identity. Announce-level TOFU pinning refuses it; a card trusted merely because it arrived would not. This is why only an in-person scan may re-pin, and why the safety number hashes both keys rather than the peer ID.
  • Why is a card read from the photo roll treated differently from the identical card read by the camera? The payload can be byte-identical, so the difference is not in what arrived but in what was witnessed. The camera saw the other phone, in person, at that moment. The photo roll saw a file, which could have been sent by anyone, screenshotted from anywhere, or posted publicly. Only physical presence is evidence about who is on the other end, and evidence is what earns the right to overwrite a key that was already pinned. The flag is captured at the read rather than later, because by the confirm step every route looks the same.
  • Explain why markVerified is allowed to run on a contact whose keys arrived through a link, when adding that link's card was not allowed to re-pin anything. Because they do opposite things. Adding a card writes keys, so it needs authority proportional to the damage a wrong key does. markVerified writes no key at all: it records that a human compared a code derived from keys already stored. If those stored keys had been substituted, the six words would not have matched and the comparison would have failed. So there is nothing to gate, and gating it would make verification impossible for exactly the contacts that most need it. It is refused only when the contact has no keys, because then there was nothing to compare.
  • Why does the safety number sort its two inputs before hashing? So both phones derive the same string without either side needing to know which of them is "first". Without sorting, A would compute H(A||B) and B would compute H(B||A), two different codes, and the only fixes are agreeing a role in advance, which there is no channel to do, or reading both codes aloud, which doubles the length of the one part of the flow users already find tedious. Sorting is free and removes the whole problem.
  • A user asks why the app kept a contact they never explicitly added. That is saveIfAbsent, and it is deliberate: anyone you message is kept as an unverified contact, which is Signal's behaviour. Without it the app would forget the person the moment their radio disappeared, since the peer store is rebuilt from live announces. It is a single entry point precisely so every conversation-starting path behaves the same way. The record it writes is the weakest possible one: whatever keys the registry held at that instant, source at its lowest applicable rank, and no verification. It can later be upgraded by setProvenKeys once a Noise session completes, which is proof rather than an announce.
  • Why does an incoming announce claiming a new Nostr key for a known peer get ignored? Because an announce establishes nothing. It is unauthenticated in the sense that matters here: anyone who can hear a peer ID can emit a packet carrying it, and the npub is the routing address for internet-delivered mail. Accepting a replacement would let an attacker redirect a contact's gift-wrapped DMs to a relay identity they control. First key wins, in both setNostrPubkey and the merge policy, and a genuine key change is handled by re-exchanging cards in person rather than by trusting the air.
