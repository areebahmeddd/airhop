In plain words

Explain it to a ten year old

Your wallet has three pockets. One holds coins you can spend right now. One holds coins you have promised to somebody but who has not taken them yet, so you cannot spend them again, but if the person never turns up you can put them back. And one holds coins somebody handed you that you have not been able to check with the bank yet, which might be real or might already have been spent by them.

The three buckets

  ┌─────────────────────────────────────────────────────────────┐
  │  SPENDABLE           proofs you hold and can use now         │
  │    verified: true    the mint has confirmed them unspent     │
  │    verified: false   received offline, NOT yet confirmed     │
  ├─────────────────────────────────────────────────────────────┤
  │  RESERVED            set aside for a send already serialised │
  │                      into a token string. Not spendable.     │
  │                      RECLAIMABLE if it never lands.          │
  ├─────────────────────────────────────────────────────────────┤
  │  (removed)           swapped, melted, or reported spent by   │
  │                      the mint. Gone from the balance.        │
  └─────────────────────────────────────────────────────────────┘

  Balances are per (MINT, UNIT) and NEVER POOLED.
  The headline never folds unverified or reserved into itself.

Why "reserved" rather than "deleted"

The moment a token string leaves the device, those proofs must not be spendable again from here, or the wallet double-spends itself. But deleting them means an abandoned sheet, a crash, or a DM that never routes destroys the value. Reserving them, and keeping the serialised token on the transaction, makes every one of those cases recoverable. This is the single design decision the whole wallet is built around.

Send, reserve, reclaim

  quoteSend(amount)
     │  select proofs, compute the recipient's swap fee
     │  "send 100" must mean THEY CAN CLAIM 100
     │  report exact: true/false
     │     false = the denominations cannot make this amount without
     │             overpaying. OFFLINE THERE IS NO CHANGE, so the
     │             difference goes to the recipient. Consent required.
     ▼
  prepareSend(quote)
     │  move the selected proofs to RESERVED under a txId
     │  serialise the cashuB token and STORE IT ON THE TRANSACTION
     ▼
  hand the token over (DM, QR, copy, mesh)
     │
     ├── confirmSend(txId)   the recipient acknowledged
     │      -> drop the reserved proofs permanently
     │
     ├── reclaimSend(txId)   nothing landed, the user takes it back
     │      -> release the reserved proofs to spendable
     │
     └── failSend(txId, reason)
            -> release, and record why

Reclaiming is not free, and the UI says so

The proofs are still valid at the mint, so the reclaim works. But if the recipient also holds the token string, then whoever reaches the mint first keeps the value. Reclaiming a send the recipient did in fact receive is a race, not a cancellation. The UI states this before reclaiming.

One bug worth remembering here, because it is the shape of every money bug: quoteSend mapped selected proofs back by secret and dropped unmatched ones without checking coverage, so a failed mapping returned exact: true with a negative fee and an empty proof list, reserving nothing. A send could hand over an empty token. The invariant now enforced is that a send either covers the amount or refuses; it can never silently send zero.

Lightning in and out

Deposit, NUT-04

  1. ask the mint for a MINT QUOTE for N sats
     -> the mint returns a bolt11 invoice and a quote id
  2. the user pays that invoice from ANY Lightning wallet
  3. poll the quote while the sheet is open
  4. once paid, request the proofs: send blinded messages,
     receive blind signatures, unblind
  5. store the proofs, verified

  If the app closes mid-flight, the quote is RECONCILED ON NEXT LAUNCH.
  If the invoice is never paid, nothing is minted, however hard the
  user taps.  (scenario W15)

Withdraw, NUT-05

  1. paste a bolt11 invoice
  2. ask the mint for a MELT QUOTE
     -> amount + FEE RESERVE (Lightning routing is not free and the
        cost is not known until the route is found)
  3. select proofs covering amount + reserve
  4. melt: hand them over, the mint pays the invoice
  5. UNUSED RESERVE COMES BACK AS CHANGE          (scenario W08)

  If the payment FAILS, the input proofs are returned.  (W09)
  If the answer never arrives, the operation is RESOLVED, not guessed. (W11)
  If the CHANGE is unreachable, that is NOT read as a refusal.  (W21)

That last one is the subtle case. A melt can succeed while the change proofs fail to arrive. Treating an unreachable change response as a failed payment would tell the user their money came back when the invoice had in fact been paid.

Interrupted operations

Every mint call is a network round trip that can die halfway. This is where most of the wallet's complexity lives, and it is the right place for it.

InterruptionDangerRecoveryScenario
Swap response lost The inputs are spent at the mint but the outputs never arrived. Retrying naively double-spends and gets refused, losing the value. The blinded messages are persisted as a swap preview before the call. On retry, replay against the mint's NUT-19 response cache. W17
Same, but the mint does not cache No cached response to replay. Recover the outputs by NUT-09 restore, using the exact blinded messages that were persisted. W18
Process killed mid-swap The preview is in memory only. It is persisted, so the next launch finds it. W17
Mint dies mid-swap Input proofs destroyed for nothing. Inputs are not removed until the outputs are in hand. W05
Deposit invoice paid, app closed Money paid, no proofs. The quote is reconciled on next launch.
Melt answer never arrives Guessing either way is wrong. Resolved against the mint rather than assumed. W11
Balance the mint already spent Showing money that does not exist. refreshAccount runs a NUT-07 state check and removes anything reported spent, rather than showing it as money. W16

The counter problem, for deterministic wallets

With NUT-13 enabled, secrets are derived from a counter per keyset. Re-deriving a counter recreates a secret the mint has already signed, and the swap is rejected. So the cursor is persisted per keyset, only ever moves forward, and a restore pushes it past everything the mint has on record. A rejected swap leaves the input proofs untouched, so the failure mode is a retry rather than a loss.

payPerson, the one ladder

Four screens can pay somebody: the DM attach menu, the contact info sheet, the Mesh peer sheet, and the Wallet Zap button. All four call one function, so they cannot disagree about what a payment does.

RungRailConditionCommitsFinalReclaimable
1RadioA direct BLE or WiFi link existsReservedNoYes
2NutzapNo radio link, their Nostr key known, they published a kind 10019, and we hold value at a mint they acceptP2PK-lockedYesNo
3Token in a DMAnything else. sendDm then picks Nostr, courier or the outbox.ReservedNoYes
4ManualNothing carried it. The token string is returned.ReservedNoYes

Radio comes first so that someone standing in front of you does not wait on a mint round trip, and so the in-person case keeps working with no internet on either phone. Rung 2 beats rung 3 when available, because locked proofs are the recipient's whether or not they ever come online, where a bearer token is theirs only once claimed.

Two rules that hold across the whole ladder

One commitment per payment. Proofs are either reserved (rungs 1, 3, 4) or P2PK-locked (rung 2), never both. A rung that fails before committing falls through to the next; a rung that fails after committing retries delivery only.

Finality is reported, never inferred. PayResult.final is true for rung 2 alone, and every confirmation names the rail that carried the money and says whether Pending will offer it back. That is not decoration: "locked to them forever" and "queued, take it back whenever" are the same gesture to the user and completely different facts about their money.

The result also reports how the DM actually left the device. Before that was surfaced, every screen said "sent over the mesh" even when there was no route and the token had merely been queued, which is the difference between "they have it" and "they might get it tomorrow".

Nutzaps

NIP-61. Ecash sent over Nostr, locked so that only the recipient can spend it, which means the event itself can be public. 

  1. fetch the recipient's kind 10019
       lists their trusted mints, their relays, and a 33-byte P2PK pubkey

  2. mint or swap ecash P2PK-LOCKED to that pubkey        (NUT-11)
       the proof carries a spending condition: only a signature from
       that key can spend it

  3. publish a kind 9321 nutzap event TO THE RECIPIENT'S RELAYS
       which is where they subscribe. Not to ours.

  4. the recipient's client swaps the token into its own wallet,
       REFUSING OUTRIGHT if the event names a mint they do not
       already hold

  5. history stays LOCAL. Airhop publishes no NIP-60 events.
RuleReason
Published to their relaysThat is where they subscribe. Publishing to ours would be a message nobody reads.
Refuse an unknown mintA High severity finding: redeeming from any mint an incoming event named would let an attacker introduce a hostile mint through a payment. NIP-61 assumes the recipient's own mint list is the filter.
P2PK-locked, not reservedThe money is committed to the recipient's key. This is the only rail that cannot be taken back, and the only one reported as final.
Falls back to an encrypted messageIf the recipient has never published a kind 10019, there is nothing to lock to, so the payment degrades to an ordinary token in a DM.
A late nutzap stops looking pendingScenario W06: a locked nutzap that reached its owner late must resolve rather than sitting in Pending forever.

The P2PK private key lives in the OS keychain under airhop.wallet.p2pk.v1, separate from the identity keys, and is destroyed by the panic wipe like everything else.

The recovery phrase

Off by default. Turning it on generates a 12 word BIP-39 phrase and switches proof creation from random secrets to NUT-13 deterministic derivation.

CoversEcash derived from the phrase, at mints the user re-adds.
ExcludesThe Airhop identity, chats, contacts and the mint list. This is a wallet backup, not an account backup.
ExcludesCoins received and never swapped, which carry the sender's secrets. They come under the phrase once swapped, which is what refreshAccount does.
  • The keychain is the source of truth. If the flag says backup is on but the phrase is gone, startup clears the flag rather than claiming coverage the user does not have.
  • The uncovered remainder is shown. StoredProof.derived tracks which proofs the phrase can rebuild, and the UI shows what is not covered rather than folding it into a green tick.
  • It cannot be turned off. Deleting a phrase that coins derive from is indistinguishable from deleting the coins. Only the panic wipe removes it.

Restore (NUT-09) re-derives the secrets on any device and asks each mint which of them it signed, so the balance is rebuilt from the mint's records rather than from a backup file. Scenario W10: "a wiped phone gets its money back from twelve words".

Moving between mints

A token names exactly one mint, so ecash from two mints can never be combined into one token. consolidateMints moves the value instead: 

  destination mint issues a bolt11 invoice
        ▲                                   │
        │                                   ▼
  source mint MELTS proofs to pay it   destination MINTS new proofs

  Result: the balance is at one mint, for one Lightning routing fee,
  with no external wallet involved.

Scenario W12 pins it.

The security model in one table

AttackMitigation
Double spendThe mint is the only authority. A proof received offline is stored as unverified and never claimed as confirmed. refreshAccount runs a NUT-07 state check and swaps; anything reported spent is removed from the balance rather than shown as money.
Fake tokenNUT-12 DLEQ verification against cached mint keys on every received token. A failing witness is rejected before the store sees it. Missing keys report "unchecked", never "valid".
Inflated amountAmounts come from the decoded proofs rather than a self-declared field, and every proof is bounded before being summed.
Token interceptionDMs encrypt the token in transit. A token posted to a public channel is a bearer instrument anyone reading can redeem, which the UI states before sending.
Interrupted sendProofs move to reserved rather than being deleted, and the serialised token stays on the transaction. An abandoned sheet, a crash, or a DM that never routes leaves the value reclaimable.
Mint failureThe user chooses which mints to trust. Balances are per (mint, unit) and never pooled, so one mint failing cannot take the rest.
Hostile payment sourceEcash is redeemed only from a mint the user already added, and incoming proofs are DLEQ-verified before anything is stored.
Proofs at restThe MMKV partition is AES-256 encrypted under a keychain-held key. If that key is unavailable the wallet locks rather than falling back to plaintext.
IP linkage over TorOn iOS only the Nostr WebSocket is routed, so mint HTTP would bypass Tor. Mint calls are refused while Tor is on unless the user opts in. On Android the proxy sits in the shared OkHttp client, so fetch is covered too.
Fee underpaymentNUT-02 input fees are computed with the mint's rounding (ceiling), or a swap is rejected for underpaying by one satoshi. Scenario W20: "send 100" still means they get 100, and a melt is funded for the fee too.

The wallet partition

Cashu proofs are bearer instruments, so wallet-store is the one MMKV partition opened with an explicit encryption key: 24 random bytes, base64 encoded to the 32 ASCII characters AES-256 allows, generated on first run and held in the keychain.

It is fetched asynchronously, so the store cannot exist at module scope. bootstrapWalletStorage() opens it and every persist read and write awaits that promise. The panic wipe deletes the partition with deleteMMKV rather than clearing it, since the file cannot be reopened without its key and the same wipe destroys the key.

Drills

  • Why are proofs reserved rather than deleted when a token is created? Because both failure directions have to be covered. If they stayed spendable, the wallet could spend the same value twice from this device. If they were deleted, an abandoned sheet, a crash, or a DM that never routed would destroy the money. Reserving them makes them unspendable and recoverable at the same time, and keeping the serialised token on the transaction is what makes the reclaim possible. Reclaiming is a race rather than a cancellation if the recipient also holds the string, and the UI says so.
  • A swap request is sent and the response never arrives. What must the wallet not do? It must not retry naively. The inputs may already be spent at the mint, so a fresh swap would be refused and the value lost. The blinded messages are persisted as a swap preview before the call, so the retry replays against the mint's NUT-19 response cache, and against a mint that does not cache, recovers the outputs by NUT-09 restore using those exact blinded messages. It must also not remove the inputs until the outputs are in hand.
  • Why can the recovery phrase not be turned off? Because once it is on, proof secrets are derived from it. Deleting the phrase is indistinguishable from deleting the coins that derive from it, so a "turn off backup" button would be a delete-my-money button wearing a different label. The only thing that removes it is the panic wipe, which destroys the coins too, so the two stay consistent.
  • Why is a nutzap the only rail reported as final? Because its proofs are P2PK-locked to the recipient's published key. They are not ours to reclaim, and they are the recipient's whether or not they ever come online. Every other rail reserves proofs that can be released back to spendable. Conflating the two would tell a user their money is safely delivered when it is actually sitting in a queue, or offer to take back money that is no longer theirs to take.
  • Why does the balance screen refuse to show one number? Because balances are per (mint, unit) and never pooled: a token names exactly one mint, so value at two mints cannot be combined without a Lightning round trip through consolidateMints. Folding them into one figure would imply a fungibility that does not exist, and would hide the fact that one mint failing cannot take the rest. The headline also excludes unverified and reserved amounts, which are broken out rather than counted as spendable money.
  • Someone asks what happens to their money if they lose their phone. What is the honest answer? Without the optional recovery phrase, it is gone, exactly like cash in a lost wallet. With the phrase enabled beforehand, a new device re-derives the secrets and asks each mint which of them it signed, rebuilding the balance from the mint's records. Even then it excludes the Airhop identity, the chats, the contacts and the mint list, and it excludes coins received and never swapped, which carry the sender's secrets rather than yours. It is a wallet backup, not an account backup, and the UI shows the uncovered remainder rather than a green tick.
