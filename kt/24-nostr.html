Nostr

When the internet is available, Airhop uses it without owning any of it. Nostr is the smallest protocol that makes that possible: signed JSON objects, dumb servers, and no accounts anywhere.

In plain words

Explain it to a ten year old

Imagine a wall in a town square where anyone can pin a note. Every note has a wax seal that proves who wrote it and that nobody has changed a word. There are hundreds of these walls in different towns, all run by different people, none of them in charge. You pin your note to five walls at once, so if one wall burns down your note still exists. If a note is private, you put it in a locked box first, and then put that box inside another box with a fake sender name on it, so even the person who owns the wall does not know who it is from or who it is for.

What Nostr is

"Notes and Other Stuff Transmitted by Relays". It is deliberately one of the smallest useful protocols in existence: an event format, a signature scheme, and a WebSocket message set. That is all.

PropertyConsequence for Airhop
Identity is a secp256k1 key pairNo accounts, no registration, no phone number. Matches Airhop's identity model exactly, and the Nostr key is derived from the same root.
Relays are dumbThey store and forward signed blobs. They do not run application logic, so there is nothing to compromise into misbehaving.
Relays are independentNo federation protocol, no peering, no shared state. A relay going away is invisible if you were using several.
Clients publish to many relaysRedundancy is the client's job. Airhop publishes to 3 to 5 and takes the first acknowledgement.
Everything is signedA relay cannot forge or alter an event. The worst a hostile relay can do is drop.
Anyone can run a relayThe set is not a permissioned list. If every relay in the bundled CSV disappeared, someone could run one this afternoon.

Airhop uses Nostr as a message transport, not as a social network. There are no profile events, no follow lists, no feeds. The relay set is a delivery mechanism the way SMTP relays are a delivery mechanism.

The event

  {
    "id":         "<32 byte hex>",     // sha256 of the serialised event
    "pubkey":     "<32 byte hex>",     // x-only secp256k1, BIP-340
    "created_at": 1735689600,           // unix SECONDS (not ms, unlike the mesh)
    "kind":       14,                   // what this event is
    "tags":       [["p","<pubkey>"]],  // indexed metadata
    "content":    "...",                // the payload, often ciphertext
    "sig":        "<64 byte hex>"      // BIP-340 Schnorr over id
  }

  id = SHA-256(JSON.stringify([
         0, pubkey, created_at, kind, tags, content
       ]))
FieldNote
idContent-derived, so an event has one identity everywhere and duplicates collapse naturally.
pubkeyx-only, 32 bytes, even-Y by BIP-340 convention. This is why Airhop normalises private keys to even Y (chapter 16).
created_atSeconds, where the mesh uses milliseconds. Mixing them up is a whole class of bug.
kindThe type discriminator, and it also decides storage: 1000 to 9999 regular, 10000 to 19999 replaceable (one per pubkey), 20000 to 29999 ephemeral (relays do not persist them), 30000+ parameterised replaceable.
tagsSingle-letter tags are indexed and can be filtered on. Airhop uses p (recipient), g (geohash), x (courier tag), mid (cross-transport message id), t (teleport marker).
sigBIP-340 Schnorr, the same signature scheme Bitcoin taproot uses. Covers id, and id covers everything else.

The ephemeral range matters: Airhop's geohash channel messages (kind 20000) and presence heartbeats (kind 20001) are in it, so relays forward them to live subscribers and do not store them. A location channel therefore leaves no persistent record on any relay, which is a real privacy property and also why joining a channel replays only up to an hour of history from relays that happen to keep a buffer.

Relays and the wire protocol

  CLIENT ──▶ RELAY

    ["EVENT", <event>]                        publish
    ["REQ", "subid", <filter>, <filter>...]   subscribe
    ["CLOSE", "subid"]                         unsubscribe

  RELAY ──▶ CLIENT

    ["EVENT", "subid", <event>]                a matching event
    ["EOSE", "subid"]                          end of stored events; live from here
    ["OK", <id>, true|false, "message"]        publish result
    ["NOTICE", "message"]                      human readable
    ["CLOSED", "subid", "reason"]              the relay ended the subscription

  A FILTER

    { "kinds": [20000], "#g": ["u4pruy"], "since": 1735689600, "limit": 200 }

Airhop's client wraps SimplePool from nostr-tools with four behaviours worth knowing:

BehaviourValueWhy
Publish is first-ACK-wins8 second timeoutThe event goes to every relay in the set and the promise resolves on the first OK, so no single relay is load bearing.
One-shot reads are time bounded6 second ceilingWithout it, a read resolves only when every relay has sent EOSE, which never happens on a connection that went away without closing. That is exactly the case where you walk out of WiFi range mid-request, and the promise would never settle, leaving a screen loading for the rest of the session.
Default DM pool5 relaysThe four well-known relays (nos.lol, offchain.pub, relay.damus.io, relay.primal.net), matched host for host with bitchat.
Per-call relay ceilingGEO_RELAY_COUNT + MAX_CUSTOM_RELAYSDeliberately higher than the default pool. A geohash cell's set is the 5 nearest relays plus the user's custom ones appended last, so capping at 5 would trim from the tail and silently drop exactly the custom entries the user added.
Auto-reconnectBuilt inSo that when the WebSocket implementation is swapped for Tor, connections re-open on their own, and a pool primed for Tor before Arti has bootstrapped retries until the circuit is up rather than ever falling back to the clear net.
The inbound pump yieldsBounded run time per batchA burst of events must not hold the JavaScript thread and freeze the UI.

Gift wrap, layer by layer

The problem: a relay sees who published an event and who it is tagged for. A naive encrypted DM hides the content and broadcasts the social graph. Gift wrap (NIP-59) fixes that with three nested layers. 

  ┌──────────────────────────────────────────────────────────────┐
  │  KIND 1059  GIFT WRAP                    what the relay sees │
  │  pubkey: EPHEMERAL, thrown away after this one event         │
  │  tags:   [["p", recipient]]                                  │
  │  created_at: now +/- 15 minutes of jitter                    │
  │  sig:    by the ephemeral key                                │
  │  content: encrypt(                                           │
  │  ┌────────────────────────────────────────────────────────┐  │
  │  │  KIND 13  SEAL                                         │  │
  │  │  pubkey: THE SENDER'S REAL KEY                         │  │
  │  │  created_at: jittered                                  │  │
  │  │  sig:    by the sender's real key  ← authentication    │  │
  │  │  content: encrypt(                                     │  │
  │  │  ┌──────────────────────────────────────────────────┐  │  │
  │  │  │  KIND 14  RUMOR         UNSIGNED, deliberately   │  │  │
  │  │  │  pubkey:     sender                              │  │  │
  │  │  │  created_at: THE REAL SEND TIME                  │  │  │
  │  │  │  content:    the message                         │  │  │
  │  │  └──────────────────────────────────────────────────┘  │  │
  │  │  ) to the recipient, from the sender's real key         │  │
  │  └────────────────────────────────────────────────────────┘  │
  │  ) to the recipient, from the EPHEMERAL key                  │
  └──────────────────────────────────────────────────────────────┘

  The relay learns:  a kind 1059 exists, addressed to this recipient,
                     from a pubkey it has never seen and will never see again,
                     at a time that is off by up to 15 minutes.
  The relay does NOT learn: the sender, the content, or the real send time.
LayerJobWhy not merged
Rumor, kind 14The content and the real timestamp.Unsigned on purpose. An unsigned event cannot be published, so it can never leak by accident, and it gives deniability: the recipient cannot extract a signed statement.
Seal, kind 13Authentication. Signed by the sender's real key.This is what lets the recipient know who wrote it. Without it, anyone could send a rumor claiming any pubkey.
Gift wrap, kind 1059Metadata hiding. Signed by a throwaway key.This is the layer the relay sees. Merging it with the seal would put the sender's real key in the relay's view, which is the entire thing being hidden.

Verification order on receipt

  1. Decrypt the gift wrap with the recipient key and the ephemeral pubkey embedded in the wrap's pubkey field.
  2. Verify the seal's Schnorr signature. Without this, DMs are forgeable by anyone who knows the recipient's pubkey.
  3. Check the inner event is actually kind 13.
  4. Decrypt the seal to reveal the rumor.
  5. Check the seal's signer matches the rumor's claimed pubkey. Otherwise a valid seal could carry a rumor attributed to someone else.
  6. Check the rumor's timestamp is plausible. The outer timestamp is randomised by design, so the rumor's created_at is the only claim about when this was sent, and nothing signs it into a window. Threads sort by time, so a far-future rumor pins itself to the bottom of a conversation forever and a far-past one buries itself in history where it is never seen. Neither breaks the crypto; both let someone choose where their message lands in your timeline. The window is the subscription's lookback plus 15 minutes of skew.

The 15 minute timestamp jitter on the seal and the wrap matches bitchat's randomizedTimestamp exactly, which keeps Airhop's events indistinguishable from bitchat's to a relay. NIP-59 suggests up to two days; matching bitchat matters more than matching the suggestion.

The cipher is not the published NIP-44

Read this before reaching for a standard library

bitchat labels its relay-DM encryption "nip44-v2" and the name is misleading. It is a bitchat-specific construction, not the registered NIP-44. An implementer who reads "NIP-44" and uses nostr-tools' NIP-44 produces DMs that no bitchat or Airhop peer can read, and the failure is silent at both ends.

Published NIP-44 v2bitchat "nip44-v2", and Airhop
CipherChaCha20 plus HMAC-SHA256XChaCha20-Poly1305, a real AEAD with a 24 byte nonce
Key scheduleHKDF extract then expand, per-message saltSingle-step HKDF, info = "nip44-v2", no salt
ECDH outputx-coordinate onlyCompressed point, 33 bytes
PaddingPadded to a power-of-two bucketNone
Framingbase64, version byte inside the payload"v2:" prefix plus base64url

Airhop implements bitchat's construction deliberately and must keep doing so. The Nostr event signature covers the encrypted content, so byte-identical output is the whole of DM interoperability. The envelope around it is NIP-17 shaped: kinds 13, 14 and 1059 carry their standard meanings and the layering is exactly NIP-59's. Only the encryption inside each layer diverges. So "NIP-17 gift wrap" elsewhere in the documentation is accurate about the structure and should be read as excluding the cipher.

Two consequences worth naming. The missing padding means ciphertext length reveals plaintext length to a relay, where the published NIP-44 would hide it. And the static ECDH between two long-lived identities means these DMs have no forward secrecy at all (chapter 18).

bitchat reached the same conclusion about its own documentation and relabelled it. Airhop records it in PROTOCOLS.md section 7.1 for the same reason.

Geohash channels

A geohash encodes a latitude and longitude pair into a short string, where each additional character subdivides the cell. Two points in the same cell share a prefix, which is what makes it a natural channel name.

ChannelPrecisionCell sizePresence allowed
#block7~153 mNo
#neighborhood6~1.2 kmNo
#city5~4.9 kmYes
#province4~39 kmYes
#region2~1250 kmYes

Presence heartbeats are restricted to precisions 2, 4 and 5. Sending a heartbeat at precision 6 or 7 would announce your position to within a city block on a public relay, continuously. The app refuses to do it, and that refusal is enforced in the presence module rather than left to the caller.

Per-cell identities

  seed = HMAC-SHA256(signingPrivKey, "airhop-geohash-seed-v1")

  privkey = HMAC-SHA256(seed, utf8(geohash) || u32_be(i))
            for i = 0, 1, 2... until the result is a valid secp256k1 scalar

The main Nostr key is published in every ANNOUNCE and used for DMs. Reusing it for location channels would let any relay operator, or anyone watching a geohash, tie a movement history to a durable identity and correlate the block, city and region cells someone posts in as one person. A fresh key per geohash breaks those links.

The derivation is deterministic, so a user keeps a stable pseudonym within a channel across restarts while remaining unlinkable across channels. Nothing on the wire depends on the derivation, only that each cell gets its own key, so bitchat and Airhop interoperate without sharing seeds. They could not anyway: the seed never leaves the device.

Display names follow bitchat's convention: the self-asserted nickname with the last 4 hex characters of the pubkey appended, or anon#abcd with no nickname. Nicknames here are untrusted decoration; the pubkey is the identity.

Teleport

A user can open any cell by entering its geohash, without being there. It runs over Nostr only, since nobody in Bluetooth range is in it, and its messages carry a t=teleport tag so other clients list the sender as teleported rather than nearby. It uses the same per-cell identity and relay selection.

Relay selection

The bundled dataset is assets/data/nostr_relays.csv: 300 or so relays with latitude and longitude, produced by the georelays toolchain (BFS discovery from a seed relay, filtering for relays that actually accept kind 20000, then IP geolocation against a DB-IP database). 

  closestRelaysToGeohash(geohash, decodeCenter, count = 5):
    center = decodeCenter(geohash)              // the CELL CENTRE
    sort by haversine distance from center,
      ties broken by URL (not insertion order)
    take the first `count`

Two details that are load bearing for interop

Relays are chosen by distance from the cell centre, not from the user. Every participant in a cell must converge on the same relay set. Selecting by personal position would give two people in opposite corners of one city cell different relays, and they would never see each other's messages despite being in the same channel.

Ties break on URL. Many relays in the directory share identical coordinates, so ties are common rather than exotic. If they broke on insertion order, two clients with differently ordered directories would pick different sets.

Relay URLs are validated strictly: wss:// or https:// only, ASCII only, no credentials, query, fragment or path, a real DNS hostname of at least two labels, not a bare IP, and not localhost, .local or .internal. That strictness is deliberate and stays. Relaxing it to permit ws:// would mean permitting cleartext for the whole app on Android (its network security config cannot scope an exception to an address range), which includes the mint URLs that carry bearer ecash. And a ws:// public host would put gift-wrapped DMs on the open internet unencrypted.

A user may add up to 5 custom relays. With geo-relay discovery on, they are appended to the nearest set; with it off, they replace it, trading interoperability for control.

Proof of work

NIP-13 defines optional proof of work for Nostr: grind the event's nonce tag until the event id has a required number of leading zero bits. Some relays require it as a spam deterrent.

Airhop does not implement it, in either direction. That is worth understanding rather than just noting.

ArgumentAssessment
PoW would deter spam in geohash channelsTrue in principle. But a phone grinding hashes is a phone burning battery, and this app is meant to run in a pocket all day. The cost falls hardest on exactly the low-end devices the product targets.
PoW would raise the cost of a Sybil floodOn the Nostr side only. The mesh is where Sybil floods actually happen, and PoW there would be worse: a flood costs the attacker one grind per identity, while every honest phone pays a grind per message.
Some relays require PoW to accept an eventReal, and it means Airhop silently cannot publish to those relays. The mitigation is publishing to 5 relays and taking the first acknowledgement, so one demanding relay is invisible.
bitchat does not implement it eitherSo adding it unilaterally would produce events with a nonce tag bitchat ignores, which is harmless, and would not raise the bar for anyone.

The honest summary: PoW is a reasonable anti-spam tool for a public posting network and a poor fit for a battery-constrained offline-first messenger. If relay-side PoW requirements become widespread, the correct response is to grind only for the specific relays that demand it, at the lowest difficulty they accept, and only when charging.

What a relay learns anyway

Gift wrap is strong. It is not complete.

LeakMitigated byResidual
Your IP addressTor, when enabledOff by default, so by default a relay sees your IP and can geolocate you roughly.
That somebody is messaging this recipientNothingThe p tag is necessary for delivery. A relay sees the recipient of every gift wrap.
Message sizeNothingbitchat's cipher does not pad, so ciphertext length reveals plaintext length.
Timing15 minute jitter on the outer timestampsA relay still sees when the connection delivered the event, which is not jittered.
Which geohash cells you are inPer-cell identities, coarse precisions for presenceA relay serving a cell sees every pubkey posting in it. Cross-cell correlation is broken; within-cell observation is not.
Your relay setNothingWhich relays you connect to is itself a fingerprint, and a geohash-derived relay set narrows your location.
Your courier tagsNothingKind 1401 drops are tagged with the recipient tag, which anyone who heard that peer's announce can compute.

The design's honest position is that Nostr is the weaker of the two transports for metadata, and that it is used only where Bluetooth cannot reach. That is why the internet layer is an extension rather than the foundation, and why the internet toggle exists at all.

If you removed the Nostr layer

Airhop would still work as a Bluetooth mesh messenger with local rooms, DMs, files, voice and offline payments. What would disappear: location channels beyond Bluetooth range, DMs to anyone not currently nearby, the mesh bridge between islands, nutzaps, courier relay drops, and any way to reach a contact in another city. It is the difference between a venue-scale tool and one that also works between cities when there happens to be a network.

Drills

  • Why three layers rather than just encrypting the message? Each layer does a different job. The rumor holds the content and the true timestamp and is deliberately unsigned, so it can never be published by accident and gives deniability. The seal is signed by the sender's real key, which is the only thing that lets the recipient authenticate them. The gift wrap is signed by a throwaway key, which is what hides the sender from the relay. Merge the seal and the wrap and the relay sees the sender's real key, which is the whole point of the exercise.
  • Someone says "just use nostr-tools' NIP-44". What happens? Every DM you send becomes unreadable to every bitchat and Airhop peer, and every one you receive fails to decrypt, with no error message that says why. bitchat's "nip44-v2" is a different construction: XChaCha20-Poly1305 rather than ChaCha20 plus HMAC, single-step HKDF with no salt, a compressed 33 byte ECDH output rather than x-only, no padding, and a "v2:" plus base64url framing. Since the event signature covers the encrypted content, byte-identical output is the entire interoperability story.
  • Why are relays picked by distance to the cell centre rather than to the user? Because publisher and subscriber must independently arrive at the same relay set or the channel silently drops traffic. Two people in opposite corners of one city cell would pick different nearest relays if selection used their own positions, publish to relays the other never subscribed to, and never see each other. Ties break on URL rather than insertion order for the same reason, since many directory entries share coordinates.
  • Why does Airhop not implement NIP-13 proof of work? Because grinding hashes on a phone costs battery, and the cost falls hardest on the low-end devices this product targets. It would deter Nostr spam but do nothing about the mesh, where floods actually happen, and where PoW would be actively worse: an attacker pays once per identity while every honest phone pays once per message. The practical cost of not having it is that relays which require PoW silently refuse Airhop events, which is masked by publishing to five relays and taking the first acknowledgement.
  • A relay operator wants to know what they can learn about a user. What is the honest answer? Without Tor: your IP, and therefore roughly where you are. Which recipients you send gift wraps to, since the p tag is necessary for delivery. The size of every message, since bitchat's cipher does not pad. Which geohash cells you post in, if they serve those cells. Which relays you connect to, which is itself a fingerprint. What they cannot learn: message content, who sent any given gift wrap, or that two of your geohash pseudonyms belong to one person.
  • Why are location channel messages kind 20000 rather than something in the persistent range? Because 20000 to 29999 is the ephemeral range: relays forward to live subscribers and do not store. That means a location channel leaves no durable record on any relay, which is the right default for a channel scoped to a physical place. The cost is that joining replays at most an hour of history from relays that happen to keep a buffer, and there is no guarantee even of that.
