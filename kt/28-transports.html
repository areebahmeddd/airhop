Transport selection

Five ways a message can travel, and no user-facing choice between them. This chapter is what each one is for, how one gets picked, and the two that are documented but not shipped.

In plain words

Explain it to a ten year old

Your phone has several ways to shout: Bluetooth, which is always available and slow; WiFi straight to another phone, which is fast but only works between two of the same kind of phone; and the internet, when there is one. It does not make you choose. It shouts on everything it has at once, and if nobody hears at all, it asks a passer-by to carry the message.

Text messages are tiny and effectively instant on any transport. Throughput only matters for files. A 1 MiB file, the per-file cap, takes about 56 seconds to one peer over Bluetooth.

Not a ladder: radios run together

The most common misunderstanding is that Airhop picks the best radio and uses it. It does not. 

  A MESSAGE ADDRESSED TO A PEER IS TTL-BOUNDED AND FLOODED ON
  EVERY LINK THE DEVICE HAS.

     phone ──┬── BLE link 1 ──▶ neighbour A
             ├── BLE link 2 ──▶ neighbour B
             ├── BLE link 3 ──▶ neighbour C
             └── WiFi link  ──▶ neighbour D

  All four get the same packet at the same time.
  A packet that ENTERS on one radio is RELAYED OUT on the other.
  Duplicates are collapsed by the seen set and by the message ID,
  so it is DISPLAYED once however many radios delivered it.

The reason is simple: no node knows the topology. The recipient may be several hops away and unreachable on the radio that looks best. Choosing one radio would mean guessing, and a wrong guess is a message that silently does not arrive.

The one place there is a ladder

Two ladders exist, and they answer different questions.

1. The direct link shortcut, in the transport layer

  unicast(peerID, packet):
    links.linkFor(peerID)  ->  write there, done
         the best link this peer has, in SEND_PREFERENCE
         order: wifi, then lan, then ble
    none                   ->  FLOOD it, addressed to them

Once a peer is bound to a link, a packet addressed to it goes over that link. WiFi Aware wins when one exists, then LAN, then Bluetooth, because the point of the fast paths is to move an attachment that BLE would have to fragment into hundreds of writes. One call answers it for every transport at once, which is the whole reason the link registry exists: see chapter 14. This is an optimisation, not the delivery guarantee: the moment the peer is more than one hop away it disappears and flooding takes over.

2. The DM ladder, in the router

RungConditionResult
1. DirectAn active Noise session existsEncrypt, then hand to unicast, which picks WiFi or BLE or floods. Returns "sent".
2. NostrA send function was injected and the peer's Nostr pubkey is knownFire-and-forget gift wrap. Returns "sent-nostr".
3. CourierAnything elseReturns "needs-courier" so the caller can seal and hand to connected peers.

There is deliberately no separate WiFi tier in the router. It would duplicate what the injected unicast callback already does, meaning the transport is consulted twice. Transport selection belongs in the callback that owns the link maps; the router only decides which tier to use.

WiFi Aware

WiFi Aware, also called Neighbour Awareness Networking, is a radio protocol for direct device-to-device WiFi with no router and no internet. It is Android only in Airhop.

FactDetail
ThroughputUp to 250 Mbps on paper
RangeAbout 30 m
Discovery API level26
Data path API level29. The peer's address is a link-local IPv6 delivered in WifiAwareNetworkInfo, which does not exist before then. Below 29 the transport reports itself unavailable and BLE carries everything.

availabilityChanged is the important one. It carries both edges, from the framework's WiFi Aware state broadcast, which fires when the user toggles WiFi, when the OS reclaims the radio for tethering, or when battery saver intervenes. That is what lets the fast path recover without a relaunch.

The honest assessment of the fast path today

WiFi currently shares the same paced fragment queue as Bluetooth, so it runs at roughly the same 18 KiB/s. The 25 ms pacing is a Bluetooth requirement, not a protocol one, and lifting it for WiFi links is planned rather than done. So the feature currently buys link diversity and a second path, not speed. Given the protocol caps a file at 1 MiB anyway, the ceiling BLE has to clear is seconds rather than minutes, which is part of why lifting it has not been urgent.

MultipeerConnectivity, removed

Documentation says this ships. It does not.

The README stack table, ARCHITECTURE.md sections 3 and 12 (including an AirhopMCModule row in the native modules table), VISION.md, GLOSSARY.md, the landing FAQ and the landing architecture page all describe iOS MultipeerConnectivity as a shipped same-platform fast path. There is no such file in ios/ and no reference to it in src/ outside comments explaining its removal.

PROGRESS.md line 115 is accurate: "The iOS MultipeerConnectivity counterpart was written, never worked on a device, and was removed." This is listed in chapter 49 with the other documentation drift.

The removal reasoning, recorded in src/bridge/NativeAirhopWiFi.ts, is sound and worth reading:

  • bitchat-iOS has never had a same-platform fast path, so removing it costs no interoperability.
  • The protocol caps an attachment at 1 MiB (512 KiB for a sent photo), so the ceiling Bluetooth has to clear is seconds rather than minutes.
  • The implementation had two independently fatal defects. Every device advertised the same MCPeerID, so the invite tie-break compared equal strings and no two iPhones ever paired. And the Bonjour declaration was missing its UDP service, so iOS 14's local-network gate refused browsing outright.

The practical consequence: iPhone to iPhone has no fast path. Bluetooth carries everything on iOS. Apple shipped a standards-based Wi-Fi Aware framework in iOS 26 which could close the gap and would even be cross-platform, at the cost of making the feature iOS 26+ only.

LAN over mDNS

Shipped, and it was the highest-value missing transport

This section used to say the LAN transport was documented as a built-in feature and absent from the code. It shipped: mDNS on _airhop-lan-v1._tcp plus TCP links, with native modules on both platforms, a reconciler, a pure dial policy and a simulation fabric. Note the service name differs from the _airhop-mesh._tcp the older documents named, kept apart from WiFi Aware's so neither reads as a typo of the other.

The gap it closes: WiFi Aware is a radio protocol rather than a way of using a network, so two phones on the same router cannot reach each other over it, and Apple demands a paired data path Android cannot complete. An iPhone and an Android sharing a WiFi network therefore had no local path at all. That is the situation on a ship, in a hotel, at a conference, or anywhere with WiFi and no route out. 

  mDNS service:  _airhop-lan-v1._tcp
  transport:     ordinary TCP links carrying the SAME packet frames BLE
                 carries, so the engine needs no new concept and the wire
                 format does not move

  MAX_LAN_LINKS  8       a dial ring, not a full mesh: 30 phones fully
                         connected is 435 sockets and 841 writes per
                         broadcast instead of 29
  instance name  random, 16 hex, minted per PUBLISHING SESSION, never
                 the peer ID: an mDNS record is cleartext and is logged
  default        OFF. publishing is an attendance list on a venue network

It sits beside WiFi Aware rather than replacing it. Aware needs no network at all, which mDNS structurally cannot do; mDNS reaches everyone on a network, which Aware cannot. Neither is a superset.

ConstraintConsequence
Client isolationMost guest and venue WiFi blocks peer-to-peer traffic at the access point, and it cannot be detected before trying. The UI says "No Airhop devices on this network" rather than spinning or claiming a failure it cannot prove.
mDNS filteringCommon even where ordinary traffic works. A manual join by address covers it.
iOS backgroundA TCP socket has no equivalent of bluetooth-central, and a suspended app has its listener reclaimed without getting it back on resume. Foreground only, as WiFi Aware already is on iOS.

The 467-byte fragment size stays regardless, because the receiver reassembles by index and the next hop may be Bluetooth. The 25 ms pacing does not: it is a Bluetooth requirement, and the pacer now asks whether anything on the path touches the radio before applying it. Chapter 10.

Chapter 29 is the whole transport: the dial ring, the rotating name, the reconciler, the six states, and why it is the only transport that is off until the user turns it on.

The reconciler pattern

Both radio controllers use the same shape, and it is worth understanding because it is the answer to a whole class of bug. 

  THE ANTI-PATTERN

    NativeAirhopWiFi?.startWiFi().catch(() => {});

  One attempt. No retry. The rejection code, the only thing that says
  WHICH of eight failures happened, discarded before anything reads it.

  Three failures follow immediately:
    1. WiFi off at start -> refused, swallowed, never retried. Turning
       WiFi on later changes nothing for the rest of the process.
    2. Permission granted a moment after start (the ordinary first-install
       race) -> the fast path is dead on a device entitled to it.
    3. WiFi toggled off mid-session -> sockets torn down natively, the
       module latched into a "started" state it cannot leave, so even an
       explicit restart resolves instantly having done nothing.

  THE RECONCILER

    a DESIRED state, an OBSERVED outcome, and ONE idempotent pass that
    closes the gap and schedules a retry when it cannot.

    backoff: 500ms, 1.5s, 4s, 10s, 30s
    "unsupported" is LATCHED FOREVER. No hardware, or an API level below
    the data path, is not a state a device leaves.

One deliberate difference between the two controllers: the WiFi one publishes no blocker. WiFi Aware is an accelerator and BLE carries everything either way, so a user with WiFi off has not lost the mesh, and saying they have would be a false alarm on the one screen that must stay trustworthy. What it does report is which situation it is in, so the Mesh tab can say the fast path is off in the same neutral voice it uses for battery saver. Saying nothing at all was its own small lie: the same file takes seconds with Aware and much longer without it, and with no note the difference reads as the app being slow.

Reporting where a message actually went

Because transports run together and some can silently reach nobody, the result type is explicit rather than a boolean. 

  interface ChannelSendResult {
    msgId:   string
    bleLinks: number    // how many radio links it went out on
    nostr:    boolean   // a relay was LIVE when the publish went out
    gateway:  boolean   // no relay, but a nearby gateway took it
  }

  bleLinks === 0 && !nostr   ->  it reached NOBODY.
                                 The UI must say so rather than render
                                 a normal sent bubble.

nostr is deliberately "a relay was live", not "this channel can reach Nostr". The latter holds whether or not the phone has internet, so a region message carried by Bluetooth alone would report "sent" having reached nobody.

Groups get their own type for the same reason. Groups have no delivery receipts on either client, so GroupSendResult reports whether the message was sealed and how many links it went out on, and that is the only honest signal the UI ever gets. Zero links means it reached nobody, and a group is Bluetooth only, so there is no internet path to fall back on.

Drills

  • Why does Airhop not pick the best radio and use it? Because no node knows the topology, and the recipient may be several hops away on a path the "best" radio does not cover. A message addressed to a peer is TTL-bounded and flooded on every link the device has, and a packet entering on one radio is relayed out on the other. Duplicates are collapsed by the seen set and the message ID. The only place a radio is chosen is the direct link shortcut, which is an optimisation for a peer already mapped to a specific link.
  • A user asks why sending a photo iPhone to iPhone is not faster than iPhone to Android. What is true? There is no same-platform fast path on iOS. MultipeerConnectivity was written, never worked on a device, and was removed, and several documents still say otherwise. So Bluetooth carries everything on iOS, at about 18 KiB/s. Android to Android does have WiFi Aware, but it currently shares the same paced fragment queue, so it runs at roughly the same speed too. The fast path today buys a second link rather than more throughput.
  • What problem does the LAN transport solve that WiFi Aware cannot? Cross-platform local connectivity on a shared network. WiFi Aware is a radio protocol, not a way of using a network: two phones on the same router cannot reach each other over it, and Apple does not implement it at all. So an iPhone and an Android on one WiFi network have no local path, which is the situation on a ship, in a hotel or at a conference. mDNS plus TCP closes it, is platform-neutral, and carries the whole mesh rather than the subset Nostr can express. It is designed in the architecture document and not implemented.
  • Why does the WiFi controller publish no blocker when the BLE one does? Because WiFi Aware is an accelerator and BLE carries everything either way. A user with WiFi off has not lost the mesh, so reporting a blocker would be a false alarm on the one screen that must stay trustworthy. What it does report is which situation it is in, so the Mesh tab can note that the fast path is off in the same neutral voice it uses for battery saver, because saying nothing at all makes the missing speed read as the app being slow.
  • Why is ChannelSendResult a struct rather than a boolean? Because "sent" is not a single fact. A message can leave the radio on zero links and be published to no relay, which means it reached nobody, and rendering a normal sent bubble for that is a lie. The struct separates how many radio links carried it, whether a relay was live at publish time, and whether a nearby gateway took it instead. The nostr field specifically means a relay was live, not that the channel is capable of reaching Nostr, because the second is true even with no connection.
