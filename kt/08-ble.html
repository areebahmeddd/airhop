Bluetooth Low Energy

BLE was designed for a heart rate strap to send a number to a phone once a second on a coin cell. Airhop uses it to run a multi-hop encrypted network. Most of the surprising constants in the protocol come from that mismatch.

In plain words

Explain it to a ten year old

Bluetooth Low Energy is a way for two devices to talk that uses very little battery. It works in two steps. First, a device shouts its name into the air every so often, and other devices listen for shouts. That is how they find each other. Second, once two devices have found each other, they agree to whisper directly, taking turns, on a schedule. Airhop makes every phone shout and listen at the same time, so all the phones in a room end up connected to each other, and a message can be passed along the chain.

BLE is not Bluetooth Classic

They share a name and a band and nothing else. Confusing them is the most common source of wrong assumptions.

Bluetooth Classic (BR/EDR)Bluetooth Low Energy
Introduced19992010, in Bluetooth 4.0
Designed forContinuous streams: audio, file transfer, serial linksTiny, infrequent messages from battery devices
Throughput1 to 3 Mbps0.125 to 2 Mbps on paper, far less in practice
Power while connectedTens of milliwatts, continuousMicrowatts average, because the radio is off between connection events
PairingUsually required, with a PIN or numeric comparisonOptional. GATT can be read and written with no pairing at all
Channels79 channels, 1 MHz apart40 channels, 2 MHz apart: 3 advertising, 37 data
DiscoveryInquiry, slow and heavyweightAdvertising packets, lightweight and continuous
Used by AirhopNoYes, exclusively

The "optional pairing" row is the one that makes Airhop possible. Because a GATT characteristic can be written without pairing, two phones that have never met can exchange bytes with no user prompt on either side. If pairing were required, a mesh of strangers would need a PIN confirmation per pair, which is not a product.

The consequence is that BLE gives Airhop no security at all. There is no link-layer encryption, no authentication, no pairing. Every security property in this app comes from the application layer: Ed25519 signatures on packets, Noise XX for sessions. That is a deliberate design, not an omission, and it is why chapter 43 assumes an attacker can transmit anything.

The stack: GAP, GATT, ATT

  ┌──────────────────────────────────────────────────────────┐
  │  APPLICATION            Airhop packets                    │
  ├──────────────────────────────────────────────────────────┤
  │  GATT   Generic Attribute Profile                         │
  │         services, characteristics, read/write/notify      │
  ├──────────────────────────────────────────────────────────┤
  │  ATT    Attribute Protocol                                │
  │         the wire format for attributes. MTU lives here.   │
  ├──────────────────────────────────────────────────────────┤
  │  GAP    Generic Access Profile                            │
  │         roles, advertising, scanning, connecting          │
  ├──────────────────────────────────────────────────────────┤
  │  L2CAP  multiplexing and segmentation                     │
  ├──────────────────────────────────────────────────────────┤
  │  LINK LAYER   state machine, channel hopping, CRC, retry  │
  ├──────────────────────────────────────────────────────────┤
  │  PHYSICAL     GFSK on 40 channels in the 2.4 GHz band     │
  └──────────────────────────────────────────────────────────┘

GAP answers "who is out there and how do I connect to them". It defines four roles: broadcaster, observer, peripheral and central. Airhop uses peripheral and central, simultaneously.

ATT is a very simple client-server protocol over a table of numbered attributes. Its unit is the attribute value, and the maximum size of one attribute value transfer is the ATT MTU. This is where the 512 byte ceiling comes from.

GATT is a convention layered on ATT: attributes are grouped into services, identified by a UUID, and each service contains characteristics, also identified by UUIDs, each with properties (read, write, write without response, notify, indicate).

Airhop's GATT profile is deliberately minimal:

  Service      F47B5E2D-4A9E-4C5A-9B3F-8E1D2C3A4B5C   (primary)
    └─ Characteristic
                 A1B2C3D4-E5F6-4A5B-8C9D-0E1F2A3B4C5D
                 properties: read, write, write-without-response, notify
                 permissions: readable, writeable, no encryption required

One service, one characteristic. Every packet in the protocol, regardless of type, is written to that one characteristic. The characteristic is a pipe, not a data model. This is why the wire format has to carry its own type byte: GATT gives no framing beyond "here are some bytes".

Those two UUIDs are the same as bitchat's, which is the entire mechanism of interoperability. A bitchat phone scanning for its service UUID finds an Airhop phone, because Airhop advertises that exact UUID. There is no negotiation, no version exchange, no handshake at this level. The UUID is the handshake.

The dual role trick

In a normal BLE product the roles are fixed: a heart rate strap is a peripheral, a phone is a central. Airhop makes every device both at once, and that single decision is what turns a point-to-point radio into a mesh. 

  A CONVENTIONAL BLE TOPOLOGY (a star)

        peripheral        peripheral        peripheral
             │                 │                 │
             └────────────┬────┴─────────────────┘
                          │
                       CENTRAL
                  (the phone, only)

  everything must pass through the centre. If the centre leaves,
  the network is gone.


  AIRHOP'S TOPOLOGY (every node is both)

     A ═══════ B ═══════ C
     ║         ║         ║
     ║         ║         ║
     D ═══════ E ═══════ F

  A is a peripheral to B and a central to D at the same time.
  Any node can leave and the graph usually stays connected.
  Nobody knows the shape of the graph, and nobody needs to.

Concretely, on each device:

  • The peripheral half runs a GATT server, publishes the service and characteristic above, and advertises. Other devices' centrals can connect to it and write packets into the characteristic. Incoming writes arrive as onCharacteristicWriteRequest on Android and didReceiveWrite on iOS.
  • The central half scans for the service UUID, opens GATT connections to advertisers it finds, discovers the characteristic, subscribes to notifications, and writes packets out.

Both halves feed the same packetReceived event up to JavaScript, and both are reachable by writeToLink. Above the native boundary a "link" is just an opaque string id with a peer on the other end; whether this device is the central or the peripheral on that link never reaches the protocol layer.

The cap is 6 concurrent central links on both platforms (MAX_CENTRAL_LINKS in the Kotlin, maxCentralLinks in the Swift). Android controllers support roughly seven GATT client connections and refuse the rest with status 133, which is an opaque failure that looks like a crashed stack. Capping at 6 turns a mystery into a policy. There is no equivalent cap on the peripheral side: a device accepts inbound connections until the controller stops accepting them.

Advertising and scanning

An advertising packet is at most 31 bytes of payload in the legacy format (Bluetooth 4.x), broadcast on channels 37, 38 and 39 in turn. 31 bytes is very little once a 16 byte service UUID is in it. 

  LEGACY ADVERTISING PDU, 31 bytes of payload

  ┌──┬──┬──────────────────────────────────┐
  │02│01│06                                 │  flags (3 bytes)
  ├──┼──┼──────────────────────────────────┤
  │11│07│F47B5E2D-...-4B5C                  │  128-bit service UUID
  ├──┴──┴──────────────────────────────────┤  (17 bytes)
  │  10 bytes left                          │
  └─────────────────────────────────────────┘

  A 128-bit UUID eats more than half the budget. This is why most
  commercial BLE products use 16-bit UUIDs from the assigned list.
  Airhop cannot: it needs a private UUID that matches bitchat's.

Android has a second frame, the scan response, which a scanner can request and which carries another 31 bytes. Airhop puts the first 8 bytes of the peer ID there as service data under the service UUID. iOS has no API for service data at all, and historically Airhop advertised the peer ID in the iOS local name instead. That was removed: nothing read the field on either platform, so it was a stable identifier broadcast to every passive scanner for no benefit, which is a tracking vector. iOS now advertises the service UUID alone, matching bitchat-iOS.

The consequence is that a scanner often learns nothing but "an Airhop device is here". It connects anyway and learns who the peer is from the first ANNOUNCE inside the connection. That is what happens on every iOS-to-Android link.

BLE scanning is the single largest battery cost in the app. A continuous low-latency scan costs roughly an order of magnitude more than low power. iOS exposes no equivalent control at all: CoreBluetooth decides, and it throttles background scanning aggressively. This asymmetry is why the power policy is declared a no-op on iOS and why getRadioState reports batteryPercent: -1 there, which the policy reads as unknown and leaves the mode alone.

Connecting

Discovery is not connection, and neither is instant. The simulation's radio fabric models this explicitly because code that assumes a peer is reachable the moment it is visible is wrong on hardware. 

  t=0     peripheral starts advertising (every 100 to 1000 ms)
  t=?     central's scan window happens to overlap an advert
              -> scan result, with RSSI
  t=+ms   RSSI gate: is this signal strong enough to be worth a slot?
          link cap: are we already at 6 central links?
  t=+50   GATT connect requested
  t=+100  connection established (LL_CONNECT_IND, then connection events)
  t=+150  service discovery: find F47B5E2D...
  t=+200  characteristic discovery: find A1B2C3D4...
  t=+250  subscribe to notifications (write the CCCD descriptor)
  t=+300  MTU exchange requested (Android: gatt.requestMtu(517))
  t=+400  onMtuChanged fires with what the peer actually granted
  t=+400  LINK IS USABLE. Now send an ANNOUNCE.

Several hundred milliseconds is normal, and a second or more is common on a busy radio. Two consequences show up in the protocol:

  • The announce cadence is 4 seconds while isolated, backing off to a jittered 15 to 30 seconds once connected. Fast while alone so two lone phones find each other quickly, slow once in a mesh so steady-state traffic and battery stay low.
  • A link-up triggers an immediate announce and a prekey bundle. But both are reused within a window rather than freshly timestamped, because a freshly minted packet cannot be deduplicated by relays. Without that, twelve phones connecting at once put roughly 6,600 prekey packets and 9,200 announce packets on the air in half a second, which is a room saturating its own airtime.

MTU, and the 512 byte ceiling

This is the most consequential number in the entire transport, and it is worth being precise about, because there are three different limits that get confused.

LimitValueWhat it constrains
Default ATT MTU23 bytesEvery connection starts here, before negotiation. Only 20 bytes are usable by a write without response.
Negotiated ATT MTUUp to 517 bytesAirhop requests 517 on Android. The peer may grant less. iOS negotiates automatically and exposes the result through maximumWriteValueLength.
Maximum attribute value512 bytesA hard limit in the Bluetooth core specification on the size of a single attribute value, independent of MTU. This is Airhop's frame budget.

Two ways exist to move a value larger than the MTU minus 3:

  • Write without response (a write command). Fast, unacknowledged, and cannot exceed MTU minus 3. Android silently truncates a larger write. This is the failure that makes over-budget frames vanish with no error.
  • Write with response, which for a value over the MTU becomes a long write: a sequence of prepare writes followed by an execute. Slower, acknowledged, and it can carry up to the 512 byte attribute limit.

Both native modules implement exactly this decision. Android reads the negotiated MTU it recorded from onMtuChanged, and picks WRITE_TYPE_NO_RESPONSE when the frame fits in MTU minus 3, otherwise WRITE_TYPE_DEFAULT so the stack does a long write. iOS asks peripheral.maximumWriteValueLength(for: .withoutResponse) and picks .withoutResponse or .withResponse the same way.

The bug this prevents, restated

The fragment budget must be the whole encoded frame. An implementation that budgets 469 bytes of payload and then adds a 16 byte header, an 8 byte sender ID and a 64 byte signature emits 557 bytes. Android truncates to MTU minus 3, iOS refuses, and the receiver's decoder fails on a signature whose last bytes never arrived. Nothing is logged at either end. Every attachment silently failed in both directions while live voice kept working, because a voice burst is capped at 210 bytes and never fragments. Airhop's real budget is 467 data bytes: 512 minus a 16 byte header, 8 byte sender, 8 byte recipient and 13 byte fragment header.

Where 18 KiB/s comes from

BLE's advertised PHY rate is 1 Mbps (or 2 Mbps on the 2M PHY). Real application throughput is a small fraction of that, and the reason is the connection event structure. 

  A BLE CONNECTION IS A SERIES OF SCHEDULED APPOINTMENTS

  connection interval (7.5 ms to 4 s, negotiated)
  │◀──────────────────────────────────────────▶│
  ┌────┐                                       ┌────┐
  │ ▮▮ │      radio completely off             │ ▮▮ │
  └────┘                                       └────┘
   event                                        event

  In one event, a limited number of packets can be exchanged.
  Between events, nothing moves, at all, regardless of how much
  data is queued. This is the whole basis of BLE's low power.

  Effective throughput ≈ (bytes per event) / (connection interval)

An iOS connection interval is typically 30 ms and cannot be forced lower by an app. Android varies by OEM. So the achievable rate is capped long before the PHY rate matters. Airhop's measured figure, 467 bytes every 25 ms, or about 18 KiB per second, is empirical: it is the fastest pacing at which fragments stop being dropped. The delay is not politeness, it is required.

TransferFragmentsTime at 25 ms
A text message1Instant
A 40 KiB compressed photo~88~2 seconds
A 512 KiB photo (the cap)~1,120~28 seconds
A 1 MiB file (the cap)~2,240~56 seconds

A channel attachment paces at 30 ms rather than 25, because each broadcast fragment is one radio write per connected peer. In a room of six peers, one broadcast fragment is six writes. Airtime cost grows with room size while the sender's own clock does not, so the pacing has to absorb the difference.

Platform differences that hurt

A backgrounded iPhone is invisible to Android

This is the single most surprising behaviour of the real network, and it is not fixable in application code.

When an iOS app leaves the foreground, CoreBluetooth moves the service UUID out of the main advertising payload into the overflow area, a proprietary Apple extension, and drops the local name entirely. Only another iOS device scanning for that exact UUID can see it. An Android scanner sees an advertisement with no recognisable service.

ScenarioWorks?
iPhone foreground to AndroidYes
iPhone background to iPhoneYes
iPhone background to Android, new discoveryNo
iPhone background to Android, link already establishedYes. The existing link keeps carrying traffic.
Android background to anythingYes. The foreground service keeps it advertising normally.

The simulation's radio fabric enforces this asymmetry explicitly (discoverableToAndroid), so it cannot be forgotten in a scenario.

Android BLE scanning counts as a location access

Android treats a BLE scan as location access unless the manifest says otherwise, because scan results can be used for positioning. And an app counts as foreground for location purposes only with a visible activity or a location-typed foreground service. A connectedDevice service does not qualify.

The result was that a backgrounded Airhop held its process up, kept a visible notification reading "Discovering and relaying nearby messages", and was handed no scan results at all.

bitchat solves this with ACCESS_BACKGROUND_LOCATION and a location service type. Airhop asserts neverForLocation on BLUETOOTH_SCAN instead, which is accurate here: a scan result is read for its service UUID, its 8 byte peer ID and its RSSI, none of which is a position. From API 31 that removes the coupling entirely. API 26 to 30 keeps it, since the flag does not exist there, and getRadioState reports which regime applies through locationRequiredForScan.

Location is still requested, but only for geohash channels, and only when the user opens one.

Some Android devices cannot advertise at all

At the API 26 floor, some chipsets have no BLE peripheral role, so bluetoothLeAdvertiser is null. Those devices scan, relay and receive, but are never discoverable. The native module answers UNSUPPORTED, and the reconciler latches that refusal once rather than retrying on a 5 second ladder forever. The Mesh tab carries a dismissible note. Stating it is the fix; the platform fact cannot be changed.

Power and the duty cycle

Policy lives in TypeScript, mechanism in Kotlin. src/services/power-policy.ts is a pure function of four facts (foreground, charging, battery band, current mode) and the native module applies whatever mode it is given, deciding nothing itself. That keeps the decision testable without a device.

ModeScanAdvertiseTX powerRSSI pollDuty cycle
performanceLOW_LATENCYLOW_LATENCYHIGH5 scontinuous
balancedBALANCEDBALANCEDMEDIUM10 scontinuous
power-saverLOW_POWERLOW_POWERLOW30 s2 s on / 28 s off
ultra-low-powerLOW_POWERLOW_POWERULTRA_LOW60 s1 s on / 29 s off

Selection order, and the order carries the policy:

  1. Backgrounded gives power-saver, or ultra-low-power on a critical battery. Nobody is waiting on discovery latency off screen, and this is where a phone spends nearly all of its day.
  2. Charging in the foreground gives performance, since the cost is someone else's.
  3. Otherwise the battery band decides: critical (10 percent or less) gives ultra low, low (20 percent or less) gives power saver, anything else gives balanced.

Foreground on battery is balanced rather than performance because a balanced scan still finds peers within seconds, and reserving the most expensive setting for "plugged in" is what stops the app being the reason a phone dies.

Hysteresis is Airhop's addition. bitchat re-resolves on every ACTION_BATTERY_CHANGED, which fires per 1 percent, so a phone hovering at a threshold flips modes repeatedly and every flip restarts the scanner. Dropping into a lower band is immediate, since running hard on a nearly flat phone is the failure that matters. Climbing back out needs +3 percent.

The duty cycle is invisible above the native boundary. JavaScript asks for scanning and keeps getting it while native decides the rate. A burst ending is never reported as an adapter or link change, or the reconciler would try to repair a state that is working correctly.

Alternatives

OptionWhy not
Bluetooth Mesh (the official SIG profile)It exists and does managed flooding with provisioning and a network key. But provisioning requires a coordinator, the network key is a shared secret across the whole mesh, and phone platforms expose no API for it. It is designed for building automation, where a single owner provisions every node. Airhop's model is strangers with no shared secret.
Bluetooth Classic RFCOMMRequires pairing, which means a prompt per pair. Higher power. No dual-role mesh story. iOS restricts it to MFi-certified accessories.
WiFi Direct / WiFi AwareFar higher bandwidth, and Airhop uses it where possible. But it does not exist across platforms (Android WiFi Aware and Apple's AWDL cannot interoperate), it is not available on all Android devices or API levels, and it costs much more power. It is an accelerator, never the foundation. Chapter 28.
Ultrasonic (audio) dataWorks with no radio permission at all, and passes through no walls. Bit rates in the tens of bps, needs the speaker and microphone, and is audible to some people and to dogs. A novelty at this scale.
NFCRange of a few centimetres, which is a security property rather than a limitation, and it is genuinely attractive for key exchange. Not used: contact exchange is camera QR only, which gives the same in-person guarantee with no extra dependency and works on every device, including ones with NFC locked to payments.
LoRaKilometres of range, but no phone has the radio. It is the right answer for fixed relay hardware, which is exactly where Airhop uses it. Chapter 47.

Drills

  • Why does every Airhop device run both GATT roles? Because a mesh needs every node to be both server and client. In the conventional star topology, peripherals cannot talk to each other and everything passes through the central. Running both roles on every device makes the graph arbitrary: A can be a peripheral to B and a central to D at the same time, so any node can leave without partitioning the network.
  • Where does 467 come from, exactly? 512 (the ATT maximum attribute value, and therefore the frame budget) minus 16 (v2 packet header) minus 8 (senderID) minus 8 (recipientID, present on a DM fragment) minus 13 (fragment header: streamID 8, index 2, total 2, inner type 1). bitchat derives 469 from the same budget with a smaller header. Being two bytes under is harmless, because the chunk size is a sender-side choice and the receiver reassembles by index.
  • Why is there no pairing, and what does that cost? Pairing would require a user prompt per pair, which makes a mesh of strangers impossible as a product. The cost is that BLE contributes zero security: no link encryption, no authentication. Every security property comes from the application layer instead, which is why the threat model assumes an attacker in radio range can transmit anything, and why every packet type that carries a claimed sender is Ed25519 signed.
  • An iPhone user says their friend on Android cannot see them. What do you check first? Whether the iPhone app is in the foreground. Backgrounded, CoreBluetooth moves the service UUID into the advertisement overflow area and drops the local name, so only another iOS device can discover it. An already-established link keeps working, so the symptom is specifically "cannot find" rather than "cannot message". This is a platform behaviour with no application-side fix.
  • Why does a refused GATT write not tear down the link? Because the stack says the same thing when its queue is simply full as when the link is gone. The announce and gossip send path used to delete a link from the link registry on any rejected write, an action nothing could undo, so one transient refusal left the phone believing it had no neighbours for the rest of the session. Teardown belongs to the disconnect event. The same reasoning is why courier handover only retires an envelope after a write is accepted.
