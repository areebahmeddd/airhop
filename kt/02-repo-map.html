Why bitchat is checked in

bitchat/ios and bitchat/android are not dependencies. They are the specification. Airhop's conformance test parses their Swift and Kotlin sources at test time and fails if a constant drifts: it reads maxPayloadBytes out of FileTransferLimits.swift, and it fails if bitchat's packet type allocation comes within 16 of Airhop's 0x50 extension range. iOS is treated as canonical where the two upstreams disagree, because it is the more mature of the two and implements more packet types.

The layering rule

One rule explains most of the structure: a lower layer may never import a higher one. 

  features/  ──imports──▶  services/  ──imports──▶  core/
      │                        │                      │
      └──imports──▶ store/ ◀───┘                      │
                       │                              │
                       └──── core/ may import store/mmkv only
                             (courier and prekey stores persist)

  core/ imports NOTHING from services/, features/, or ui/.
  core/ has NO native dependencies. It runs in plain Node under jest.

The payoff is that the entire protocol is testable in CI with no phone attached, and that a fix in gossip sync fixes iOS and Android at the same instant. Airhop's answer to bitchat's biggest structural problem (two native codebases that drift, which once broke iOS to Android messaging for months over a fragment size mismatch) is simply that there is one implementation.

Imports that cross a top-level layer are written as path aliases (@core/mesh/wire/packet-codec); imports inside a layer stay relative. Aliases live in tsconfig.json and are mirrored in package.json for jest. So a diff that reaches across layers is visible in the import block.

One handle per partition

src/store/mmkv.ts is the only place a partition is opened, and it memoizes by id. A second handle on the same file is fatal: MMKV maps the file into memory, and two mappings can produce writes that clobber each other. This also matters for the panic wipe, which walks a list of partition ids and clears each through its single handle.

src/features and src/ui

features/ holds screens and screen-level logic, grouped by area: chat/ (18 files, including the 6,625 line message-thread.tsx), wallet/, settings/ (with a sections/ subdirectory of 13 settings screens), contacts/, discovery/ (the mesh radar and peer list), and onboarding/.

ui/ holds shared components (bottom sheet, toast, alert modal, avatar, status dot, error boundary), hooks, the theme tokens, and the font setup. There is no navigation library: the four-tab state machine is hand-rolled in src/app/app.tsx, and screens are plain components. Styling is StyleSheet plus theme tokens, with no Tailwind.

utils/ holds stateless helpers with no side effects: username generation, mentions, message preview text, geohash grid maths, conversation ordering, media policy, deep links, formatting. Every one has a test.

src/bridge and the native trees

Five contracts, and they are the entire surface between TypeScript and native code. Bytes cross base64 encoded, the only representation both runtimes agree on safely.

SpecBacked bySurface
NativeAirhopBLE.tsAirhopBLEModule.swift, AirhopBLEModule.kt14 methods, 10 events. Advertising, scanning, writes, radio state, power mode, background service, Tor probe, VPN watch.
NativeAirhopWiFi.tsAirhopWiFiModule.ktAndroid only. Start, stop, write, plus 4 events including availabilityChanged.
NativeAirhopVoice.tsAirhopVoiceModule.swift, AirhopVoiceModule.ktAAC-LC capture and playback.
NativeAirhopTor.tsAirhopTorModule.swift, AirhopTorManager.swiftiOS only. Start Arti, report bootstrap phase, wipe state.
NativeAirhopTorSocket.tsAirhopTorSocket.swiftiOS only. The SOCKS5 socket that TorWebSocket sits on.

None of these knows anything about packets, routing or encryption. That is the point: native code is harder to test, harder to keep consistent across two platforms, and harder to reason about, so it is limited to one module per hardware capability and no more.

The Android tree also holds service/AirhopForegroundService.kt, which is what keeps the process alive under Doze and OEM battery managers, and MainApplication.kt / MainActivity.kt. The iOS tree holds AppDelegate.swift with the CoreBluetooth state restoration identifier.

Never run prebuild

ios/ and android/ are checked in and hand-modified. npx expo prebuild regenerates them from app.json and would delete every native module. This is stated in the README as a caution and it is the single most destructive command in this repository.

Tests

Three tiers, in increasing order of ambition.

  1. Co-located unit tests in __tests__/ folders beside the code they cover. Around 90 files. These pin byte layouts, crypto vectors, store behaviour and pure helpers.
  2. Lifecycle tests in src/__tests__/lifecycle/: cold start, mid session, teardown. These drive the real app shell against a modelled OS.
  3. The multi-device simulation in src/__tests__/simulation/. A World with a single fake clock, a radio fabric that models the air between phones, and full isolated copies of the app as devices. Scenarios are labelled A01 to A06, B01 to B07, C01 to C09, M01 to M12, N01 to N14, R01 to R05, S01 to S04, W01 to W21, F01 to F06, X01 to X03. Chapter 44 covers this in full.

Naming conventions that carry meaning

Three families of string are addresses rather than labels. Renaming one does not move data, it orphans it.

FamilyShapeExampleCost of renaming
Keychain itemairhop.<domain>.<thing>.v1airhop.wallet.p2pk.v1The secret becomes unreachable and survives the panic wipe.
HKDF domain separatorairhop-<purpose>-v1airhop-dr-root-v1Every key derived from it changes, so old and new builds cannot talk.
MMKV partition id<name>-storewallet-storeThe next launch opens a file that has never been written, while the old data sits on disk unreferenced.

Three names predate the convention and stay: airhop-chat, wallet-state and activity. No store declares a migrate function, so changing any of these safely means shipping a per-store migration that reads the old name and writes the new one, at least one release before the old name is dropped.

Drills

  • Why is src/core/ forbidden from importing native modules? So the entire protocol runs under jest in CI with no device. That is what lets the wire format, both handshakes, the ratchet, gossip sync and the routing be tested on every pull request. It also means the same code is what runs on both platforms, so a protocol bug cannot exist on one and not the other.
  • Where would you add a new packet type, and what would you have to touch? The enum in core/mesh/wire/packet-codec.ts, at 0x52 or above. Then a codec module in wire/ with a test. Then a case in MeshService.routePacket and a handler. If it should survive a partition, a sync bit in gossip-sync.ts. If it needs padding, a case in padsBLEFrame. And PROTOCOLS.md section 3.
  • Why is mesh-service.ts 6,000 lines rather than split up? It is the composition root: it holds the radios, the identity, the registry and the stores, and almost every handler needs several of those at once. Splitting it would mean either passing a large context object everywhere or creating circular imports. The subsystems it coordinates are split, into core/mesh/*, and those are where the logic and the tests live. This is a defensible shape, but it is also the file most in need of a second pass. See chapter 49.
  • Someone renames chat-store to messages-store in a refactor. What happens? Every existing user's entire message history becomes invisible on next launch, and stays on disk with nothing referencing it, so it is not even destroyed by a store clear. The panic wipe would also miss it, since it walks a hardcoded list of partition ids. This is why the naming rule is in the architecture document rather than in a style guide.
