The wire format

Every byte that leaves the radio, in order. This is the contract between Airhop, bitchat iOS, bitchat Android, and any relay hardware in between. It is the one part of the system that cannot be changed unilaterally.

In plain words

Explain it to a ten year old

Every message is put in an envelope with a label on the front. The label says what kind of thing is inside, who sent it, who it is for, when it was sent, and how many more times it is allowed to be passed along. The letter inside might be squashed smaller to fit, and it is signed at the bottom so nobody can pretend to be someone else. Every app that speaks this language uses exactly the same envelope, so an Airhop phone and a bitchat phone can read each other's post.

The frame, byte by byte

  FIXED HEADER (v2 = 16 bytes)

  offset  size  type      field
  ──────  ────  ────────  ────────────────────────────────────────────
  [0]        1  u8        version = 2
  [1]        1  u8        type          (the packet type registry below)
  [2]        1  u8        ttl           (7 default, decremented per hop)
  [3..10]    8  u64 BE    timestamp     (Unix MILLISECONDS, not seconds)
  [11]       1  u8        flags         (see below)
  [12..15]   4  u32 BE    payloadLength

  VARIABLE SECTIONS, in this exact order

  senderID       8 bytes    always present
  recipientID    8 bytes    only when hasRecipient = 1
  route                     only when hasRoute = 1:
                              [count u8][hop1 8B]...[hopN 8B]
  originalSize   4 bytes    only when isCompressed = 1
  payload        payloadLength bytes (minus the originalSize field)
  signature     64 bytes    only when hasSignature = 1

  THEN, for the packet types that need it, the WHOLE FRAME is
  PKCS#7-padded up to 256, 512, 1024 or 2048 bytes.
FieldWhy it is thereTrap
version Lets a decoder know which header layout follows. Airhop emits 2 and decodes 1 or 2. bitchat emits its core broadcasts (announce, message, leave) as v1 and uses v2 for file transfer and source-routed packets. Both sides decode either.
type The discriminator. GATT gives no framing, so the payload's meaning has to be in band. An unknown type is relayed but not interpreted. That is what makes extensions safe.
ttl Bounds propagation. Decremented at each relay, dropped at zero. Plaintext and forgeable. Never make a trust decision from it alone. The direct-peer rule pairs it with link binding for exactly this reason.
timestamp Freshness. Every packet is held to a +/- 2 minute window at ingress and is neither relayed nor acted on outside it. Milliseconds, not seconds. A seconds value is decades stale to the receiver and is silently dropped.
flags Says which optional sections are present. Two of the five bits are normalised out of the signing preimage. See below.
payloadLength Where the payload ends. Counts the payload plus the compression preamble, and not the route block. A sender-supplied claim. Every read that uses it is bounds-checked against what actually arrived.
senderID Who claims to have sent it. 8 bytes, the first half of SHA-256(noiseStaticPubKey). A claim. It is meaningful only after the signature is checked against a key bound to that ID.
recipientID Who it is for. Omitted entirely for broadcasts. Three encodings mean broadcast: flag clear, all zeros, or all 0xFF. Android writes the last one. Refusing it would silently lose Android live voice and public file transfers.

One packet type is the exception that proves the header design: 0x02, a public message in #bluetooth, whose payload is the message text as bare UTF-8 and nothing else. bitchat's BLEPublicMessageHandler reads String(data: packet.payload, encoding: .utf8) and renders the whole payload as the body. Anything wrapped around the text would be displayed as part of it. So the framing has to be entirely in the header for that type.

Why location channels needed their own type

bitchat has the same location channels at the same geohash precisions, but it publishes them to Nostr relays and never over Bluetooth. On the Bluetooth mesh, bitchat has exactly one public room, which its UI labels "bluetooth". So the Bluetooth copy of a location channel message is an Airhop-only path, and a bitchat peer already receives the Nostr copy. Sent under 0x02 it would be rendered in their mesh room as well, addressed to an audience its author never chose. Under 0x51 it is a type neither bitchat client interprets, so they relay it without showing it.

Unknown does not mean lost. bitchat's type switch logs case .none and falls through to scheduleRelayIfNeeded, and RelayController.decide receives the type as booleans that are all false for an unknown one, so it takes the ordinary broadcast relay path. A named Airhop channel therefore crosses a mesh made entirely of bitchat phones while staying invisible to their users. That is pinned end to end by a three node scenario in the conformance tests.

TLV, the encoding used everywhere inside

Almost every payload with more than one field uses type-length-value. It is not one format: the length width differs by payload, and that is a compatibility detail rather than a mistake.

PayloadTypeLengthWhy
ANNOUNCEu8u8Fields are tiny (32 byte keys, 32 byte nicknames) and 31 bytes of advertising discipline carried over. A 1 byte length caps a nickname at 255 bytes, well past its 32 byte budget.
File packetu8u16, except content which is u32File content can be a megabyte. A u16 length would cap it at 64 KiB.
Gossip filteru8u16 BEA 400 byte filter needs more than 255.
Courier envelopeu8u16 BECiphertext up to 16 KiB.
Group stateu8u16 BEA roster of 16 members is over a kilobyte.
PrivateMessagePacketu8u8This is the reason DMs are capped at 255 bytes of content. bitchat's is the same, and all three implementations return nothing rather than truncating.

The universal rule is skip what you do not know. A decoder reads type and length, and if the type is unrecognised it advances by the length and continues. That is what lets Airhop add TLV 0x07 (a Nostr public key) to an announce, and tags 0x05 to 0x07 to a file packet, at zero cost in either direction: a bitchat client reads the file and ignores the extras.

One TLV is read and never written: Bitle relay hardware marks itself with 0xB1, outside the range either client assigns. Airhop reads bit 0 and draws those peers as equipment rather than people. That flag decides presentation and nothing else, because a node signs its own announce, so any device can claim to be infrastructure. Since the claim only removes actions from its own row, there is nothing to gain by making it falsely.

Signing, and the preimage rule

The signature does not cover the bytes on the wire. It covers a normalised re-encoding of the packet. 

  signingBytes(packet) = encodePacket({
      ...packet,
      ttl:       0,          // so relays can decrement without breaking it
      isRSR:     false,      // so a stored packet can be retagged as a response
      flags:     flags & ~SIGNED,   // so the signature does not sign itself
      signature: 64 zero bytes,
  }, padding = TRUE)         // ALWAYS padded, for EVERY type

  signature = Ed25519.sign(signingBytes(packet), signingPrivKey)

Three consequences, each of which was a real bug at some point:

  1. TTL is zeroed. Otherwise a relay that decrements TTL would invalidate the signature, and no multi-hop packet could ever be verified. This is the whole reason the field is normalised.
  2. IS_RSR is cleared. Gossip sync answers a request by replaying a stored packet with the RSR flag set. If that flag were in the preimage, the stored signature would no longer verify and every sync response would be dropped.
  3. Padding is forced on, for every type. bitchat's toBinaryDataForSigning() encodes with padding on unconditionally, so pad bytes are inside the signed material of every signed packet. Using the per-type wire policy here would re-sign announces, messages, board posts and files over a different preimage, and no bitchat node would verify anything Airhop sends.

Not everything is signed, and that is deliberate

UnsignedWhy it is safe
Noise handshake messages (0x10)The peer may not hold our signing key yet, and the handshake authenticates itself: it only completes when the remote static key hashes to the claimed peer ID.
Messages inside a Noise session or a ratchetThe session already authenticates them. A redundant signature would cost 64 bytes and leak the sender's identity to relays that can read the header.
Fragments (0x20)Authenticity belongs to the inner packet, which is signed and re-verified after reassembly. A per-fragment signature would cost 64 of the 512 bytes for nothing. bitchat sends signature: nil and neither side's fragment path inspects one.
PING and PONGThe reply's echoed 8 byte nonce binds it to the probe. They carry no content and cost nothing to forge harmlessly.

Signatures are required exactly where a claimed sender is otherwise unverifiable: announces, public and private channel messages, attachments, voice frames, board posts and gateway uplinks.

Padding: two different rules

Padding appears twice, and conflating the two breaks the protocol in opposite directions.

Which packetsWhy
Signing preimage Every type, always Interop. bitchat's signing encoder pads unconditionally, so any deviation means nothing anyone else sends can be verified here, and nothing sent from here can be verified anywhere.
Outbound wire frame 0x10, 0x11, 0x12, 0x50 only Privacy. These are the types whose ciphertext length reveals plaintext length. Everything else has a size that is already public.

The algorithm is PKCS#7 into one of four block sizes: 256, 512, 1024, 2048. Every pad byte equals the pad length, so stripping is self-describing. The block is chosen for dataSize + 16, budgeting for an AEAD tag, matching bitchat exactly. If the data exceeds the largest block, padding is a no-op, because it will be fragmented anyway.

Why padding everything is not a safe default

It buys nothing for a type whose size is already public, and it costs real airtime on an 18 KiB/s radio. A 30 byte PING becomes 256 bytes. Worse, a roughly 309 byte live voice burst becomes 512, which is past the fragment frame budget and past most negotiated MTUs. That is the precise outcome the 210 byte burst content budget exists to prevent: a voice packet must never enter the fragment scheduler, which caps concurrent transfers and would starve file sends while somebody talks.

Decoders accept both forms. decodePacket tries the bytes as-is first, then retries after stripping PKCS#7, exactly as bitchat does, so an implementation that pads more than we do stays readable.

The non-canonical DEFLATE problem

This is the subtlest thing in the wire layer and it is worth understanding properly.

DEFLATE output is not canonical. Any conforming encoder produces a valid stream, but not the same bytes. iOS uses Apple's compression_encode_buffer, Android uses java.util.zip.Deflater, and Airhop uses pako. All three inflate each other's streams, but none reproduces another's output, and the "only if smaller" check can even make them disagree on whether to compress at all.

Now recall that the signature covers a re-encoding. So verifying a packet re-encodes it, and therefore re-compresses it. Under a different encoder, that produces different bytes, a different preimage, and a rejected signature on a perfectly valid packet.

The fix is to never re-compress a payload that arrived compressed:

  interface WirePayload {
    bytes:      Uint8Array;   // exactly as transmitted
    compressed: boolean;      // whether the ORIGINATOR compressed it
    forPayload: Uint8Array;   // the decoded array these bytes decode to
  }

  decodePacket() attaches a WirePayload to every packet.
  encodePacket() reuses it verbatim, but ONLY when
      wire.forPayload === packet.payload   (reference identity)

  If a caller replaces the payload, the binding breaks and the encoder
  falls back to compressing. Without that check, a same-length payload
  swap would be signed against the pre-swap bytes and verify anyway.

This is required in two places:

  • Verification, so a packet signed by any implementation verifies here.
  • Relaying, because a relay re-encodes. Re-compressing would replace the originator's bytes with the relay's own and invalidate the signature for every node downstream.

Locally originated packets have no received form and are compressed normally, so this never changes what Airhop emits. Airhop's outbound DEFLATE is byte-identical to reference zlib, locked by test vectors in packet-compression.test.ts, verified against zlib 1.3.1 which is also what Android's Deflater produces. It is not yet verified against Apple's encoder, which would require running CompressionUtil.compress on Apple hardware.

The decompression bomb

originalSize is a sender-supplied field. A packet can declare 100 bytes and carry a stream that expands to a gigabyte. Inflating it whole before noticing is an out-of-memory crash that any unauthenticated peer in radio range can trigger.

So output is capped at the declared size while inflating, not measured afterwards. The decoder refuses the packet at the first byte over. Both bitchat clients bound it the same way: iOS inflates into a buffer allocated at exactly originalSize, and Android does the same before probing for one further byte. A valid stream inflates to exactly originalSize, so nothing legitimate is affected.

A real finding from this area

A 24 byte frame declaring COMPRESSED with payloadLength = 4 left the read offset exactly at the end of the buffer, and DataView throws on an out-of-range read rather than returning null like every other failure path. decodePacket has no try/catch and neither does its caller, so the RangeError escaped into the native packetReceived listener. Twenty four attacker-chosen bytes. A malformed frame must decode to null, never throw, and there is now an explicit bounds guard before that read.

Packet IDs

There is no nonce field in the header. Identity is derived from content: 

  PacketID = SHA-256( type[1] || senderID[8] || timestamp_u64_BE[8] || payload )[0:16]

Matching PacketIdUtil.swift and PacketIdUtil.kt. This 128 bit value is used for two things: the deduplication seen-set (1000 entries, 5 minute window) and the gossip sync GCS filter.

Notice what is excluded: TTL, flags, recipientID and the signature. So the same logical packet has one ID no matter how many hops it has taken, which is exactly what deduplication needs. And notice what is included: the timestamp. Two identical messages sent one millisecond apart are different packets, which is why a named channel message carries its own message ID inside the payload as well.

Source routes: followed, never originated

When hasRoute = 1, the packet carries a hop list: [count u8][hop1 8B]...[hopN 8B]. The sender and the final recipient are not in the list; they are in the header.

Airhop follows routes and never originates them, and never emits the directNeighbors TLV (0x04) that route planning depends on. Following is close to free and keeps Airhop from being a node other implementations must route around: a relay named in the list unicasts to the next name, and falls back to flooding when that hop is unreachable.

Originating would require publishing our adjacency in cleartext to every nearby radio. A ten-entry neighbour list lets one passive listener reconstruct who is standing next to whom, which is exactly the inference the whole design tries to avoid. bitchat's own peer-ID rotation analysis rejects it for the same reason, and bitchat stopped emitting it. Flooding is the documented fallback for a route that cannot be built, and it is what Airhop already does.

The cost is real and worth stating: with no adjacency to route on, every directed send falls back to flooding. That is more airtime in a dense mesh, with no correctness change.

Extending the format safely

Five rules, each learned from a bug:

  1. New packet types start at 0x52. Never claim a value near bitchat's frontier. One byte with two meanings makes each side's parser depend on the other's validation not to misfire.
  2. New TLV tags go above the range the other side assigns. bitchat holds ANNOUNCE tags 0x01 to 0x06; Airhop's Nostr key is 0x07. Reading one as the other would corrupt both sides.
  3. Skip unknown TLVs by length, never abort. That single behaviour is what makes forward compatibility work.
  4. Decide the padding rule explicitly. A new encrypted type belongs in padsBLEFrame. A new public or time-critical type does not.
  5. Decide the gossip rule explicitly. A type with no sync bit has no catch-up at all, silently. Moving location channels off 0x02 would have dropped them out of sync entirely if bit 24 had not been allocated at the same time.

Drills

  • Why is TTL excluded from the signature but recipientID included? TTL changes legitimately at every hop, so including it would make a signature valid for exactly one hop. RecipientID never changes in transit, and it decides who the packet is for, so it must be authenticated: otherwise a relay could redirect somebody else's directed packet.
  • An Airhop packet fails signature verification on a bitchat phone. Name three plausible causes, in order. One: the padding rule. If we signed with the per-type wire policy instead of forcing padding on, the preimage differs for every unpadded type. Two: re-compression. If verification re-compressed the payload with a different encoder, the preimage differs. Three: a normalisation mismatch, TTL or IS_RSR not being cleared identically. All three produce the same symptom, a valid packet that will not verify, which is why they are pinned by test vectors rather than by inspection.
  • Why does #bluetooth not carry a message ID in its payload? Because bitchat's handler renders the entire payload as the message body, so any wrapper would appear as text. It does not need one: both implementations derive the same content-stable identifier from sender, timestamp and content (bridgeStableID here, MeshMessageIdentity.stableID in bitchat), which is what the bridge keys on and what the Nostr copy dedupes against.
  • Someone proposes padding every outbound frame "for consistency". Argue against it. It buys nothing where the size is already public, and it costs airtime on an 18 KiB/s shared radio: a 30 byte PING becomes 256 bytes. Worse, a roughly 309 byte voice burst becomes 512, past the fragment frame budget and most negotiated MTUs, which would push live voice into the fragment scheduler and starve file transfers. The correct rule is exactly bitchat's: pad only where ciphertext length reveals plaintext length.
  • How would you add a "poll" packet type without breaking anything? 0x52 in the enum. A codec module in wire/ with round-trip and malformed-input tests. A case in routePacket. Not in padsBLEFrame if it is public. A gossip bit above 24 if replies should survive a partition, and a candidate max-age. Signature mandatory, checked through senderIsAuthentic. Then a conformance scenario proving a bitchat node relays it without rendering it.
