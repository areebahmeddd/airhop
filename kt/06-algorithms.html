The algorithm graveyard

Every algorithm Airhop uses beat a field of alternatives, and most of those alternatives are dead for interesting reasons. This chapter is the whole field: what broke, how it broke, what replaced it, and why Airhop chose what it chose.

In plain words

Explain it to a ten year old

Locks get picked. When somebody finds a way to pick a kind of lock, everybody has to change to a new kind, and the old one goes in the bin. This is the bin. Some locks were bad from the start, some were fine until computers got fast, some were fine until somebody found a clever shortcut, and a few were fine but too fiddly to fit correctly so people kept installing them wrong.

Hash functions

AlgorithmOutputStatusWhat happened
MD5 (1992)128 bitbroken Collisions found in 2004, then in seconds on a laptop. In 2012 the Flame malware used an MD5 collision to forge a Microsoft code-signing certificate and impersonate Windows Update. Still, disgracefully, found in the wild for "checksums".
SHA-1 (1995)160 bitbroken Theoretically weakened from 2005. In 2017 Google's SHAttered produced two different PDFs with the same hash. In 2020 chosen-prefix collisions made forging realistic documents practical. Git is still migrating away from it.
SHA-2 (2001)224 to 512 bitsolid No meaningful attack in 24 years. Same Merkle-Damgard structure as SHA-1, but a much stronger compression function. SHA-256 is what Airhop uses everywhere.
SHA-3 (2015)224 to 512 bitsolid A completely different construction (sponge, Keccak), chosen by open competition as insurance in case SHA-2 ever fell. Slower in software. Not needed here, and using it would break bitchat compatibility.
BLAKE2 / BLAKE3Variablesolid, faster Genuinely better than SHA-256 on speed. Rejected for one reason only: the wire format is shared, and every packet ID, peer ID and gossip filter hash must match bitchat byte for byte.

Length extension, and why HMAC exists

SHA-1 and SHA-2 are Merkle-Damgard constructions: they process the input in blocks, carrying state forward. The final state is the output. So an attacker who sees SHA-256(secret || message) can resume from that state and compute SHA-256(secret || message || padding || evil) without knowing the secret at all.

That is why naive "authentication" by hashing a secret with a message is broken, and why HMAC's nested double-hash construction exists. SHA-3's sponge construction is immune by design. Airhop uses HMAC for the courier tag, the geohash seed, the channel identity derivation and every ratchet chain step.

The cache timing attack, which is the whole argument

A software AES implementation looks up values in tables indexed by key-dependent data. Table lookups hit or miss the CPU cache, and a cache miss is measurably slower. An attacker running code on the same machine, or in some cases just measuring response times, can observe which table entries were touched and reconstruct the key. This is not theoretical: practical extractions have been demonstrated repeatedly.

ChaCha20 has no lookups. It performs the same additions, rotations and XORs regardless of the key, so its timing carries no information. That is why it was added to TLS, why WireGuard uses it exclusively, and why every Noise suite anyone actually deploys is the ChaCha variant.

For Airhop the decision is doubly forced. The target devices include cheap Android phones where hardware AES cannot be assumed, and the cryptography runs in JavaScript, which is the worst possible place to implement a table-based cipher safely. And the protocol name Noise_XX_25519_ChaChaPoly_SHA256 is mixed into the handshake's initial state, so a different cipher is not a configuration change, it is a different protocol that no bitchat node can speak.

Cipher modes, and why AEAD won

A block cipher encrypts one fixed-size block. A mode is how you use it on a real message, and the history of modes is a history of footguns.

ModeStatusFailure
ECBnever Each block encrypted independently, so identical plaintext blocks give identical ciphertext blocks. The famous encrypted penguin image, still clearly a penguin. Leaks structure directly.
CBClegacy Fixes the pattern leak, but with no authentication it is vulnerable to padding oracle attacks: an attacker submits modified ciphertexts and learns the plaintext from whether the padding error differs from other errors. Broke TLS repeatedly (BEAST, Lucky 13, POODLE).
CTRneeds a MAC Turns a block cipher into a stream cipher. Fine, and catastrophic on nonce reuse.
Encrypt-then-MACcorrect but manual The right composition, and people got the order wrong constantly. MAC-then-encrypt and encrypt-and-MAC are both attackable.
AES-GCMgood, sharp edges Proper AEAD. But nonce reuse is catastrophic in a specific way: it leaks the authentication subkey, which lets an attacker forge arbitrary messages, not just replay one. With a 96-bit nonce, random generation becomes risky after about 232 messages.
ChaCha20-Poly1305Airhop's choice AEAD, no tables, and the same nonce-reuse warning without the table-lookup class of side channel.
XChaCha20-Poly1305Airhop's choice where there is no counter Extends the nonce to 192 bits, which makes random nonces safe indefinitely. Used for private channels and Nostr DMs, where members have no shared counter and could not have one.

AEAD is the lesson, not the algorithm

Two decades of TLS vulnerabilities came from people composing encryption and authentication by hand and getting it subtly wrong. AEAD makes the composition one indivisible operation with no way to use only half of it. A failed tag returns nothing, not partial plaintext, not garbage. That is the design pattern worth carrying into anything you build.

Ed25519 in detail

This is the scheme signing every announce, every public message, every attachment, every board post and every voice frame in the app, so it is worth knowing properly. 

  THE SHAPE

    curve       Edwards25519, a twisted Edwards curve, birationally
                equivalent to Curve25519
    private     32 bytes, hashed to produce a scalar and a prefix
    public      32 bytes, a compressed curve point
    signature   64 bytes: (R, s)

  SIGNING message m with private key k

    h        = SHA-512(k)             -> (a, prefix)
    r        = SHA-512(prefix || m)   <- THE NONCE, DERIVED NOT RANDOM
    R        = r·G
    S        = SHA-512(R || A || m)
    s        = r + S·a  mod L
    signature = (R, s)

  VERIFYING with public key A

    S  = SHA-512(R || A || m)
    check   s·G  ==  R + S·A

  The verification equation only balances if the signer knew `a`.
PropertyWhy it matters here
Deterministic nonce The single most important property. r comes from hashing the key with the message, not from the random number generator. So signing is safe on a device with broken randomness, which is exactly the failure that destroyed ECDSA in the PlayStation 3 and Android wallet cases. It also means the same message signed twice gives identical bytes, which is what keeps Airhop's content-derived packet IDs stable.
No parameter choices There is no curve to pick, no hash to pick, no padding scheme. Whole classes of misuse simply do not exist.
Complete addition formulas Edwards curves have addition formulas with no special cases, so implementations do not need branches. Branches are where timing leaks live.
Small and fast 32-byte keys, 64-byte signatures. A signature is 64 of the 512 bytes in a Bluetooth frame, which is 12.5 percent. RSA-3072 would be 384 bytes, which is 75 percent of the entire frame and would make the protocol impossible.
Fast batch verification Relevant for a node verifying many packets, though Airhop does not currently batch.

Ed25519's one genuine wart

The original specification left some verification details ambiguous, so different libraries disagree about which edge-case signatures are valid: cofactor handling, non-canonical encodings, small-order points. This produced real interoperability bugs in consensus systems, where two nodes must agree exactly on validity.

RFC 8032 and later work tightened it. For Airhop it does not bite, because a rejected signature means a dropped packet rather than a network split, and because all three implementations use mainstream libraries. It is worth knowing if anyone ever proposes using signature validity as a consensus rule.

Ed25519 and X25519 are the same curve, and Airhop still keeps two keys

You can convert between the Edwards and Montgomery forms and use one key pair for both signing and key agreement. Airhop deliberately does not: cross-protocol attacks between signature and key-agreement schemes are a live research area, and the two operations stress a key differently. Two key pairs cost 32 extra bytes in the keychain and remove the entire class. It also makes the roles legible in code: noiseStaticPrivKey agrees, signingPrivKey authenticates.

Which curve, and the NIST question

CurveUsed byAssessment
NIST P-256 (secp256r1)TLS, smartcards, most enterprise works, unloved Its constants were generated from unexplained seeds, so nobody outside the process can verify they were not chosen adversarially. There is no known weakness. But it also has awkward addition formulas requiring special cases, which makes constant-time implementation harder, and its history includes Dual_EC_DRBG, a NIST random generator with a plausible backdoor.
Curve25519Signal, WireGuard, SSH, TLS 1.3, Airhop the default choice Every constant is explained and derivable from design criteria, which is what "nothing up my sleeve" means. Fast, safe formulas, no special cases, hard to implement wrongly.
secp256k1Bitcoin, Nostr, Cashu, Airhop fine, and mandatory here A Koblitz curve, chosen for efficiency. Airhop uses it not by preference but because Nostr is defined on it and Cashu is Bitcoin-adjacent. Neither is negotiable.
Curve448RareRoughly 224-bit security. Slower and larger for a margin nothing needs today.

Airhop therefore runs two curves, which is one more than ideal, and the reason is interoperability rather than taste. Curve25519 for everything on the mesh, secp256k1 for everything on the internet and in the wallet, bridged by an HKDF that derives the Nostr key from the signing key.

Airhop has no passwords at all, and that is a security property

There is no login, no passphrase, no PIN protecting the identity. So there is no password to phish, to reuse across sites, to brute force, or to be compelled to reveal. Key material is protected by the OS keychain, which is hardware-backed on modern devices and gated by the device unlock the user already has.

The one place a human-memorable secret appears is the optional 12-word BIP-39 wallet recovery phrase, and even there the words are the entropy (128 bits of it) rather than a password protecting something else, so no stretching function is required.

Post-quantum

A sufficiently large quantum computer would run Shor's algorithm and break every public-key algorithm in this chapter. None exists, and the engineering gap is enormous, but the threat has a name worth knowing. 

  WHAT A QUANTUM COMPUTER WOULD BREAK

    Shor's algorithm     factoring and discrete logarithms
                         => RSA, DSA, ECDSA, Ed25519, X25519, ALL of it
                         COMPLETELY broken, not weakened

    Grover's algorithm   generic search, square-root speedup
                         => symmetric ciphers and hashes lose HALF
                            their bit strength
                         AES-256 -> ~128 bit, still fine
                         SHA-256 -> ~128 bit, still fine

  SO: asymmetric is destroyed, symmetric is merely halved.

"Harvest now, decrypt later"

An adversary can record encrypted traffic today and decrypt it in twenty years when the hardware exists. That makes the threat present tense for anything with long-term value.

It is a much smaller problem for Airhop than for most systems, because forward secrecy already deletes the keys. Noise XX's ephemeral private halves are destroyed at split, and the Double Ratchet deletes each message key immediately after use. A recorded session cannot be decrypted later even with a quantum computer, because the key it would recover no longer exists anywhere.

The exposures that remain are the ones without forward secrecy: Nostr DMs, which use a static ECDH between two long-lived identities, and courier envelopes sealed to a static key when no prekey was available. Both are already listed as gaps in chapter 49 for non-quantum reasons, and this is a second reason.

Post-quantum candidateJobCost
ML-KEM (Kyber)Key agreement~1.2 KB public key against Curve25519's 32 bytes
ML-DSA (Dilithium)Signatures~1.3 KB public key, ~2.4 KB signature
SLH-DSA (SPHINCS+)Signatures, hash-based, very conservative~8 to 30 KB signatures

Why Airhop cannot adopt these today

A Bluetooth frame is 512 bytes. An ML-DSA signature alone is roughly five times that. A single packet would become five fragments before carrying any content, on a radio that moves 18 KiB per second. The protocol would not merely slow down, it would stop being viable.

What everybody else does is hybrid: run the classical exchange and a post-quantum one and combine both outputs, so it is secure if either holds. Signal shipped PQXDH, iMessage shipped PQ3, TLS 1.3 has hybrid key exchange. All of those are on transports with megabytes of headroom. On a 512-byte frame it is a research problem, not an engineering task.

Drills

  • Why ChaCha20 rather than AES? Not security, both are unbroken. Software AES uses lookup tables indexed by key-dependent data, so cache timing can leak the key, and that is only mitigated by hardware AES instructions which cheap Android phones do not guarantee. ChaCha20 is add, rotate and XOR with no tables, so it is naturally constant time and fast in software. This app runs its cryptography in JavaScript on the widest possible range of devices, which makes the argument decisive. And the Noise suite name is mixed into the handshake state, so the cipher is part of the protocol identity rather than a setting.
  • Why Ed25519 rather than ECDSA? The nonce. ECDSA needs a fresh unpredictable random value per signature, and reusing or biasing it reveals the private key algebraically. That destroyed the PlayStation 3's code signing and drained Android Bitcoin wallets. Ed25519 derives its nonce deterministically by hashing the private key with the message, so it is safe even on a device with broken randomness. It also has no parameter choices to get wrong, complete addition formulas that need no branches, and it gives identical bytes for the same input, which keeps content-derived packet IDs stable.
  • Why is SHA-1 broken and SHA-256 not, given the same structure? Both are Merkle-Damgard, but SHA-1's compression function has exploitable differential characteristics and its output is only 160 bits. Practical collisions arrived in 2017 with SHAttered and chosen-prefix collisions in 2020. SHA-256's compression function has resisted 24 years of analysis and its 256-bit output puts collisions at 2128. They share the length-extension weakness, which is why HMAC exists and why hashing a secret with a message directly is never acceptable.
  • What is a padding oracle, and what killed that whole family? With CBC mode and no authentication, an attacker submits modified ciphertexts and observes whether the server reports a padding error differently from any other error. Each answer leaks one byte, and repeated queries recover the plaintext without ever knowing the key. It broke TLS repeatedly. What killed the family is AEAD: encryption and authentication as one operation where a failed tag returns nothing at all, so there is no distinguishable error to observe.
  • How exposed is Airhop to a future quantum computer? Less than most systems, because forward secrecy already deletes the keys. Shor's algorithm would break every asymmetric primitive here, but a recorded Noise session cannot be decrypted later because the ephemeral private halves were destroyed at split and each ratchet message key is deleted after one use. Grover's algorithm halves symmetric strength, leaving ChaCha20 and SHA-256 at about 128 bits, which is fine. The genuine exposures are the two places with no forward secrecy: Nostr DMs, which use a static ECDH between long-lived identities, and courier envelopes sealed to a static key. Adopting post-quantum primitives is blocked by size: an ML-DSA signature is roughly five times a whole Bluetooth frame.
  • Name the single strongest structural defence in the whole cipher suite choice. No negotiation. TLS spent two decades patching downgrade attacks because a client and server negotiate which algorithms to use, and an attacker in the middle can influence that. Noise fixes the entire suite in the protocol name, and that name is mixed into the handshake's initial hash state, so two parties who disagree simply fail to complete rather than falling back to something weaker. There is no weaker option to fall back to.
