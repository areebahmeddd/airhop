The Noise protocol

Two phones that have never met, with no certificate authority, no server and no shared secret, end up with a mutually authenticated encrypted channel in three messages. This is how.

In plain words

Explain it to a ten year old

Two strangers want to talk privately in a room full of people. They each pick a random number nobody else knows. They shout out a clue to their number, one each. From the two clues, and their own secret numbers, they can each work out the same shared secret, but nobody listening can. Then, using that secret to whisper, they each tell the other who they really are. If either name turns out to be a lie, the whispering stops working immediately, so neither can pretend.

What Noise is

Noise is a framework rather than a protocol. You choose a handshake pattern and a cipher suite, and the framework generates a protocol with formally analysed properties. It was designed by Trevor Perrin, who also co-designed the Signal protocol. WireGuard is built on Noise IK. WhatsApp's client-to-server transport is Noise. It is deployed at enormous scale and has been formally verified several times over.

Its two design decisions that matter here:

  • No certificate authorities. Authentication is by raw public key. There is no PKI to bootstrap, which is exactly what a serverless system needs.
  • No negotiation. The protocol name is fixed and both sides must already agree on it. There is no cipher suite negotiation, so there is no downgrade attack. The name itself is mixed into the initial state, so a mismatch fails immediately rather than being exploitable.

The symmetric state

Everything in a Noise handshake operates on three variables. If you understand these three, the rest is mechanical.

VariableNameWhat it accumulatesPublic?
h handshake hash Every byte that went over the wire, hashed in order. A running transcript digest. YES. Anyone who captured the handshake can recompute it exactly.
ck chaining key Every DH shared secret, mixed in via HKDF. NO. It depends on ephemeral private keys that are destroyed at split.
k cipher key The current AEAD key, replaced every time ck advances. Null until the first DH. No.

Three operations move them:

  mixHash(data):    h = SHA-256(h || data)
                    // absorbs PUBLIC bytes. Never key material.

  mixKey(dhOutput): ck, k = HKDF(ck, dhOutput, 2 outputs)
                    n = 0                    // reset the nonce counter
                    // absorbs SECRET material.

  encryptAndHash(plaintext):
        if k exists:  ct = AEAD(k, n++, aad = h, plaintext); mixHash(ct); return ct
        else:         mixHash(plaintext); return plaintext unchanged

  decryptAndHash(ciphertext):
        if k exists:  pt = AEAD-open(k, n++, aad = h, ciphertext)
                      mixHash(ciphertext); return pt
        else:         mixHash(ciphertext); return ciphertext unchanged

The single most important line in this chapter

h absorbs only bytes that went over the wire. ck absorbs the secret DH outputs. Therefore h is public and ck is not. Using h as key material is a critical vulnerability, and it was one in Airhop: the Double Ratchet root key was seeded from the handshake hash, so anyone who captured the three handshake packets (which flood the mesh at TTL 7) could recompute the root key and forge or decrypt every Double Ratchet message in that conversation.

h is safe as a channel binder, which is all Noise defines it for. The Airhop source now carries that warning directly on the handshakeHash field.

One more detail that broke interoperability once: initialisation runs mixHash(prologue) even when the prologue is empty. Standard Noise always does this, and so does bitchat, so h becomes SHA-256(protocol_name) rather than the protocol name itself. Skipping it left Airhop's h one hash behind bitchat's, which is used as the AEAD associated data when the static key is sealed in message 2. Same key, different AAD, tag mismatch, and no cross-implementation handshake could ever complete.

XX, message by message

  NOTATION
    e   ephemeral key, freshly generated, used once, destroyed
    s   static key, the long-lived identity
    ee  DH(my ephemeral, their ephemeral)
    es  DH(ephemeral, static)     roles depend on direction
    se  DH(static, ephemeral)

  THE PATTERN
    -> e
    <- e, ee, s, es
    -> s, se

Message 1: initiator sends 32 bytes

  INITIATOR
    generate ephemeral keypair (e_priv, e_pub)
    mixHash(e_pub)
    encryptAndHash(empty)          // k is null, so this is just mixHash(empty)
    SEND: e_pub                    // 32 bytes, entirely in the clear

  RESPONDER
    mixHash(e_pub)
    decryptAndHash(rest)           // k is null, passthrough

Nothing is encrypted and nothing is authenticated. An observer sees a random 32 byte value. The only thing accomplished is that both sides now share one public ephemeral key and their transcripts agree.

Message 2: responder sends 96 bytes

  RESPONDER
    generate ephemeral keypair
    mixHash(my_e_pub)                          // "e"
    mixKey( DH(my_e_priv, their_e_pub) )       // "ee"  ← FIRST SECRET
        ck advances, k now exists
    enc_s = encryptAndHash(my_static_pub)      // "s"   48 bytes (32 + 16 tag)
        the static key is now ENCRYPTED
    mixKey( DH(my_static_priv, their_e_pub) )  // "es"
    enc_payload = encryptAndHash(empty)        // 16 bytes (tag only)
    SEND: e_pub(32) || enc_s(48) || enc_payload(16)   = 96 bytes

  INITIATOR
    mixHash(their_e_pub)
    mixKey( DH(my_e_priv, their_e_pub) )       // same "ee" value
    their_static = decryptAndHash(enc_s)       // learns who they are
    mixKey( DH(my_e_priv, their_static) )      // "es" from the other side
    decryptAndHash(enc_payload)

Two things happened here, and both are structural:

  • Identity hiding. The responder's static key is transmitted after the first DH, so it is encrypted. A passive observer never learns who answered. This is why the pattern order is e, ee, s, es and not e, s, ee, es.
  • The initiator now knows the responder's identity, and can decide whether to continue.

Message 3: initiator sends 64 bytes

  INITIATOR
    enc_s = encryptAndHash(my_static_pub)        // "s"   48 bytes
    mixKey( DH(my_static_priv, their_e_pub) )    // "se"
    enc_payload = encryptAndHash(empty)          // 16 bytes
    SEND: enc_s(48) || enc_payload(16)           = 64 bytes

  RESPONDER
    their_static = decryptAndHash(enc_s)
    mixKey( DH(my_e_priv, their_static) )        // "se"
    decryptAndHash(enc_payload)

Now both sides have performed the same three DH operations in the same order, so their chaining keys are identical, and each knows the other's static public key. The handshake is complete. 

  THE THREE DH OPERATIONS AND WHAT EACH BUYS

    ee   ephemeral x ephemeral   FORWARD SECRECY
                                 Both private halves are destroyed at split,
                                 so a later compromise of either static key
                                 cannot reconstruct this session.

    es   responder static x initiator ephemeral
                                 AUTHENTICATES THE RESPONDER to the initiator.
                                 Only the real holder of that static key can
                                 compute it.

    se   initiator static x responder ephemeral
                                 AUTHENTICATES THE INITIATOR to the responder.

  Remove any one and a specific property disappears. Remove ee and there
  is no forward secrecy. Remove es and you can be talking to anyone.

Split, and the third output

  split():
    k1, k2, exporterSecret = HKDF(ck, empty, 3 outputs)

    initiator: send with k1, receive with k2
    responder: send with k2, receive with k1

    then ZERO: localStaticPriv, localEphemeralPriv, k, h, ck

Standard Noise derives two outputs. Airhop asks for three and keeps the third as the exporterSecret, which seeds the Double Ratchet.

Why the third output is free

HKDF-Expand derives each output block from the previous one: T(1) = HMAC(PRK, info||1), T(2) = HMAC(PRK, T(1)||info||2), and so on. Asking for a third block does not change the first two. So k1 and k2 are bit identical to a two-output split, and a bitchat peer negotiates exactly the same transport keys and never knows a third value was computed. Zero interoperability cost.

And unlike h, the exporter secret descends from ck, which absorbed ephemeral DH outputs whose private halves are destroyed at split. It cannot be reconstructed from long-term keys, and it cannot be recomputed by an observer. Chapter 18 explains why that is exactly the property the ratchet needs.

The zeroing at the end is best effort in JavaScript. The arrays are filled with zeros, but the engine may have copied them during garbage collection and there is no way to reach those copies. This is a known and unavoidable limitation of doing cryptography in a managed runtime, and it should be stated rather than glossed.

The transport session

  encrypt(plaintext):
    n = sendCounter++
    ct = ChaCha20-Poly1305(sendKey, nonce(n), aad = empty).seal(plaintext)
    return [4 byte BE n] || ct

  decrypt(message):
    n = read the 4 byte BE prefix
    if replayWindow.isValid(n) is false     -> THROW "replay detected"
    pt = ChaCha20-Poly1305(recvKey, nonce(n), aad = empty).open(rest)
    replayWindow.markSeen(n)
    return pt

  nonce(n) = 12 bytes: [00 00 00 00][n as LE u32][00 00 00 00]

The nonce is prepended in the clear, which is bitchat's useExtractedNonce: true mode. That is what allows out-of-order decryption, which matters on a mesh where a packet can take two different paths and arrive in the wrong order.

The replay window

  A 1024-BIT SLIDING WINDOW, 128 BYTES

  highest = 5000
                        ┌──── bit 0 = message 5000
  bits: [1][0][1][1]... │
         │  │  │  └──── bit 3 = message 4997
         │  │  └─────── bit 2 = message 4998  (not seen)
         │  └────────── bit 1 = message 4999
         └───────────── bit 0 = message 5000  (seen)

  isValid(n):
     n > highest              -> true, it is new
     highest - n >= 1024      -> false, too old to judge
     bit already set          -> false, replay
     otherwise                -> true

  markSeen(n) with n > highest shifts the whole bitmap left by (n - highest).

This is the same construction IPsec and WireGuard use. It tolerates reordering up to 1024 messages while making replay impossible inside that window, and it costs 128 bytes of state per session.

The send counter throws at 2^32 rather than wrapping. Wrapping would reuse a (key, nonce) pair, which is the catastrophic failure from chapter 16. Four billion messages in one session is not a realistic scenario, but the failure mode has to be "refuse" rather than "silently break".

Noise X, for the courier

  Noise_X_25519_ChaChaPoly_SHA256      pattern:  -> e, es, s, ss

  seal(senderStaticPriv, recipientStaticPub, plaintext):
    mixHash(recipientStaticPub)              // PRE-MESSAGE: known in advance
    generate ephemeral e
    mixHash(e_pub)
    mixKey( DH(e_priv, recipientStaticPub) )       // "es"
    enc_s = encryptAndHash(senderStaticPub)        // "s"  48 bytes
    mixKey( DH(senderStaticPriv, recipientStaticPub) )  // "ss"
    enc_payload = encryptAndHash(plaintext)
    ZERO e_priv
    return e_pub(32) || enc_s(48) || enc_payload

  open(recipientStaticPriv, envelope):
    ... the mirror image ...
    returns { plaintext, senderStaticPubKey }

How Airhop drives it

  A sends a DM to B, no session exists

  A: sendDm -> no session
     create NoiseHandshake.createInitiator(myStaticPriv)
     msg1 = writeMsg1()                            32 bytes
     packet type 0x10, UNSIGNED, recipientID = B, ttl 7
     QUEUE the message text as pendingText
     FLOOD it (B may be several hops away)

  B: onNoiseHandshake, payload is 32 bytes -> this is msg1
     createResponder(myStaticPriv)
     readMsg1()
     msg2 = writeMsg2()                            96 bytes
     send back

  A: payload is 96 bytes -> msg2
     readMsg2()
     msg3 = writeMsg3()                            64 bytes
     send
     session = split()
     tryInitDR()  ← seeds the ratchet from exporterSecret

     ⚠ A COMPLETES ONE MESSAGE BEFORE B DOES.
       So the DR init and the queued-invite flush happen AFTER msg3
       goes out, not before, or anything sent in that window is
       decrypted by nobody.

  B: payload is 64 bytes -> msg3
     readMsg3()
     session = split()

     THEN, before storing the session:
       sessionBindsTo(remoteStaticPub, claimedPeerID)?
         SHA-256(remoteStaticPub)[0:16] == claimed peer ID
       no  -> DISCARD. The peer is not who the header says.
       yes -> store it

  BOTH: flush pendingText over the new session
SituationHandling
Crossed initiations. Both sides start a handshake at once. Tie-break on the lower peer ID. The loser resets to responder, and carries its queued text across the flip so a simultaneous initiation does not drop DMs.
Stuck handshake. msg2 or msg3 lost, or the peer went away mid-handshake. A 30 second timeout, checked lazily on the next send. bitchat gets the same recovery from event-driven session clears; an age check is the equivalent safety net here.
Identity binding. A completed session is only stored if the authenticated remote static key hashes to the claimed peer ID. This is bitchat's rule and it is what makes the peer ID meaningful rather than a label.
A verified LEAVE arrives. Retire the session. A leave is a deliberate shutdown, so the peer tears their own session down; keeping ours would seal the next DM under a session that no longer exists on the other side, where it is silently discarded but reported as sent.
An ordinary link drop. Keep the session on purpose. Resuming one is far cheaper than a fresh handshake and radios drop links constantly.
Handshakes are unsigned. Deliberate, and matching bitchat. The peer may not hold our signing key yet, and the handshake authenticates itself: it completes only when the static key derives to the claimed peer ID.

What you get and what you do not

Guaranteed

  • Mutual authentication. Both sides prove possession of their static private key.
  • Forward secrecy per session. A static key compromised tomorrow does not open today's session, because the ephemeral private halves are gone.
  • Identity hiding. Static keys are transmitted encrypted. A passive observer of the handshake learns neither party's long-term key.
  • Replay resistance. The 1024-nonce sliding window inside the session.
  • Integrity. Every transport message is AEAD authenticated.
  • Deniability. Everything inside the session is authenticated by a symmetric key both parties hold, so neither can prove to a third party what the other said.

Not provided

  • Per-message forward secrecy. One session key covers the whole session. Compromise it mid-session and every message in that session is readable. This is precisely the gap the Double Ratchet fills.
  • Post-compromise security. Noise alone never recovers from a compromise within a session.
  • Metadata protection. The packet header carries sender and recipient IDs in the clear. Who is talking to whom is visible on the mesh.
  • Protection against a wrong key. XX authenticates that the peer holds the key it presented. Whether that key belongs to the person you think it does is chapter 20's problem.
  • Anything, if the handshake is MITMed on first contact. Trust on first use is a real weakness, and the QR scan and safety number exist to close it.

Alternatives

OptionVerdict
TLS 1.3 Rejected. Requires certificate authorities and server certificates, which a serverless system cannot have. Self-signed certificates would reduce it to raw public key authentication with an enormous ASN.1 parser attached, which is a large attack surface for no benefit. It also assumes a client-server asymmetry that a mesh does not have.
X3DH alone Rejected as a session protocol. X3DH is an asynchronous key agreement, and it does not mutually authenticate in the handshake: the receiver does not authenticate the sender. It solves a different problem (initiating with an offline party), which Airhop solves with Noise X plus prekeys instead.
Signal protocol wholesale Rejected. The Signal protocol assumes a server for prekey distribution and message routing, and the Signal service requires a phone number. The Double Ratchet part of it is used, on top of Noise.
Noise IK instead of XX One fewer round trip, and WireGuard's choice. But it requires the initiator to already know the responder's static key, which on a mesh of strangers is exactly what is not true. It would work for a contact whose key you hold, and that is a real optimisation available later.
MLS (RFC 9420), as used by Marmot and White Noise Different problem. MLS is a group key agreement designed to scale to thousands of members with efficient add and remove. Airhop's groups cap at 16 with a creator-signed roster, and its DMs are pairwise. MLS also assumes a delivery service that orders messages, which a mesh with no total order cannot provide. Covered in chapter 18.
OTR Superseded. Its deniability and forward secrecy properties are what Double Ratchet generalised and improved, and it does not handle asynchronous delivery.

Drills

  • Why is the pattern e, ee, s, es and not e, s, ee, es? Because the ee operation is what creates the first cipher key. Placing s after it means the static key is transmitted encrypted, which gives identity hiding: a passive observer never learns who answered. Placing it before would send the responder's long-term identity in the clear to anyone listening, which on a mesh where handshakes flood at TTL 7 would be a broadcast of who is talking to whom.
  • What exactly is wrong with using the handshake hash as key material? It is public. mixHash absorbs only bytes that went over the wire: the protocol name, the prologue, and each handshake message verbatim. Anyone who captured the three handshake packets recomputes it exactly. Airhop had this bug: the Double Ratchet root key was seeded from it, so any bystander in the room could derive the root key and forge or decrypt every DR message in that conversation. The fix is the exporter secret, which descends from the chaining key and therefore from ephemeral private keys that no longer exist.
  • Why does asking HKDF for three outputs not break bitchat interop? Because HKDF-Expand chains: each output block is derived from the previous one plus a counter. Adding a third block leaves the first two byte-identical. bitchat negotiates exactly the same k1 and k2 and has no way to know a third value was computed locally.
  • Noise XX already gives forward secrecy. Why add the Double Ratchet? Because Noise's forward secrecy is per session, not per message. One key pair covers every message until the next handshake, so an attacker who compromises the session key mid-conversation reads all of it, before and after. The Double Ratchet rotates a key per message and recovers after a few steps even from a live compromise. It also covers the offline case: a ratcheted message left with a courier keeps forward secrecy while the recipient is away.
  • Why are Noise handshake packets not signed, when almost everything else is? Two reasons. The peer may not hold our signing key yet, since the announce that carries it may not have arrived, so a required signature would make first contact impossible. And the handshake authenticates itself: it completes only when the remote static key hashes to the claimed peer ID, so an impostor cannot complete one under someone else's identity. A signature would add 64 bytes and prove something the handshake already proves.
  • The initiator completes the handshake one message before the responder. What goes wrong if you ignore that? Anything the initiator sends in that window is decrypted by nobody: it has a session, the responder does not yet. Airhop hit this exactly, losing first-contact DMs and group invites. The fix is to run tryInitDR and flush queued invites after msg3 goes out rather than at split.
