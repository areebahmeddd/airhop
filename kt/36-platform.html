Platform and native code

The protocol is one TypeScript implementation. The hardware is two operating systems that disagree about almost everything. This chapter is the boundary between them, and every place a platform fact leaks through it.

In plain words

Explain it to a ten year old

The brain of the app is written once, in one language, so it behaves the same on every phone. But a phone's radio, microphone and locked drawer can only be reached in the phone's own language, so there is a small translator at the bottom. The translator is kept as small and stupid as possible: it knows how to turn the radio on and hand over bytes, and it knows nothing about what any of the bytes mean.

Why so little native code

Hardware requires native code. Routing, cryptography, Nostr and payments do not. Native code is harder to test, harder to keep consistent across two platforms, and harder to reason about. So there is one module per hardware capability and no more.

ModulePlatformCapability
AirhopBLEModuleBothBLE GATT peripheral and central, radio state, power mode
AirhopVoiceModuleBothAAC-LC capture and playback
AirhopWiFiModuleBothWiFi Aware fast path. Same-platform only: Apple requires a paired data path Android cannot complete.
AirhopLANModuleBothmDNS discovery on _airhop-lan-v1._tcp and the TCP links behind it. Android uses NsdManager, iOS uses NWListener and NWBrowser. One contract, two implementations, and the mesh engine does not know which it has. Chapter 29.
AirhopAppModuleAndroidProcess-level operations that belong to no radio. Currently one method, restart(), which relaunches into a fresh process. Android only for a reason rather than for now: iOS gives an app no supported way to relaunch itself and exit() there is grounds for rejection.
AirhopTorModule, AirhopTorSocketiOSEmbedded Arti and the SOCKS socket it fronts
AirhopForegroundServiceAndroidHolding the process up under Doze

None of them knows anything about packets, routing or encryption. That is the design constraint, and everything below follows from it.

The payoff is direct. bitchat's iOS and Android are separate native codebases that drift: an Android fragment size mismatch (500 bytes against iOS's ~469) broke iOS to Android messaging for months with nobody noticing. Airhop's answer is that there is nothing to drift, because there is one implementation. A fix in gossip sync fixes both platforms at the same instant.

The rule that keeps this small

Anything richer would put protocol knowledge on the native side, which this design exists to prevent. The test is simple: if a proposed native method needs to know what a packet type means, it is the wrong method.

One detail that matters for shipping: the WiFi and Tor specs are hand-maintained rather than Codegen input, and every call is optional-chained. TurboModuleRegistry.get returns null on a platform where the module does not exist, so an iOS build has no WiFi module and a JavaScript-only update can land on an older native binary that lacks a method. The controllers latch "unsupported" on the first pass rather than crashing.

Background execution

A mesh node that only works while the app is open is not a mesh node. Both platforms make this hard, in different ways.

The Android scan flag is what makes the rest deliver

Android treats a BLE scan as a location access unless the manifest says otherwise, and an app counts as foreground for location purposes only with a visible activity or a location-typed foreground service. A connectedDevice service does not qualify.

So a backgrounded Airhop held its process up, kept a notification reading "Discovering and relaying nearby messages", and was handed no scan results at all. A visible promise of a service that was not running.

bitchat solves this with ACCESS_BACKGROUND_LOCATION and a location service type. Airhop asserts neverForLocation instead, which is accurate here: a scan result is read for its service UUID, its 8-byte peer ID and its RSSI, none of which is a position. From API 31 that removes the coupling entirely. API 26 to 30 keeps it, since the flag does not exist there, and getRadioState reports which regime applies through locationRequiredForScan.

Location is still requested, but only for geohash channels, and only when the user opens one. That is a meaningful difference in what the app asks for and why.

The permission primer is mounted outside the onboarding flow on purpose. A user who killed the app mid-onboarding gets a next launch that skips onboarding entirely, and the primer still has to appear. It explains why Bluetooth is needed before the OS dialog, so a refusal is not the first thing a new user does.

A denied permission produces a blocker on the Mesh tab with a one-tap route to the right settings screen, rather than a spinner. Denials that cannot be re-prompted (the OS only asks once) get an explicit "open Settings" path.

The power policy

BLE scanning is the largest battery cost in the app. A continuous low-latency scan costs roughly an order of magnitude more than low power, and the app is meant to run in a pocket all day.

Policy in TypeScript, mechanism in Kotlin

src/services/power-policy.ts is a pure function of four facts. The native module reports the battery and applies whichever mode it is given, and decides nothing itself. That keeps the decision testable without a device, and puts "how hard to run the radios" beside "whether to run them at all" in the radio controller.

ModeScanAdvertiseTX powerRSSI pollDuty cycle
performanceLOW_LATENCYLOW_LATENCYHIGH5 scontinuous
balancedBALANCEDBALANCEDMEDIUM10 scontinuous
power-saverLOW_POWERLOW_POWERLOW30 s2 s on / 28 s off
ultra-low-powerLOW_POWERLOW_POWERULTRA_LOW60 s1 s on / 29 s off

Selection order, and the order carries the policy:

  1. Backgrounded gives power-saver, or ultra-low-power on a critical battery. Nobody is waiting on discovery latency off screen, and this is where a phone spends nearly all of its day.
  2. Charging in the foreground gives performance, since the cost is someone else's.
  3. Otherwise the battery band decides: critical at 10 percent or less gives ultra low, low at 20 percent or less gives power saver, anything else gives balanced.

Foreground on battery is balanced rather than performance because a balanced scan still finds peers within seconds, and reserving the most expensive setting for "plugged in" is what stops the app being the reason a phone dies.

The five knobs move together

A duty-cycled low-power scan beside a low-latency advertise at full TX power saves almost nothing, since the advertiser transmits continuously either way. Tuning one in isolation is how a power policy becomes a placebo.

Hysteresis is Airhop's addition. bitchat re-resolves on every ACTION_BATTERY_CHANGED, which fires per 1 percent, so a phone hovering at a threshold flips modes repeatedly and every flip restarts the scanner. Dropping into a lower band is immediate, since running hard on a nearly flat phone is the failure that matters; climbing back out needs +3 percent. Native also only reports the battery every 5 percent, so it is not a bridge crossing per percent for a decision whose thresholds are ten points apart.

The duty cycle is invisible above the native boundary. JavaScript asks for scanning and keeps getting it while native decides the rate. A burst ending is never reported as an adapter or link change, or the reconciler would try to repair a state that is working correctly.

In the foreground on a low battery, peers can take up to half a minute to appear, which is indistinguishable from a broken mesh unless it is stated. The Mesh tab shows a muted "Battery saver, scanning less often" note, with no button (charging is the fix) and no dismiss (it clears itself). It stays silent while backgrounded, where nobody is waiting.

iOS is a declared no-op

CoreBluetooth exposes no scan-rate control and already throttles background BLE aggressively. setPowerMode exists on both platforms so the shared reconciler has one code path, and getRadioState reports batteryPercent: -1 there, which the policy reads as unknown and leaves the mode alone.

The reconciler

Both radio controllers use the same shape, and it is the answer to an entire class of bug. 

  A DESIRED STATE          "we want scanning and advertising"
  AN OBSERVED OUTCOME      what native actually reports
  ONE IDEMPOTENT PASS      close the gap, or schedule a retry

  BLE backoff:   a ladder ending in a steady interval
  WiFi backoff:  500ms, 1.5s, 4s, 10s, 30s (slower on purpose: nothing
                 the user is looking at depends on this transport)

  "UNSUPPORTED" IS LATCHED FOREVER.
     No BLE peripheral hardware, or an API level below the WiFi Aware
     data path, is not a state a device leaves. Retrying it on a 5s
     ladder for the life of the mesh is pure battery cost.

Two failures this shape eliminates, both of which existed:

  • A one-shot start with a swallowed rejection. WiFi off at start meant the attach was refused and never retried; turning WiFi on later changed nothing for the rest of the process. A permission granted a moment after start, which is the ordinary first-install race, left the fast path dead on a device entitled to it.
  • A refused write tearing down a healthy link. The announce and gossip send path deleted a link from the link registry on any rejected write, an action nothing could undo, so one transient refusal left the phone believing it had no neighbours for the rest of the session. Teardown belongs to the disconnect event.

One deliberate difference: the WiFi controller publishes no blocker, because WiFi Aware is an accelerator and BLE carries everything either way. Reporting a blocker would be a false alarm on the one screen that must stay trustworthy. It reports state instead, so the Mesh tab can note the fast path is off in the same neutral voice it uses for battery saver.

Build and release

Never run npx expo prebuild

ios/ and android/ are checked in and hand-modified. Prebuild regenerates them from app.json and would delete every native module. This is the single most destructive command in the repository, and it is flagged as a caution in the README.

AndroidiOS
BuildGradle to an .aabXcode to an .ipa
Minimum OS8.0, API 2616.0
CI on every changeFull R8-minified release build. So a broken keep rule, or a dependency that stops being 16 KB aligned, fails a pull request rather than a tagged release.Unsigned Release build on a macOS runner, so native and release-only breakage fails the same pull request.
Release automationFully automated: release.yml builds and signs the APK and AAB.Placeholder. Distribution credentials do not exist, so the shipped .ipa is still produced by hand from Xcode.
Dependency lockingandroid/app/gradle.lockfile, regenerated in the same commit as a dependency changeios/Podfile.lock, regenerated with npx pod-install in the same commit

Neither platform uses EAS, and there is no EAS configuration. Its main draws are prebuild and managed credentials, and this project does not run prebuild.

The R8 release build in CI is worth calling out as good practice: a minified build is where reflection-based libraries and missing keep rules fail, and those failures otherwise appear for the first time on a release tag, in front of users.

Drills

  • Why is the native layer only five modules? Because anything richer would put protocol knowledge on the native side, and then it would have to be implemented twice and kept in step. bitchat's own history is the argument: two native codebases drifted until an Android fragment size mismatch broke cross-platform messaging for months with nobody noticing. Keeping native to one module per hardware capability means the protocol has exactly one implementation, and a bug in it exists on both platforms or neither.
  • Explain the Android scan flag problem to someone who has never shipped an Android app. Android assumes a Bluetooth scan is a way of locating the device, so it gates scan results behind location permission unless the manifest declares otherwise. Separately, an app only counts as foreground for location purposes with a visible activity or a location-typed foreground service, and Airhop's is a connectedDevice service. So a backgrounded app held its process up, showed a notification promising to relay messages, and received no scan results at all. Declaring neverForLocation removes the coupling from API 31 onward, and it is accurate here because a scan result is read for its service UUID, peer ID and signal strength, none of which is a position.
  • Why does the power policy live in TypeScript when the mechanism is native? So the decision is a pure function of four facts and can be tested in CI without a device. The native module reports the battery and applies whichever mode it is handed, deciding nothing. It also keeps "how hard to run the radios" next to "whether to run them at all" in the same controller, rather than splitting one policy across two languages where the halves can disagree.
  • What is the reconciler and what bug class does it eliminate? A desired state, an observed outcome, and one idempotent pass that closes the gap or schedules a retry. It eliminates the fire-and-forget start: one attempt with the rejection swallowed, so WiFi off at launch means the fast path is dead for the whole process, a permission granted a second late leaves it dead on an entitled device, and a mid-session toggle latches the module into a state it cannot leave. It also draws the line that a refused write is not a dead link, because the stack says the same thing when its queue is merely full.
  • Why does CI build a fully minified R8 release on every change? Because a minified build is where reflection-based libraries and missing keep rules fail, and where alignment requirements bite. Those failures otherwise appear for the first time on a release tag, in front of users, at the moment it is hardest to fix. Building it on every pull request turns a release-day emergency into a red check on a branch.
  • Why is there no push notification support, and what is the consequence? Because waking a fully killed app requires a push server, which is infrastructure the project will not operate: it would be a party that knows who is being messaged and when, and a service that could be shut down. Local notifications fire while the process is alive, which Android's foreground service maintains and iOS provides whenever the OS has the app awake. The consequence is that a force-stopped iOS app stays silent until reopened, and that is an accepted trade rather than a bug.
