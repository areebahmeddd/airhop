Gossip sync

You walk out of range for ten minutes and come back. The room has moved on. Gossip sync is how your phone asks "what did I miss" using a 400 byte summary instead of a list of everything it already has.

In plain words

Explain it to a ten year old

Two friends each have a box of stickers and want to swap the ones the other is missing. Reading out every sticker would take all day. So instead each of them makes a tiny coded summary of their box, small enough to fit on a scrap of paper, and hands it over. The other one looks at their own stickers, checks which are not mentioned in the summary, and hands over just those. Sometimes the summary makes a mistake and says "I already have that" when they do not, so occasionally one sticker is missed. That is fine, because they do this again fifteen seconds later.

The set reconciliation problem

Two devices each hold a set of recent packets. They want the union, with the smallest possible amount of data on the wire.

Naive approachCost for 1000 packetsVerdict
Send every packet you holdMegabytesAbsurd on an 18 KiB/s radio.
Send every packet ID you hold1000 x 16 bytes = 16 KBThirty fragments per round, every fifteen seconds, per peer. Still absurd.
Send a Bloom filter~1.2 KB at 1 percent false positive rateFits, but larger than needed and it does not fragment gracefully.
Send a Golomb coded set400 bytes, cappedFits in one BLE frame with room to spare.

The information-theoretic floor for a probabilistic set membership structure at false positive rate f is n x log2(1/f) bits. A Bloom filter is about 44 percent above that floor. A Golomb coded set gets within a few percent, which is why Bitcoin's compact block filters (BIP-158) use one, and why bitchat does too.

Golomb coded sets

The idea in four steps. It is simpler than the name suggests. 

  1. HASH each item into a range [1, M)

     packetID -> SHA-256(packetID) -> first 8 bytes as u63 BE (sign bit cleared)
              -> h64 mod M

  2. SORT the resulting values ascending, drop duplicates

     [ 41, 178, 219, 900, 1502, ... ]

  3. DELTA ENCODE: store the GAPS, not the values

     [ 41, 137, 41, 681, 602, ... ]

     If n values are spread evenly over M, the average gap is M/n.
     That is the whole trick: gaps are small and clustered, values are not.

  4. GOLOMB-RICE ENCODE each gap with parameter P

     value x = gap - 1
     q = x >> P          write q ones, then a zero      (unary)
     r = x & (2^P - 1)   write r as exactly P bits      (binary)

     Small gaps cost about P+1 bits. Large gaps cost more, but they are rare.

Membership testing does not decode the whole structure in Airhop's implementation: it decodes to a sorted list of the mapped values, then binary searches it. That is a small memory cost (a few hundred BigInts) in exchange for a much simpler and more auditable implementation than streaming decode.

A GCS has false positives but never false negatives. If the filter says "not present", the item is definitely absent. If it says "present", it is probably present. For gossip sync that asymmetry is exactly the right way round: the failure mode is occasionally not sending something the peer actually lacked, which the next round fixes, rather than flooding them with things they already have.

Setting M = count x 2^P rather than a fixed constant is what keeps the false positive rate independent of set size. If M were fixed and the set grew, collisions would rise. Tying M to the count keeps the average gap at 2^P regardless of how many items there are, which is exactly the condition Golomb-Rice coding is optimal under.

Trimming, and why it trims from the tail

The store holds up to 1000 packets but only about 355 fit in 400 bytes. So the encoder trims, and the direction matters. 

  candidates are sorted NEWEST FIRST
  count = min(candidates.length, capacityEstimate)
  encoded = encodeFirst(count)
  while encoded.length > 400 and count > 1:
      count = floor(count * 9 / 10)      // drop 10 percent per pass
      encoded = encodeFirst(count)

The modulus M is fixed to the initial candidate count and does not move as the tail is trimmed. If it moved with each retry, every mapped value would change and the loop would never converge on anything meaningful.

Trimming from the tail of a newest-first list means the covered set is a contiguous newest prefix, which is what makes the since cursor below exact. Trimming in hash order would leave an arbitrary subset that no timestamp can describe.

Why an overflow does not emit an empty filter

If encoding a single element still overflows, the encoder returns an empty filter with includedCount: 0. That is a deliberate last resort, and it is worth understanding why it is dangerous: an empty filter reads as "I have nothing", so the responder replies with its entire store. And overflow is likeliest on the busiest mesh, which is precisely where you least want a peer to draw down 1000 packets. The shrink loop exists so that path is effectively unreachable.

The wire format

  REQUEST_SYNC (0x21) payload, TLV: type u8, length u16 BE, value

    0x01  P       1 byte      Golomb-Rice parameter
    0x02  M       4 bytes BE  hash range
    0x03  data    variable    the Golomb-Rice bitstream
    0x04  types   1-8 bytes   SyncTypeFlags bitmask, little endian,
                              trailing zero bytes trimmed
    0x05  since   8 bytes BE  coverage cursor, ms since epoch. OPTIONAL.
    0x06  fragmentIdFilter    NOT IMPLEMENTED by Airhop, in either direction

  Packet framing:
    ttl        = 0            link-local, never relayed
    flags      = SIGNED, plus HAS_RECIPIENT when unicast
    recipient  = the peer being asked (unicast is the normal path)

The request is signed when possible but a signature is not required on receipt. A REQUEST_SYNC carries no content, and every packet it draws back is independently verified by the requester, so a forged request cannot inject anything. The risk is amplification, which the rate limiter bounds. Requiring a signature would break first contact, where a peer's sync round arrives before its announce and there is no key to check against. bitchat does not gate on it either. A signature that is present and wrong is refused.

A round, step by step

  EVERY 15 SECONDS, ON DEVICE A

  1. prune candidates past their per-type window
  2. for each connected peer P:
       build a filter over everything A holds, newest first
       REGISTER the pending request against P   ◀── BEFORE the send
       unicast REQUEST_SYNC to P, ttl 0

  ON DEVICE B, RECEIVING IT

  3. rate limit FIRST, before decoding
       more than 8 answers to this peer in the last 30 s?  -> ignore
  4. decode the filter, the type bits and the optional cursor
  5. for every packet B holds:
       not fresh by B's own window?             skip
       type not in the requested bits?          skip
       older than the cursor, if one was sent?  skip
       already in A's filter?                   skip
       otherwise -> add to the response, tagged { ttl: 0, isRSR: true }
  6. write the response packets straight back down the SAME link

  BACK ON DEVICE A

  7. each response arrives with ttl 0 and IS_RSR
  8. A checks: is there an outstanding request to the peer on this LINK,
     within 30 seconds?
       yes -> exempt from the freshness window, process normally
       no  -> DROP. The flag alone is a claim anyone can make.

Three rules that all three implementations enforce

  • The request is link-local (ttl 0). It asks what the peer on the far end of this link is missing. Relaying it asks the wrong node.
  • Every response is link-local (ttl 0) and tagged IS_RSR. Without ttl 0, the requester's flood router treats each replayed packet as new, which it is, and re-floods it. One peer rejoining after a partition would push the entire archive back across the mesh.
  • Requests are unicast. A broadcast request has no peer to register against, so nothing it draws back can be attributed, and nothing can be exempted from the freshness window. Broadcast exists only as a discovery-phase fallback before any peer is attributed.

The registration happening before the send is not fussiness: on a fast link the response can outrun the sender's own continuation, and a response landing before its registration looks exactly like an unsolicited one and is dropped.

Type bits

A request names the types it wants in a SyncTypeFlags bitfield, and a responder answers only with those. A bit that maps to no known type is ignored, which is what makes the set extensible in both directions.

Bit 7, files, deliberately absent

An attachment is up to 1 MiB, so serving one from sync is ten to forty-five seconds of exclusive radio time per asking peer, against a filter sized at 400 bytes for items that are meant to be small and numerous. bitchat's own reassembly also expires 30 seconds after the first fragment, so a re-flooded file frequently fails on arrival anyway and the airtime buys nothing.

The interop cost is bounded and symmetric: a bitchat peer may ask for bit 7 and gets nothing, and Airhop never asks for it. Neither side errors. What it means for a user is that a channel attachment missed while out of range is not backfilled, where text, board posts and group messages are. Media on the mesh is best effort at the moment it is sent.

Bit 9, prekeys, the one real gap

Airhop distributes its own prekey bundle by flooding it to each new link, and accepts and verifies bundles that reach it that way, but it does not reconcile them through sync. The effect is narrow: a device that arrives after a bundle has already flooded cannot pull one from a peer that still holds it, so a courier message sealed to that owner falls back to their long-lived static key instead of a one-time prekey. The message is still delivered and still encrypted. What is lost is forward secrecy for that envelope. Chapter 13 explains why that matters.

Bit 24, not 11

Airhop's named public channels needed their own bit, because they no longer ride bit 1 with the mesh room. bitchat's table ends at 10 and it allocates forward, so 11 is the next value it would reach for. 24 leaves it thirteen values of room and stays under 31, which the encoder needs: 1 << 31 is negative in JavaScript, and the byte-wise encoder would silently fold a higher bit onto a lower one.

What is absent from both, and why

  • Courier envelopes are directed deposits and must not spread by gossip. That would turn a targeted handoff into a broadcast.
  • Ping, pong and gateway carriers are ephemeral and would replay as unanswerable echoes.
  • Live voice is only useful in the moment, and receivers drop stale frames anyway.
  • Rotating-ID presence is valid only inside its epoch, and syncing it would let a device that was never in radio range collect presence it could not otherwise observe.

Candidate windows

One blanket window would be wrong in both directions: it would keep presence alive after its sender left, and expire board posts meant to outlive everyone carrying them.

TypeWindowWhy
ANNOUNCE60 sPresence that outlives its sender misreports who is in the room. This is a consensus rule in bitchat-android's sync spec and matches bitchat-iOS's stale-peer timeout.
CHANNEL_MSG and CHANNEL_MSG_AIRHOP900 s (15 min)Carrying the room's recent history across a partition is the point of gossip. bitchat-iOS publicMessageMaxAgeSeconds.
GROUP_MESSAGE900 sA group is a conversation, not a noticeboard, and a member away for a quarter of an hour is the case backfill exists for. Longer would be pointless: a roster change rotates the epoch key, and a message sealed under the old one can no longer be read.
BOARD_POST7 daysA backstop only. Posts carry their own author-chosen expiry, which the board store enforces on receipt. This just stops an entry sitting in the LRU forever.

A packet stamped in the future is treated as expired rather than fresh. A future timestamp is either a badly skewed device or a sender trying to pin an entry at the head of everyone's candidate set forever, and neither is something to carry on someone else's behalf.

The store itself is a 1000-entry ordered map, newest at the end, oldest evicted. bitchat-Android's equivalent holds only 100, which is one of the divergences Airhop resolves toward iOS.

The since cursor, and the trap inside it

This is the most easily-inverted piece of logic in the whole subsystem, and getting it backwards breaks catch-up silently.

The wrong reading

"since is a request boundary: do not send me anything older than my oldest packet."

Send it unconditionally and a device that just joined, holding only recent packets because it was not there, tells every peer to withhold precisely the history it turned up to collect.

The correct reading

"since is a coverage disclaimer: my filter was truncated and it only reaches back this far."

It is sent only when the filter could not cover everything held: the store exceeded the cap, or the encoder trimmed the tail to fit 400 bytes. It names the oldest packet the filter actually reaches. 

  since = (includedCount > 0 && includedCount < candidates.length)
            ? candidates[includedCount - 1].timestamp
            : undefined

Candidates are ordered newest first, so the covered set is a contiguous newest prefix and the cursor is exact. A responder holding something older than the cursor knows it is outside the filter rather than missing from it, and skips it instead of re-sending it every round.

Amplification control

One REQUEST_SYNC can replay a peer's whole store. A peer asking in a tight loop is an amplifier pointed at both the responder and the shared radio.

ControlValueEffect
Response rate limit8 answers per 30 s per peerA normal peer asks every 15 s and gets an answer every time. Anything faster is throttled. Matches bitchat.
Rate limit checked before decodingThe diff pass is the expensive part; a looping peer should not be able to make us pay for it.
Attribution by link, not by claimed senderThe budget must be per physical neighbour, or one peer minting sender IDs gets an unbounded number of budgets over a single link.
Responses ride ttl 0They stop at the requester. A rejoining peer's catch-up cannot re-flood the mesh.
Budget cleared on link dropA genuine reconnect is not throttled by the previous session's traffic.

The threat model calls this sync amplification and it is one of the named countermeasures: REQUEST_SYNC and every packet answering one ride at TTL 0, so a rejoining peer's catch-up cannot re-flood the mesh, and responses to one peer are capped at 8 per 30 seconds.

Alternatives

StructureTradeVerdict
Bloom filter Simplest, most familiar. About 44 percent larger than the information-theoretic floor for the same false positive rate. Would need roughly 1.2 KB where GCS needs 400 bytes, which is three BLE frames instead of one. Not worth it.
Cuckoo filter Similar size to GCS, and supports deletion. Deletion is not needed here (entries age out) and it is more complex to make byte-compatible across three implementations.
Invertible Bloom lookup table (IBLT) Reconciles a set difference in one round trip with size proportional to the difference, not the set. Theoretically superior when the difference is small. Needs a good estimate of the difference size up front, and it fails catastrophically rather than gracefully if that estimate is wrong. GCS degrades to "sends a bit too much", which is the right failure shape for a radio.
Merkle tree / range sync Logarithmic, exact, no false positives. What Scuttlebutt and several CRDT systems use. Needs multiple round trips over a link that may not survive them, and needs a total order on the set. Airhop's set is a bag of independent packets with no order.
Vector clocks / version vectors The classic answer for replicated state. Requires per-peer state that grows with the number of peers ever seen, which is unbounded in a public mesh and is itself a privacy leak (it records everyone you have met).
Just re-flood everything periodically No structure at all. This is what happens if you get the ttl 0 rule wrong, and it is exactly the failure gossip sync exists to prevent.

Drills

  • Why does a GCS have false positives but never false negatives, and why is that the right way round here? Because membership is tested by looking for the item's mapped value in the encoded set. If the item is present, its value is definitely there. If it is absent, its value may still collide with a different item's. So a "yes" can be wrong and a "no" cannot. For sync that means the failure is occasionally not sending something the peer actually lacked, which the next round fixes fifteen seconds later. The opposite failure, flooding a peer with things it already has, would be unbounded and would cost airtime every round.
  • Why must a sync response carry both IS_RSR and ttl 0? Different jobs. ttl = 0 keeps it link-local, so the requester's flood router does not treat each replayed packet as new and push the whole archive back across the mesh. IS_RSR tells the requester this is the answer to its own question, so it can exempt the packet from the plus or minus two minute freshness window, which sync responses are old by definition. Both fields are normalised out of the signing preimage, so retagging a stored packet leaves its original signature intact.
  • Explain the since cursor to somebody who is about to send it on every request. Do not. It is a coverage disclaimer, not a request boundary. It means "my filter got truncated and only reaches back this far, so anything older than this is outside it rather than missing from it". Sent unconditionally, it tells peers to withhold anything older than your oldest packet. For a device that just joined and therefore holds only recent packets, that withholds exactly the history it turned up to collect, and the failure is completely silent.
  • Why is bit 7 (files) excluded, and what does a user lose? Serving a 1 MiB attachment from sync is ten to forty-five seconds of exclusive radio time per asking peer, and bitchat's own reassembly expires 30 seconds after the first fragment, so a re-flooded file frequently fails on arrival anyway. The user loses backfill of channel attachments missed while out of range. Text, board posts and group messages are still backfilled. Media on the mesh is best effort at the moment it is sent, and that is the honest way to describe it.
  • Why is the modulus M fixed during the trim loop? Because M determines every mapped value. If M moved with each retry, every value in the filter would change on every pass, so the encoded size would jump around unpredictably and the loop would never converge on a meaningful subset. Fixing M to the initial candidate count means trimming only removes elements, which monotonically shrinks the encoding.
