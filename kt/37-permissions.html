Permissions and consent

A mesh app has an unusually hard permission problem. It needs Bluetooth before it can do anything at all, it needs location on older Android for reasons that have nothing to do with location, and a refusal is close to permanent. Get the sequencing wrong and the app looks broken while every radio sits idle.

In plain words

Explain it to a ten year old

Your phone is like a house with locked rooms. The app has to knock before it can go into the Bluetooth room, the camera room, the microphone room. You can say yes, or no, or "no and stop asking". That last one really does mean stop: after it, knocking makes no sound at all, and the only way to open the door is to walk to the phone's own settings and unlock it from there. So the app explains why it is knocking before it knocks, once, and if you have locked a door for good it stops pretending it can knock and just offers to walk you to the settings.

Three states, not one boolean

Where permission flows usually go wrong

Treating a permission as granted-or-not collapses two situations that need opposite handling. src/platform/permissions.ts keeps three.

StateMeansCorrect response
undetermined The OS prompt has never been shown Show it. Saying anything of our own first is a second dialog nobody asked for.
deniable Denied once, but the OS will still prompt Ask again. The user is now inside the flow that needs it, so the ask finally has context.
blocked Denied for good: twice on Android, any denial on iOS The only state that deserves a message from us, and that message must carry the way out.

The whole distinction reduces to one field the platform gives us, canAskAgain. ensurePermission(get, request, copy) resolves all three into a plain boolean so every caller can stay linear: 

  ensurePermission(get, request, copy)
        │
        ├─ current = await get()          check first: an already-granted
        │                                  permission never costs a trip
        │                                  through the prompt machinery
        ├─ current.granted        -> true
        │
        ├─ current.canAskAgain
        │     ├─ asked = await request()
        │     ├─ asked.granted       -> true
        │     └─ asked.canAskAgain   -> false, and NO dialog of our own
        │           (declining a prompt they were looking at is an
        │            answer, not an error. Nagging here is noise.)
        │
        └─ showBlockedAlert(copy)   -> false
              "Camera access is off"
              "...so Airhop cannot scan a contact's QR code."
              [ Open Settings ]  [ Not now ]

showBlockedAlert deep-links into the Settings app through Linking.openSettings() rather than describing where to tap. That is the difference between a dead end and a two-tap fix, and it is the same dialog every blocked path in the app uses.

Every permission the app asks for

Six runtime permissions, and a longer list of install-time declarations behind them.

PermissionAsked whenUsed forCost of refusing
Bluetooth First launch, before the mesh starts Scanning, advertising, connecting. The entire mesh. Total. No peers, ever. Only Nostr still works.
Location After the mesh is up (iOS); folded into the BLE ask on Android 11 and below Resolving the geohash cell for area channels. On Android 30 and below it is also what BLE scanning needs. Area channels stay empty. On old Android, the mesh itself.
Notifications Last in the startup sequence System notifications for messages Degrades gracefully: in-app badges and haptics still work.
Camera On demand, when scanning a QR or taking a photo Contact QR scan, photo and video capture Contacts can still be added by pasted code or peer ID.
Photos On demand Sending images, picking a saved QR, saving your own QR No gallery attachments.
Microphone On demand Voice notes and live push-to-talk No voice; text and files unaffected.

Order matters and is enforced. On a fresh install, concurrent prompts raced: the notification prompt was swallowed and sometimes crashed. Every prompt outside the BLE batch is now awaited one after another.

Android: the split at API 31

src/platform/ble-permissions.ts. Android changed Bluetooth permissions in API 31, and the app asks for genuinely different things on each side of that line. 

  androidApiLevel() >= 31              androidApiLevel() <= 30
  ─────────────────────────            ──────────────────────────
  BLUETOOTH_SCAN                       ACCESS_FINE_LOCATION
    + neverForLocation                   (and nothing else)
  BLUETOOTH_ADVERTISE
  BLUETOOTH_CONNECT                    Bluetooth permissions are
                                       install-time here; scanning is
  no location at all                   coupled to location with no
                                       way to say otherwise

  optional, batched into the same run of dialogs, never required:
    NEARBY_WIFI_DEVICES     API 33+, for the WiFi Aware fast path

Two properties of that function are easy to miss and both were bugs once:

  • The optional permission is batched but not required. WiFi Aware is an accelerator; the mesh must run without it. A denial there never fails the gate. Batching it means the user answers one run of dialogs rather than two.
  • The fast-path check reads both lists. They move independently. A build that adds an optional permission reaches phones whose required grants are already settled, so a check reading only the required list returns early for the life of the install and the new permission is never requested at all. On API 33 and above both lists sit in the same NEARBY_DEVICES group, so the extra pass is granted without a dialog. That is what makes re-requesting safe here: an optional permission carrying its own group would re-prompt on every launch once denied, and would need a persisted "already asked" marker instead.

hasBlePermissions() is the read-only counterpart. It checks the required permissions and never prompts, which is what makes it safe to call on app resume, where the user may have just granted in Settings. Re-requesting there is either a no-op or a prompt thrown at somebody who did not ask, and both leave the mesh dead until a restart. It deliberately ignores the optional ones: a missing accelerator grant must not shut down a transport that does not depend on it.

One permission is declared but never requested

ACCESS_LOCAL_NETWORK sits in the manifest so the WiFi Aware socket keeps working later, but it is not in the request list. Local network protection is only enforced for apps targeting Android 17, and this app targets 36, so asking now would show a dialog that unlocks nothing. It gets added in the same commit that raises the target, and it will need the persisted marker described above, because it carries its own permission group.

neverForLocation, and a deliberate divergence

android:usesPermissionFlags="neverForLocation" on BLUETOOTH_SCAN is a promise to the OS that scan results will not be used to derive a physical position. For Airhop that promise is accurate: a scan result is read for the service UUID, the peer ID and the RSSI, none of which is a position. The flag releases scanning from the location permission and from the system location toggle.

Where this differs from bitchat/android, and why

bitchat requires location at every API level, and therefore also needs ACCESS_BACKGROUND_LOCATION and a location foreground-service type. That coupling costs a backgrounded phone every scan result, and costs anyone whose location is set to "Approximate" a mesh that finds nobody. Airhop declares the flag and drops the coupling above API 31. The advertisement and the wire protocol are untouched, so interop is unaffected. This is one of the clearest cases in the codebase of diverging from the reference implementation for a concrete user benefit.

The geohash channels still need real location, and location-service.ts requests it when one opens. Denying that costs channels, not the mesh.

iOS: prompts you do not control

There is no BLE permission code for iOS, and that is correct. CoreBluetooth prompts on first use of a manager, backed by the usage strings compiled into Info.plist. There is no way to query the answer from JavaScript, and no way to ask again.

KeyShown when
NSBluetoothAlwaysUsageDescriptionFirst CoreBluetooth use. This string is the primer on iOS.
NSBluetoothPeripheralUsageDescriptionAdvertising, on older iOS versions.
NSLocationWhenInUseUsageDescriptionOpening an area channel. Says explicitly that the exact position never leaves the device.
NSLocalNetworkUsageDescriptionThe high-bandwidth local transport.
NSCameraUsageDescriptionQR scan and capture.
NSMicrophoneUsageDescriptionVoice notes and live voice.
NSPhotoLibraryUsageDescriptionAttaching images.
NSPhotoLibraryAddUsageDescriptionSaving a photo, or downloading your own QR.

UIBackgroundModes declares bluetooth-central and bluetooth-peripheral, which is what lets the mesh keep scanning and advertising when the app is not in front. Chapter 36 covers what iOS actually delivers in that state.

On iOS hasBlePermissions() resolves true and ensureBlePermissions() returns granted. That is not a lie so much as a statement that this layer has nothing to contribute: the answer lives in system settings and the radio controller finds out by trying.

The startup sequence

startMeshWithPermissions() in src/app/app.tsx. The important design property is stated in one line: the mesh must not wait for the permission conversation to finish. 

  identity loaded
        │
        ├─ primer needed?   not seen before  AND  not already granted
        │     │              (3 s check timeout, default false)
        │     └─ show sheet, wait up to 120 s, then continue regardless
        │
        ├─ ensureBlePermissions()          up to 60 s
        │     ├─ answered  -> applyBlePermissionResult(perm)
        │     └─ timed out -> publish NOTHING. `null` is "the OS never
        │                     answered", which is not any answer it
        │                     could have given.
        │
        ├─ primeTorRoutingOnStartup()      guarded: a throw here would
        │                                  silently prevent the mesh
        │                                  from existing at all
        ├─ initMeshService(identity, nick) <-- the mesh now EXISTS
        ├─ retryRadios()                   the grant may have landed
        │                                  while the mesh was building
        └─ startMeshDependents()
              ├─ wallet unlock, reconcile, nutzap watcher
              └─ sequentially, one prompt at a time:
                    location      (iOS only in practice)
                    notifications (last, so it lands cleanly)

Why every await is time-boxed

Everything before initMeshService is a conversation with the OS, and it is not a conversation the app controls. The primer resolves on a sheet the user has to dismiss. PermissionsAndroid.requestMultiple settles on a dialog hosted by another process, which an Activity teardown can orphan, and OEMs that reap the Activity behind a foreground service do exactly that. Either one going quiet used to leave a running app with no mesh at all and a Mesh tab reading "starting..." for the rest of the session, which is indistinguishable from a broken radio.

Missing a deadline costs nothing that matters. The radio controller reads the real grant off the device on its first pass and publishes the true blocker, so a permission answer that arrives late, or never, changes only how quickly the banner is right.

Note what is not published on a timeout. Guessing would put a red banner over a permission the user may well have granted, so the null case writes nothing and lets the controller's own reading of the device be the source.

The primer sheet

One screen, shown at most once per install, immediately before the OS dialogs. It exists because a chat app asking for location reads as tracking, and because two refusals on Android block the permission for good.

Four things the primer deliberately is not

Not a gate. The app behind it already works, and nothing downstream branches on what the user chose.

Not a question. Dismissing by drag or backdrop counts as acknowledged, because there is no wrong way to close an explanation and nothing should be waiting on a specific gesture.

Not repeated. Gated on permissionPrimerSeen so somebody who declined does not get the lecture on every launch, and gated on the permission not already being held so a returning user never sees it at all.

Not able to hang. It resolves however it is dismissed, it resolves immediately if it is somehow already up, and if it never appears the 120 second deadline fires and acknowledgePermissionPrimer() is called anyway to put the store back in step. A primer that failed to resolve would hold BLE startup behind it forever, which is far worse than the problem it exists to prevent.

Its rows mirror the prompts that are about to fire, in the order they fire: Bluetooth, then Location on Android only, then Notifications. Each row says what the permission does and what it does not. It is Android-only in practice, and correctly so: on iOS the CoreBluetooth prompt carries our own usage string and there is no location coupling to explain away, so that prompt is the primer.

It is implemented as a store rather than a prop for one reason: it has to be awaitable from startMeshWithPermissions, a module-level async function with no access to React state. Same shape as the alert store: transient state, a component reading it, and a plain function callers can await.

Naming the reason: BleBlocker

A single "granted" boolean collapsed two situations that need different responses, so the mesh state store records why the mesh cannot run, not merely that it cannot.

BleBlockerMeansBanner offers
noneRunningNothing
startingGranted, radios coming upNothing
unsupportedNo BLE on this deviceNothing that helps
permission-deniedRefused, still askableAsk again
permission-blockedRefused for goodOpen app settings
location-permissionAndroid 11 and below: what the user saw was a location dialogAsk again, named correctly
adapter-offBluetooth switched offEnable Bluetooth
location-services-offSystem location toggle offOpen location settings

blePermissionBlocked is kept as a separate flag rather than folded into the union, and the reason is subtle: only the permission request can answer whether a refusal is permanent. Neither platform reports it through the radio. A later reconcile reading the device would otherwise downgrade a known-permanent refusal back to "ask again", and the banner would offer a prompt the OS silently swallows.

Notice the ordering in applyBlePermissionResult: locationRequired is checked before the blocked-versus-denied split. Both of those resolve to the same action, so naming the permission the user actually saw matters more than distinguishing them. And a denial that can still be re-asked gets no dialog at all, because the Mesh banner already says what is wrong and carries the button that fixes it. Stacking a modal on top is two things to dismiss for one problem.

One separate hardware fact rides alongside: bleAdvertisingUnsupported. Some chipsets have no peripheral role, so the device can scan and relay but can never advertise. That is distinct from every blocker, because the mesh is working; one half of it is simply unavailable on this hardware and always will be.

The Permissions screen

Settings has a screen listing all six with their current state. Two things are deliberately not true on it, because pretending otherwise is how a permissions screen becomes a lie.

Nothing on this screen can revoke a permission

No mobile OS lets an app hand one back. Android 13 has revokeSelfPermissionOnKill, but it kills the process to do it, and iOS has no equivalent at all. So switching a granted row off opens system settings, where revoking actually happens, and the switch stays on until the OS says otherwise.

The state is never cached

It is re-read from the OS every time the screen comes forward, via an AppState listener on active. That is the whole point: the user leaves for system settings, changes something, and comes back expecting the list to agree with what they did. A cached copy gets exactly that case wrong.

Each of the six reads is individually wrapped. A module that throws, because of an unsupported platform or a permission not declared in this build, leaves its row unmanaged rather than taking the screen down. iOS Bluetooth is permanently unmanaged, which is honest: there is nothing to report.

Android Bluetooth is the interesting row. Android cannot be asked whether a denial is permanent without an Activity, so the answer comes from the last request that was made, which is the same blePermissionBlocked flag the mesh banner reads. Without it this row could only ever say "askable" and would offer an Allow button that the OS silently swallows for somebody who has already refused twice.

Granting from this screen does the same follow-up work the startup path does, and for the same reason: record whether the refusal is permanent, nudge retryRadios(), and on Android 11 and below also set the location grant and refresh the geo channels, because there the two are one permission. Splitting that logic between the two callers is how they drift.

Camera, photos, microphone

These three are asked on demand, at the moment the feature needs them, which is the only time an explanation is unnecessary. They all go through ensurePermission, so they behave identically everywhere in the app: check, prompt if askable, and only produce a dialog of our own when the OS will no longer prompt. 

  tap "scan a QR"
        │
        ├─ ensurePermission(getCameraPermissions,
        │                   requestCameraPermissions,
        │                   { label: "Camera access",
        │                     purpose: "scan a contact's QR code" })
        │
        ├─ true   -> open the viewfinder
        └─ false  -> stay on the entry screen. Pasting a contact code
                     and typing a peer ID are still right there, so a
                     camera refusal is never a dead end for the task.

That last property is worth stating as a design rule: every permission in this group has a working path around it. Camera refusal leaves paste and manual entry. Photos refusal leaves the camera. Microphone refusal leaves text and files. Only Bluetooth has no alternative, which is exactly why it is the one that gets a primer.

What breaks it

  • Ungranted BLE with no gate. The original failure mode, and the reason this layer is explicit rather than lazy. startScanning and startAdvertising throw SecurityException, the mesh service swallows it, and the app looks completely fine while never seeing a single peer. Silent, total discovery failure.
  • An orphaned OS dialog. The prompt is hosted by another process. An OEM that reaps the Activity behind a foreground service can destroy it while the dialog is up, and the promise never settles. The 60 second deadline is a backstop for a step that can hang rather than fail, which is not a state the app can detect from the inside.
  • Re-requesting on resume. Either a no-op or a prompt thrown at somebody who did not ask. This is why hasBlePermissions() exists as a separate, non-prompting read.
  • An optional permission with its own group. Re-requesting is only safe because the optional permission shares the required ones' group on API 33 and above. Add one that does not and it re-prompts on every launch after a single denial. This is written down at the call site because it is the trap the next change will fall into.
  • Concurrent prompts. On a fresh install, racing the notification prompt against the others swallowed it and sometimes crashed. They are sequenced now, one await at a time.
  • Guessing on a timeout. Publishing a blocker for an answer that never arrived would show a red banner over a permission the user may have granted. The null case is deliberately silent.

If you removed it

On Android the app would install and run and find nobody, forever, with no indication why. That is the exact bug this layer was built to fix. On iOS almost nothing would change, because CoreBluetooth prompts on its own and the usage strings are in the bundle either way. Removing only the primer would be survivable and measurably worse: more first-refusals on a permission where a second refusal is permanent, and no explanation for the location dialog that a chat app has no obvious reason to show.

Alternatives

ApproachHow it worksWhy not here
Ask everything at first launch One batch of dialogs before the app is usable Highest refusal rate of any pattern, because none of the asks has context yet. It also puts camera and microphone prompts in front of a user who may never use either.
Ask nothing until it fails Let the native call throw and react to the error This is precisely the old behaviour. The throw is swallowed, so the failure is invisible and the app appears to work.
Require location on Android at every level bitchat's approach: one code path, no API-level branch Simpler, and it costs a backgrounded phone every scan result plus a dead mesh for anyone on "Approximate" location. The branch is worth its complexity.
Block the app behind the primer A hard gate: no mesh until acknowledged Turns an explanation into a hostage situation, and creates a state where a sheet that fails to render bricks the app. It resolves either way for that reason.
No deadlines, just await Trust the platform promises to settle They do not always. An orphaned dialog leaves a running app with no mesh and no error, which reads to the user as broken hardware.

Drills

  • Why does the app show its own explanation before the Bluetooth prompt on Android, but not on iOS? Two reasons, both platform facts. On Android a second refusal makes the permission permanently blocked, so the cost of a poorly-contextualised first ask is very high and the only remedy afterwards is a trip to system settings. And on Android 11 and below the mesh asks for location, which in a chat app reads as tracking and needs explaining before the dialog rather than after. On iOS neither applies: CoreBluetooth prompts on first use carrying our own usage string, so that prompt already is the primer, and there is no location coupling to explain away. The sheet still renders correctly on iOS if it is ever shown; it is simply not needed.
  • The permission request promise never settles. What does the user see? A working app. After 60 seconds the deadline fires, nothing is published about the permission because "the OS never answered" is not an answer, and initMeshService runs anyway. The radio controller then reads the actual grant off the device on its first reconcile and publishes the true blocker. So the only thing the timeout changes is how quickly the banner becomes correct. This matters because the promise really can be orphaned: the dialog is hosted by another process, and OEMs that reap the Activity behind a foreground service destroy it while the dialog is up. Before the deadline existed, that left a running app with no mesh and a Mesh tab reading "starting..." for the whole session.
  • Why is blePermissionBlocked a separate flag rather than one more BleBlocker value? Because the two are learned from different sources with different lifetimes. The blocker is re-derived by the radio controller from the device on every reconcile. Whether a refusal is permanent can only be learned from the permission request itself, since neither platform reports it through the radio. Folding them together means the next reconcile downgrades a known-permanent refusal back to "ask again", and the banner offers an Allow button that the OS silently swallows. Keeping them apart is also why the Permissions screen can render an honest Android Bluetooth row at all.
  • A reviewer says the fast-path check in ensureBlePermissions should only look at the required permissions, since the optional one cannot fail the gate. Answer them. The two lists move independently over time. A future build adds an optional permission and ships to phones whose required grants were settled long ago. A fast path reading only the required list returns early on every launch for the life of that install, so the new permission is never requested even once. Checking both means the first launch after the update falls through to the request, and on API 33 and above both lists are in the NEARBY_DEVICES group so the user sees no extra dialog. The caveat is written at the call site: this is only safe while the optional permission shares a group. One carrying its own group would re-prompt on every launch after a denial and would need a persisted marker.
  • Explain neverForLocation to a privacy reviewer who suspects it is a loophole. It is a declaration to the OS that scan results will not be used to derive a physical position, and the OS enforces it by stripping location-inferring data from the results. For Airhop the declaration is accurate: a result is read for the service UUID, the peer ID and the RSSI, none of which is a position, and the app never correlates them into one. What it buys is real: scanning no longer requires the location permission, and no longer depends on the system location toggle. The reference implementation does not use it and therefore also needs background location and a location foreground-service type, which costs a backgrounded phone every scan result. Location for the geohash area channels is requested separately, by the feature that actually uses a position, and denying it costs channels rather than the mesh.
  • Why does the Permissions screen open system settings instead of turning a permission off? Because no mobile OS allows it. Android 13 added revokeSelfPermissionOnKill, which kills the process to do it, and iOS has no equivalent at all. A switch that appears to revoke and does not is worse than no switch, so the row navigates to the place where revocation actually happens and stays on until the OS reports otherwise. The same honesty rule is why the screen re-reads every permission from the OS whenever it comes forward: the user leaves, changes something in settings, and comes back expecting the list to match, which is exactly the case a cached value gets wrong.
  • Why is notifications asked last, and after the mesh has already started? Two separate reasons. Last, because concurrent prompts on a fresh install raced: the notification prompt got swallowed and sometimes crashed, so every prompt outside the batched BLE run is now awaited one at a time. After the mesh, because notifications are the permission with the mildest consequence, degrading to in-app badges and haptics, and nothing about starting the radios depends on it. The general rule holds throughout the sequence: nothing that can fail may sit between the app and a working mesh.
