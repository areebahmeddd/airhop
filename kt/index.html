Airhop, explained from the ground up

This is the manual you would want on day one as a maintainer, and the one you would want on the day someone senior asks you to defend a design decision. It starts at radio waves and ends at an engineering review of the whole thing.

The sixty second version

Airhop is a messaging app that does not need the internet. Phones near each other talk over Bluetooth. Each phone repeats what it hears, so a message can hop across strangers' phones to reach someone further away than any single radio can reach. Messages are encrypted so the phones in the middle carry sealed envelopes they cannot open. When the internet is available, the same app reaches further using Nostr relays. It can also carry money, as offline Cashu ecash tokens. There are no accounts, no servers we run, and nothing to seize or shut down.

Contents

Ground rules of this document

  • Everything is checkable. Where a claim comes from code, the file is named. Where it comes from a document in docs/, the document is named. Where it is my own judgement, it says so.
  • Claims and reality are kept apart. Several features are documented in the repository but are not in the code. Those are marked not shipped wherever they appear, and listed together in chapter 49.
  • Numbers are sourced. Every timing constant comes either from a named file in this repository or from the corresponding bitchat source under bitchat/.
  • No hand waving on security. Where a property does not hold, the chapter says so plainly rather than describing the intent. Courier tags are not unlinkable. Tor use is visible. Peer IDs do not rotate.

Status of the software

Airhop v1.0.x has not had an external security audit. The cryptography is implemented against audited primitive libraries (@noble/*, reviewed by Cure53) but the protocol composition on top of them is reviewed in-house only. Treat every security statement in this manual as a description of the design, not as an assurance.
