In plain words

Explain it to a ten year old

Imagine posting a letter inside three nested envelopes, each addressed to a different person. The first person opens theirs and finds an envelope addressed to the second, so they pass it on. The second does the same. Only the third opens the last envelope and posts the letter. The first person knows who you are but not what you sent or where it ended up. The last knows where it went but not who sent it. Nobody in the chain knows both.

How onion routing works

  YOU ──▶ GUARD ──────▶ MIDDLE ──────▶ EXIT ──────▶ destination

  knows:  your IP        guard's IP     middle's IP    exit's IP
          middle's IP    exit's IP      destination
          NOT the        NOT you        NOT you
          destination    NOT the dest

  each hop peels one layer of encryption. no single relay
  ever holds both ends of the association.

  the GUARD is sticky. you keep the same one for weeks, because
  rotating it means eventually picking a hostile one, and one
  chance of that beats a fresh chance every circuit.

Roughly 8,000 volunteer-run relays, a public consensus document listing them, and a directory system to fetch it. That is the whole network. Airhop uses it as an ordinary SOCKS5 client would, which is the point: no custom protocol, no bespoke anonymity claim.

What Tor does not hide

Four things worth being precise about

That you are using Tor. Without a bridge, the relay list is public, so anyone watching your network sees a connection to a known Tor address. Chapter 26 is the answer to that, and it is a separate problem from anonymity.

Application-layer identity. Tor hides your IP. It does not hide a Nostr public key you sign every event with, and it does not hide a message you signed. Chapter 24 covers what a relay still learns.

Traffic patterns from a global observer. Tor's threat model explicitly excludes an adversary who can watch both ends of a circuit at once and correlate timing.

Bluetooth. Tor is an internet-only concern. The mesh keeps working whatever happens here, and every failure message in the app says so.

One crate, two FFI faces

What the app actually gets

A SOCKS5 listener on 127.0.0.1:39050 and a status snapshot. That is the entire surface. No control port, no torrc, no configuration file, nothing to misconfigure. The app points its sockets at the port and reads the status to draw a banner.

This replaced a split design: Arti on iOS only, and Orbot detection on Android. That version had two failure surfaces, two definitions of "on", and a dependency on the user installing a separate app. The Orbot path is gone.

Three load-bearing properties

Each of these is a decision recorded in the crate, not an accident of how it happens to work.

1. It cannot leak

arti_client has no clearnet path. Every byte that enters the listener leaves through a circuit or does not leave at all. So failing closed is a property of the design rather than of timing: there is no window, however short, in which a request takes a direct route because the circuit was not up yet.

That is a genuinely different guarantee from "we check a flag before dialling". A flag can be read before it is set; a client with no clearnet code path cannot dial the clear net at all.

2. The listener binds before bootstrap

start returns only once the port is accepting, so a caller that gets AIRHOP_TOR_OK may dial immediately. A dial made during bootstrap waits for a circuit; a dial made after a bootstrap that never completed fails.

Binding after bootstrap instead would leave the app unable to tell "starting" from "broken" for the whole bootstrap, and leave callers probing the port to find out. Neither platform has to probe.

3. Progress is real

TorClient::bootstrap_events() is the client's own view of how far along it is and why it is stuck. Nothing infers state from log text, which is the usual way a Tor integration ends up lying to its own UI.

One more, smaller: panics abort rather than unwind. Unwinding across an FFI boundary is undefined behaviour, and aborting is the one option that is sound without wrapping every entry point in catch_unwind. A panic in a Tor client is a bug worth a crash report, not something to swallow.

Six operations, identical on both platforms, in src/bridge/NativeAirhopTor.ts.

Status is also pushed, as a TorStatusChanged event. Without a subscriber a stalled bootstrap is never reported, which is why subscribeTorStatus returns null rather than throwing wherever the native module is absent.

The TypeScript side collapses that into a three-value TorBootstrapPhase: idle, starting, blocked. The Mesh banner reads it.

The one place the platforms differ

The lifecycle is identical. Coverage is not, and the difference is not a bug that has gone unfixed. It is a platform constraint.

AndroidiOS
How the proxy is applied Installed into React Native's shared OkHttp client TorWebSocket handed to nostr-tools
What is covered Every socket the app opens, fetch included Only the Nostr WebSocket
Why OkHttp is one shared client with a proxy setting React Native's WebSocket cannot speak SOCKS5 on iOS, and there is no shared HTTP client to point at a proxy
Consequence A Cashu mint call goes through Tor A mint call would go clear, so it is refused instead

Both fail closed at the socket, which is the property that matters: nothing on either platform silently takes a direct route. What differs is how much of the app the protection reaches.

The mint hole

The honest statement of it

With Tor on, an iPhone cannot make a Cashu mint request without revealing this device's IP to the mint and linking it to the proofs being swapped. Mint calls are plain fetch, and on iOS nothing but the Nostr WebSocket is covered.

So wallet-service refuses the call rather than making it. There is a setting to allow it anyway, off by default, which exists because a user in a place where the wallet matters more than the IP should be able to make that trade knowingly rather than discovering it afterwards. Chapter 32 covers what a mint learns.

Dormancy, not stopping

setAppForeground(false) puts Arti into DormantMode. This is not advisory and it means the same thing on both platforms even though the pressure differs. 

  iOS       the process is suspended anyway, so circuits do not
            survive a long background spell either way

  Android   the foreground service keeps the process alive, so
            WITHOUT this a backgrounded Airhop keeps a consensus
            fresh and guards warm all day on a battery


  why dormancy and not a stop:

    stopping would DROP THE GUARDS
      -> a fresh bootstrap on every return to the app
      -> and the device looks like a BRAND NEW CLIENT to a
         guard each time, which is worse for anonymity than
         keeping one

  safe to call whatever the Tor preference says: with nothing
  running it is a no-op.

Why it is off by default

Three reasons, and none of them is that Tor is unsafe.

  • It is slow. Three hops of volunteer bandwidth. A relay connection that took 200 ms takes seconds, and with a bridge, longer.
  • It is conspicuous where it matters most. Without a bridge, using Tor is visible to the network operator, and in some places that visibility is itself the risk. Chapter 26.
  • Most people, most of the time, are not the threat model. An always-on default trades everyone's battery and latency against a risk few of them carry, and it makes the setting meaningless as a signal of intent.

The gate in tor-routing.ts is explicitly not a safety measure: both platforms fail closed at the socket, so nothing reaches the clear net whether it is set or not. It prevents futility, not leakage.

Tor and the panic wipe

Why Tor needs its own wipe call

Arti's data directory sits outside the media cache on both platforms: Application Support on iOS, the app's files directory on Android. The wipe's ordinary cache sweep does not reach it.

What it holds is a cached consensus, chosen guard nodes and directory state. Together those are evidence on disk that this device used Tor and roughly when, which for a user whose reason for wiping is a device search is exactly the wrong thing to leave behind. wipeTorState() stops Arti and deletes all of it.

The transport state directory is wiped alongside it, and it sits beside Arti's rather than inside it, because Arti owns the layout of its own directory. Chapter 35 is the whole wipe.

What breaks it

  • A network that blocks Tor. The common case, and the whole subject of the next chapter. Bootstrap stalls, the deadline fires, and the phase becomes blocked.
  • A build without the native library. Any ABI it was not built for. This must degrade to "Tor unavailable" rather than taking the app down at import time, which is why the module is fetched with TurboModuleRegistry.get rather than getEnforcing and every caller null-checks.
  • Stopping instead of going dormant. Drops the guards, costs a full bootstrap on every return, and presents the device to a guard as a new client each time.
  • Inferring state from log text. The usual way a Tor integration lies to its UI. bootstrap_events() exists precisely so nothing has to.
  • A panic that unwinds across the FFI. Undefined behaviour. panic = "abort" makes it a crash instead, which is diagnosable.
  • Forgetting the state directory in a wipe. Leaves a cached consensus and a guard list on disk, which is evidence the device used Tor.

If you removed it

The mesh is untouched, so the app keeps working offline exactly as before. What goes is the ability to use the internet layer without handing a relay operator your IP address, and with it the users for whom that is the point: anyone whose network is watched, anyone whose association with a relay is itself the risk. It would also remove the most complex build machinery in the repository, which is a real cost saved and worth stating honestly. The trade is a smaller, simpler app that is materially less useful to the people it was built for.

Alternatives

ApproachHow it worksWhy not here
Orbot, or any separate Tor app Detect a SOCKS proxy another app provides What Android used to do. It needs the user to install and run a second app, gives two definitions of "on", and leaves the app unable to say why Tor is not working. Removing it removed a whole failure surface.
Bundling the C tor binary The traditional route: ship the executable, write a torrc, drive the control port iOS forbids an app spawning an executable. It also means a config file, a control protocol and a process to supervise, all of which are surfaces Arti-as-a-library does not have.
A VPN One hop, encrypted, provider-operated Moves trust rather than removing it: the provider sees everything Tor's guard would, plus the destination, and is a single entity with a billing relationship to you.
I2P Garlic routing, fully peer-to-peer, no exits by design Strong for in-network services, but Airhop needs to reach ordinary Nostr relays on the open internet, which is exactly what I2P is not for.
Nothing, and rely on the mesh Offline-only, no internet layer at all Coherent, and it is the fallback whenever Tor fails. It costs the global reach that makes a message deliverable to someone in another city.

Drills

  • Someone asks whether Airhop can leak a real IP while Tor is starting up. Answer precisely. No, and the reason is structural rather than a timing guarantee. arti_client has no clearnet code path at all: every byte entering the SOCKS listener leaves through a circuit or does not leave. A request made before a circuit exists fails; it does not fall back. That is a stronger claim than "we check a flag first", because a flag can be read before it is set. The related honest caveat is coverage rather than leakage: on iOS only the Nostr WebSocket is routed, so a Cashu mint call is refused rather than routed, and on Android the proxy is in the shared OkHttp client so everything including fetch is covered.
  • Why does the SOCKS listener bind before bootstrap rather than after? So that start returning AIRHOP_TOR_OK is a usable signal. A caller can dial immediately: a dial during bootstrap waits for a circuit, a dial after a failed bootstrap fails. If the port only appeared once bootstrap completed, the app could not tell "still starting" from "broken" for the whole bootstrap window, and every caller would have to probe the port to find out. Neither platform probes, which is the observable consequence of the choice.
  • Backgrounding the app makes Tor dormant rather than stopping it. Why is that the better default? Because stopping drops the guard nodes. Guards are deliberately sticky, held for weeks, precisely so that a user gets one chance of picking a hostile entry rather than a fresh chance on every circuit. Restarting from cold on every return to the app both costs a full bootstrap and presents the device to a guard as a brand new client each time, which is worse for anonymity than staying dormant. On iOS the process is suspended anyway so the practical difference is small; on Android the foreground service would otherwise keep a consensus fresh and guards warm all day on a battery, which is the case dormancy exists for.
  • Why did the Orbot path get removed? Because it made "Tor is on" mean two different things. The Android path detected a proxy another app provided, which required the user to install and run Orbot, gave the app no view of bootstrap progress or of why a connection failed, and produced a second fail-closed design to reason about. Embedding Arti on both platforms collapses that into one crate with one lifecycle, one status word and one set of return codes, and nothing above the FFI branches on platform for Tor's lifecycle any more. The only surviving difference is coverage, and that one is a platform constraint rather than a design choice.
  • Why does the panic wipe need a dedicated wipeTorState() rather than relying on the cache sweep? Because Arti's data directory is deliberately not in the cache: Application Support on iOS, the files directory on Android, both outside what the sweep reaches. What it holds is a cached consensus, a chosen guard list and directory state, and together those are evidence on disk that this device used Tor and roughly when. For a user whose reason for wiping is a device search, that is exactly the wrong residue to leave. The pluggable transport state directory sits beside Arti's rather than inside it, because Arti owns its own layout, and it is wiped in the same call.
  • Why is the native module fetched with get rather than getEnforcing? Because a missing Tor library must degrade to "Tor unavailable", not crash the app at import time. That is not hypothetical: a build for an ABI the library was not compiled for, or a build that omitted it, is a real state, and the mesh has no dependence on Tor whatsoever. The same reasoning runs through the layer: subscribeTorStatus returns null rather than throwing when the module is absent, and every caller null-checks. The cost is that a missing subscriber means a stalled bootstrap is never reported, which is why the subscription is set up at the same time the client is started.
