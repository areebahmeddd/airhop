In plain words

Explain it to a ten year old

Turning code into an app is like baking: you gather ingredients, follow steps, and something comes out of the oven. The interesting part here is that this kitchen writes down the exact weight of every ingredient, refuses to bake if anything has been swapped, and publishes a receipt so anyone can check the cake they were given is the cake the recipe describes.

The chain, end to end

  YOUR TYPESCRIPT
        │
        │  BABEL          strips types, transforms JSX,
        │  babel-preset-expo   applies the reanimated plugin LAST
        ▼
  PLAIN JAVASCRIPT
        │
        │  METRO          resolves every import, bundles the graph
        │                 into ONE file, reads path aliases from tsconfig
        ▼
  ONE BUNDLE
        │
        │  HERMES         compiles JS to BYTECODE ahead of time
        ▼
  BYTECODE, embedded as an asset
        │
        ├──▶ GRADLE   compiles android/ Kotlin, links the bundle,
        │             R8 minifies, produces .aab / .apk
        │
        └──▶ XCODE    compiles ios/ Swift, links arti.xcframework
                      and the bundle, produces .ipa

  TypeScript's own compiler NEVER emits anything here.
  `tsc --noEmit` runs as a CHECK only; Babel does the stripping.

Why tsc does not build the app

Babel removes types by deleting them without understanding them, which is fast and requires no type checking. That means the build cannot be blocked by a type error, and equally that type errors are invisible to the build. So npm run typecheck exists as a separate CI gate. Both are needed: one for speed, one for correctness.

Never run npx expo prebuild

ios/ and android/ are checked in and hand-modified: five native modules per platform, a foreground service, an embedded Arti framework, manifest entries for background modes and the neverForLocation scan flag. Prebuild regenerates all of it from app.json and deletes every one of them.

It is the single most destructive command in the repository, and the README flags it as a caution. The prebuild script still exists in package.json, which is worth being aware of.

EAS is not used and is unlikely to be: its main draws are prebuild and managed credentials, and this project does not run prebuild. The cost is that iOS release signing is manual.

Three lockfiles, and a fourth kind

A lockfile records the exact version and content hash of every dependency, so two builds from the same source produce the same binary. This project has three, plus a fourth thing that is not quite a lockfile.

FileLocksRegenerated by
package-lock.jsonEvery npm dependency, transitively, with integrity hashes. 547 KB.npm install
android/app/gradle.lockfileEvery Gradle dependency for the app module../gradlew app:dependencies --write-locks, in the same commit as the change
ios/Podfile.lockExact CocoaPods versions.npx pod-install, in the same commit
vendor.lock.jsonChecked-in binaries. Not a dependency lock. See below.node scripts/verify-vendored.js --write

The "same commit" rule matters. A dependency change without its lockfile update produces a pull request that builds differently on every machine, and the divergence surfaces later as an unreproducible bug. There is a sync-locks workflow to regenerate both native lockfiles on demand and commit them.

vendor.lock.json

The most unusual file in the build system, and worth understanding properly because it addresses a real supply-chain problem. 

  {
    "files": {
      "ios/Frameworks/arti.xcframework/Info.plist":            "cac99db4...",
      "ios/Frameworks/arti.xcframework/ios-arm64/Headers/arti.h": "55165590...",
      "ios/Frameworks/arti.xcframework/ios-arm64/libarti_bitchat.a": "5461a231...",
      ... one SHA-256 per file, seven in total ...
    }
  }

The problem it solves

ios/Frameworks/arti.xcframework is roughly 35 MB of prebuilt static library that is not compiled here, committed straight into the repository, and shipped inside the iOS app. It is the Tor client.

Nobody reviews a binary diff. Git alone will not tell you the bytes changed for a reason: a swapped blob looks exactly like a legitimate update in a pull request summary. A malicious Tor implementation inside a privacy app is close to the worst possible outcome, and it would be invisible in review. 

  node scripts/verify-vendored.js            check the tree against the lock
  node scripts/verify-vendored.js --write    record the tree as the new lock

  Run in CI as `npm run verify:vendored`, on every pull request.

What it does and does not prove

It does not prove the binary is trustworthy. It proves the binary has not changed without somebody explicitly and visibly re-recording the hash. That converts an invisible substitution into a visible one-line diff in vendor.lock.json that a reviewer will notice and have to ask about.

The complementary document is bitchat/ios/docs/ARTI-BINARY-PROVENANCE.md, which is where the question of where the binary came from belongs.

The scripts folder

Ten Node scripts, none of which ship in the app. Each exists because something failed silently once.

ScriptJobWhy it exists
check-invisibles.js Rejects invisible characters in tracked text files. The best story in the folder. cashu.ts once carried literal control bytes where escape sequences were meant: a character class intended as [\x00-\x1f] held the raw bytes themselves, and a word boundary held a backspace. The expressions silently matched nothing, so a mint-safety check accepted every mint it was asked about. The same bytes made git treat the file as binary, so no diff of it was ever readable in review. A money-handling file became unreviewable and unenforced at once, and nothing in the toolchain objected.
verify-vendored.js Checks every vendored binary against vendor.lock.json. See above.
generate-relays.js Regenerates src/data/relays.ts and the landing site's copy from assets/data/nostr_relays.csv. Metro does not bundle .csv, so the directory ships as a TypeScript module. Bundling it means no network dependency on first launch, no third party learning who is asking for relays, and no fetch to fail offline, which is exactly when this app matters most. Airhop does not fetch a relay list at runtime from any URL.
validate-relays.js Validates a candidate relay CSV before it replaces the vendored copy. Fails closed. The directory is compiled into the bundle, so a bad row ships to every user. It also reports which hosts entered and left, because counts alone cannot show a hostile row arriving in a pull request.
relay-url.js A second copy of validateRelayUrl, for build-time scripts. The app's copy is TypeScript bundled by Metro; this runs in plain Node under CI, and nothing can share a module across that boundary. relay-url-parity.test.ts asserts the two agree so they cannot drift. It also collapses hosts listed twice, bare and with an explicit :443, because those are one relay and bitchat collapses them before choosing a cell's set.
source-manifest.js Writes a SHA-256 manifest of every git-tracked file, in plain sha256sum format. So anyone can prove the source they hold is the source that shipped, with sha256sum -c and no tooling from this repository. Comment lines are ignored by sha256sum, which is what lets the file carry its own instructions.
i18n-audit.js Reports hardcoded English strings, and unused catalog keys. Two directions of one question, and both drift silently: a string that never reached the catalog leaves a screen untranslatable, and a catalog entry nothing references leaves a translator working on text nobody reads. --max is a ratchet, run in CI at --max 0.
i18n-check-native.js Guards the strings the OS renders: iOS permission prompts in .lproj/, the Android foreground notice in values-*/, and the locale list Android 13's picker reads. Those never reach t(), so they are invisible to the catalog test. Without it a language ships a complete catalog and still shows an English system dialog, silently.
i18n-build-locale.js Builds a locale from a flat { key: text } map, and refuses to build a broken one. Key order, section markers and escaping come from en.ts, so the emitted file is complete and ordered by construction and the only thing left to review is the words. Fatal: a missing or extra key, an empty string, a placeholder that does not match English, a plural set that is not the language's CLDR categories, a protocol token that did not survive, or a character from a script the language does not write in.
i18n-lib.js Reads the catalog from outside TypeScript, through the compiler API. The catalog is TypeScript rather than JSON so it can carry section markers and be type-checked. A script cannot require() it, and unlike a regex the compiler API cannot be confused by an apostrophe, a brace inside a string, or a multi-line value.

What knip actually is

A dead-code finder. You declare your entry points, it walks the import graph from them, and anything unreachable is reported: unused files, unused exports, unused types, and dependencies in package.json that nothing imports. 

  knip.json

    entry:    App.tsx
              src/**/__tests__/**          tests are entry points too, or
              src/**/__benchmarks__/**     every tested-but-unused export
              scripts/*.js                 would be reported
              press/build.mjs, press/tools/*.mjs

    project:  src/**/*.{ts,tsx,js}, scripts/**/*.js, press/**/*.mjs

    ignoreDependencies:  ["expo-updates"]
    ignoreExportsUsedInFile: true

Why dead code is a security concern, not just tidiness

Unused code is unreviewed code that still ships. It enlarges the attack surface, it confuses the next reader about what is live, and an unused dependency is a supply-chain risk with no benefit. In a project whose selling point is a small auditable protocol core, running this as a hard CI gate rather than a report is the right call.

ignoreExportsUsedInFile: true allows a module to export something it also uses internally, which is common for testability. expo-updates is ignored because it is referenced by native configuration rather than by an import.

DecisionReason
A full R8-minified release build on every change Minification is where reflection-based libraries and missing keep rules fail, and where 16 KB page alignment requirements bite. Those failures otherwise appear for the first time on a release tag, in front of users, at the worst possible moment. Building it per pull request turns a release-day emergency into a red check on a branch.
An unsigned iOS Release build in CI So native and release-only breakage fails the same pull request Android does, even though distribution credentials do not exist.

Gradle wrapper validation The wrapper is a checked-in JAR that runs during every build. Validating it against the official release stops a substituted wrapper executing arbitrary code in CI.
fail_ci_if_error: true on coverage upload A silently failing upload means the coverage badge quietly stops meaning anything.
permissions: contents: read Least privilege by default, escalated per job only where a job genuinely writes.
Concurrency cancels in-progress PR runs Pushing twice does not queue two 45 minute Android builds.

A separate codeql.yml runs GitHub's static analysis on pull requests, pushes, and a schedule.

The native build pipeline

Two binaries in this app are compiled from source rather than downloaded: the embedded Tor client and the pluggable transports it dials. Together they are the most involved build machinery in the repository, and every unusual thing about it follows from one rule: a binary nobody here compiled must not ship. 

  native/arti          Rust      ->  libarti_airhop.so   (3 Android ABIs)
                                 ->  arti.xcframework    (iOS)

  native/iptproxy      Go        ->  IPtProxy.aar        (Android)
                       gomobile  ->  IPtProxy.xcframework (iOS)

  each has four scripts, and they mean different things:

    build-in-container.sh   Android, in the pinned image.  SUPPORTED PATH,
                            and what CI checks against
    build-android.sh        Android, directly.  refuses a toolchain that
                            does not match TOOLCHAIN.env exactly
    build-apple.sh          iOS.  needs a Mac: lipo and xcodebuild are
                            macOS only
    fetch-sources.sh        (iptproxy) pinned checkouts on the host

TOOLCHAIN.env, one file for both

Every pinned version lives in native/arti/TOOLCHAIN.env, read by the scripts, by the Dockerfile and by CI. One file for both native builds, because they share an NDK and a container.

PinValueWhy it is pinned here
ARTI_CLIENT_VERSION0.46.0Must match arti-client and tor-rtcompat in Cargo.toml. The build asserts they agree.
RUST_VERSION1.98.0Must match rust-toolchain.toml. A compiler bump moves both together.
ANDROID_NDK_*r28c, with a SHA-256NDK r28 and later use 16 KiB load-segment alignment by default, which Google Play requires for 64-bit libraries.
GO_VERSION1.26.8, with a SHA-256The transports are Go.
IPTPROXY_VERSION + _COMMIT5.5.1, and a commit hashBoth, so the source cannot change behind a tag.
GOMOBILE_VERSIONa pseudo-versionUpstream's build script resolves gomobile with @latest, so the same script run twice can produce different binaries. This pins it, and the build fails loudly if it drifts from their go.mod.
DNSTT_COMMITa commit hashIPtProxy references dnstt through a replace directive rather than the module proxy, so it needs its own pin.
DEBIAN_SNAPSHOTa timestampSystem packages resolve against a frozen archive, so an apt install in the image is reproducible.
NATIVE_SOURCE_DATE_EPOCHa fixed timestampBuild timestamps embedded in output would otherwise change every hash.

What the builds verify about themselves

Neither script trusts its toolchain. Each of these checks exists because the failure it catches is invisible until it reaches a phone.

CheckCatches
Exported symbols, every entry point in every sliceA partial rebuild, where a symbol is present in one architecture and missing from another. The linker only notices when somebody happens to build for that architecture.
16 KiB page alignment (Android)A Play Store rejection. Read back with llvm-readelf, never assumed from the toolchain default.
No build-machine pathsAn absolute path from a developer's disk inside a shipped binary. Both a reproducibility failure and a small leak about whoever built it.
Exactly the ABIs and slices the app packages (iptproxy)A missing one, which only surfaces on a user's phone; and an extra one, which is upstream's default list creeping back and committing a macOS slice nothing links.
The generated binding surface (iptproxy)gomobile derives class and symbol names from the Go package, so an upstream rename would otherwise appear as a crash on a phone or a compile error in the app.

SHA256SUMS and the reproducibility test

Each tree records the hash of every artifact it produces, per platform, and those files are committed. The test is stated in both READMEs in the same words:

Run the container build twice from clean

If SHA256SUMS.android moves, something unpinned leaked into the build. That is the whole reason for the frozen Debian snapshot, the fixed source epoch, and pinning gomobile rather than letting @latest resolve.

The git add is not optional on a first build

verify-vendored.js hashes tracked files, so a binary that has never been added is invisible to it, and --write would record a manifest that silently omits it. Both READMEs say so at the point where somebody would skip it.

Why build rather than vendor

Upstream IPtProxy commits a prebuilt xcframework and publishes an aar on Maven, and their CocoaPod installs the committed binary. Either route puts a large binary nobody here compiled into the app, which is exactly what scripts/verify-vendored.js exists to prevent. fetch-sources.sh goes as far as deleting the committed xcframework so their already-built shortcut cannot ship it by accident.

The release workflow

release.yml, triggered by a v*.*.* tag or a manual dispatch naming an existing tag. Four jobs.

JobDoes
release Resolves and validates the tag: it must exist, and must match ^v[0-9]+\.[0-9]+\.[0-9]+$ exactly, because the version written into app.json is the tag without its leading v. Generates the changelog (git-cliff, configured by cliff.toml) and creates the GitHub release.
android-release Builds and signs the APK and AAB with the upload keystore, and attaches them.
sbom Generates a software bill of materials in SPDX JSON via anchore/sbom-action, and uploads it to the release.
source-manifest Publishes SHA-256 hashes of every tracked source file, with attestations (id-token: write, attestations: write), so the source can be proven to match the release.

iOS release is manual

There is an ios-release placeholder, and distribution credentials do not exist, so the shipped .ipa is produced by hand from Xcode. Android is automated end to end. This is listed as a gap in chapter 49: a manual release step is a step that can be done differently each time, and it is the one part of the pipeline whose output nobody can reproduce.

SBOM plus source manifest is a genuinely strong posture

The SBOM says what went in. The source manifest says exactly which bytes the release was built from, in a format verifiable with sha256sum -c and nothing else. Together with vendor.lock.json for the one binary that is not compiled here, that is three independent answers to "is what I have what you shipped". Very few projects of this size do any of the three.

Test vector files

Two JSON files in docs/spec/ are part of the build's correctness story rather than being documentation.

courier-test-vectors.json

What it is

Golden vectors for the courier wire format, published so a second implementation can be written without reading the TypeScript, and asserted by courier-vectors.test.ts against the running code, so the file cannot go stale while the suite is green.

The header explains why this format in particular earns vectors: three ways of getting it wrong fail silently. The envelope is accepted, carried, then dropped at deposit with nothing logged at either end.

Silent failureEffect
Expiry in seconds instead of millisecondsAbout 1000x too small, so every envelope reads as long expired.
Writing the copies TLV as 1 instead of omitting itA decoder that requires the omission rejects every carry-only envelope, which is the ordinary delivery case.
Wrong epoch-day arithmetic in the recipient tagProduces a tag no carrier matches, so mail is never delivered.
 
  WHAT IS ACTUALLY IN IT

    recipientTag   the HMAC definition, plus two worked cases:
                     nowMillis 0             -> epochDay 0     -> tag hex
                     nowMillis 1728000000000 -> epochDay 20000 -> tag hex

    envelopeTLV    the exact byte order, plus TWO encoded examples:
                     copies 4  -> the 0x04 TLV IS present
                     copies 1  -> the 0x04 TLV IS ABSENT

    limits         ttl 86400000 ms, slack 3600000 ms,
                   max 16384 bytes, initialCopies 4

It also carries, in a comment, the statement that the tag is not unlinkable and that this is inherited rather than chosen, which is a good example of the project documenting a weakness in the machine-readable spec rather than only in prose. And it notes that upstream is drafting an equivalent, with the instruction to diff the two rather than merge, because agreement is the interoperability property and a difference is a finding.

Vendored source parsing

The other half of the same idea, and more unusual: conformance.test.ts reads bitchat's own Swift and Kotlin at test time. It pulls maxPayloadBytes out of FileTransferLimits.swift and fails if Airhop's caps no longer fit under the ceiling it implies, and it parses their MessageType enum and fails if their allocation comes within 16 of Airhop's 0x50 range. Drift in the other project becomes a red build here rather than a field failure later.

Drills

  • What does Metro do, and why is tsc not part of the build? Metro is the bundler: it resolves every import from an entry point, walks the graph, and produces one JavaScript file, reading path aliases from tsconfig.json so nothing is declared twice. Types are stripped by Babel, which deletes them without understanding them, so the build is fast and cannot be blocked by a type error. That means type errors are invisible to the build, which is why tsc --noEmit runs as a separate CI gate.
  • What is vendor.lock.json and what does it actually prove? A SHA-256 per file of the checked-in Arti xcframework, roughly 35 MB of prebuilt Tor client that is not compiled here and ships inside the iOS app. It proves the binary has not changed without someone explicitly re-recording the hash. It does not prove the binary is trustworthy. Its value is turning an invisible substitution, which no reviewer would catch in a binary diff, into a one-line change in a JSON file that a reviewer will notice and question.
  • Why does check-invisibles.js exist? Because cashu.ts once contained literal control bytes where escape sequences were intended: a character class meant as [\x00-\x1f] held the raw bytes, and a word boundary held a backspace. The expressions silently matched nothing, so a mint-safety check accepted every mint it was asked about. The same bytes made git treat the file as binary, so no diff of it was readable in review. A money-handling file became simultaneously unreviewable and unenforced, and nothing else in the toolchain objected.
  • Why is knip run as a hard gate rather than a report? Because unused code is unreviewed code that still ships. It enlarges the attack surface, misleads the next reader about what is live, and an unused dependency is supply-chain risk with no compensating benefit. For a project whose entire pitch is a small auditable protocol core, letting dead code accumulate undermines the claim, so it fails the build rather than producing a warning nobody reads.
  • Why build a fully minified Android release on every pull request? Because minification is where reflection-based libraries fail without a keep rule, and where page alignment requirements bite. Those failures otherwise appear for the first time on a release tag, in front of users, at the moment they are hardest to fix. Building it per pull request converts a release-day emergency into a red check on a branch, at the cost of a 45 minute job.
  • Why does the courier format have published test vectors when nothing else does? Because three ways of implementing it wrong fail completely silently: the envelope is accepted, carried, and then dropped at deposit with nothing logged at either end. Expiry in seconds is 1000x too small so everything reads as expired; writing the copies TLV as 1 instead of omitting it makes every carry-only envelope rejected; and wrong epoch-day arithmetic produces a tag no carrier matches. The vectors are also asserted by a test against the running code, so the published spec cannot drift from the implementation while the suite is green.
