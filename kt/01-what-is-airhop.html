What Airhop is

A messaging app whose first assumption is that there is no network. Everything else follows from that one decision.

In plain words

Explain it to a ten year old

Imagine you are at a festival and the phone signal is dead. Normally your message has to travel to a company's computer far away and back, so with no signal it goes nowhere. Airhop skips the company. Your phone whispers the message to the phones around you over Bluetooth. Those phones whisper it onward. After a few hops it reaches your friend. Nobody in the middle can read it, because it is locked in a way only your friend can open. If a phone in the middle happens to have internet, it can also throw the message over the internet to cover more ground.

The same explanation for a senior engineer: Airhop is a dual transport, serverless, key-based messenger. Transport one is a controlled-flood Bluetooth Low Energy mesh with a seven hop time-to-live and per-packet Ed25519 authentication. Transport two is Nostr, a relay protocol where clients publish signed events to independent WebSocket servers. Sessions are Noise XX with a Double Ratchet layered on top for per-message forward secrecy. Value transfer is Chaumian ecash (Cashu), which is a bearer token and therefore moves offline. Identity is an on-device key pair; there is no registration step anywhere in the product.

The problem it exists for

Every mainstream messenger has an invisible dependency: a company's servers, reachable over an ISP's network, resolved by DNS. Any one of those can be removed, and all three routinely are.

SituationWhat actually failsWhat Airhop does
National internet shutdown Mobile data and fixed lines are cut at the operator. Signal, WhatsApp and Telegram all stop, since all three need a route to their servers. Bluetooth mesh is unaffected. It is a local radio, not a network service. Nothing is being routed anywhere.
Earthquake or hurricane Cell towers lose power or backhaul. Handsets show bars but nothing routes. Same. Plus the courier: a phone can physically carry a sealed message out of the dead zone.
Crowd of 100,000 people Cells are congested, not down. Everything times out. Density is an advantage rather than a problem: more phones means more relays and better mesh reach.
Surveillance without shutdown The network works, and metadata about who talks to whom is collected at the operator or the service. Bluetooth leaves no internet signature at all. Over Nostr, gift-wrap hides sender and recipient from the relay, and Tor hides the IP.
Ship, plane, basement, remote valley No coverage. Bluetooth mesh works. WiFi Aware between Androids gives a fast path for files.

The mission statement in the README says it in one line: make censorship-resistant communication available to anyone during disasters, blackouts, protests, or any situation where networks are unavailable, surveilled, or shut down.

The three layers

Almost every question about Airhop is answered by knowing which of three layers the answer lives on. 

  LAYER 3   INTERNET          Nostr relays, Tor, gateway, bridge, nutzaps
            reach: global     needs: a working internet connection
            role: EXTENSION   if it disappears, the app still works

  LAYER 2   LOCAL RADIO       BLE mesh, WiFi Aware, mDNS LAN (planned)
            reach: ~350 m     needs: nothing but the phones
            role: FOUNDATION  if it disappears, the app is a normal messenger

  LAYER 1   THE DEVICE        keys, storage, panic wipe, the screens
            reach: one phone  needs: nothing
            role: TRUTH       everything above is a way of moving what is here

The direction of dependency only ever points downward. Layer 3 enhances layer 2, never enables it. That is principle 2 below, and it is the single rule that decides most arguments in the codebase. If a proposed feature would make a core function stop working without internet, it does not go in, or it goes in as an optional extra.

The seven principles

These come from docs/design/VISION.md. They are not aspirations, they are veto rules. Each one has killed a feature.

  1. Security first. Every design decision passes a security lens before a product lens. Example casualty: media in private channels. Channel text is encrypted, but attachments ride the signed-but-unencrypted file path, so allowing them would have quietly broken the privacy the channel advertises. So media is refused there (src/utils/media-policy.ts).
  2. Offline first. Every feature must work with zero internet. Example casualty: sending attachments over Nostr, which would need an HTTP file host (NIP-96) and therefore a central server that can log, throttle or take down files.
  3. No accounts, ever. There is no create-account screen. Identity is a key pair generated on first launch. Example casualty: server-side backup, push notifications from a company server, and any username registry.
  4. No central server. No infrastructure to seize. Example casualty: NIP-29 relay-managed groups, which would make a relay the authority on who may speak.
  5. Ephemerality by default. No plaintext message content is written to disk. The panic wipe destroys everything in under a second. Example consequence: attachments are swept on a schedule, seven days by default, with no unbounded option.
  6. bitchat wire compatibility. Airhop nodes must talk to bitchat nodes. The packet format, service UUIDs and peer ID derivation are fixed. Example casualty: raising the file size cap. bitchat iOS refuses anything over roughly 1.13 MiB when it decodes, silently, so raising it would look like it worked while every attachment to an iPhone vanished.
  7. Protocol compliance over clever shortcuts. When in doubt, do what bitchat does. Example consequence: Airhop implements bitchat's non-standard "nip44-v2" encryption for Nostr DMs rather than the published NIP-44, because byte-identical output is the whole of interoperability there.

What it deliberately is not

Not a video call app

Bluetooth carries about 18 KiB per second per link. A low quality video call needs roughly ten times that. And the two same-platform fast paths cannot talk to each other, so there is no cross-platform high bandwidth link to build on. Recorded clips are sent as files.

Not a server

No relays, no mints, no infrastructure is operated by this project. The relay list is a bundled CSV of other people's relays. The mint is whichever one the user adds.

Not a moderated platform

Moderation is client side only: mute and block lists on your own device. There is no protocol-level mechanism to remove content from other people's phones, and there deliberately never will be, because such a mechanism is also a censorship mechanism.

Not an analytics product

No crash reporting to any server, no usage analytics, no tracking. The diagnostics screen shows local counters only.

Where it sits in the landscape

Offline and private messengers fall into three families. Knowing which family a competitor is in explains most of the differences.

FamilyExamplesWorks offlineNeeds hardwareThe catch
Internet-only messengersSignal, Threema, Session, White NoiseNoNoExcellent at what they do, and they stop entirely when the network does.
Radio mesh with dedicated hardwareMeshtastic, goTennaYesYesKilometres of range, but you must buy and carry a device, and bandwidth is tiny.
Phone-to-phone meshBridgefy, Berty, Briar, bitchat, AirhopYesNoWorks on devices people already own, but range depends on how many people are running it.

Airhop is in the third family and extends it with the second layer of the internet stack. The two closest comparisons deserve a sentence each:

  • Briar is the most philosophically similar: Bluetooth, WiFi and Tor, with its own Bramble protocol stack. It is Android and desktop, has no iOS build, and has no payment or internet-relay layer.
  • bitchat is the direct ancestor. Airhop shares its wire protocol byte for byte and can join the same mesh. See chapter 46 for the complete difference list.

A claim worth correcting

The README's comparison table lists Airhop's platforms as "iOS, Android, Desktop, Web, CLI" while listing bitchat's as "iOS, Android". Desktop, web and CLI are roadmap items v1.4 to v1.7 and do not exist. Comparing shipped competitors against your own roadmap in the same table is the kind of thing a reviewer notices first. Chapter 49 lists this with the other documentation drift.

Drills

  • Why can Airhop not simply use Signal's protocol and be done with it? Two reasons. Signal's transport is Signal's own servers, so it does not solve the offline case at all. And the Signal service ties an account to a phone number, which is a registration step and a permanent identifier, which principle 3 forbids. The Signal algorithms are used: Double Ratchet is exactly Signal's, and it is layered on top of Noise XX.
  • If the internet works, why not just use the internet? It does, when available. But the offline path has to be the default rather than a fallback, because a fallback is code that is never exercised and therefore does not work when it is needed. Bluetooth carrying the primary path is what keeps it tested every day.
  • Someone says "a mesh app is useless because nobody else has it installed". What is the honest answer? That is correct and it is the real limitation. Mesh range scales with user density: seven hops of 30 to 50 metres is 210 to 350 metres only if there is a person with the app standing at each hop. Two mitigations exist. Wire compatibility with bitchat doubles the effective user base at zero cost. Relay hardware (chapter 47) puts a node where nobody stands. Neither makes an empty field work.
  • What is the single decision that most shapes the codebase? Wire compatibility with bitchat. It fixes the packet layout, the service UUIDs, the peer ID derivation, the file size caps, the courier expiry, the Nostr DM cipher and the packet type registry. Most "why is it like that" questions bottom out in "because a bitchat phone has to be able to decode it".
