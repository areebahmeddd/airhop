Chapter 31 · Media and transports

Live voice

Real-time audio across a multi-hop Bluetooth mesh, on a radio that moves 18 KiB per second and adds up to 220 ms of deliberate delay per hop. It works because the requirements are much smaller than they look and every constant was chosen against a stopwatch.

In plain words

Explain it to a ten year old

It is a walkie-talkie. You hold a button, talk, and let go. Your voice is squeezed down to about the size of two pages of text per second, chopped into small packets, and thrown into the room. The phones listening wait a third of a second before playing, so that if a packet is a little late there is still something to play. When you let go, the whole recording is also sent as a normal voice message, so anyone who missed it can still hear it.

The codec

ParameterValueWhy
CodecAAC-LCHardware encoders and decoders exist on every phone, so it costs almost no CPU or battery. It is what bitchat uses, so bursts cross between the two apps.
Sample rate16 kHzWideband speech. Telephony is 8 kHz and sounds like a telephone; 16 kHz sounds like a person in the room. Doubling again to 32 kHz buys almost nothing for speech.
ChannelsMonoStereo doubles the bitrate to convey nothing about one speaker.
Bitrate~16 kbpsThe point where AAC-LC speech stops improving audibly at 16 kHz mono.
Codec byte0x01VoiceBurstCodec.aacLC16kMono in bitchat. One byte, so a future codec is a value rather than a format change.
ADTS headersNoneThe codec byte fully describes the frames, so the receiver rebuilds the AudioSpecificConfig from it. Carrying ADTS would spend 7 bytes per frame on information already known.

Opus would be the better codec in isolation: better quality per bit at these rates, designed for exactly this use, and it handles packet loss more gracefully. It is not used because bitchat uses AAC-LC and interoperability of live voice across the two apps is worth more than the quality difference. It is also not hardware-accelerated on every device, where AAC is.

The burst format

One burst is one press of the button. The same bytes are the payload of a VOICE_FRAME (0x29) broadcast and of a NoisePayloadType.VOICE_FRAME (0x08) DM, so one format serves both scopes and only the envelope differs. Byte-identical to bitchat's VoiceBurstPacket.swift. 

  [burstID: 8 bytes][seq: u16 BE][flags: u8][payload...]

  flags  name       payload
  ─────  ─────────  ─────────────────────────────────────────────
  0x01   START      [codec: u8]                    seq = 0, reserved
  0x00   DATA       repeated [len: u16 BE][raw AAC frame]
  0x02   END        [totalDataPackets: u16 BE][durationMs: u32 BE]
  0x04   CANCELED   empty. receivers discard the whole burst.

  A BURST, IN ORDER

  press
    │
    │  START is sent with the FIRST CAPTURED FRAME, not on button-down.
    │  A burst is only real once there is audio in it, and announcing one
    │  before the microphone has produced anything turns a failed capture
    │  into a live bubble on the far side that never plays.
    ▼
  seq 0   START   [codec 0x01]
  seq 1   DATA    [len][frame][len][frame]        batched to fit 210 bytes
  seq 2   DATA    ...
  ...     ~15 packets per second
  seq N   END     [totalDataPackets][durationMs]
    │
  release
    │
    └─ the same audio is ALSO finalised as an .m4a and sent as an
       ordinary voice note, so the reliable copy lands in the thread

A burst may legitimately begin at a DATA packet

START is sent once. So a lost packet at the head of a burst, or walking into range mid-sentence, would otherwise mean silence. Both Airhop and bitchat open the assembly with the default codec in that case. This is a small rule that makes the difference between "the feature is unreliable" and "you hear the second half of what someone said", which is what a walkie-talkie should do.

CANCELED exists so a user can abort mid-sentence and have the partial burst discarded rather than played.

The 210 byte rule

The single most important constant in this chapter

A voice packet's content is capped at 210 bytes (pttMaxBurstContentBytes) so that the encoded frame never enters the fragment scheduler.

Three consequences follow, and each one is a rule elsewhere in the codebase:

  1. Voice frames are never padded. Padding a roughly 309 byte burst would push it to the 512 byte block, past both the fragment frame budget and most negotiated MTUs, which is exactly the outcome the 210 byte budget exists to prevent. So padsBLEFrame deliberately excludes VOICE_FRAME.
  2. The fragment scheduler caps concurrent transfers, so a voice packet entering it would queue behind file fragments and starve, and would in turn starve file sends while somebody talks. Scenario M06 pins that talking while a file is in flight starves neither.
  3. DATA packets batch frames. Multiple encoded AAC frames, each length-prefixed, are packed into one packet up to the 210 byte budget, so the packet rate stays around 15 per second rather than one per frame.

This is also why live voice kept working during the era when every attachment silently failed: a burst never fragments, so the 557-byte fragment bug could not touch it.

Relaying live audio

Ordinary relay jitter is 10 to 220 ms. Three hops of that is up to 660 ms, which is nearly twice the entire playback buffer.

RuleValueReason
Relay jitter8 to 25 msThree hops is at most 75 ms, comfortably inside a 350 ms buffer.
TTL cap, sparse mesh7Voice should reach as far as text does when there is airtime for it.
TTL cap, dense mesh (degree 6+)5A sustained stream flooded to full depth in a busy graph would crowd out everything else.
Never gossipedReplaying stale audio is worthless and would cost airtime that live audio needs. There is no sync bit for 0x29.
Broadcast only for 0x29A DM burst uses NoisePayloadType 0x08 inside a session instead. A 0x29 that is not a broadcast is refused.

Fragments share the same time-critical policy for the same reason: both are streams where per-hop delay accumulates into a user-visible failure rather than into slowness.

The jitter buffer

Packets arriving over a mesh do not arrive evenly. Playing each one as it lands produces stuttering. The buffer trades a fixed delay for smooth output.

ConstantValueTrade
Buffer depth350 msToo small and every jitter spike is a gap. Too large and the conversation stops feeling live. 350 ms absorbs several hops of relay jitter, which is what a mesh actually produces, and is inherited from bitchat's push-to-talk design.

There are no delivery acknowledgements and no retransmission for individual frames. That is correct for live audio: by the time a retransmission arrived, the moment it belongs to has already played. Reliability is provided by the fallback voice note, which is sent as an ordinary file when the button is released.

Security and replay

AuthenticitySigned like a public message. An unsigned or forged frame is dropped before a decoder sees it. The audio path is the last place to be lenient about who sent something.
Confidentiality in a DMThe same payload inside NoisePayloadType 0x08, so it rides the Noise session.
Confidentiality in a roomNone, by design. A public burst is public, exactly like the text beside it.
Freshness30 seconds, much tighter than the general 2 minute window. Matches bitchat's pttPublicFrameMaxAgeSeconds.
Blocked sendersFiltered at the single dispatch chokepoint before the handler runs, so a blocked peer's burst costs one signature check and nothing else.
Own echoA burst from our own peer ID is dropped immediately.

The replay attack this closed

VOICE_FRAME originally had no freshness window at all, so a recorded burst could be replayed verbatim, later, at someone else. Imagine capturing "the police are at the north gate" and replaying it an hour later into a different crowd. It was a Medium severity finding, fixed with a 30 second bound plus a broadcast requirement, matching bitchat. Scenario M07 pins it: a recorded voice burst cannot be replayed later at someone else.

The timing fingerprint that remains

A steady ~15 packet per second cadence reveals that someone is speaking to someone, even under Noise encryption, because the packet rate is a signature of live audio. An observer with a radio learns that a conversation is happening and roughly how long each utterance was. Nothing in the design hides that, and nothing cheaply could: padding to a constant rate would mean transmitting continuously, which is a battery and airtime cost nobody would accept. bitchat documents the same observation.

Alternatives

OptionVerdict
Opus instead of AAC-LCTechnically better: superior quality per bit at these rates, designed for real-time speech, better packet loss concealment. Rejected because bitchat uses AAC-LC and live voice interoperability across all three clients is worth more, and because AAC has hardware acceleration everywhere.
Codec2 or similar at 1 to 3 kbpsWhat Meshtastic-class LoRa systems would need. Robotic but intelligible. Unnecessary here: 2 KiB/s is only 11 percent of one BLE link, so there is nothing to buy with the quality loss.
Full-duplex callingTwo simultaneous streams, plus echo cancellation, plus much tighter latency requirements. The mesh's per-hop jitter makes sub-200 ms round trips unrealistic beyond one hop. Push-to-talk is the honest shape for this transport.
Forward error correction on framesWould improve resilience to loss without retransmission. Costs bandwidth on every burst and cannot be adopted unilaterally without breaking bitchat compatibility.
VideoNot possible. The lowest usable video is an order of magnitude over the link budget, and the two same-platform fast paths cannot interoperate, so there is no cross-platform high-bandwidth link to build on. Packet type 0x30 VIDEO_FRAME was specified and retired for exactly this reason, and the retirement is recorded in the packet codec so it is not reintroduced.

Drills

  • Why is 210 bytes the most important number in live voice? Because it keeps a burst out of the fragment scheduler. The scheduler caps concurrent transfers, so a voice packet entering it would queue behind file fragments and starve, and would in turn starve file sends while somebody talks. It is also why voice frames are never padded: padding a roughly 309 byte burst to the 512 byte block would push it past both the fragment frame budget and most negotiated MTUs, which is exactly the outcome the budget exists to prevent.
  • Why does live voice get an 8 to 25 ms relay window instead of 10 to 220? Because the receiver plays out of a 350 ms jitter buffer, so relay delay is not a throughput question, it is the difference between hearing a sentence and hearing gaps. Three hops of the ordinary window is up to 660 ms, nearly twice the whole buffer. The tighter window makes three hops at most 75 ms. The TTL is also clamped to 5 in a dense mesh, because a sustained stream at full depth would crowd out everything else.
  • Why is START sent with the first captured frame rather than on button-down? Because a burst is only real once there is audio in it. Announcing one before the microphone has produced anything turns a failed capture, a denied permission or a busy audio session into a live bubble on the far side that never plays. It also means a receiver must handle a burst that begins at a DATA packet, which happens when START is lost or when someone walks into range mid-sentence; both clients open the assembly with the default codec in that case.
  • Why is there no retransmission of lost voice frames? Because by the time a retransmission arrived, the moment it belongs to has already played out of the jitter buffer. Live audio's correct failure mode is a small gap, not a delayed insert. Reliability is provided at a different layer: the same audio is finalised as an .m4a and sent as an ordinary voice note when the button is released, so anyone who missed the live version can still hear it.
  • What does an observer with a radio learn while someone is using push to talk? That someone is speaking, and roughly for how long. A steady 15 packet per second cadence is a signature of live audio, and it is visible even when the frames are Noise-encrypted in a DM. Nothing hides it, and nothing cheaply could: padding to a constant rate means transmitting continuously, which no phone battery would accept. The content and, in a DM, the participants stay protected. The fact of a conversation does not.
  • Why did live voice keep working during the period when no attachment ever arrived? Because a burst is capped at 210 bytes and never fragments, so the 557-byte over-budget fragment bug could not touch it. That is a good example of why the bug survived: the feature that looks most fragile, real-time audio over a mesh, was the one that was fine, while the boring one silently failed in both directions with no error at either end.
