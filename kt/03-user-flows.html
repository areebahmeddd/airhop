Why the generating screen is held for five seconds

Key generation is two calls to crypto.getRandomValues and two scalar multiplications. It finishes in single-digit milliseconds. A screen that flashes past communicates that nothing happened. The five second hold with staged text is doing a real job: it is the only moment in the product where the user learns that their identity is a key on this phone and nowhere else. That understanding is what makes the panic wipe and the missing backup make sense later.

The failure that must not happen

loadIdentity() returns null when there is no identity, and throws when the keychain is unreachable. Treating a throw as "no identity" would send a returning user through onboarding and generate a second identity, orphaning their first. keychain.ts documents this distinction at the function, and app.tsx branches on it: an error falls through to onboarding only after the possibility of a locked keychain has been considered.

Every launch after that

  1. Identity loads from the keychain. The item is stored AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY, so this read succeeds on a locked phone as long as it has been unlocked once since boot. That matters because iOS relaunches the app on a Bluetooth event, and that relaunch has to be able to join the mesh.
  2. The wipe marker is checked. If a previous panic wipe died partway through, it resumes here.
  3. MeshService is constructed and started. Radios come up through the reconciler, the announce timer starts at 4 seconds (isolated cadence), gossip sync starts on a 15 second interval, the courier store loads from disk, prekeys are replenished.
  4. Nostr is built if the internet toggle is on and the Tor gate allows it. Relays connect, the DM inbox subscribes with a 24 hour lookback, courier drops for today's and neighbouring days' tags subscribe.
  5. The wallet bootstraps. bootstrapWalletStorage() fetches the AES key from the keychain and opens the encrypted partition. If the keychain refuses, the wallet reports itself locked rather than opening unencrypted.
  6. Deferred work runs once past onboarding: notification permission, media retention sweep, nutzap watcher, Tor revalidation.

Notice what is not here. There is no pairing, no bonding, no PIN, no user prompt. GATT writes are open on the characteristic. Authentication is entirely at the application layer, by Ed25519 signature, which is why every check in step 2 above matters.

The direct-link rule

An announce still carrying TTL 7 came straight from its author, because every relay decrements. So it can bind a link to a peer. But TTL is a plaintext field an attacker sets freely. So the rule has a second half: a link binds to the first peer that announces directly on it, and a later claim from a different peer ID on the same link is treated as relayed. Without that second half, one hostile radio could mint unlimited "directly connected" identities, all of them immune to eviction because direct peers are the ones protected from trimming. That is scenario C04.

Why the origin TTL is randomised

A relay decrements TTL. So a packet arriving with the protocol maximum was authored by whoever just transmitted it. To a passive listener with a radio, that separates "this phone is nearby" from "this phone is talking". Drawing from 5 to 7 weakens the signal: two thirds of public messages become ambiguous. It does not remove it, because the top of the range is still unambiguous. Removing it entirely would need relays that sometimes decline to decrement, which is a coordinated protocol change across implementations.

This is applied to public messages only. Announces keep a fixed TTL 7 because the direct-link rule depends on it, and weakening that rule to gain a little unlinkability would reopen the Sybil vector above.

Sending a direct message

     │

     │              send it when msg3 goes out

     │                 payload = [0x01][PrivateMessagePacket TLV]
     │
     ├─ 3. Build the packet: HAS_RECIPIENT | SIGNED, ttl 7
     │
     ├─ 4. unicast(peerID, packet)
     │       a WiFi link to that peer?  use it
     │       a BLE link to that peer?   use it
     │       neither?                   FLOOD it, addressed to them
     │                                  (relays carry it, only they decrypt)
     │
     └─ 5. ALWAYS enqueue in the outbox, even on success.
           Nothing counts as delivered without an authenticated receipt.
              │
              ▼
        DELIVERED receipt arrives -> outbox entry resolved, tick shown
        READ receipt arrives      -> double tick

The bug this shape exists to prevent

A DM over an established session with a direct link used to return "sent" and never be queued. If the peer had restarted and discarded its session, it received nothing while the sender saw a tick. Now every mesh send is enqueued, matching bitchat's rule that nothing counts as delivered without an authenticated acknowledgement. All three receipt paths clear the entry, and a receipt arrives well inside the 15 to 30 second flush interval, so the cost is a queue entry that lives for a few seconds.

When the recipient is not reachable

This is the ladder that makes the app useful in the situations it was built for. It is evaluated in order and stops at the first rung that can carry the message.

RungConditionWhat happensWhat the user sees
1. Direct A Noise session exists. Encrypt and unicast over WiFi or BLE. If no direct link, flood it addressed to them, so it crosses up to 7 hops. Sent, then a tick on the receipt.
2. Nostr Their Nostr pubkey is known (from an announce or a saved contact) and a relay is live. Gift wrap the message (rumor 14, seal 13, wrap 1059) and publish to the DM relay set. Sent over the internet.
3. Courier At least one directly linked peer whose Noise key we hold. Seal once with Noise X to a one-time prekey if we have one, else to their static key. Hand the same bytes to up to 4 couriers, each with a spray budget of 4. Also park a copy on relays as kind 1401 if online. Carried by a friend.
4. Outbox only Nothing above was possible. Held locally for up to 7 days, retried on every reconnect and every 45 seconds. Queued. Not a tick, and not a failure.

The honesty rule matters as much as the ladder. "Carried by a friend" is returned only when a courier actually accepted the write onto its own link. A speculative flood at a peer several hops away resolves false, because there is nothing to acknowledge it. A relay drop is not a carrier either: nobody carried that copy and it never touched the mesh.

The 45 bytes that broke every attachment

The fragment budget is the whole encoded frame, not the payload. Spending 469 bytes on payload plus a 16 byte header, an 8 byte senderID and a 64 byte signature produces a 557 byte frame, 45 over the 512 byte ATT ceiling. Android writes without response and the stack truncates to MTU minus 3; iOS refuses the write. Either way the far side fails to decode, and nothing is reported at either end. Every fragment of every attachment was discarded before any handler saw it, in both directions, while live voice kept working because a burst is capped at 210 bytes and never fragments. This is the single best example in the codebase of why silent failures are the dangerous kind.

Holding the microphone

  press and hold
     │  audio session switches to record mode
     │  native capture starts: AAC-LC, 16 kHz, mono, 16 kbps
     ▼
  first encoded frame arrives (NOT on button-down)
     │  START packet: [burstID 8][seq=0][flags=0x01][codec=0x01]
     │  a burst is only real once there is audio in it
     ▼
  DATA packets, seq 1, 2, 3...
     │  [burstID][seq][flags=0x00][len u16][AAC frame][len][frame]...
     │  batched up to 210 bytes so a burst NEVER fragments
     │  ~15 packets per second, ~2 KiB/s
     │  signed like a public message
     ▼
  relays forward with 8 to 25 ms jitter (not the usual 10 to 220)
     │  TTL clamped to 5 in a dense mesh, 7 otherwise
     ▼
  receiver: VoicePlayer assembles, buffers 350 ms, then plays
     │  up to 8 concurrent bursts
     │  a burst may legitimately BEGIN at a DATA packet
     │    (walked into range mid-sentence, or START was lost)
     ▼
  release
     │  END packet: [totalDataPackets u16][durationMs u32]
     │  the same audio is also finalised as an .m4a and sent
     │  as an ordinary voice note, so the reliable copy lands in chat

Two rules make this work on a shared radio. Voice frames are never padded, because padding would push a 309 byte burst to 512 and into the fragment scheduler. And voice frames are never gossiped, because replaying stale audio is worthless and would cost airtime that live audio needs.

Teleport is the same flow with the geohash entered by hand instead of derived from a fix. Nobody in Bluetooth range is in that cell, so it runs over Nostr only, and its messages carry a t=teleport tag so other clients list the sender as teleported rather than nearby.

Paying somebody

Four entry points (the DM attach menu, a contact sheet, a mesh peer sheet, and the wallet Zap button) all call one function, payPerson in src/services/payment-router.ts, so they cannot disagree about what a payment does.

RungRailWhenFinalReclaimable
1RadioA direct BLE or WiFi link exists.NoYes
2NutzapNo radio link, their Nostr key is known, they published a kind 10019, and we hold value at a mint they accept.YesNo
3Token in a DMAnything else. sendDm then picks Nostr, courier or the outbox.NoYes
4ManualNothing carried it. The token string is returned for the user to hand over.NoYes

Radio comes first so that someone standing in front of you does not wait on a mint round trip, and so the in-person case works with no internet on either phone. Rung 2 beats rung 3 when available, because P2PK-locked proofs are the recipient's whether or not they ever come online, whereas a bearer token is only theirs once claimed.

Two invariants hold across the whole ladder:

  • One commitment per payment. Proofs are either reserved (rungs 1, 3, 4) or P2PK-locked (rung 2), never both. A rung that fails before committing falls through; a rung that fails after committing retries delivery only.
  • Finality is reported, never inferred. PayResult.final is true for rung 2 alone, and every confirmation names the rail that carried the money and says whether Pending will offer it back.

Adding and verifying a contact

Two things are tracked separately, and confusing them is a security bug rather than a UX detail.

FieldQuestion it answersValues
sourceHow did the keys arrive on this device?qr, link, manual
verificationHas a human confirmed these are the right keys?verified or not

They are independent. A contact learned from a link can be verified later on a phone call. Two routes exist:

  1. Scan their QR in person. The camera witnesses the exchange. This is the only route allowed to re-pin keys already bound to a peer ID, because the physical presence is the evidence. The card carries both public keys, and the peer ID is checked against SHA-256(noisePub)[0:16] before anything is trusted.
  2. Compare a safety number. Six words derived from both parties' Noise and signing keys, identical on both phones, read to each other over a channel they trust: a call, a radio, another app. This confirms keys already held rather than importing any, so it grants no re-pinning power and needs none. It is what lets somebody you can only reach by voice be verified at all.

An airhop:// link records source: "link" and is never marked verified. That distinction was a real security finding: a linked card used to mint a "Verified" contact, which would let anyone who could get you to tap a link impersonate someone.

The safety number covers both keys deliberately. A peer ID is SHA-256 of the Noise key alone, so reading a peer ID aloud would not catch the attack that matters: a forged card that keeps the victim's real peer ID and Noise key while substituting the attacker's signing key.

The panic wipe

One tap on the Profile screen opens a confirmation. Three quick taps skip it entirely. The sequence is ordered, time-boxed and resumable. 

  0.  beginPanicWipe()            write the marker FIRST. Everything below is
                                  a sequence, not a transaction, and the process
                                  can die anywhere in it.
  0a. bumpWipeGeneration()        invalidate startup work still in flight
  0b. stopNutzapWatcher()         it holds this identity's Nostr key in a closure
      setNutzapRebinder(null)     and forget HOW to rebuild it

                                  a plaintext snapshot of every thread on disk

  1.  wipeAllSecrets()            walk the keychain registry. Every item is
      timeout 5 s                 attempted even after one fails. Guarded AND

                                  reject, it never answers.
                                  -> keysDestroyed: true | false

  2.  clearAll() on 15 MMKV partitions
      wipeWalletStorage()         deleteMMKV, not clearAll: the file cannot be
                                  reopened without its key and step 1 destroyed
                                  the key

  3.  reset every zustand store in memory, including the transport health flags
      (torActive false, bridgeActive false, clockSkewed false: a security
       indicator that over-claims is worse than none)

  4.  dismissAllNotifications()   each carries a sender name and a preview,
      timeout 2 s                 and they outlive the process

  5.  teardownTorState()          then NativeAirhopTor.wipeTorState():
      timeout 2 s                 stop Arti and delete its directory. It sits
                                  under Application Support, not the cache, and
                                  holds a cached consensus, chosen guard nodes
                                  and timestamps: evidence that this device used
                                  Tor and roughly when.

  6.  clearLocationCache()        module state with a 5 minute TTL

  7.  wipeCacheDirectory()        the WHOLE cache, not just airhop_ prefixed
                                  files. A sent document, a sent video, a small
                                  image sent unmodified and the saved QR card
                                  all live under other names or in the pickers'
                                  own subdirectories, and every one used to
                                  survive.

  8.  endPanicWipe()              NOT in a finally, and NOT conditional on
                                  keysDestroyed. A throw on the way here means
                                  it did not finish, and the marker surviving is
                                  what makes the next launch pick it up.

  return { keysDestroyed }

Why the ordering is what it is

The notification tray and Tor moved to last on purpose. Both are slow: dismissing the shade is a native round trip, and wiping Arti polls for its process to exit before deleting a directory tree. For a gesture whose threat model is a phone being taken, running those first would spend the seconds that matter on a notification shade while the keys and fifteen message partitions were still on disk.

keysDestroyed is the one thing reported to the user, because a locked keychain on a booted-but-unlocked device is exactly the seizure case, and "your keys are gone" must never be claimed falsely. If it comes back false, the profile screen says so, a banner appears, and the next launch retries the delete through sweepOrphanedSecrets.

After the wipe the app is left in a first-run state and drops to onboarding. The process is not terminated and the sandbox is not otherwise touched.

Drills

  • A user says "it says sent but my friend never got it". Walk through the possibilities. Ask what the indicator actually said. "Sent" with no tick means it left the radio but no receipt came back, which is normal for a multi-hop send and is why the outbox keeps retrying. "Carried by a friend" means a courier accepted it, which means delivery waits on that person physically meeting the recipient. "Queued" means nothing carried it. If a tick appeared, a DELIVERED receipt was authenticated, so it did arrive. The one historical bug in this area, a mesh DM reported sent and never queued after the peer had discarded its session, is fixed by always enqueueing.
  • Why does the location channel publish to relays near the cell centre rather than near the user? Because publisher and subscriber must independently arrive at the same relay set. Two people in opposite corners of one city cell would otherwise pick different nearest relays, publish to relays the other never subscribed to, and never see each other despite being in the same channel. Ties in the sort break on URL rather than insertion order for the same reason, since many relays in the directory share coordinates.
  • The panic wipe is interrupted by the phone being switched off. What happens on next boot? The wipe marker is still set, because endPanicWipe was never reached. The next launch reads it and resumes the sequence. Separately, if the keychain refused the delete because the phone had booted but not been unlocked, sweepOrphanedSecrets retries at the next launch, which is past that unlock, where the same delete usually just works. Its marker partition is deliberately excluded from the list of partitions the wipe clears, since clearing it halfway through would destroy the only thing that could finish the job.
  • Why does a photo go out at 25 ms per fragment rather than as fast as possible? Because without the delay the radio drops fragments and the transfer never completes. It is a Bluetooth requirement, not a protocol one: LAN transport needs no such pacing. A channel attachment uses 30 ms instead of 25, because each broadcast fragment requires one radio write per connected peer, so airtime cost grows with room size.
