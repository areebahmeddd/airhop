In plain words

Explain it to a ten year old

Imagine a busy post office. There are lots of specialists: someone who weighs parcels, someone who writes addresses, someone who decides which van a parcel goes on, someone who keeps the list of customers. None of them talks to the others directly. Instead there is one desk in the middle where every parcel passes through, and the person at that desk knows all the specialists and walks the parcel from one to the next. The mesh service is that desk. It does very little work of its own. It knows who does what.

What a composition root is

A composition root is the one place in a program where all the independent pieces are built and wired to each other. Everything else can then be written as if it has no idea the others exist.

The pieces in Airhop are genuinely independent, and each is tested on its own: the packet codec knows nothing about radios, the flood router knows nothing about encryption, the courier store knows nothing about the screen. That independence is what makes them testable. But somebody has to hold the radio handle, the identity, the peer registry, the session table and the message stores all at once, because almost every real operation touches several of them in one step.

Why it is not split

Every handler needs three or four of the owned objects simultaneously. Splitting the file leaves exactly two options, and both are worse. Either you pass a large context object into every handler, which is the same coupling with more typing, or the subsystems start importing each other, which is a circular import graph. The logic that can stand alone already does: it lives under src/core/mesh/* and that is where the unit tests are. What is left in the service is wiring.

The honest counterpoint

This is a defensible shape, not an unimprovable one. 6,349 lines is past the point where a reader can hold the whole file in their head, and it is the file most in need of a second pass. The engineering review names it explicitly. The realistic improvement is extracting cohesive handler groups that share a narrow slice of state (voice, the Nostr bridge, the courier path) rather than a mechanical split by line count.

Lifecycle: five verbs

There is exactly one instance per process, held at module scope in _instance. Five functions move it between states, and the distinctions between them are not cosmetic. 

  initMeshService(identity, nickname)          App.tsx, once, after
    │                                          identity is loaded
    ├─ _instance?.dispose()   <-- not stop(). The outgoing instance
    │                             holds the OLD identity's private keys
    │                             and must not fire against the new one
    ├─ _instance = new MeshService(identity)
    └─ _instance.start(nickname)


  start(nickname)                              also: presence Online
    ├─ running = true
    ├─ clearRadioStopGrace()   cancels a teardown scheduled <150 ms ago
    ├─ radio.start()           hands the radios to the RECONCILER, not
    │                          three fire-and-forget native calls
    ├─ announceManager timer
    ├─ gossip + requestSync
    └─ subscribe to stores


  stop()                                       presence Away, panic wipe
    ├─ running = false
    ├─ radio.suspend()         records the decision; touches no radio
    ├─ sendLeave()             the farewell has to reach the wire
    ├─ closeVoice()            ends open bursts with END packets
    └─ setTimeout(150ms) -> radio teardown
                               grace so the LEAVE actually leaves


  dispose()                                    replacement, panic wipe
    ├─ stop()
    ├─ clearRadioStopGrace()   drop the courtesy; apply teardown NOW
    ├─ radio.stop(); radio.dispose()
    └─ wifi.dispose()          stops the retry ladder, so a pending
                               attach cannot reopen a socket under an
                               identity that no longer exists


  destroyMeshService()                         panic wipe only
    ├─ _instance?.dispose()
    └─ _instance = null        releases the last reference to the
                               identity's private key bytes

Three ordering bugs this shape exists to prevent

The 150 ms grace. radio.stop() reconciles on the same tick and reaches the native "stop advertising" call before it returns. Taking the radios down first meant the LEAVE and the voice END were handed to a transport already told to shut. A peer going Away vanished from everyone else's list by 60 second timeout instead of instantly, and an open voice burst ended in a stall.

suspend() before the farewell. It records "we are going offline" without touching hardware, so nothing can restart the radios behind a user who just chose to go away. That was the real reason the stop used to come first, and it is preserved without the cost.

closeVoice() in stop(). This was missing entirely. Teardown took down the radios, the timers, the subscriptions and the Nostr pool, and left the microphone open with every inbound voice session still holding its jitter buffer. Going Away, or triple-tapping to panic wipe, left a stranger's audio coming out of the speaker of a phone whose mesh had just been stopped.

Why destroyMeshService exists at all

stop() takes the radios down but leaves the module holding a service whose identity field still contains the wiped identity's private keys. JavaScript gives no way to zero those bytes. Releasing the last reference is the strongest thing available, and it also guarantees the next launch builds a mesh from the new identity rather than finding a stale one. See chapter 35 for the rest of the wipe.

One packet, end to end

Every byte that arrives from any radio enters at one function, handleRaw(linkID, dataBase64). Following it once is the fastest way to understand the file. 

  native BLE / WiFi Aware
        │  base64 string + linkID
        ▼
  handleRaw(linkID, data)
        │
        ├─ base64ToBytes            malformed -> return, silently
        ├─ bytesReceived += n       counters for the diagnostics screen
        ├─ decodePacket(bytes)      bad header/length -> return
        │
        ├─ isFreshOrSolicited()     +/- 2 min window, unless this packet
        │                           answers something we asked for
        │                           (see chapter 11)
        │
        ├─ type === FRAGMENT ?
        │     ├─ addressed to us -> do NOT relay (the whole file would
        │     │                     be relayed back at the receiver)
        │     ├─ otherwise       -> flood-route it onward
        │     └─ feed the assembler; a completed inner packet
        │        re-enters at routePacket() with no second flood
        │
        ▼
  routePacket(packet, linkID)
        │
        ├─ dedup: seen this packet ID in the last 5 min? drop
        ├─ for us, or broadcast?    -> dispatch (below)
        ├─ relayable? ttl > 0       -> floodRouter.schedule(jitter)
        └─ neither                  -> drop
        │
        ▼
  switch (packet.type)             19 cases, table below
        │
        ▼
  handler                          decrypts, verifies, writes a store
        │
        ▼
  zustand store  ->  React re-renders  ->  the message appears

The important property of this path is that relaying and consuming are independent. A broadcast packet is both dispatched to our own handler and scheduled for relay. A packet addressed to somebody else is relayed without ever being decrypted, which is what makes the middle of the mesh blind.

Sending, and the transport ladder

Outbound is the mirror image, and the service is where the choice of rail is made. A direct message is the richest case: 

  sendDm(peerID, text)
        │
        ├─ enqueue in the outbox FIRST, always
        │    "the write left the radio" is not delivery, and a peer that
        │    restarted and dropped its session receives nothing while
        │    the sender sees a tick
        │
        ├─ do we hold a Double Ratchet state for them?
        │     yes -> ratchetEncrypt -> DR_ENCRYPTED
        │     no  -> completed Noise session? -> NOISE_ENCRYPTED
        │            neither -> start an XX handshake, queue the message
        │
        ├─ pick a rail, in order of cost:
        │     1. links.linkFor(peerID)   the best link this peer has,
        │                                in SEND_PREFERENCE order:
        │                                wifi, then lan, then ble
        │     2. BLE flood               they may be several hops away
        │     4. Nostr gift wrap      we hold their npub and have internet
        │     5. courier envelope     nobody can reach them right now,
        │                             so hand a sealed copy to strangers
        │
        └─ the outbox entry clears only on an AUTHENTICATED receipt

Rungs 4 and 5 are what make Airhop different from a plain Bluetooth chat app. Chapter 13 covers the courier, chapter 24 the Nostr path, chapter 28 how the ladder is evaluated in practice.

Control

retryRadios() is worth singling out. It is called after any permission grant, from startup and from the Permissions screen alike. A grant is not the same as a working radio: Bluetooth may still be off, and on Android the stack honours a fresh grant a moment after the app can see it. The radio controller is the only thing that knows how to tell those apart, so both callers nudge it rather than deciding for themselves. Chapter 37 covers the permission side.

What it deliberately does not do

Three rules that keep the file from growing without limit

No cryptography of its own. Every primitive comes from src/core/crypto. The service composes calls; it never implements a construction. That is why the crypto is testable without a phone.

No presentation. It writes to zustand stores and never touches a component. This is what lets the entire protocol run in Jest with no renderer, which is how the multi-device simulations in chapter 44 are possible at all.

No native calls outside the two controllers. BLE goes through RadioController, WiFi through WiFiController. Both are reconcilers: you tell them the state you want, they read the device and converge on it with backoff. Direct native calls were the old shape and produced two dead radios behind a confident UI.

One boundary is worth stating from the other direction: addVerifiedContact seeds the peer registry but deliberately does not touch the peer store. Being a contact is not evidence of being nearby, and the Mesh tab must keep meaning "in range right now". Chapter 14 is the long version of that distinction.

What breaks it

  • A refused GATT write treated as a disconnect. This was a real bug with a wide blast radius. The stack refuses writes for ordinary reasons: its queue is full, the GATT server is mid-setup, another transfer has the link busy. Deleting the link from the link registry is unrecoverable, because nothing re-adds a link except a fresh connect event, which never comes for a link that stayed up. One transient refusal removed a healthy neighbour permanently, so the phone reported zero links and the composer marked every later message failed, on a working radio next to a listening peer. Only the disconnect event may tear a link down.
  • A subscription that outlives the instance. Every *Unsub handle exists for this. A callback firing against a disposed service reaches a wiped identity.
  • A panic wipe landing in an await gap. Startup is full of awaits, and a wipe can happen in any of them. The guard is the wipe generation counter: capture it, re-check after every await, and abandon the work if it changed. Without it, startup resurrects the identity the wipe destroyed.
  • Two instances. Only possible through a bug in the init path, and it would produce two advertisers under one peer ID, duplicate announces, and a session table split across objects. initMeshService disposes the outgoing instance before constructing the new one specifically to make this impossible.

If you removed it

There would be no application. Every engine underneath is real and tested, and not one of them can send a message on its own: the codec has no radio, the router has no keys, the courier store has no transport. The wiring is not incidental to the system, it is the system. The realistic version of this question is "what if it were split", and the answer is in the review chapter: a worthwhile refactor, low risk if done by cohesive handler group, and not a correctness problem today.

Alternatives

ShapeHow it would lookWhy not here
Dependency injection container A registry resolves engines by token; handlers declare what they need Moves the wiring into a runtime graph that no longer type-checks statically. In a codebase whose main safety property is exhaustive TypeScript, that is a real loss for an ergonomic gain.
Event bus Engines publish and subscribe; nothing holds anything Every ordering bug in the lifecycle section becomes invisible. "The LEAVE must reach the wire before the radios come down" is not expressible as two independent subscribers.
Actor model Each engine owns a mailbox and its own state; the service becomes a supervisor The right answer at a much larger scale, and how a server-side version of this would be built. On one phone, with one JavaScript thread, it buys isolation nobody needs and costs a message-passing layer around every field read.
Split by line count Six files of a thousand lines each Produces either a giant context parameter or circular imports, with no reduction in coupling. Splitting by cohesive state is the version worth doing.

Drills

  • Defend a 6,349 line file to a reviewer who has already decided it is technical debt. Agree with the discomfort and then separate two claims. The claim "this file is too long to read comfortably" is true and is recorded as a review finding. The claim "this length is caused by mixing responsibilities" is false: the responsibilities are already separated into eleven engines under src/core/mesh, each independently unit tested without a phone. What remains is wiring, and wiring is exactly the thing that cannot be split without either passing a large context object into every handler or creating circular imports. The improvement worth making is extracting cohesive groups that share a narrow slice of state, such as voice or the Nostr bridge, not a mechanical split by line count.
  • Why does initMeshService call dispose() on the outgoing instance rather than stop()? Because it is a replacement, not a pause. stop() takes the radios down but leaves every timer's teardown on a 150 ms grace, leaves the WiFi retry ladder running, and leaves the object holding the old identity's private keys on its identity field. Any of those firing against the new instance is a bug, and the WiFi one is a security bug: a pending attach could reopen a socket under an identity that no longer exists. dispose() drops the grace, stops the ladder, and releases the radio.
  • A message is sent to a peer with a live direct link and an established session, and the write returns without error. Why is it still queued? Because a successful write means the bytes left this radio, which is not delivery. The far side may have restarted and discarded its session, in which case the packet is silently undecryptable while the sender shows a tick. Nothing counts as delivered without an authenticated acknowledgement, which is also bitchat's rule. All three receipt paths clear the entry and a receipt arrives well inside the flush interval, so the cost is a queue entry that lives a few seconds.
  • Trace an inbound fragment belonging to a file addressed to this device. Where does it get relayed? Nowhere. handleRaw checks the recipient before touching the assembler, and a fragment addressed to us is fed straight in without a relay. Fragments carry their parent's recipient ID, so a DM attachment is directed at exactly one device; relaying anyway meant the receiver rebroadcast every fragment of a file it was itself the destination for, which for a large file is the entire transfer duplicated onto the air. Once the assembly completes, the inner packet re-enters at routePacket and is never flooded a second time.
  • Why does the service write to zustand stores rather than calling into components? Because it makes the entire protocol runnable with no renderer. The multi-device simulations construct several isolated module registries in one Jest process, each with its own mesh service, wire them to a fake radio fabric and a single fake clock, and assert on store contents. That is only possible because nothing in the send or receive path touches React. It is also what keeps the presentation layer free of protocol logic, so a screen cannot accidentally change routing behaviour.
  • Why must a refused BLE write never remove the link? Because refusal and disconnection are different events with different meanings, and only one of them is recoverable. Links are added to the link registry exclusively by a native connect event, so a link removed while it is still physically up is never re-added, and the phone believes it has no neighbours. The observed failure was one phone panic-wiping and two bystanders silently losing the ability to talk to each other. Refusals are ordinary and transient: a full queue, a busy transfer, a GATT server mid-setup. The disconnect event owns teardown, and the fragment relay path already followed that rule.
