Storage and the panic wipe

Every guarantee above this layer assumes the device holds its secrets and can destroy them on demand. This chapter is where those two assumptions are actually implemented, and where they stop being true.

In plain words

Explain it to a ten year old

Your phone keeps three kinds of thing. The most important keys go into a special locked drawer the phone's own hardware guards. Your messages go in a normal box the phone encrypts when it is switched off. Photos go in a folder that gets emptied every week. If you tap the panic button three times, all three are destroyed in about a second, in a careful order, and the app tells you honestly if the locked drawer refused to open.

Three tiers of storage

  ┌──────────────────────────────────────────────────────────────┐
  │ TIER 1   OS KEYCHAIN / KEYSTORE                              │
  │          hardware-backed on modern devices                    │
  │          4 items, all listed in one registry                  │
  │  · identity (Noise + Ed25519 private keys)                    │
  │  · wallet MMKV encryption key                                 │
  │  · wallet P2PK private key                                    │
  │  · wallet recovery phrase, if enabled                         │
  ├──────────────────────────────────────────────────────────────┤
  │ TIER 2   MMKV PARTITIONS                                      │
  │          memory-mapped key-value files, JSI-bound             │
  │          15 partitions + 1 encrypted wallet partition         │
  │  · messages, contacts, outbox, groups, board, settings,       │
  │    courier bag, prekeys, activity, bookmarks, place names     │
  ├──────────────────────────────────────────────────────────────┤
  │ TIER 3   THE CACHE DIRECTORY                                  │
  │          ordinary files on disk                               │
  │  · received attachments, sent documents and videos,           │
  │    small images sent unmodified, the saved QR card            │
  └──────────────────────────────────────────────────────────────┘

A fourth thing exists and is deliberately not persisted: live Noise sessions and the peer registry. Those are in-memory only, so a restart discards them and every session re-handshakes. That is a cost paid on purpose.

The OS keychain

src/core/crypto/keychain.ts is the only module in the entire codebase that calls expo-secure-store. Everything else goes through it. 

  export const KEYCHAIN_ITEMS = {
    identity:            "airhop.identity.v1",
    walletEncryptionKey: "airhop.wallet.mmkvKey.v1",
    walletP2pkKey:       "airhop.wallet.p2pk.v1",
    walletRecoveryPhrase:"airhop.wallet.recovery.v1",
  } as const;

  export type KeychainItem = (typeof KEYCHAIN_ITEMS)[keyof typeof KEYCHAIN_ITEMS];

Why this registry is a security control, not a style choice

expo-secure-store has no clear-all. So the panic wipe deletes the items listed here and nothing else. A secret written under an ad-hoc key would survive a wipe, silently, forever.

The exported type is a union of exactly these four names, so a caller cannot write a secret outside the registry: it is a compile error. That turns "remember to add it to the wipe list" into something the type system enforces.

One distinction the module documents at the function signature and that callers must respect: readSecret returns null when absent and throws when the keychain is unreachable. Treating a throw as "no identity" sends a returning user back through onboarding and generates a second identity, orphaning their first.

wipeAllSecrets attempts every item even after one fails, because a keychain that refuses one value may release the next, and throws only if something was left behind, so the caller can report keysDestroyed: false rather than overclaiming.

The accessibility class decision

iOS keychain items carry an accessibility class deciding when they can be read. Airhop uses AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY rather than the WHEN_UNLOCKED default, and both halves matter.

HalfReasonCost
AFTER_FIRST_UNLOCK iOS relaunches the app on a Bluetooth event after termination, and that relaunch must load the identity to join the mesh. WHEN_UNLOCKED refuses the read on a locked phone, so a phone in a pocket would silently stop being a mesh node. The item is readable while the phone is locked, as long as it has been unlocked once since boot.
THIS_DEVICE_ONLY The default class is included in encrypted iCloud and iTunes backups and restorable onto another device. An identity that can be restored elsewhere is an identity that can be seized from a backup. No transfer to a new phone. There is no account recovery, by design.

The residual: the keychain is unreadable between boot and the first unlock. That window is exactly the seizure case, which is why the panic wipe reports whether it succeeded and why the next launch retries.

MMKV partitions

MMKV is a memory-mapped key-value store with a JSI binding, so reads are synchronous and fast enough to call during a render. That is why it is used instead of AsyncStorage: a chat list that has to await its own data cannot render in one pass.

One handle per partition, and this is not negotiable

src/store/mmkv.ts is the only place a partition is opened, and it memoizes by id. A second handle on the same file is fatal: MMKV maps the file into memory, and two mappings can produce writes that clobber each other. It also matters for the wipe, which walks a list of partition ids and clears each through its single handle.

Fifteen partitions are cleared by the panic wipe:

PartitionWhy a wipe must reach it
chat-storeEvery message.
outbox-storeUndelivered plaintext DMs awaiting a route. Exactly the content a wipe exists to destroy.
contacts-storeWho this identity knows, plus their public keys. The social graph.
activity-storeThe notification feed: message previews and sender names. Plaintext content.
blocked-storeWho this identity has blocked, which is tied to its relationships.
board-storeSigned public posts tied to this identity's signing key.
prekey-storeOur one-time prekey private keys and peers' bundles. Identity-linked key material.
courier-storeSealed envelopes carried for other people. Unreadable here, but a bag of a neighbour's mail is evidence this phone stood next to whoever deposited it, and a recipient tag names who it is for to anyone who heard that person announce.
group-store, group-invite-outboxPrivate-group epoch keys, which decrypt every group message, and signed states owed to unreachable members carrying the same keys.
geohash-bookmarks-storeCells the user saved. A bookmark reveals a place they care about.
place-names-storeGeocoded names for cells the user opened, which trace where they have been active.
transfer-storeIn-flight attachment progress.
settings-storeOnly device preferences, but a wipe must leave a clean first-run state.

One partition is deliberately excluded

The wipe marker's own partition must never appear in that list. It records that a wipe is running, so clearing it halfway through destroys the only thing that could finish the job after a crash.

peer-store is also absent, but for a different reason: it has no MMKV persistence at all, so it resets when the process restarts.

The encrypted wallet partition

Cashu proofs are bearer instruments, so this is the one partition opened with an explicit encryption key. 

  FIRST RUN
    generate 24 random bytes
    base64 encode -> exactly 32 ASCII characters, which is what AES-256 takes
    store in the keychain as airhop.wallet.mmkvKey.v1

  EVERY LAUNCH
    bootstrapWalletStorage()
      await the keychain read
      open the MMKV partition with encryptionKey
      EVERY zustand persist read and write awaits that promise

    keychain refuses?
      -> the wallet reports itself LOCKED
      -> it does NOT fall back to opening unencrypted
      -> no proof ever reaches plaintext disk

  PANIC WIPE
    deleteMMKV, not clearAll.
    The file cannot be reopened without its key, and the same wipe
    destroys the key.

Because the key arrives asynchronously, the store cannot exist at module scope. That is an unusual shape for a zustand store and it is forced by the requirement, not chosen.

The wipe also has to reset the storage bootstrap itself, not just the service. deleteMMKV unlinks the file, but the JavaScript handle and the resolved ready promise are module scope and survive it. Three things went wrong without that reset: the wallet reported itself unlocked and hydrated against a partition that no longer existed; any later write recreated the file through the stale handle, still holding an AES key whose keychain copy had just been destroyed, leaving ciphertext no future launch could ever open; and re-onboarding in the same process wrote the new identity's proofs under that dead key.

Names are addresses

Three families of string are addresses rather than labels. Renaming one does not move data, it orphans it.

FamilyShapeCost of renaming
Keychain itemairhop.<domain>.<thing>.v1The secret becomes unreachable and survives the panic wipe.
HKDF domain separatorairhop-<purpose>-v1Every key derived from it changes, so old and new builds cannot decrypt each other.
MMKV partition id<name>-storeThe next launch opens a file that has never been written, while the old data sits on disk unreferenced and unwipeable.

Three names predate the convention and stay: airhop-chat, wallet-state (beside the wallet-store partition) and activity. No store declares a migrate function, so changing any of these safely means shipping a per-store migration that reads the old name and writes the new one, at least one release before the old name is dropped.

The panic wipe, step by step

Triggered from the Profile screen. One tap opens a confirmation sheet; three quick taps skip it and wipe immediately.

StepActionTimeoutWhy here
0beginPanicWipe()Record the intent before anything is destroyed. Everything below is a sequence, not a transaction, and the process can die anywhere in it.
0abumpWipeGeneration()Invalidates startup work still in flight. Stopping the nutzap watcher only reaches one already installed; a startup mid-publish would install its replacement afterwards.
0bstopNutzapWatcher(), setNutzapRebinder(null)The watcher holds this identity's Nostr private key in a closure and a relay subscription under its pubkey. And forgetting how to rebuild it matters, because the mesh calls the rebinder on every transport rebuild.
0cdropPendingChatPersistence()A throttled write holds a plaintext snapshot of every thread and is armed to put it back on disk. Cancelled rather than flushed.
1wipeAllSecrets()5 sGuarded and time-boxed: the try/catch covers a keychain that refuses, the deadline one that goes quiet. A Keystore that stalls does not reject, it never answers.

Why the tray and Tor moved to the end

Both are slow: dismissing the shade is a native round trip, and wiping Arti polls for its process to exit before deleting a directory tree. For a gesture whose threat model is a phone being taken, running them first spends the seconds that matter on the notification shade and a Tor consensus cache while the keys and fifteen message partitions are still on disk. Neither depends on the keys existing, so both belong after the data is gone.

Why the cache sweep is the whole directory

The wipe used to clear only files prefixed airhop_. A sent document, a sent video, an image small enough to send unmodified and the saved QR card all live under other names or in the pickers' own subdirectories, and every one of them survived every wipe. Prefix-based cleanup is a whitelist, and a whitelist of things to destroy is the wrong way round.

Resumability, and the two markers

Two independent mechanisms make a wipe survive a process death.

The wipe marker

Written before anything is destroyed, cleared only when the whole sequence completes. Its partition is excluded from the clear list. On the next launch, a surviving marker means the sequence is resumed.

The orphan sweeper

sweepOrphanedSecrets(), called at launch on the branch where there is definitively no identity. It enforces the invariant that no identity means no secrets, and reports whether anything defied it.

The sweeper is what turns a failed panic wipe from permanent into a retry, and its reasoning is worth reading in full because it is subtle:

  • The wipe most likely to fail is the one that matters. AFTER_FIRST_UNLOCK refuses reads and deletes on a phone that has booted but not been unlocked, which is exactly the seizure the gesture exists for. Without a retry the keys stay for good. The next launch is past that unlock, where the same delete usually just works.
  • It is not framed as "retry the wipe", and that is the point. A secret with no identity to own it has no owner and no reader, so deleting it is unconditionally correct. That means no persisted "a wipe was attempted here" flag is needed, and a wipe leaves no trace of having been attempted.
  • The identity item is deliberately not swept, and the reason is a race rather than a scruple. The caller runs this without waiting, on its way to showing the welcome screen, and the very next thing onboarding does is write an identity. A delete still in flight when that lands would destroy the key the user just created, leaving an app that cannot start. Nothing is lost by skipping it, since the caller only reaches here because no identity was found.
  • It reports a leftover only when positively confirmed: the delete was refused and a subsequent read still hands back a value. A keychain that refuses both is unreadable rather than dirty, and claiming otherwise would put an alarm about data at rest in front of someone whose device is merely locked.

The one claim it must not make falsely

  interface PanicWipeResult {
    keysDestroyed: boolean;
  }

Every step of the wipe is best effort except this one. The reason is stated directly in the source: "your keys are gone" must never be claimed falsely. A locked keychain on a booted-but-unlocked device is exactly the seizure case.

So the result carries one boolean, the Profile screen says so when the OS refused, a wipeIncomplete banner appears, and the next launch retries. Everything else, the notifications, Tor, the cache, fails silently because its failure changes nothing the user needs to decide about.

This is also why the keychain step continues past a failure rather than abandoning the rest. A throw there used to abandon everything below: all fifteen MMKV partitions, every store, the wallet file and the media cache stayed on disk, and the caller surfaced nothing, so the user got a confirmation haptic and a dead app over completely intact data.

What a wipe cannot do

LimitDetail
Flash memory does not overwriteDeleting a file on a flash-based device unlinks it. The physical blocks are reclaimed by the controller's wear levelling on its own schedule, and there is no way to force it from an app. What protects the residue is full-disk encryption: the OS holds the file key, and modern devices delete it, which is why the keychain step matters more than the file deletion does.
Copies outside the sandboxA photo saved to the gallery, a token copied to the clipboard, a screenshot, a shared file. All outside Airhop's reach.
The app switcher snapshotiOS and Android capture a screenshot of the app when it backgrounds. Airhop does not cover this, and it is listed in the threat model.
The other side of the conversationWiping your device does not wipe theirs. There is no remote delete, and there deliberately never will be, because a remote delete mechanism is also a remote censorship mechanism.
What is already on the networkA gift-wrapped DM sitting on a relay, a courier envelope in somebody's bag, a public message in the mesh's gossip cache. Ephemeral kinds and 24-hour expiries bound it; nothing revokes it.
A compromised OSAll guarantees are void. Listed as out of scope.
Zeroing memory reliablyJavaScript arrays are filled with zeros where possible, but the engine may have copied them during garbage collection and there is no way to reach those copies. An unavoidable limitation of doing cryptography in a managed runtime.

Drills

  • Why is the keychain item registry a union type rather than just a list? Because expo-secure-store has no clear-all, so the panic wipe can only delete items it knows about. A secret written under an ad-hoc key would survive a wipe silently and forever. Making KeychainItem a union of exactly the registered names turns "remember to add it to the wipe list" into a compile error rather than a review comment.
  • Why AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY and not the default? AFTER_FIRST_UNLOCK because iOS relaunches the app on a Bluetooth event, and that relaunch must load the identity to join the mesh; the WHEN_UNLOCKED default refuses that read on a locked phone, so a phone in a pocket would silently stop being a mesh node. THIS_DEVICE_ONLY because the default class is included in encrypted iCloud and iTunes backups and restorable onto another device, and an identity restorable elsewhere is an identity seizable from a backup. The cost is that the keychain is unreadable between boot and the first unlock.
  • Why does the panic wipe write a marker before it starts? Because the wipe is a sequence, not a transaction, and the process can die anywhere in it: the OS can kill the app, the battery can go, the user can force-quit. A marker written first and cleared only on completion means the next launch can tell that a wipe was interrupted and resume it. That is also why the marker's own partition is excluded from the list of partitions the wipe clears, and why endPanicWipe is not in a finally.
  • Why is keysDestroyed the only thing reported? Because it is the only claim the user must not be lied to about. Failing to dismiss notifications or delete the Tor directory changes nothing they need to decide. "Your keys are gone" changes everything, and the case where it fails is precisely the seizure case: a booted but never unlocked phone whose keychain refuses. So the result carries that one boolean, the screen says so, a banner appears, and the next launch retries through the orphan sweeper.
  • Why does the orphan sweeper skip the identity item? A race. The caller runs it without awaiting, on its way to the welcome screen, and the very next thing onboarding does is write an identity. A delete still in flight when that write lands would destroy the key the user just created, leaving an app that cannot start, which is far worse than the problem being fixed. Nothing is lost, because the sweeper only runs on the branch where loadIdentity found nothing, and a keychain that refuses reads refuses deletes too.
  • A journalist asks whether a wipe makes their phone safe to hand over. What do you say? It destroys the keys, the messages, the contacts, the courier bag, the wallet file and the media cache, and the app confirms whether the keys specifically went. It does not overwrite flash, so residue depends on the OS's full-disk encryption rather than on Airhop. It cannot touch anything outside the sandbox: gallery saves, clipboard, screenshots, the app switcher snapshot. It does not wipe the other side of any conversation, and it does not revoke what is already on a relay or in somebody's courier bag. Those bounds are real and should be stated rather than glossed.
