Testing and simulation

You cannot unit test a mesh. So the project builds twenty phones in one process, each a fully isolated copy of the app, drives them through a modelled radio on a single fake clock, and asserts properties that must hold under every interleaving.

In plain words

Explain it to a ten year old

You cannot borrow twenty phones and twenty friends every time you change one line of code. So the app builds twenty pretend phones inside the computer, each one running the whole real app, and a pretend room between them where messages take time to travel and sometimes go missing. Then it tells a story: these five walk away, this one's battery dies, this one is a liar. And afterwards it checks the rules that should always be true, like "nobody saw the same message twice".

Four tiers

TierWhat it provesWhere
1. UnitByte layouts, crypto vectors, pure helpers, store behaviour. ~90 files in __tests__/ folders beside the code.src/**/__tests__/

3. SimulationMulti-device behaviour: delivery, convergence, adversaries, chaos.src/__tests__/simulation/
4. ConformanceThat Airhop's constants still match the vendored bitchat sources, parsed at test time.simulation/conformance.test.ts

Tier 1 is possible at all because src/core/ has no native dependencies. The entire protocol, both handshakes, the ratchet, the wire format, gossip sync and the routing run in plain Node under jest with no phone attached.

How twenty phones fit in one process

This is the trick the whole simulation rests on, and it is worth understanding because it is genuinely clever.

The problem

Airhop is full of module-scope singletons, by design. getMeshService() returns one mesh. useChatStore is one store. createMMKV({id}) returns one instance per id. That is correct for an app, where there is one phone, and fatal for a simulation, where twenty phones have to disagree with each other about the state of the world.

The fix

jest.isolateModules, which builds a fresh module registry: a second copy of mesh-service, of every store, of the MMKV mock, and critically of DeviceEventEmitter, so native events raised inside one phone cannot be heard by another.

Each phone is a closure over its own private copy of the entire app, and nothing in src/ had to change to allow it. No dependency injection framework, no test-only constructor parameters, no seams cut into production code.

Two consequences follow, and both are load bearing:

  • Types cannot cross the boundary usefully. Device A's message class identity differs from device B's. Everything the harness hands back is structural, and every cross-device comparison is by value.
  • The control surface is what a user can do, not what an internal function can do: send, open, background, kill, wipe. That is deliberate. If a scenario cannot be written against that surface, that is a finding about the app, not a gap in the harness.

One clock, one timeline

  THERE IS EXACTLY ONE CLOCK, AND IT IS JEST'S FAKE TIMERS.

  Every device's OS model, every native module, the real mesh service's own
  setTimeouts, and every fabric schedule onto it.

  That is not a convenience. It is the property that makes the harness
  trustworthy. Two clocks would let the simulation invent an interleaving
  that hardware cannot produce, and a race-condition harness that reports
  IMPOSSIBLE races is worse than no harness, because every failure has to
  be argued about before it can be believed.
MechanismDetail
world.advance(ms, stepMs = 5)Steps forward, flushing microtasks between steps so promise continuations (every native call is a promise) land in a realistic order relative to timers. 5 ms matches the shortest thing Airhop schedules, the 8 ms voice relay jitter floor, so no scheduled event can be skipped over.
world.settle(budget, quiet)Advances until nothing new happens. "Quiet" is defined as no new trace lines rather than no pending timers, because Airhop always has pending timers (announce, gossip, outbox sweep) so an empty timer queue would never arrive. What convergence actually needs is "the network has stopped saying anything new".
Two clocks in the APIworld.now is elapsed simulated time starting at 0. world.wallClock() is epoch milliseconds, which is what a packet timestamp field carries. A hand-forged packet stamped with now looks decades stale to the receiver's freshness window and is dropped for the wrong reason, so the test would pass for the wrong reason.
The merged timelineEvery device writes into one ordered trace tagged with who it was. A multi-device bug is never explained by one device's log; it is explained by seeing device B's scan start three milliseconds after device A's advertise stopped.
Seeded PRNGEvery scenario prints its seed. A red soak run is only useful if it can be re-run byte for byte.
Collect, then reportA scenario gathers every check and prints the whole account against the timeline, rather than throwing on the first mismatch. For a multi-device failure the interesting question is never "which assertion failed", it is "what was the sequence across five phones that got us there".
Timer leak detectionThe scenario records the timer count at start and checks it at the end, so a subsystem that leaves a timer armed fails the scenario.

The radio fabric

Everything above the fabric is the real Airhop. Everything below it is physics. The fabric owns exactly the facts a radio cannot know about itself, and nothing else.

The rule that makes it useful

The fabric has no idea what a packet means, which is the point: a medium that understood the protocol could not find a protocol bug. A bitchat node and an Airhop node are the same kind of object to it, which is the only way a mixed mesh can be tested honestly.

Behaviour modelledWhy it is there
Discovery is not instantA scanner takes time to see an advertiser, and a GATT connection takes longer still. Code that assumes a peer is reachable the moment it is visible is wrong on hardware.
A backgrounded iPhone is invisible to an Android scannerCoreBluetooth moves the service UUID into the advertisement overflow area and drops the local name. Established links keep working. This asymmetry is the single most surprising thing about the real network and it is enforced here.
Links are ordered but lossyGATT delivers in order on a given link, so reordering is off by default and must be asked for. Loss, duplication and corruption are all real and all off by default too.
Range is symmetric unless asked otherwiseAsymmetric range is a rabbit hole and the bugs being hunted do not need it.
Some Android chipsets cannot advertisecanAdvertise: false, so the null-advertiser path is exercised.
Latency, jitter, loss, duplication, corruptionPer-link conditions a scenario dials in.

Five fabrics exist beside the radio one:

relay-fabric, relay-nodeBare repeater hardware that holds no keys and never announces.

Nostr is modelled through an offline socket that stands in for relays, so gift wrap, geohash channels, gateway and bridge traffic all run through real code paths.

Properties, not outcomes

Why this file is the reason chaos tiers are worth running

For two phones and a scripted exchange you can write down the expected outcome. For twenty phones, a flapping radio and a partitioned relay set you cannot: the number of legal outcomes is enormous, and enumerating them would mean encoding the implementation's behaviour as the expectation, which tests nothing.

So the assertions are properties. "Everyone who could hear it ended up with the same messages" is true of a correct system under every interleaving and false under none of them. A property that survives a thousand random schedules is evidence; a scripted expectation that passes once is not.

InvariantStatement
ConvergenceEveryone who could hear a message ended up with it.
No duplicatesNothing renders twice. Keyed on the protocol message id, which is exactly what dedup is supposed to key on: if two rows share an id, the app rendered one message twice.
Nothing forged rendersAn unsigned or wrongly signed packet never reaches a bubble.
Delivery state never runs backwardsRead does not become delivered.
Badges match their threadsUnread counts agree with contents.
Sender kept its own copySeparate from convergence, because it is a different failure: the message went out but the composer lost it.
No sat is created or destroyedCheckable arithmetic, because the simulated mint tracks everything it issued and everything it kept in fees.
No leaked timersThe timer count at the end matches the start.

Two design details that keep the harness credible:

  • Convergence compares sets, not sequences. Two devices can legitimately order two messages sent in the same millisecond differently, because they arrived in different orders and the tie-break is local. Requiring identical sequences would fail on correct behaviour, which is how a harness loses its credibility.
  • A device is only expected to hold messages it did not write. The sender's own copy is a different row with a different id: the composer mints a local id for the optimistic echo while the wire copy carries the protocol id. A broadcaster never receives its own broadcast back, so comparing raw id sets across devices would report a failure on a perfectly converged room.
  • Each check returns findings rather than throwing, so one scenario reports every way it went wrong instead of only the first.

The bitchat actor

The most valuable single file in the test suite

Wire compatibility is a non-negotiable in VISION.md, and PROGRESS.md was honest that it had never been proven anywhere but on paper. A compatibility test that only checks Airhop against itself cannot find a divergence, because both sides share the bug.

So this node is written to bitchat's rules rather than to Airhop's, and its whole job is to disagree when Airhop is wrong.

  • It interprets only the packet types bitchat defines. Airhop's extensions (0x12, 0x50, 0x51) reach no handler, while still being relayed like any other packet, because bitchat's type switch logs case .none and falls through to its relay scheduler. Both halves matter: Airhop's extras must cost bitchat nothing and must still cross a mesh made of bitchat phones.
  • It refuses a courier envelope whose expiry is beyond 24 hours plus 1 hour of slack, which is what bitchat's store does, and which silently ate every Airhop envelope before that constant was corrected.
  • It verifies signatures before displaying or relaying, and relays with the TTL decrement and dedup any bitchat node performs.
  • It deliberately does not reuse Airhop's mesh service. It does reuse packet-codec, because that file is the claim under test: if Airhop's encoder and bitchat's decoder disagree, the byte layout is wrong, and the layout is the thing both projects have agreed on.

A real mint in the process

The wallet scenarios do not stub the mint. They run a real one. 

  The seam is globalThis.fetch, which is what @cashu/cashu-ts uses for
  every call. So EVERYTHING ABOVE THE WIRE RUNS FOR REAL:

     real blinding    real unblinding    real proof selection
     real fee arithmetic                 real DLEQ verification

  And the mint does REAL BDHKE, because it is only forty lines of
  secp256k1, and a mint that returned made-up signatures would make
  every DLEQ check pass or fail FOR THE WRONG REASON. DLEQ is precisely
  what stands between a user and a forged token.
What this buys that a stub cannot
Double-spend is real. The mint keeps a spent set, and the second person to present a proof is refused by the same code path a real mint uses.
Value conservation is checkable. Everything the mint ever signed is known, and so is everything it kept in fees, so "no sat was created or destroyed" is an arithmetic fact rather than an assumption. Both terms are needed once a mint charges: a swap reissues less than it takes, and the difference is not lost, it is the mint's.
Failure is injectable at the transport, so "the mint went away mid-swap" is the same event the app would see in a tunnel.
NUT-19 response caching is modelled, so the interrupted-swap replay path is exercised against a mint that caches and one that does not.
BOLT-11 invoices are encoded properly, because cashu-ts decodes them and rejects a quote whose invoice disagrees with the amount.

Conformance against the vendored source

The most unusual and most valuable idea in the suite: the tests parse bitchat's Swift and Kotlin sources at test time and fail on drift.

X01 is a live mixed mesh: an Airhop phone and a bitchat phone talking to each other. X02 proves Airhop's private extensions cost a bitchat node nothing while still crossing it. X03 is the constant check.

What cannot be tested this way

The simulation models the OS contract. It cannot prove the hardware honours it.

Unverifiable without hardwareRisk
Real BLE discovery timingThe fabric models delay; real chipsets vary widely by manufacturer and by how busy the band is.
MTU negotiation on real siliconThe write-type decision depends on what the peer actually grants.
CoreBluetooth behaviour in the fieldState restoration, background throttling, and the overflow-area advertisement are modelled from documentation.
OEM battery managersXiaomi, Huawei and Oppo kill background apps in ways no model captures.
Real Tor circuitsBootstrap timing, a network that blocks Tor, whether a bridge actually gets through, and how long Snowflake takes to find a volunteer.
Relay hardwareBitle, ESP32 nodes, LoRa trunks. Simulated against a bare repeater; never run against hardware. Chapter 47.
Apple's DEFLATE encoderCompression parity is verified against zlib 1.3.1, which is what Android produces, but not against Apple's, which needs Apple hardware to run.
Battery consumptionThe power policy is testable as a pure function; its effect on a real battery is not.
Crowds above the low tens25 phones converge (B06). 200 is untested, and full fanout is the reason that matters. Chapter 45.

Drills

  • How do twenty independent copies of a singleton-heavy app run in one process? jest.isolateModules builds a fresh module registry per device: a separate mesh service, separate stores, a separate MMKV mock, and critically a separate DeviceEventEmitter, so native events raised inside one phone cannot be heard by another. Each phone is a closure over its own copy of the app, and nothing in the production source had to change to allow it. The cost is that types cannot cross the boundary, so every cross-device comparison is structural.
  • Why does the harness insist on a single clock? Because two clocks would let the simulation invent an interleaving that hardware cannot produce, and a race-condition harness that reports impossible races is worse than no harness: every failure has to be argued about before anyone believes it. Jest's fake timers are the one clock, and every device's OS model, every native module, the real mesh service's own timeouts and every fabric schedule onto it.
  • Why assert properties rather than expected outcomes? Because for twenty phones with a flapping radio and a partitioned relay set, the number of legal outcomes is enormous. Enumerating them means encoding the implementation's current behaviour as the expectation, which tests nothing and passes even when the behaviour is wrong. "Everyone who could hear it ended up with it" and "nothing renders twice" are true of any correct system under every interleaving and false under none, so surviving a thousand random schedules is evidence.
  • Why does the bitchat actor not reuse Airhop's mesh service? Because a compatibility test that checks Airhop against itself cannot find a divergence: both sides share the bug. The actor is written to bitchat's rules, so its job is to disagree when Airhop is wrong. It does reuse packet-codec, deliberately, because that file is the claim under test: if Airhop's encoder and bitchat's decoder disagree, the byte layout is wrong, and the layout is the thing both projects agreed on.
  • Why run a real Cashu mint rather than stubbing it? Because a mint that returned made-up signatures would make every DLEQ check pass or fail for the wrong reason, and DLEQ is precisely what stands between a user and a forged token. A real forty-line BDHKE mint also makes double-spend real, since the second presenter is refused by the same code path a real mint uses, and makes value conservation an arithmetic fact rather than an assumption, since everything issued and everything kept in fees is known.
  • What would you tell an auditor the simulation does not prove? Anything about hardware. Real BLE discovery timing, MTU negotiation on real silicon, CoreBluetooth's actual background behaviour, OEM battery managers, real Tor circuits, and relay hardware are all modelled from documentation rather than measured. Compression parity is verified against zlib but not against Apple's encoder. And crowd behaviour above the low tens is untested, which matters specifically because full fanout is implemented where the spec documents subsetting.
