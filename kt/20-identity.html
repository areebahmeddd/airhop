Identity and trust

Encryption is easy compared to knowing who you are encrypting to. This chapter is the hardest problem in the product: binding a key to a person, with no server, no registry, and no authority.

In plain words

Explain it to a ten year old

There is no register of who is who. So when your phone hears a new name for the first time, it writes down the fingerprint that came with it and refuses to ever change that entry, because a stranger could shout the same name later. The only way to correct it is to stand next to the person and scan their code with the camera, or to read six words aloud to each other and check they match. Everything else is a guess your phone is honest about.

The identity tree

  ONE ROOT, GENERATED ON DEVICE, NEVER TRANSMITTED

  ┌─ noiseStaticPrivKey  (X25519, 32 random bytes)
  │     └─ noiseStaticPubKey
  │           └─ peerID = hex(SHA-256(pub))[0:16]      8 bytes, 16 hex chars
  │                 └─ username = adjective-noun-4hex
  │
  └─ signingPrivKey     (Ed25519, 32 random bytes)
        ├─ signingPubKey        signs every packet
        │
        ├─ HKDF("airhop-nostr-key-v1")
        │     └─ nostrPrivKey (secp256k1)
        │           └─ nostrPubKey (x-only, 32 bytes)   the durable npub
        │
        └─ HMAC("airhop-geohash-seed-v1")
              └─ geohash seed
                    ├─ HMAC(seed, "u4pruy" || 0) -> per-cell key for u4pruy
                    ├─ HMAC(seed, "u4pru"  || 0) -> per-cell key for u4pru
                    └─ ... one unlinkable identity per cell

  Everything below the root is DERIVED. There is exactly one secret to
  back up, one to wipe, and one to lose.

Two independent random keys at the root, then everything else by one-way derivation. Nothing is stored twice, nothing needs separate provisioning, and the panic wipe has exactly one item to destroy for identity.

The Nostr key is derived rather than stored because a second stored secret is a second thing to back up, a second thing to wipe, and a second way to end up with a device holding half an identity. The derivation is one-way, so the Nostr key cannot be walked back to the signing key.

Peer IDs

  peerID = hex(SHA-256(noiseStaticPubKey)).slice(0, 16)

  8 bytes on the wire. 16 hex characters as a string.
  Example: 3a9f2c1b8e4d5f60
PropertyConsequence
Derived from the public keyYou cannot choose your peer ID. There is nothing to squat, nothing to register, and no first-come-first-served race.
Preimage resistantAn attacker cannot construct a Noise key that hashes to someone else's peer ID. 2^64 work for a targeted collision.
Verifiable from the announceEvery announce carries the Noise public key, so a receiver recomputes the derivation and refuses a mismatch. bitchat names this rejection .senderMismatch(derivedPeerID:).
Bound to a completed Noise sessionA session is only stored if the authenticated remote static key hashes to the claimed peer ID. This is what makes the ID meaningful rather than a label.
Does not rotateacknowledged limitation The same device is linkable across sessions forever, until the identity is regenerated. Listed as out of scope in the threat model. Only per-cell geohash identities are ephemeral.

Names

Two different things are called a name, and they have opposite trust properties.

The derived username

peerIDToUsername("3a9f2c1b...")
  byte[0] % 128 -> adjective
  byte[1] % 128 -> noun
  first 4 hex   -> suffix

  "swift-falcon-3a9f"

Cannot be chosen. Cannot be claimed by anyone without the key it derives from. 128 x 128 x 65536 is about a billion combinations. Both word lists are exactly 128 entries so the byte modulo is perfectly uniform.

The announced nickname

ANNOUNCE TLV 0x01, up to 32 UTF-8 bytes, chosen freely by the sender. A bitchat peer picks its own nickname and Airhop renders what it announces.

This is decoration, not identity. Which is why a public-channel sender is always shown with a #last4 suffix from the peer ID, so two people with the same nickname stay distinguishable.

Nickname canonicalisation

The same visible name has more than one valid encoding. "Jose" with an acute accent is either U+00E9 or U+0065 followed by the combining acute U+0301. The two render identically and compare unequal.

Airhop normalises to Unicode NFC on both encode and decode, so everything downstream of the wire compares one form. Without it, an accented name typed on one platform and announced from another fails to match: an at-mention never fires, and one person occupies two rows of a participant list. Both failures are silent, which is what makes it worth a rule rather than a bug report.

This is a local canonicalisation, not a wire change. The packet still carries whatever bytes the sender chose, peer IDs derive from keys rather than names, and no signature covers the normalised form, so a peer that normalises differently stays fully interoperable.

Truncation to the 32 byte budget counts UTF-8 bytes and drops whole code points. Counting UTF-16 units would be wrong twice: 32 emoji is 128 bytes, four times the budget, and a slice can land inside a surrogate pair and emit a lone half that decodes to a replacement character on the far side. The cut also backs off past a trailing combining mark or zero-width joiner, so a name never ends in a mark rendered on a dotted circle or half a split emoji. 32 bytes is about ten Devanagari characters, so the budget is reached most often in exactly the scripts that write with marks.

Trust on first use, and its two tiers

Here is the problem in its sharpest form. An announce is signed with a key carried inside that same announce. So the signature proves the announce is self-consistent and nothing more. 

  THE ATTACK

  Victim V announces:
     senderID   = V's peer ID
     noisePub   = V's X25519 public key      ← broadcast IN THE CLEAR
     signingPub = V's Ed25519 public key
     signature  = V's signature

  Attacker A hears it and crafts:
     senderID   = V's peer ID                 ← copied
     noisePub   = V's X25519 public key       ← copied, it was public
     signingPub = A's OWN Ed25519 public key  ← substituted
     signature  = A's signature over the whole thing

  Now check it:
     SHA-256(noisePub)[0:16] == senderID ?    ✓ PASSES (it is V's real key)
     signature verifies against signingPub ?  ✓ PASSES (A signed with A's key)

  Both checks pass. The announce is internally consistent and forged.

Signature checking alone cannot stop this. The only defence is to refuse to replace a key already bound to a peer ID.

TierSourceMay create a pinMay replace a pin
1. TOFUA self-signed ANNOUNCEYes, if none existsNever
2. ProvenNoise payload 0x21 inside a completed sessionYesYes. Proven beats assumed.
Out of bandAn in-person QR scanYesYes. The camera witnessed it.
Out of band, weakerAn airhop:// link, or a card in a geohash DMYesNo. Recorded as source: "link", never verified.

The rejection is whole-update, not keep-the-key-take-the-rest. If a conflicting announce arrives, the entire update is dropped, including the nickname and the capability bits, because they come from the same unverified source. Accepting any of it would still let an attacker rewrite how that peer is presented. This mirrors bitchat's BLEAnnounceTrustPolicy .signingKeyMismatch and .keyMismatch.

Identity pinning has no expiry, deliberately. Reachability does. They are different questions, and conflating them was a real bug: a LEAVE arrives precisely when a peer has stopped announcing, so resolving its signing key through the reachability window refused the genuine ones. Hence pinnedSigningKey(), which ignores the TTL, alongside get(), which applies it.

The 0x21 identity proof

TOFU has a race: whoever announces first wins the pin. If an attacker gets there first, the real peer is locked out of their own identity on that device. AUTHENTICATED_PEER_STATE is how that heals. 

  NoisePayloadType 0x21, sent INSIDE a completed Noise XX session

    [version = 0x01]
    TLV 0x01  capabilities   minimal little-endian
    TLV 0x02  Ed25519 signing public key

The session only completes when the remote static key hashes to the claimed peer ID, so arriving inside one is proof of possession of the Noise private key, which no observer can fake. Three consequences:

  • A proven signing key may correct a TOFU pin.
  • An announce may never overwrite a proven one.
  • Two different proven keys for one peer ID cannot both be real, so the first one stands and the second is refused. That is the only case the caller has to act on.

Decoding is all or nothing: an unknown version, a missing or duplicated required field, a non-minimal capability encoding, or a malformed length all change no state. A partial parse of an authenticated identity claim is worse than no parse.

Capabilities, hints versus proof

Peers advertise what they support so features can degrade gracefully. The bits are byte-for-byte with bitchat's PeerCapabilities.

The capability downgrade attack

Announced bits are a discovery hint. Anyone can copy a victim's public Noise key off the air and self-sign an announce carrying whatever bits they like. If encrypted media selection depended on the announced bit, an attacker could announce bit 8 off for a victim and force every attachment sent to them into the signed cleartext form, readable by every node it crosses.

So the rule is absolute: only the authenticated bit counts. Encrypted private media is selected only on a capability proven inside a Noise session via 0x21. Announced bits are enough to start a handshake, never enough to change how we send. update() on the registry cannot lower authenticatedCapabilities, so the next announce cannot quietly reduce a proof back to a claim.

Verification: QR and safety numbers

Two orthogonal facts are tracked, and confusing them was a real security finding:

FieldQuestionValues
sourceHow did the keys arrive?qr, link, manual
verificationHas a human confirmed them?verified or not

They are independent, so a contact learned from a link can be verified later on a call. Only source: "qr" may re-pin keys already bound to a peer ID.

Route 1: the QR contact card

  airhop:v1/<base64url>

  [0]        u8     version = 1
  [1..8]     8      peerID
  [9..40]    32     Noise static public key (X25519)
  [41..72]   32     Ed25519 signing public key
  [73]       u8     nickname length, 0 to 32
  [74..M]    utf8   nickname
  [M+1..+32] 32     Nostr public key (secp256k1)

  Total: 106 + nickname bytes

Every card carries all three keys: Noise and signing for Bluetooth, and the Nostr key so a contact met only by QR is still reachable over the internet. On scan, the peer ID is checked against SHA-256(noisePub)[0:16] before anything is trusted.

Airhop can also read bitchat's own verification QR, where the Nostr key is optional, so absence means "mesh-only contact from bitchat" rather than a malformed card.

Route 2: the safety number

Six words both people read to each other over a channel they already trust: a phone call, a radio, another app. 

  peerFingerprint(noisePub, signingPub)
      = SHA-256("airhop-fingerprint-v1" || noisePub || signingPub)

  safetyNumber(ours, theirs)
      = SHA-256("airhop-safety-number-v1" || sorted(ours, theirs))

  then take 6 x 7-bit indices, MSB first, into a 128-word list
      = 42 bits, six words
Design choiceReason
Covers both keysA peer ID is SHA-256 of the Noise key alone, so reading a peer ID aloud would not catch the attack that matters: a forged card that keeps the victim's real peer ID and Noise key while substituting the attacker's signing key.
Inputs are sorted before hashingSo neither side needs to know who is who, and both derive the same string. Without it each side derives a different code and the exchange doubles in length.
Six words, 42 bitsSized against the attack rather than to a round number. Forging a match means grinding keys until the pair hash lands on the same six words: 2^42 for one targeted pair, and it must be done before the two people speak. Every extra word is another word to read over a bad line, and a code nobody finishes reading protects nothing.
Bit extraction is pinned in codeSeven-bit indices taken most significant bit first, defined once so two devices agree exactly rather than depending on how a runtime slices bytes. The word list itself is presentation.
It imports nothingA match sets a flag, a mismatch tells the user to stop. Neither writes a key, so unlike the scan path there is no re-pinning power to gate and none is needed.

This is the route that makes verification possible with someone you can only reach by voice, which in a blackout may be the only channel available.

Pseudonyms and the contact card

In a location channel you appear under a per-cell secp256k1 key with no link to your durable identity. That is the point. But sometimes two people who met in a cell want to become real contacts.

Noise payload 0x22, CONTACT_CARD, carries that assertion. A per-cell pubkey and a peer ID are unlinkable by construction, so only the holder can assert they are the same person.

RuleWhy
Sent only on explicit user actionNever automatic, and never an automatic reply to an inbound card. Otherwise receiving a card would deanonymise you.
Gift-wrapped from the sender's per-cell keyThe envelope stays pseudonymous. Only the card body identifies the sender.
Validated exactly like a scanned cardPeer ID must equal SHA-256(noisePub)[0:16].
Treated as not in personIt may introduce a contact but never re-pin keys already bound to a peer ID.
Threads merge only after both cards have crossedMerging moves replies to the durable rail, which attributes senders by known Nostr key alone. Merging earlier strands them in an unattributed thread.

The machinery underneath all of this, meaning the three code formats, the card byte layout, the five ways a contact can arrive and the merge policy that decides which of them may overwrite what, is 21.

What stays unsolved

GapStatusHonest framing
Peer IDs never rotate Out of scope, documented The same device is linkable across sessions forever. bitchat has an entire design document on peer ID rotation and has not shipped it either, because rotation breaks the direct-link rule, courier tags, contact pinning and the outbox all at once. This is the largest open privacy question in the design.
TOFU on first contact Inherent If an attacker is present at first contact and wins the announce race, they own that identity on your device until an in-person scan corrects it. The 0x21 proof heals the case where the real peer later completes a session, but not the case where the attacker also completes one first.
No key rotation or revocation Not implemented A compromised identity cannot be revoked. The only remedy is to regenerate, which produces a new peer ID and a new username, and every contact must re-scan. There is no "this key is retired" message.
Nicknames are free text Deliberate A bitchat peer chooses its own nickname freely and Airhop renders what it announces. The #last4 suffix on public messages is the mitigation, and it is a mitigation rather than a solution.
No transitive trust Deliberate There is no web of trust and no vouching path in Airhop (bitchat has a vouch capability bit; Airhop does not implement the feature). Every verification is bilateral. That is simple and honest, and it does not scale to verifying a crowd.

Drills

  • Why is a valid Ed25519 signature on an announce not enough? Because the signature is checked against a key carried inside that same announce, so it only proves internal consistency. The Noise public key is broadcast in the clear, so an attacker copies the victim's peer ID and Noise key, substitutes their own signing key, and signs. The derivation check passes and the signature check passes. Only refusing to replace a key already bound to that peer ID stops it.
  • Why may a 0x21 payload overwrite a TOFU pin when an announce may not? Because it arrives inside a completed Noise XX session, and a session only completes when the remote static key hashes to the claimed peer ID. That is proof of possession of the Noise private key, which no observer can fake. TOFU binds whoever announced first, and an attacker can win that race; a proof cannot be won by racing. Proven beats assumed, and the reverse never happens, because update() cannot clear the authenticated fields.
  • Why does the safety number cover both keys rather than just the peer ID? Because a peer ID is SHA-256 of the Noise key alone. The attack that matters keeps the victim's real peer ID and real Noise key and substitutes only the signing key, so reading a peer ID aloud would match perfectly while the attacker holds the key that authenticates every packet. Covering both keys is what makes the comparison meaningful.
  • Why does a link-delivered contact card get a weaker status than a scanned one? Because the camera is the evidence. An in-person scan means both people were physically present, which is what justifies letting it re-pin keys. A link can be forwarded, planted, or sent by anyone, so it can introduce a contact but may never overwrite keys already bound. Minting a "Verified" badge from a link was a real High severity finding: it would let anyone who could get you to tap a link impersonate a contact.
  • Six words is only 42 bits. Signal uses 60 digits. Is that enough? It is sized against the attack rather than to a round number. Forging a match means grinding key pairs until the pair hash lands on the same six words: about 2^42 work for one specific targeted pair, and it has to be completed before those two people speak. Against that, every extra word is another word to read over a bad phone line, and a code nobody finishes reading protects nothing. It is a defensible trade, and it is a smaller margin than Signal's, which is worth saying rather than hiding.
  • What happens if someone regenerates their identity? They become a completely different person to the network: new Noise key, new peer ID, new username, new Nostr key, new geohash identities. Every contact's pin for the old ID stays and is now dead. Nobody can message them under the old identity, and there is no revocation message to say so. That is the cost of having no registry, and it is the same reason there is no account recovery.
