Forward secrecy and the ratchet

The assumption behind this chapter is that your keys will eventually be compromised. The question it answers is how much that costs you, and how quickly you recover.

In plain words

Explain it to a ten year old

Imagine a padlock that changes its own combination every time you use it, and forgets the old one immediately. If a thief steals the padlock today, they cannot open anything you locked yesterday, because that combination no longer exists anywhere. And after you use it a couple more times, they cannot open tomorrow's things either, because the lock has moved on to combinations they never saw.

Four properties, precisely

PropertyQuestion it answersAirhop
Confidentiality Can an eavesdropper read this message now? Yes, everywhere. AEAD under a key only the two parties hold.
Forward secrecy If my key is stolen tomorrow, can they read what I sent yesterday? Per session from Noise XX. Per message from the Double Ratchet, between Airhop peers.
Post-compromise security (break-in recovery, future secrecy) If my key is stolen today and I do not notice, will they still be reading in an hour? Yes, from the DH ratchet, after a few round trips. Not from Noise alone.
Deniability Can the recipient prove to a third party that I said this? Yes, deniable. Message authenticity comes from a symmetric key both parties hold, so either could have produced it. This is why DMs inside a session carry no Ed25519 signature.

The symmetric ratchet

The simpler of the two halves. A chain key advances one step per message, and each step throws off a message key and a new chain key. 

  kdfCk(ck):
    messageKey = HMAC-SHA256(ck, 0x01)
    nextCk     = HMAC-SHA256(ck, 0x02)
    return [nextCk, messageKey]

  CK0 ──▶ CK1 ──▶ CK2 ──▶ CK3 ──▶ CK4 ...
   │       │       │       │
   ▼       ▼       ▼       ▼
  MK0     MK1     MK2     MK3        one key per message, used once

  ONE WAY. HMAC is not invertible, so from CK3 you cannot compute CK2,
  and therefore not MK2 or anything before it.

  Delete CK2 after using it and message 2 is gone forever, even from you.

The two distinct constant bytes matter: without them the message key and the next chain key would be the same value, and holding one message key would let you advance the chain and read everything after. That is domain separation at its smallest scale.

The symmetric ratchet gives forward secrecy but not post-compromise security: an attacker who takes the current chain key can compute every future key in that chain. Which is what the second ratchet is for.

The DH ratchet

Each side carries a ratchet key pair and rotates it. Every time you see a new public key from the other side, you perform a fresh Diffie-Hellman and mix it into the root key. 

  kdfRk(rootKey, dhOutput):
    out = HKDF-SHA256(ikm = dhOutput, salt = rootKey,
                      info = "airhop-dr-root-v1", length = 64)
    return [newRootKey = out[0:32], newChainKey = out[32:64]]

  ALICE                                      BOB
  DHs = A1                                   DHs = B1

  A sees B1 for the first time:
     RK, CKr = kdfRk(RK, DH(A1, B1))         ← receiving chain
     generate A2
     RK, CKs = kdfRk(RK, DH(A2, B1))         ← sending chain
     send with A2 in the header

  B sees A2 for the first time:
     RK, CKr = kdfRk(RK, DH(B1, A2))
     generate B2
     RK, CKs = kdfRk(RK, DH(B2, A2))
     send with B2 in the header

  Every reply injects NEW entropy neither side controlled before.
  An attacker who stole the state at A1/B1 is locked out once both
  sides have rotated once, because they never saw A2's or B2's
  private half.

This is the source of post-compromise security. It requires a reply: a conversation where one side only ever sends never rotates the other side's key, so recovery never happens. That is inherent to the algorithm, not a defect of this implementation.

The header

  40 bytes, sent in the clear, AUTHENTICATED AS AAD

    [0..31]   DHs_pub   the sender's current ratchet public key
    [32..35]  PN        u32 BE, messages sent in the PREVIOUS sending chain
    [36..39]  N         u32 BE, this message's number in the current chain

  wire: [header 40][ciphertext + 16 byte tag]

The header is not encrypted (that would be "header encryption", an optional Signal extension Airhop does not implement) but it is authenticated: it is passed as AEAD associated data, so tampering with N or PN to force key derivation down a wrong path fails the tag check.

PN exists so the receiver knows how many messages were in the previous chain and can derive the keys for any that are still missing before switching chains.

Out of order messages

Airhop's mesh delivers out of order routinely: two copies of a packet can take different paths with different hop counts. So skipped keys are not an edge case, they are normal. 

  ratchetDecrypt(state, message):
    1. is this key already in MKSKIPPED?           -> use it, delete it, done
    2. is the header's DH key new?                 -> skipMessageKeys(header.pn)
                                                      dhRatchetStep(header.dhPub)
    3. skipMessageKeys(header.n)                   -> derive and cache the gap
    4. derive the next receiving key, decrypt, advance

  skipMessageKeys(until):
    if until - Nr > 1000  -> THROW "too many skipped messages"
    while Nr < until:
      derive MK, store under "<DHr hex>:<Nr>"
      if the cache is at 1000, evict the oldest
      Nr++
BoundValuePrevents
MAX_SKIP1000A peer claiming N = 4,000,000,000 forcing four billion HMAC operations. This is a one-packet denial of service without the bound.
Cache size1000 entriesMemory exhaustion by a peer that sends many out-of-order messages. Oldest evicted first, using Map insertion order.

The tension inside the skipped-key cache

A stored skipped key is a message key sitting in memory waiting for a message that may never come. That is a small, bounded erosion of forward secrecy: if the device is compromised while keys are cached, those specific messages become readable. Signal has the same property. The mitigation is the cap plus the fact that the cache is in memory only, never persisted, so it does not survive a process restart. Enlarging the cap would trade more forward secrecy for better out-of-order tolerance; 1000 is Signal's own figure.

Seeding, and the bug that mattered

The ratchet needs a shared root key. Airhop takes it from the Noise handshake rather than running a separate key agreement. 

  rootKey = HKDF-SHA256(
              ikm  = session.exporterSecret,     // the THIRD HKDF output of split()
              info = "airhop-dr-seed-v1",
              len  = 32
            )

  initSender(rootKey, theirNoiseStaticPub)     // the initiator
  initReceiver(rootKey, myNoiseStaticPriv)     // the responder
Candidate seedVerdict
handshakeHash (h) CRITICAL BUG This is what Airhop originally used. mixHash absorbs only bytes that went over the wire, so h is public to anyone who captured the handshake, and handshakes flood the mesh at TTL 7. Any bystander could recompute the root key and forge or decrypt every Double Ratchet message in that conversation.
Static-static ECDH Rejected. It stays derivable from long-term keys forever, so it provides no forward secrecy at all: the whole point of the ratchet would be undone at its root.
A fourth handshake message carrying a fresh secret Rejected. It costs a round trip, and it would be an Airhop-only message that bitchat cannot parse.
exporterSecret CORRECT The third HKDF output of split(), descending from the chaining key. The chaining key absorbed ephemeral DH outputs whose private halves are destroyed at split, so it cannot be reconstructed from long-term keys and cannot be recomputed by an observer. Both sides already hold it, so it costs no extra round trips, and k1/k2 stay bit identical so bitchat interop is untouched.

The migration cost was real and worth noting: old and new builds derive different root keys and cannot decrypt each other's Double Ratchet messages. A protocol-level change like this has no graceful path, which is why the domain separator ends in v1.

The responder cannot speak first

A subtlety of the algorithm that has bitten this codebase: 

  initSender(rk, theirPub):
    DHs = fresh keypair
    RK, CKs = kdfRk(rk, DH(DHs.priv, theirPub))    ← HAS a sending chain
    ...

  initReceiver(rk, myStaticPriv):
    DHs = { priv: myStaticPriv, pub: derived }
    CKs = NULL                                      ← NO sending chain
    ...

A receiver-initialised state has no sending chain. The Double Ratchet grants it one only on its first DH ratchet step, which happens when it receives a message. So the side that answered the handshake cannot send until the side that started it has spoken.

That is the algorithm working correctly, not a defect. But ratchetEncrypt throws rather than returning null, and an exception on the send path is not something a UI can do anything useful with. So there is an explicit canEncrypt(state) predicate, and both call sites check it and fall back to the plain Noise transport if the ratchet is not ready. Before that check existed, replying to a first contact crashed the send path.

The initiator's ratchet also starts against the responder's Noise static public key rather than a fresh ephemeral, because Alice cannot know a fresh ephemeral of Bob's without another round trip. The transcript-derived root key is what keeps that chain secret despite the key being long lived, and Bob rotates to a fresh ratchet key on his first step.

The offline problem, and prekeys

The Double Ratchet assumes a session exists. Signal solves the "recipient is offline and has no session" case with X3DH: the recipient publishes a signed prekey and a batch of one-time prekeys to a server, and a sender combines four DH operations to derive a shared secret without any interaction.

Airhop deliberately does not use X3DH. Three reasons:

  1. X3DH's job is already done. The Noise handshake seeds the ratchet, so there is no need for a separate asynchronous key agreement for live sessions.
  2. X3DH assumes a server. Prekeys are published to a key distribution service. Airhop has none, so prekeys are gossiped over the mesh as packet type 0x24 instead, and are never published to Nostr.
  3. The offline case has a different shape. Airhop's offline path is the courier: a one-way sealed envelope carried by a stranger. Noise X plus a one-time prekey gives that path forward secrecy without a full X3DH construction.

Two honest gaps

Nostr DMs have no forward secrecy. The conversation key is HKDF over a static ECDH between two long-lived secp256k1 keys. Compromise either key and every gift-wrapped DM ever sent between those two identities, including ones an adversary archived from a relay years earlier, becomes readable. This is a property of NIP-17 and of bitchat's construction, not an Airhop choice, and it cannot be fixed unilaterally without breaking interop. It deserves to be stated because "end to end encrypted" reads as stronger than it is here.

Prekeys are not reconciled through gossip sync. Bundles flood on link-up but bit 9 is unimplemented, so a device that arrives late cannot pull a bundle from a peer that holds one, and its courier envelope silently falls back to the static key. The message still delivers and is still encrypted; only forward secrecy is lost, and nothing in the UI says so.

Why not MLS, in detail

MLS (RFC 9420) is the strongest group messaging construction that exists, and Marmot, the protocol behind White Noise, brings it to Nostr. It is genuinely better than what Airhop does for groups. Three reasons it does not fit here:

  1. It needs an ordered delivery service. MLS epochs advance in a total order, and every member must apply the same commit sequence. A BLE mesh with flooding, dedup and partitions has no total order and cannot manufacture one. Two members in separate partitions would diverge into incompatible epochs with no reconciliation path.
  2. Its advantage appears at scale Airhop does not have. TreeKEM's logarithmic cost matters at hundreds or thousands of members. At 16, the pairwise key delivery Airhop uses is simpler and cheaper.
  3. Interoperability. Groups are bitchat compatible on the wire (0x25, creator-signed roster, ChaCha20-Poly1305 under an epoch key). Adopting MLS would fork that.

The honest counterpoint: Airhop's group construction has no per-message forward secrecy within an epoch. Every member holds the epoch key, and every message in that epoch is encrypted under it. Compromise a member and you read the whole epoch. Key rotation bumps the epoch and older epochs are refused, so it is not unbounded, but it is much weaker than DMs. That is the correct criticism to expect, and the correct answer is that a serverless mesh has no way to run TreeKEM today, not that the current design is equivalent.

Drills

  • Define forward secrecy and post-compromise security, and say which one needs a reply. Forward secrecy: compromising a key today does not reveal messages encrypted before the compromise, because the keys that encrypted them have been deleted. Post-compromise security: after a compromise, the conversation becomes secure again once fresh entropy neither the attacker nor the previous state controlled is injected. PCS needs a reply, because the DH ratchet only turns when you receive a new ratchet public key from the other side. A one-way conversation never recovers.
  • Why are there two ratchets rather than one? They do different jobs. The symmetric ratchet gives forward secrecy cheaply, one HMAC per message, but an attacker who takes the current chain key computes every future key in that chain. The DH ratchet fixes that by injecting fresh Diffie-Hellman entropy whenever the peer rotates its key, which locks out an attacker who does not hold the new private half. Forward secrecy from one, recovery from the other.
  • Why is MAX_SKIP 1000 and not unbounded? Because N is an attacker-controlled 32 bit field in an unauthenticated position until the tag is checked, and deriving keys up to it is a loop. A peer claiming four billion would make the receiver perform four billion HMAC operations, which is a one-packet denial of service. 1000 is Signal's own figure and covers real out-of-order delivery on a mesh comfortably.
  • Someone points out that a photo sent in a DM has weaker properties than the text beside it. Are they right? It depends on the peer. When the recipient has proven capability bit 8 inside a Noise session, the file is sealed as Noise payload 0x20 and gets session confidentiality. When they have not, it falls back to the signed cleartext FILE_TRANSFER, which is authentic but readable by every node it crosses. Neither form gets Double Ratchet treatment, so an attachment never has per-message forward secrecy. So yes, they are right, and the mitigation is that the fallback is selected only on an authenticated capability, so nobody in radio range can force an attachment into the clear by announcing the bit off.
  • Why is White Noise's MLS not simply better? For groups it is better, and worth saying so. But MLS needs a delivery service that gives every member the same ordered sequence of commits, and a flooding mesh with partitions cannot provide one: two members in separate partitions would advance to incompatible epochs with no reconciliation. Its logarithmic advantage also only appears at hundreds of members, where Airhop caps at 16. The correct framing is that MLS solves a different deployment shape, one that assumes connectivity.
  • What is the weakest link in Airhop's forward secrecy story? Nostr DMs. They use a static ECDH between two long-lived secp256k1 identities, so there is no forward secrecy at all: compromise either key and every gift-wrapped message ever exchanged, including archived ones, is readable. It is inherited from NIP-17 and bitchat's cipher and cannot be changed unilaterally. Second weakest is a courier envelope sealed to a static key when no prekey bundle was available, which happens silently because prekeys are not reconciled through gossip sync.
