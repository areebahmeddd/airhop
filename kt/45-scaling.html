Scale and chaos

"How does it scale?" has a different answer here than in any server system. There is no capacity to add. The scarce resource is airtime in a shared band, and it does not grow when more people arrive.

In plain words

Explain it to a ten year old

Imagine a room where everyone can only talk by shouting, and only one person can be heard at a time. Two people is easy. Twenty is fine if they take turns. Two hundred and the room is just noise, no matter how polite everyone is, because there is only so much air. More people means the message can travel further, and it also means everyone has less time to speak.

Why this is not backend scaling

A server systemAirhop's mesh
BottleneckCPU, memory, database, bandwidth at a known pointAirtime in a shared 2.4 GHz band
Adding capacityAdd machinesImpossible. The band is fixed and shared with every WiFi network and microwave in the building.
More usersMore load, more capacity neededMore load and more relays. Reach improves while per-node airtime shrinks.
ObservabilityCentral metricsNone. No node can see the graph. There is no dashboard, by design.
FailureA tier saturates and errorsDelivery probability degrades gradually and silently.
The right question"How many requests per second?""At what density does delivery probability fall below useful?"

A backend engineer's instinct is to look for the tier that saturates. Here the answer is that the medium saturates, everywhere at once, and the only levers are how many transmissions each message causes and how far it travels.

The counter-intuitive part

A crowd helps and hurts at the same time. More phones means more relays and better reach, and it also means more bodies absorbing 2.4 GHz, more devices contending for the band, and more transmissions per message. The two effects fight, and which wins depends entirely on how many transmissions each message causes.

The airtime budget

Here is the arithmetic a reviewer will want, done explicitly. 

  ONE BLE LINK    ~18 KiB/s
  ONE TEXT PACKET ~100 to 300 bytes encoded
  ONE WRITE       ~5 to 15 ms of link time in practice

  A MESSAGE'S TOTAL COST = (number of nodes that relay it)
                         x (links each writes to)

  FULL FANOUT, which is what Airhop implements:
     every node writes to every link except the ingress one

     n nodes, average degree d
     transmissions ≈ n x (d - 1), bounded by TTL and collapsed by dedup

  DETERMINISTIC SUBSET, which is what bitchat implements:
     every node writes to a message-ID-seeded subset

     transmissions ≈ n x subset_size,  where subset_size << d
RoomNodesTypical degreeWrites per message, full fanoutAssessment
Two friends211Trivial

A large meeting506, capped~250Plausible, untested

The degree cap helps a great deal: Airhop holds at most 6 central links, so a node in a crowd of a thousand still writes to a handful of neighbours rather than to everyone. That turns the growth from quadratic in node count to roughly linear. Linear in a room of a thousand is still a lot of writes per message on a shared band.

Three existing controls bound it further, and they are the reason the system works at 25:

  • Dedup means each node transmits a given message at most once.
  • TTL 7 bounds depth, and time-critical traffic is clamped to 5 in a dense graph.
  • Jitter widening with degree means the denser the room, the longer each node waits, so somebody else's relay usually wins first and dedup does the work.

The three regimes

RegimeSymptomWhat actually failsMitigation
Too sparse "Nobody is here." There is no path. TTL is irrelevant. The courier: a person carries the message. And relay hardware, which puts a node where nobody stands. This is the regime bitchat compatibility helps most, because it doubles the effective user base at zero cost.
Ideal Everything works. Nothing. n/a
Too dense "It is slow", then "some messages do not arrive." Contention. Writes are refused, fragments drop, transfers stall, and delivery probability falls silently and gradually. Degree cap, jitter widening, TTL clamping for streams. Fanout subsetting is the missing one.

The dense failure is the dangerous one because it is graceful in the worst sense: nothing errors, nothing logs, messages just become less likely to arrive. A user experiences it as "this app is unreliable in crowds", which is the exact situation it was built for.

The fanout problem

The single most significant scaling item

PROTOCOLS.md section 4 lists a fanout subset of roughly ceil(sqrt(n)) links, deterministic and excluding the ingress peer, as a routing constant. There is no such code in src/. MeshService.relayPacket writes to every link except the ingress one. 

  WHAT BITCHAT DOES

    A node relaying a broadcast writes to a SUBSET of its links,
    chosen deterministically from the MESSAGE ID. So different
    messages take different subsets, and coverage is statistical
    across many messages rather than guaranteed per message.

    FULL fanout is kept for the types that must reach everybody:
       announces, fragments, sync packets
    Directed traffic keeps full targeted fanout.

  THE TRADE

    full fanout   guarantees that if a path exists within the TTL,
                  the packet takes it. Costs the most airtime.

    subsetting    accepts a small probability that one message misses
                  one node, and leans on GOSSIP SYNC to repair the gap
                  within 15 seconds. Costs far less airtime.

Airhop already has the repair mechanism: gossip sync reconciles public messages, board posts and group messages every 15 seconds, and the per-type candidate windows are 15 minutes for messages. So the safety net that makes subsetting viable is in place and running. What is missing is the thing it would be a safety net for.

The honest position: full fanout is defensible at the tested scale, it is untested above the low tens, and the standard mitigation is available, specified in this project's own protocol document, and not implemented.

A second, cheaper item sits beside it. FloodRouter keeps pending relay timers in a map keyed by packet ID, so the machinery to cancel a scheduled relay when a duplicate arrives first exists. But the receive path drops a duplicate before reaching any cancellation, so the timer fires anyway and its copy is deduplicated by everyone who already has it. bitchat cancels. In a dense room where jitter is deliberately long precisely so that somebody else's relay wins, this is real wasted airtime for a small change.

ConcernPosition
Relay capacityNot the project's problem in the usual sense: it operates none. 300+ independent relays, 5 per cell, no single one load bearing.

Relay selection convergenceBy cell centre with URL tie-breaks, so every participant independently arrives at the same set. This is a correctness property, not a performance one, and getting it wrong splits the channel silently.

The internet half genuinely scales, because it is somebody else's infrastructure and there is a lot of it. The interesting failure there is not capacity, it is the relay set fragmenting: if two clients disagree about which relays serve a cell, they are in different rooms with the same name.

What I would change

PriorityChangeWhy
1 Implement message-ID-seeded fanout subsetting for broadcast relays, keeping full fanout for announces, fragments, sync and directed traffic. It is the specified behaviour, it is what bitchat does, gossip sync already provides the repair mechanism, and it is the difference between a room of 200 working and degrading silently.
2 Cancel a scheduled relay when a duplicate arrives first. The timer map already exists. It is a small change that directly reclaims airtime in exactly the dense case where jitter is deliberately long.
3 Add a 100 and a 200 node scenario to the simulation, asserting convergence and measuring writes per message. Right now the honest answer to "does it work in a crowd of 200" is "we do not know". Adding the scenario turns that into a number, and gives change 1 a before-and-after.
4 Instrument writes per message and refused writes as local diagnostics. There is no telemetry and there should not be, but a local diagnostics screen showing airtime pressure would let a field tester report something more useful than "it felt slow".
5 Lift the 25 ms pacing on WiFi Aware links. The pacing is a Bluetooth requirement, not a protocol one. On a WiFi link it turns a 250 Mbps path into an 18 KiB/s one, which is the entire value of the fast path.

Drills

  • "How does this scale?" Answer in three sentences. It does not scale the way a server does, because there is no capacity to add: the scarce resource is airtime in a shared 2.4 GHz band, and that is fixed. More users improves reach, because a message hops further, and simultaneously increases contention, because every relay costs airtime. So the real question is at what density delivery probability falls below useful, and the levers are how many transmissions each message causes and how far it travels.
  • A room of 200 people. What breaks first? Airtime. Each node relays to every non-ingress link, and with the degree capped at 6 that is roughly 1,000 writes per message across the room. Dedup means each node transmits once, TTL bounds depth, and jitter widens with degree so somebody else's copy usually wins, but none of those reduce the number of transmissions the way subsetting would. The symptom is graceful in the worst sense: writes get refused, fragments drop, transfers stall, and delivery probability falls silently.
  • Why does a crowd help and hurt at the same time? More phones means more relays, so a message can cross seven hops of real people rather than dying at hop two. It also means more bodies absorbing 2.4 GHz, which cuts per-hop distance at exactly the moment node count rises, and more devices contending for a band already shared with every WiFi network in the building. Which effect wins depends entirely on how many transmissions each message causes, which is why fanout is the lever that matters.
  • What is the honest answer to "have you tested this at scale"? 25 phones converge on one channel in the simulation, and a seeded soak of hundreds of random events across eight phones holds every invariant. Above the low tens is untested, and that matters specifically because the protocol document specifies fanout subsetting and the code implements full fanout, so the one mitigation for the dense case is documented and absent. Adding a 200-node scenario would turn "we do not know" into a number.
  • Why is there no telemetry to answer these questions from the field? Because no analytics reach any server, deliberately: no crash reporting, no usage metrics, no tracking. That is a principle rather than an oversight, and it costs exactly this: there is no way to learn what happens in a real crowd except by being in one. The available compromise is local diagnostics a field tester can read and report themselves, which is strictly better than "it felt slow" and still sends nothing anywhere.
