Chapter 30 · Media and transports

Files and media

Sending a photo over a radio that moves 18 KiB per second, to a recipient who may be six phones away, without letting anyone in between read it or forge it. Every constraint in this chapter has a named source.

In plain words

Explain it to a ten year old

A photo is far too big to shout in one go, so it is cut into about a thousand numbered pieces and sent one at a time, taking about half a minute. The other phone collects the pieces and glues them back together. Before it shows you the picture, it checks two things: that the signature on it really belongs to the person who claims to have sent it, and that a file claiming to be a photo actually starts with the bytes a photo starts with.

The file packet

One whole file per packet, as a TLV blob. There is no application-level chunking: the fragment layer splits the packet for the radio and reassembles it on the far side. Byte-compatible with bitchat's BitchatFilePacket. 

  Tag   Field       Length   Notes
  ────  ──────────  ───────  ──────────────────────────────────────────
  0x01  fileName    u16
  0x02  fileSize    u16      the VALUE is a u32
  0x03  mimeType    u16
  0x04  content     u32      last. u16 accepted from legacy senders.
  0x05  channel     u16      AIRHOP: routes a room attachment
  0x06  durationMs  u16      AIRHOP: voice length, value is u32
  0x07  caption     u16      AIRHOP: 512 bytes max

Tags 0x05 to 0x07 are Airhop additions. bitchat skips unknown tags by reading their u16 length, so they cost nothing in either direction: a bitchat client reads the file and ignores the extras.

The packet is signed at the outer layer, mandatorily, and the signature is re-verified after reassembly. That was a real High severity finding: attachments were never signature-checked, so anyone in range could drop a photo into a DM thread the UI badges as verified and end-to-end encrypted, attributed to that contact. bitchat already refused the unsigned case ("Dropping raw file transfer with missing/invalid signature").

Every size cap, and where it comes from

There are six different numbers here and they are not arbitrary.

ConstantValueWhat it boundsWhy that number
MAX_FILE_BYTES 1 MiB The absolute ceiling for any file. bitchat's general file limit. Not ours to raise.
MAX_IMAGE_BYTES, MAX_VOICE_BYTES 512 KiB Received photos and voice notes. bitchat's per-type caps, enforced when it decodes.
MAX_SENT_IMAGE_BYTES 256 KiB Photos this app sends. Half the receive cap, and the reason is subtle. bitchat expires a half-built assembly 30 seconds after the FIRST fragment, not after the last: its buffer stamps a timestamp once and never refreshes it. At about 20 ms pacing, 512 KiB is around 1,120 frames and 22 seconds, so a photo at the ceiling only lands if the link never forces a single retry. 256 KiB is about 11 seconds, which leaves room for the backoff a busy link forces. bitchat's own photos are around 45 KB at a 448 px edge, so this is still generous.
MAX_BITCHAT_TRANSFER_BYTES 350 KiB The line past which sending to a bitchat peer is worth warning about. Not a cap. Airhop to Airhop carries the full 1 MiB happily, because Airhop's reassembly times out on idle rather than total duration. Above 350 KiB the file is dropped on arrival by a bitchat peer and we would otherwise show a sent tick.
MAX_FRAMED_FILE_BYTES ~1.13 MiB The reassembly ceiling. bitchat's FileTransferLimits.maxFramedFileBytes formula, verbatim: 1 MiB plus max fileName and mimeType TLVs plus the packet envelope. Mirrored so the reassembler accepts the largest file a bitchat peer can send.
MAX_VIDEO_SECONDS 15 Camera recording length. There is no transcoder in the app, and quality in the picker applies to stills only, so length is the only lever on size. At the 1 MiB ceiling a longer clip would be refused after the user had already shot it, which is the worst possible moment to say no. A picked video is still checked at pick time, since nothing bounds what is already in the library.
MAX_PAYLOAD_BYTES 10 MiB The generic decompression bound. bitchat Android's number, not iOS's, deliberately. Airhop caps inflation at the declared size while it runs rather than checking afterwards, so a large declared size costs nothing to refuse.

Why the file cap cannot be raised unilaterally

bitchat-iOS refuses any packet whose declared expanded size passes its framed ceiling, and it refuses it by returning nil with nothing logged. Raising Airhop's cap past that would leave sending, Android delivery and the local UI all working while every attachment to an iPhone silently stopped arriving, with no error at either end. bitchat-Android allows 10 MiB, so the ceiling is iOS's alone and there is no cross-platform number to raise to.

This is enforced rather than remembered: conformance.test.ts reads maxPayloadBytes out of the vendored FileTransferLimits.swift and fails if Airhop's caps no longer fit under the ceiling it implies.

MIME resolution and magic bytes

Resolved, never passed through

A picker often returns nothing, and an empty or unrecognised type is dropped on arrival by both clients, which looks identical to a successful send from the sender's side. 

  resolveMimeType(declared, filename):
    declared type, IF the allow-list admits it
    else inferred from the file EXTENSION
    else "application/octet-stream"     ← always accepted, renders as a document

The allow list

CategoryTypes
Imagesimage/jpeg, image/jpg, image/png, image/gif, image/webp
Audioaudio/mp4, audio/m4a, audio/x-m4a, audio/aac, audio/mpeg, audio/mp3, audio/wav, audio/x-wav, audio/ogg
Documentsapplication/pdf, application/octet-stream
VideoAny video/*. Airhop's extension; bitchat has no video MIME type at all, which was one of its documented gaps.

Both audio/m4a and audio/x-m4a appear because platforms disagree on which is canonical. Airhop sends audio/mp4 and accepts both.

Magic byte validation

On receipt, the declared type is checked against the file's leading bytes, so a file cannot lie about what it is. 

  image/jpeg    FF D8 FF
  image/png     89 50 4E 47 0D 0A 1A 0A
  image/gif     47 49 46 38 (37|39) 61          "GIF87a" or "GIF89a"
  image/webp    52 49 46 46 .... 57 45 42 50    "RIFF" .... "WEBP"
  audio/mp4     length > 100 only               recorder output varies by
  audio/m4a                                     platform; bitchat is lenient
  audio/aac                                     here too and size-caps instead
  audio/mpeg    ID3 tag, or an MPEG frame sync
  application/octet-stream, video/*, unknown    SKIPPED, deliberately

application/octet-stream skips validation because its whole meaning is "arbitrary bytes"; there is nothing to check against. Video skips because the container zoo is large and bitchat is lenient there too. This is the same leniency profile bitchat's MimeType.matches uses, which matters because a stricter check would refuse files a bitchat peer considers valid.

Scenario M03 pins the attack: "a file that lies about its type is refused".

Private media, and the downgrade attack

A DM attachment can travel two ways, and the difference is confidentiality.

The legacy form: signed cleartext 0x22

A directed FILE_TRANSFER. It is signed, so a relay cannot forge it, but it is not confidential: every node the fragments cross can read the whole file. bitchat classifies this as the legacy migration fallback and has scheduled its removal.

The sealed form: Noise payload 0x20

The whole file packet is encrypted inside the recipient's Noise session before fragmenting, so relays carry opaque ciphertext. Airhop seals to 0x20 whenever the recipient has proven capability bit 8.

The downgrade attack, and why "proven" is the operative word

Announced capability bits are a discovery hint. Anyone can copy a victim's public Noise key off the air and self-sign an announce carrying whatever bits they like. If encrypted media selection depended on the announced bit, an attacker could announce bit 8 off for a victim and force every attachment sent to them into the readable form.

So the rule is absolute: only a capability proven inside a completed Noise session, via payload 0x21, selects encrypted sending. Nobody in radio range can force an attachment into the clear. Scenario M09 pins it: "a private photo is sealed in the session, not signed in the open".

Sealing lives in the router (it needs the session) while fragmentation lives in the file transfer service (it needs the paced queue), so there is a buildNoisePayloadPacket that hands the packet back instead of writing it. One Noise ciphertext of a few hundred kilobytes still has to be split into single-write frames and paced onto the radio.

Bit 9, privateMediaReceipts, adds durable deduplication of stable media IDs, which is what permits a bounded retry. It does not replace bit 8.

Where media is allowed

Media rides the BLE file-transfer path only. It is flood-broadcast over Bluetooth, never bridged to Nostr, and signed but not encrypted in the public case. So it is offered only where that is coherent.

ContextMediaWhy
#bluetoothYesPublic anyway, and everyone in it is reachable over BLE.
Mesh DMs, dm:<peerID>YesTravels over BLE to that peer, sealed when they have proven bit 8.
Location channels and teleported cellsNoNostr-scoped. Media cannot ride Nostr, so remote participants would never receive it.
Private #name channelsNoThey encrypt their text. Broadcasting unencrypted media would quietly break the privacy the channel advertises.
Private groupsNoSame reasoning.
Geohash DMs, dm:nostr_<pubkey>NoNostr-only pseudonym chats.

This mirrors bitchat's canSendMediaInCurrentContext exactly, so the two apps behave identically about what a channel can carry.

The channel tag (0x05) had its own finding: it used to auto-join arbitrary rooms. Now the tag must name a room the receiver has actually joined and that canSendMedia allows, otherwise the attachment is refused. Scenario M08 pins it: an attachment cannot be forged, misrouted, or aimed at a room you never joined.

Why media does not ride Nostr

Nostr relays carry small signed events, not file bytes. Sharing a file over Nostr means uploading it to a separate HTTP host and posting a link (NIP-96). That host is a central server that can log, throttle, or take down your files, which is exactly what this app avoids. So attachments travel only over Bluetooth, LAN or WiFi.

On disk, and the retention sweep

  RECEIVE
     fragments reassemble -> inner packet -> signature re-verified
     -> magic bytes checked -> written to the CACHE directory
        with the prefix "airhop_"

  RETENTION  (Privacy -> Keep media for)
     7 days by DEFAULT, 14 or 30 by choice.  NO UNBOUNDED OPTION.
     sweepExpiredAttachments() runs at launch, capped at 200 deletions
     per pass so a large backlog does not block startup.

  PANIC WIPE
     wipeCacheDirectory() empties the WHOLE cache, not just the
     airhop_ prefixed files. A sent document, a sent video, a small
     image sent unmodified and the saved QR card all live under other
     names or in the pickers' own subdirectories, and every one of them
     used to survive.

The no-unbounded-option decision matters: the threat model lists physical device seizure, and a stored photo outliving its conversation is exactly the evidence a seizure recovers. A "keep forever" setting would be a foot-gun disguised as a preference.

Auto-download is a setting. With it off, an incoming attachment shows as a card and nothing touches disk until the user accepts. That mirrors bitchat's explicit-accept behaviour, and it matters on a metered or hostile mesh.

Image compression

A modern phone photo is 3 to 8 MB. The send cap is 256 KiB. So compression is not an optimisation, it is the only way the feature exists.

Quality settingRough targetUse
LowSmallest, fastest to sendA crowded mesh, a weak link, or a bitchat recipient.
MediumDefaultOrdinary use.
HighClosest to the capA good link where detail matters.

For comparison, bitchat's own photos are around 45 KB at a 448 pixel edge, which is about two seconds of transfer. That is the size at which media on a mesh is genuinely pleasant, and it is a useful anchor when arguing about caps.

An image already small enough is sent unmodified, which is why the panic wipe has to clear the whole cache rather than only prefixed files: an unmodified send never gets the prefix.

Drills

  • Why does Airhop send photos at 256 KiB when the receive cap is 512 KiB? Because bitchat expires a half-built assembly 30 seconds after the first fragment rather than the last: its buffer stamps a timestamp once and never refreshes it. At about 20 ms pacing, 512 KiB is roughly 1,120 frames and 22 seconds, so a photo at the ceiling only lands if the link never forces a single retry. 256 KiB is about 11 seconds, leaving room for the backoff a busy link forces. Airhop to Airhop is unaffected either way, because Airhop's own reassembly times out on idle rather than total duration.
  • Why is MIME resolved rather than passed through? Because a picker frequently returns nothing, and an empty or unrecognised type is dropped on arrival by both clients, which from the sender's side looks exactly like a successful send. So the type is taken from the declared value when the allow list admits it, else inferred from the extension, else application/octet-stream, which is always accepted and renders as a document. A file always has a type that will be accepted.
  • Explain why "proven" capability matters for private media. Announced capability bits are self-signed with a key carried in the same announce, and the victim's public Noise key is broadcast in the clear, so anyone can announce arbitrary bits under a victim's peer ID. If the encrypted-media decision read the announced bit, an attacker could announce bit 8 off for a victim and force every attachment sent to them into the signed cleartext form, readable by every relay. Only a bit proven inside a completed Noise session, via payload 0x21, selects encrypted sending.
  • Why can you not post a photo in a private channel? Because private channel text is sealed with XChaCha20-Poly1305 under the channel key, while media rides the file-transfer path, which is signed but not encrypted. Allowing an attachment there would broadcast it in the clear inside a room the UI presents as private, which is worse than not having the feature. It mirrors bitchat's own policy of allowing media only in the mesh room and mesh DMs.
  • A user asks why their photo from last month is gone. What do you say? Media is swept on a schedule, seven days by default, with 14 and 30 available in Privacy settings and no unbounded option. That is deliberate: the threat model includes physical device seizure, and a stored photo outliving its conversation is exactly the evidence a seizure recovers. If they need to keep something, saving it to the device gallery takes it out of Airhop's cache and out of the sweep.
