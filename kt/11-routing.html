Chapter 11 · The protocol

Flood routing

No node knows the shape of the network, and nobody could keep such a map current if they had one. So Airhop does not route. It floods, with a hop limit, a duplicate filter and a random delay. Those three things are the entire algorithm, and each one is load bearing.

In plain words

Explain it to a ten year old

Imagine a room of people passing on a rumour. You do not know where your friend is standing, so you tell everyone next to you, and they tell everyone next to them. Two rules stop it going forever. First, each retelling ticks down a counter, and when it reaches zero nobody passes it on. Second, if you have already heard this exact rumour, you stay quiet. And everyone waits a random moment before repeating, so that people do not all shout at the same time.

Why flooding and not routing

Classic mobile ad hoc network research spent two decades on routing protocols: AODV, DSR, OLSR, batman-adv. All of them build and maintain some model of the topology. All of them assume that the model can be kept roughly current. In Airhop's environment that assumption fails hard.

Assumption a routing protocol makesReality in a crowd
Links are stable for seconds to minutes.A person turns around and a link drops. Someone walks past and a new one appears. Link lifetime is often under ten seconds.
Neighbours can be enumerated reliably.RSSI fluctuates by 20 dB from body position alone; a peer is discoverable, then not, then is again.
Control traffic is cheap relative to data.Airtime is the scarce resource. Topology updates in a room of 50 phones cost more than the messages.
Nodes cooperate honestly.Anyone in radio range can transmit anything, including fabricated topology. A route table is an attack surface.
Publishing adjacency is acceptable.A neighbour list broadcast in the clear tells one passive listener who is standing next to whom. That is exactly the inference the product exists to prevent.

Controlled flooding gives up optimality and buys robustness. It never needs to know the topology, it heals around a break automatically, it has no state to poison, and it publishes nothing about who is near whom. The cost is redundant transmissions, and the whole design of the next few sections is about bounding that cost.

The algorithm

  A PACKET ARRIVES ON LINK L

    1. decode. malformed -> drop (never throw)
    2. freshness: |now - timestamp| <= 2 minutes?
           no, and not a solicited sync response -> DROP, do not relay
    3. LEAVE only: verify the signature FIRST. unverifiable -> drop, do not relay
    4. packetID = SHA-256(type|sender|timestamp|payload)[0:16]
       seen in the last 5 minutes?  -> DROP silently
    5. record it in the seen set
    6. ttl' = min(packet.ttl, 7), then clamp if time critical
       ttl' > 1 ?
           schedule a relay of {packet with ttl = ttl'-1}
           after a random delay drawn from the degree-scaled window
    7. track it for gossip if it is a gossiped type
    8. dispatch to the type handler

Note the ordering. Relay happens before verification for every type except LEAVE. That is the right default: a relay carries traffic for peers whose signing keys it has never seen, and demanding a key before forwarding would break multi-hop delivery for exactly the strangers the mesh exists to reach. A node forwards opaque bytes it may not be able to check.

LEAVE is the exception because it is an instruction rather than content. It costs nothing to forge for any peer ID in earshot, it evicts that peer from everyone's view, and forwarding one that has already been refused spends the room's airtime and carries the attack to any node that checks less strictly.

The relay itself writes to every link except the one it arrived on (split horizon). Not writing back to the ingress link is what stops a two node mesh spinning forever, and it is the cheapest possible optimisation.

TTL, and why seven

Time to live is a hop counter, decremented at each relay and dropped at zero. It is the only thing that guarantees termination.

TTLEffective reach at 30 to 50 m per hopRedundant transmissions in a dense room
1One hop. Neighbours only.Minimal
390 to 150 mModest
7210 to 350 mBounded, but grows fast with density
15450 to 750 m in theoryImpractical. Every extra hop multiplies the transmission count in a dense graph.

Seven is inherited from bitchat and it is a good number for three independent reasons:

  1. It matches the useful scale. 210 to 350 metres is a venue, a city block, a march, a campus. Beyond that the sparse case dominates: there is simply nobody standing at hop eight.
  2. Cost grows superlinearly. In a graph with average degree d, a naive flood at TTL n can cost on the order of dn transmissions before dedup bites. Dedup collapses that dramatically, but the airtime spent before duplicates are suppressed still grows with depth.
  3. It is a fixed, interoperable constant. Changing it unilaterally would make Airhop packets travel further or less far than bitchat's on the same mesh, which is a behaviour difference that is hard to reason about and impossible to debug in the field.

Some types deliberately use less. LEAVE rides TTL 3. REQUEST_SYNC and every packet answering one ride TTL 0 and are strictly link-local. Public message origin TTL is drawn from 5 to 7 rather than fixed at the maximum, for the authorship-privacy reason in chapter 03.

Deduplication

Without a duplicate filter, a flood in a graph with any cycle runs forever. TTL bounds it but does not stop the exponential blowup inside those seven hops. Dedup is what makes the flood affordable. 

  class Deduplicator
    Map<hex(packetID), timestampMs>
    MAX_SIZE  = 1000 entries
    EXPIRY_MS = 5 minutes

    has(id):  present AND within 5 minutes  -> true
              present but older              -> delete, return false
    add(id):  re-insert to refresh LRU order,
              evicting the oldest when full
ChoiceReason
Content-derived ID, no nonce fieldThe same logical packet has one ID regardless of how many hops it took, because TTL, flags and signature are excluded from the hash. A nonce field would need to be signed and would waste bytes.
1000 entriesEnough for several minutes of traffic in a busy room. bitchat iOS uses the same; bitchat Android's gossip cache is only 100, which is one of the divergences Airhop resolves toward iOS.
5 minute windowLong enough that a slow multi-hop copy is still caught. Short enough that a legitimate resend after five minutes is not silently swallowed.

purgeExpired stops at the first fresh entryInsertion order means once a fresh entry is seen, everything after it is fresher. Turns a full scan into an early exit.

What dedup does not do

It is per device. It says nothing about a phone that never heard the original. That is why it cannot serve as the replay bound on its own, and why there is a separate freshness window on the timestamp. Freshness is the part that travels; dedup is the part that is local.

It also does not cover fragments, which skip the router's dedup entirely and are deduplicated per index inside their assembly instead.

Jitter, and why it scales with degree

If every node relays the instant it receives, all of them transmit at the same moment, collide on a shared radio, and the flood destroys itself. This is the broadcast storm problem, and it is one of the oldest results in ad hoc networking.

Jitter fixes it by staggering the retransmissions, which lets the first copy propagate and lets dedup silence everyone else.

Degree (Bluetooth peers)Jitter windowReasoning
0 to 210 to 40 msSparse. Relay almost immediately, because there is nobody else to do it and a slow relay risks the chain breaking before it propagates.
3 to 560 to 150 msModerate. Some redundancy exists, so wait a little and let it work.
6 to 980 to 180 msDense. Somebody else's relay very likely wins first.
10+100 to 220 msVery dense. Duplicate suppression should do most of the work; the more neighbours, the more likely one of them already relayed.

This is bitchat's RelayController policy, matched. Degree here is LinkRegistry.degree(), read through a callback so the window adapts continuously as people arrive and leave. It is the live count of Bluetooth peers, and both halves of that were bugs once.

It used to count links, across every transport, and both were wrong

Peers, not links. Bluetooth is dual-role: two phones that meet each dial the other, so one neighbour contributed two links and every room read as twice as crowded as it was. The dense threshold was crossed at three real peers where bitchat crosses at six, clamping voice and fragment range to five hops earlier than it should.

Bluetooth only. The delay exists for radio contention: every phone in earshot hears a packet at the same instant, and rebroadcasting together drowns the room out. A socket on LAN or WiFi Aware does not compete for that airtime, so counting it slowed the radio down for no reason.

Both halves now match bitchat's peerRegistry.connectedCount. The fix is invisible to the simulator, which models one link per pair; on hardware the degree roughly halves. Chapter 14 has the registry.

One thing bitchat does that Airhop does not: cancelling a scheduled relay when a duplicate arrives first. Airhop's FloodRouter keeps pending relay timers in a map keyed by packet ID, so the mechanism is there, but the receive path drops a duplicate before reaching any cancellation logic. In practice the effect is small (the relay still fires and its copy is deduplicated by everyone who already has it) but it is real airtime, and it is the cheapest available optimisation for a dense room. Noted in chapter 49.

Directed packets are still flooded

This is the point people find most surprising. A DM addressed to one peer is broadcast, not routed. 

  A wants to send to F. A has no idea where F is.

     A ──▶ B ──▶ C ──▶ D
     │     │     │
     └──▶ E ──▶ F ◀────┘

  A floods the packet with recipientID = F, ttl 7.
  B, C, D and E all relay it. None of them can read it.
  F receives it, decrypts it, and renders it.
  D and C also receive it, see it is not for them, and relay onward
  until the TTL runs out.

  Everyone in a 7 hop radius sees that A sent SOMETHING to F.
  Nobody but F sees WHAT.

The optimisation on top is the direct link shortcut: if a peer has been mapped to a specific link, a packet addressed to it goes down that link alone. That turns the common case into one write instead of a flood. But it is an optimisation, not the delivery guarantee, and it disappears the moment the peer is more than one hop away.

The privacy consequence is stated plainly in the threat model: packet headers carry sender and recipient IDs in the clear, exactly as bitchat's do. Who is talking to whom is not hidden on the mesh. Only the content is.

There is one rendering rule that keeps this from being a confidentiality bug: a directed packet is relayed by everyone but rendered only by the addressee. That was a real finding once, where attachments were rendered by every relay rather than only the recipient.

Source routes

The v2 header can carry an explicit hop list. Airhop follows them and never originates them. 

  nextHopFor(packet, myPeerID):
    if the route list contains my peer ID at position i,
    return the peer ID at position i+1 (or the recipientID if I am last)
    else return null

  relayPacket(packet, ingressLink):
    nextHop = nextHopFor(...)
    if nextHop is reachable over WiFi and not the ingress link  -> one write
    if nextHop is reachable over BLE  and not the ingress link  -> one write
    otherwise FALL THROUGH TO FLOODING

Following costs almost nothing and keeps Airhop from being a node that other implementations must route around: a bitchat peer that has computed a path through us is owed the hop it asked for.

Originating would require emitting the directNeighbors TLV, publishing our adjacency in cleartext to every nearby radio. One passive listener could then reconstruct the social graph of a room. bitchat's own peer-ID rotation analysis rejects it and bitchat stopped emitting the list. Flooding is the documented fallback for a route that cannot be built, and it is what Airhop already does.

Fanout subsetting, and where Airhop stands

bitchat has one further optimisation Airhop does not implement, and it is worth being explicit about because PROTOCOLS.md section 4 lists it as a routing constant.

Documented but not implemented

PROTOCOLS.md lists "Fanout subset size: ~ceil(sqrt(n)), deterministic fanout, excludes ingress peer". There is no such code in src/. MeshService.relayPacket writes to every link except the ingress one. This is a documentation-versus-code gap, and it is also the most significant scaling item on the list in chapter 49.

What bitchat actually does, and why it matters:

  FULL FANOUT (what Airhop does)
    a node with 6 links relays to all 5 non-ingress links
    room of 25 phones, one message -> hundreds of writes

  DETERMINISTIC SUBSET (what bitchat does)
    a node with 6 links relays to a subset seeded by the MESSAGE ID
    so different messages take different subsets, and coverage is
    statistical across many messages rather than guaranteed per message

    announces, fragments and sync packets keep FULL fanout, because
    those are the ones that must reach everybody
    directed traffic keeps FULL targeted fanout

The trade is coverage against airtime. Full fanout guarantees that if a path exists within the TTL, the packet takes it. Subsetting accepts a small probability that a particular message misses a particular node, in exchange for a large reduction in redundant writes, and leans on gossip sync (chapter 12) to repair the gaps.

Airhop's full fanout is defensible for the crowd sizes it has been tested at (scenario B06 converges 25 phones on one channel, B07 checks that a forming crowd does not drown itself in control traffic). It is not obviously defensible at 200. The honest position is: this is untested above the low tens, and the mitigation bitchat uses is available and not taken.

The freshness window

Every packet is held to a plus or minus 2 minute window on its timestamp at ingress, and outside it the packet is neither relayed nor acted on.

QuestionAnswer
Why not rely on dedup?Dedup is per device with a 5 minute window. It says nothing about a phone that never heard the original. Freshness is the part that travels.
Why 2 minutes?Phones are NTP synced and an offline real-time clock drifts by seconds a day, not minutes. So the failure mode is rare and visible (a peer whose clock is wrong cannot talk to anyone) rather than silent.
What about gossip sync, which replays old packets by design?A response carries IS_RSR and ttl = 0, and the receiver skips the window only when the packet claims RSR and arrives from a peer it has an outstanding request to, inside a 30 second response window. The flag alone is a sender's claim; the pending request is the receiver's own record. This is why sync requests are unicast.
Are there tighter windows?Yes. Announces get 15 minutes (symmetric, the union of what both bitchat clients accept). Live voice gets 30 seconds, because stale audio is worthless and replaying a recorded burst at someone later is an attack scenario (M07).
What if our own clock is wrong?The app infers it. If two or more different peers send packets outside the window, it blames its own clock and shows a banner. One peer sending stale packets is that peer replaying; several peers disagreeing at once points at what they have in common. Any accepted packet clears the flag.

Alternatives from the literature

ProtocolHow it worksWhy not here
AODV (reactive) Flood a route request, the destination replies, both ends cache the path. Used by Zigbee and by the old 802.11s mesh. The route discovery flood costs as much as just flooding the data. Cached routes go stale in seconds when the nodes are people. And the reply path is a spoofing target.
OLSR (proactive, link state) Every node floods its neighbour set continuously; everyone computes shortest paths. Multipoint relays reduce the flooding cost. Continuous topology broadcast is exactly the privacy leak Airhop refuses, and the control overhead in a room of 50 phones exceeds the data.
batman-adv Nodes do not know full paths, only the best next hop, learned from originator message counts. Very robust in real deployments. Still requires continuous originator broadcasts and per-neighbour state, and still publishes adjacency implicitly. Better suited to fixed WiFi mesh nodes than to moving phones.
Bluetooth Mesh (the SIG profile) Managed flooding with a TTL, exactly like Airhop, plus provisioning, network keys, and relay/friend/low-power node roles. The architecture is right, the trust model is wrong: provisioning requires a coordinator and a network key shared across the whole mesh, which suits building automation and not strangers in a crowd. And no phone platform exposes it.
Gossip / epidemic protocols Each node forwards to a random subset with some probability, giving high delivery with far fewer transmissions than full flooding. This is essentially what bitchat's fanout subsetting is. It is the most credible upgrade path for Airhop's scaling, and it is the recommendation in chapter 49.
Geographic routing (GPSR and relatives) Forward toward the destination's coordinates. Requires knowing where the destination is, which means publishing everybody's location. A non-starter for this product.

Drills

  • Why is a packet relayed before its signature is checked? Because a relay routinely carries traffic for peers whose signing keys it has never seen, and it may never see them: the sender might be six hops away and its announce might not have reached us. Demanding a key before forwarding would break multi-hop delivery for exactly the strangers the mesh exists to reach. Forwarding is separate from delivery, and a relay never renders what it forwards. LEAVE is the one exception, because it is an eviction instruction rather than content.
  • Explain the broadcast storm problem and Airhop's answer. If every node relays immediately on receipt, all neighbours transmit simultaneously on a shared medium, collide, and the flood destroys itself. The answer is jitter: a random delay before relaying, drawn from a window that widens with how many neighbours you have. In a sparse graph you relay almost immediately, because nobody else will. In a dense one you wait, because somebody else's copy will very likely arrive first and silence you through the duplicate filter.
  • Why is TTL not in the signed preimage, and what does that allow? Because it changes at every hop by design. If it were signed, a signature would be valid for exactly one hop and multi-hop delivery would be impossible. What it allows is that TTL is unauthenticated: an attacker can set it freely. So no trust decision may rest on TTL alone, which is why the direct-peer rule pairs a maximum TTL with a link binding rather than trusting the field.
  • A room has 200 phones. What worries you? Full fanout. Every node relaying to every non-ingress link means the number of writes per message grows with the number of edges, and airtime is the scarce resource in a band already shared with everyone's WiFi. Dedup bounds it, and jitter widens with degree, but neither reduces the number of transmissions the way subsetting would. This is untested above the low tens, and bitchat's message-ID-seeded subset is the available mitigation that is not implemented.
  • Why does a sync response get an exemption from the freshness window, and why is that not a hole? Because gossip sync exists to replay old packets, so without an exemption it could not work at all. It is not a hole because the exemption needs two independent things: the sender's IS_RSR claim and the receiver's own record of an outstanding request to that specific peer within the last 30 seconds. The flag alone grants nothing. That is precisely why requests are unicast rather than broadcast: a broadcast request has no peer to register against, so nothing it draws back can be attributed.
