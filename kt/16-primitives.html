Crypto primitives

In plain words

Explain it to a ten year old

There are only a few kinds of tool here. A lock that only one key opens. A signature that proves you wrote something and that nobody changed it. A handshake where two people who have never met end up holding the same secret number without ever saying it out loud. A fingerprint machine that turns anything into a short unique smudge. And a way to turn one secret into many different secrets so they cannot be mixed up. Everything else in this app is those five things, arranged carefully.

Notice what is not here: no RSA, no AES, no NIST P-curves, no SHA-1, no MD5, no custom cipher. Every choice is a modern, widely reviewed primitive with a constant-time reference implementation.

Curve25519: X25519 and Ed25519

One curve, two encodings, two uses. This confuses people constantly, so it is worth being precise.

X25519Ed25519
Curve formMontgomeryTwisted Edwards
OperationDiffie-Hellman key agreementEdDSA signatures
Question it answers"Can we agree on a secret nobody watching can learn?""Did this specific key holder produce these bytes, unaltered?"
Airhop calls itnoiseStaticPrivKey / noiseStaticPubKeysigningPrivKey / signingPubKey
Security levelRoughly 128 bits, comparable to 3072 bit RSA

They are birationally equivalent (you can convert between the forms mathematically) but Airhop keeps them as two independent key pairs. That is deliberate. Reusing one key for both agreement and signing is a known footgun: signature schemes and DH schemes stress the key differently, and cross-protocol attacks between them are a live research area. Two keys costs 32 extra bytes in the keychain and removes the whole class.

X25519 in one picture

  ALICE                                          BOB
  ─────                                          ───
  a  = 32 random bytes  (private)                b  = 32 random bytes
  A  = a * G            (public)                 B  = b * G

              ──────  A  ─────▶
              ◀─────  B  ──────

  shared = a * B                                 shared = b * A
         = a * (b * G)                                  = b * (a * G)
         = (a*b) * G                                    = (a*b) * G
                        SAME 32 BYTES

  An observer sees A and B. Recovering a from A means solving the
  elliptic curve discrete logarithm problem, which is infeasible.

The output of x25519.getSharedSecret is the x-coordinate of the shared point. It is not a key. It has structure and it is not uniformly random, which is why every protocol that uses it feeds it through a KDF before using it as key material. Noise does this with mixKey; the Double Ratchet does it with kdfRk.

Airhop uses X25519 in five distinct places: the three ephemeral DH operations inside a Noise XX handshake, the two DH operations inside Noise X, every ratchet step in the Double Ratchet, one-time prekeys, and the sealing of courier envelopes.

Ed25519 in one picture

  SIGN                                    VERIFY
  ────                                    ──────
  sig = Ed25519.sign(message, priv)       ok = Ed25519.verify(sig, message, pub)

  64 byte signature = (R, s)              recomputes and checks the equation

  Properties you get:
    * unforgeable without the private key
    * covers the EXACT bytes: one bit changes, verification fails
    * DETERMINISTIC. The same message and key always give the same
      signature, because the nonce is derived from a hash of the key
      and the message rather than from randomness.

The determinism matters here for a subtle reason: it means signing is safe on a device with a broken random number generator, which historically destroyed ECDSA keys (the PlayStation 3 case, and several Bitcoin wallets). It also means a packet signed twice produces identical bytes, which keeps content-derived packet IDs stable.

What Ed25519 does not give you: confidentiality (a signature reveals the message), or non-repudiation in the social sense that matters here. Airhop wants the opposite of non-repudiation for private messages, which is why DMs inside a Noise session carry no signature. See chapter 17.

AEAD: ChaCha20-Poly1305

AEAD means authenticated encryption with associated data. It does two jobs at once, and you must never do only one of them. 

  ENCRYPT(key, nonce, aad, plaintext) -> ciphertext || tag(16 bytes)

     ChaCha20 turns (key, nonce, counter) into a keystream.
     ciphertext = plaintext XOR keystream          ← confidentiality

     Poly1305 computes a MAC over aad || ciphertext ← integrity
     using a one-time key derived from ChaCha20 block 0.

  DECRYPT(key, nonce, aad, ciphertext||tag) -> plaintext OR FAILURE

     The tag is checked FIRST. If it fails, nothing is returned.
     Not "returns garbage". Not "returns partial". Nothing.
PartGuaranteeWhat breaks without it
EncryptionAn observer learns nothing about the content.Everything is readable.
Authentication tagAny modification is detected.An attacker can flip bits in the ciphertext and flip the corresponding bits in the plaintext, because a stream cipher XORs. Undetected message tampering.
Associated data (AAD)Extra bytes are authenticated but not encrypted.Headers could be swapped between messages. Airhop uses this for the Double Ratchet header and for the group ID plus epoch on group messages.

ChaCha20 rather than AES for a specific reason: it is a software cipher with no table lookups, so a portable implementation is naturally constant time. AES in software is vulnerable to cache timing attacks unless the CPU has AES-NI instructions, and the devices this app targets include cheap Android phones where that is not guaranteed. ChaCha20 also runs faster in software on such devices. This is the same reasoning that put ChaCha20 in TLS, in WireGuard, and in the Noise protocol suites everyone actually deploys.

The two variants

ChaCha20-Poly1305XChaCha20-Poly1305
Nonce12 bytes (96 bits)24 bytes (192 bits)
Safe with random nonces?No. Birthday collision after about 2^32 messages.Yes. Collision probability is negligible even after 2^80 messages.
RequiresA counter, managed carefullyNothing. Just use random bytes.
Airhop uses it forNoise transport (counter nonce), group messages (explicit nonce), Double Ratchet (zero nonce, single-use key)Private channels, bitchat's Nostr DM cipher

XChaCha20 works by first running the HChaCha20 function over the key and the first 16 bytes of the nonce to derive a subkey, then running ordinary ChaCha20 with that subkey and the remaining 8 nonce bytes. The practical effect is that you can generate nonces randomly and stop thinking about it, which is exactly what you want when there is no natural counter, as in a channel where any member may send at any time with no shared sequence.

Nonces, the most dangerous parameter

The rule

Never use the same (key, nonce) pair twice. For a stream cipher this is catastrophic, not degraded. Two messages encrypted under the same keystream can be XORed together to cancel the keystream entirely, leaving plaintext1 XOR plaintext2, which is often enough to recover both. Poly1305 is worse: nonce reuse can leak the authentication key, which lets an attacker forge arbitrary messages.

Airhop has four nonce strategies, one per context, and each is correct for its context:

ContextStrategyWhy it is safe
Noise transport A 4 byte big-endian counter, prepended to each message, expanded into the 12 byte nonce as [0,0,0,0][counter LE][0,0,0,0]. Each direction has its own key and its own counter, so no value repeats. The counter is prepended so the receiver can decrypt out of order using a sliding replay window. The session throws at 2^32 messages rather than wrapping.
Double Ratchet An all-zero nonce. Legitimate, because every message key is used exactly once. The ratchet derives a fresh 32 byte key per message from the chain, so there is no second message under that key for the nonce to collide with. This looks alarming and is correct.
Private channels, Nostr DMs 24 random bytes, XChaCha20. The extended nonce makes random generation safe. There is no shared counter to maintain across members, and there could not be.
Group messages An explicit 12 byte nonce carried in the envelope, with AAD = groupID || epoch. Matching CryptoKit's ChaChaPoly so bitchat interoperates. The epoch in the AAD is what prevents a message from one epoch being replayed into another.

SHA-256, HMAC, HKDF

SHA-256

A hash takes any input and produces a fixed 32 bytes. The properties that matter:

  • Preimage resistance. Given an output, you cannot find an input that produces it. This is what makes peer IDs work: an attacker cannot construct a Noise key that hashes to someone else's peer ID.
  • Collision resistance. You cannot find two inputs with the same output. This is what makes packet IDs meaningful for deduplication.
  • Determinism. Same input, same output, on every device and every platform. This is what makes safety numbers work.

Airhop uses SHA-256 in five places:

  peerID       = hex(SHA-256(noiseStaticPubKey)).slice(0, 16)     // 8 bytes
  packetID     = SHA-256(type || sender || timestamp || payload)[0:16]
  GCS h64      = SHA-256(packetID)[0:8] as u63 BE, sign bit cleared
  fingerprint  = SHA-256(domain || noisePub || signingPub)
  Noise        = mixHash, and inside HMAC and HKDF

Why 8 bytes is enough for a peer ID

64 bits of a preimage-resistant hash. To find a Noise key hashing to a chosen peer ID takes about 2^64 operations, which is out of reach. To find any two keys with the same peer ID takes about 2^32 by the birthday bound, which is very reachable, but that is a collision between two attacker-controlled identities and buys nothing: both would be the attacker's own keys, and neither would impersonate a real user. The security property needed is preimage resistance, not collision resistance, and 64 bits delivers it.

The real limitation is different: a peer ID does not rotate. It derives from the long-term Noise key, so the same device is linkable across sessions until the identity is regenerated. That is stated in the threat model as out of scope. Only per-cell geohash identities are ephemeral.

HMAC-SHA256

A keyed hash. HMAC(key, message) proves that whoever produced the output knew the key. Plain SHA-256(key || message) is not a safe substitute, because Merkle-Damgard hashes are vulnerable to length extension: an attacker who sees the output can append data and produce a valid output for the extended message without knowing the key. HMAC's nested construction removes that.

Airhop uses HMAC for the courier recipient tag, geohash identity derivation, private channel Nostr identity derivation, and inside every ratchet chain step.

HKDF

Extract then expand. Takes non-uniform input keying material (like a raw DH output, which has mathematical structure) and produces any number of uniformly random independent keys. 

  PRK    = HMAC(salt, ikm)                    // extract: concentrate entropy
  OKM[1] = HMAC(PRK, info || 0x01)            // expand: stretch to any length
  OKM[2] = HMAC(PRK, OKM[1] || info || 0x02)
  ...

Noise uses a variant with no info string and the chaining key as the salt. That is why noiseHkdf(ck, ikm, count) in noise-xx.ts looks slightly different from the RFC 5869 shape: it is the Noise specification's version, and it must match bitchat exactly.

The three-output split

Noise's split() normally derives two transport keys. Airhop asks for three, and takes the third as the exporterSecret that seeds the Double Ratchet. This costs nothing in interoperability: HKDF derives each block from the previous one, so k1 and k2 are bit identical to a two-output split. bitchat negotiates exactly the same transport keys and never knows a third value was computed. Chapter 18 explains why the exporter secret and not the transcript hash.

secp256k1, and why there are two curves

Airhop uses two different elliptic curves, and a reasonable first reaction is that this is one too many.

CurveUsed forWhy it must be this one
Curve25519Everything on the mesh: sessions, signatures, ratchets, prekeysIt is what Noise specifies and what bitchat uses. Modern, fast, safe defaults.
secp256k1Nostr identity, geohash identities, Cashu P2PK locksNostr is defined on secp256k1 with BIP-340 Schnorr signatures. Cashu is Bitcoin-adjacent and uses the same curve. Neither is negotiable.

The bridge between them is HKDF. The Nostr private key is derived from the Ed25519 signing private key: 

  nostrPrivKey = HKDF-SHA256(
                   ikm  = ed25519 signing private key,
                   salt = none,
                   info = "airhop-nostr-key-v1",
                   len  = 32
                 )

One root identity therefore has one stable Nostr identity across mesh, relays and payments, with no link to a phone number or email, and with nothing extra to provision, back up or wipe. The derivation is one-way, so the Nostr key cannot be walked back to the signing key.

A comment worth reading in the source

identity.ts carries a long note explaining what is deliberately absent: it once had a nostrPubKey field set to the Ed25519 public key, with a comment claiming that was the npub. Both were wrong. The Nostr identity is secp256k1 and it comes from HKDF over the signing private key; the Ed25519 public key bears no relation to it. Nothing read the field, so nothing was broken, but it was a plausible-looking value that would have published an address no relay could deliver to.

The even-Y normalisation

Nostr public keys are 32 byte x-only keys, following BIP-340, which fixes the convention that the point has an even Y coordinate. A raw random 32 byte scalar can land on odd Y, which would make the x-only point used in ECDH the wrong (negated) point and break interoperability silently. 

  normalizeSecretKeyEvenY(priv):
    if getPublicKey(priv, compressed)[0] == 0x02  -> already even, return priv
    else                                          -> return (n - priv) mod n

And on the decrypt side, the sender's x-only key is tried with both parities (0x02 then 0x03), matching bitchat. This is the sort of detail that is invisible until two implementations fail to talk to each other for no visible reason.

Domain separation

The same key derivation used for two purposes must not produce the same output. Every derivation in Airhop carries a unique string.

SeparatorDerives

The safety number pair is the clearest example of why this matters: the pair hash takes the individual fingerprint's output as its input, so without different separators one could be substituted for the other.

All of these end in v1 for a reason. Changing a separator changes every key derived from it, which means old and new builds cannot decrypt each other. That is a deliberate migration mechanism, and it is why they are listed in ARCHITECTURE.md as one of the three families of name that are addresses rather than labels.

Randomness

Every private key, ephemeral key, nonce, stream ID and message ID comes from crypto.getRandomValues, which is the platform CSPRNG: SecRandomCopyBytes on iOS, /dev/urandom through the Android framework.

The polyfill must be the first import

Hermes, the JavaScript engine React Native uses, does not implement crypto.getRandomValues. react-native-get-random-values provides it, and its import sits at the very top of src/app/app.tsx with a comment saying it must be first. If any @noble module is imported before the polyfill, key generation fails at runtime, and in the worst case a library could fall back to a weak source. This is one line that quietly holds up the entire security model.

The library choice

Airhop uses Paul Miller's @noble family: @noble/curves, @noble/ciphers, @noble/hashes. All MIT licensed, all audited by Cure53.

AlternativeWhy not
libsodium (via a native binding)The gold standard, but it is native code. That would mean a native dependency inside src/core/, which is the one rule that makes the entire protocol testable in CI without a phone. It would also mean two builds to keep in step.
WebCryptoHermes exposes almost none of it, and what exists does not cover Curve25519 or ChaCha20.
tweetnacl-jsVenerable and small, but unmaintained, no ChaCha20-Poly1305 AEAD in the shape Noise needs, and no secp256k1.
Rolling your ownNo.

The honest caveat: JavaScript cannot guarantee constant time. A JIT may branch on data, garbage collection timing varies, and the engine offers no primitive for timing-invariant comparison. @noble is written to be constant time as far as the language allows, and it is careful about it, but a physical side-channel attacker with sample access to the device is outside what any pure-JS implementation can defend. For Airhop's threat model (a remote or nearby network attacker, plus device seizure) this is acceptable. For a threat model including a local timing adversary with repeated measurements, it is not, and that should be stated rather than assumed away.

The @cashu/cashu-ts library brings its own secp256k1 operations for blinding and DLEQ verification, which is a second crypto implementation in the tree. It is scoped to the wallet.

Pitfalls this codebase actually hit

PitfallWhat happenedFix
Using a public value as key material The Double Ratchet root key was seeded from the Noise handshake hash. Only wire bytes go through mixHash, so that value is public to anyone who captured the handshake, and handshakes flood at TTL 7. Anyone in the room could recompute the root key and forge or decrypt DR messages. Seeded from the exporter secret, a third HKDF output of the same split, descending from the chaining key that absorbed the ephemeral DH outputs.
A skipped hash step Noise always runs mixHash(prologue) after initialisation, even when the prologue is empty. Skipping it left Airhop's handshake hash one hash behind bitchat's, which is used as AEAD associated data when the static key is sealed in message 2. Same key, different AAD, tag mismatch, and no bitchat to Airhop handshake could ever complete. Run it unconditionally.
Assuming an encoder is canonical DEFLATE output is not canonical, so re-compressing during signature verification produced different bytes and rejected valid packets. Keep the received wire form and reuse it verbatim. Chapter 09.
Verifying only when asked to Announces were signature-checked only when the sender set the SIGNED flag, which let the sender opt out of being checked. verifyPacket returns false when SIGNED is clear, so one unconditional call covers both "no signature" and "bad signature".
Confusing "no key" with "no check" Public messages from senders not yet in the registry were accepted unverified, so an unsigned packet claiming a known ID rendered as that peer. A missing key is a failed check, never a skipped one.
A decoder that throws A malformed compressed frame raised RangeError out of the decoder into a native callback with no handler. A malformed frame must decode to null, never throw.

Drills

  • Why does Airhop keep two separate key pairs when X25519 and Ed25519 are the same curve? Because reusing one key across a key agreement scheme and a signature scheme is a known footgun with a live literature of cross-protocol attacks. The two schemes stress the key differently. Two key pairs costs 32 extra bytes in the keychain and eliminates the entire class. It also makes the roles legible in the code: noiseStaticPrivKey is for agreement, signingPrivKey is for authentication.
  • The Double Ratchet uses an all-zero nonce. Is that a bug? No, and it is worth being able to say why confidently. The rule is never to reuse a (key, nonce) pair. The ratchet derives a fresh 32 byte message key for every single message from the chain key, so each key is used exactly once. With a single-use key there is no second message under it for the nonce to collide with, so any fixed nonce is safe. What would be a bug is a fixed nonce with a reused key, which is what the Noise transport avoids with its counter and what XChaCha20 avoids with a 24 byte random nonce.
  • Why is 64 bits enough for a peer ID? Because the property needed is preimage resistance, not collision resistance. Finding a Noise key that hashes to a chosen peer ID takes about 2^64 operations. Finding any two colliding keys takes about 2^32 by the birthday bound, but both would be the attacker's own keys, so it impersonates nobody. The real weakness of the peer ID is not its length, it is that it never rotates, which makes a device linkable across sessions.
  • Why HMAC rather than SHA-256 of the key concatenated with the message? Length extension. SHA-256 is a Merkle-Damgard construction, so from SHA-256(key || m) an attacker can compute SHA-256(key || m || padding || extra) without knowing the key. HMAC's nested double-hash structure removes that. This matters directly for the courier tag, which is an HMAC over a context string and an epoch day.
  • Someone proposes swapping ChaCha20-Poly1305 for AES-256-GCM "because it is faster". Respond. It is faster only on hardware with AES-NI, and the devices this app targets include cheap Android phones where that is not guaranteed. In software, AES needs table lookups, which makes constant-time implementation hard and opens cache timing attacks; ChaCha20 has no lookups and is naturally constant time. And it would break the wire protocol entirely: the Noise suite name Noise_XX_25519_ChaChaPoly_SHA256 is part of the handshake's initial state, so a different cipher is a different protocol that no bitchat node can speak.
  • What is the strongest criticism of the crypto stack? That it is pure JavaScript, so constant-time behaviour is best effort rather than guaranteed, and that the composition of primitives has not been externally audited even though the primitives themselves have. The primitives are the right ones and the compositions follow published specifications, but "correct by inspection" is not the same as "audited", and the project says so.
