Fragmentation

A photo is half a megabyte. A Bluetooth write is 512 bytes. This chapter is the twelve hundred pieces in between, and the reason the reassembly code is one of the most defensively written files in the repository.

In plain words

Explain it to a ten year old

You want to send a long letter, but the postbox only takes small cards. So you cut the letter into 1,120 numbered cards, write "card 47 of 1,120" on each one, and post them one at a time. The person at the other end collects them, sorts them by number, and tapes the letter back together. If some cards go missing they wait a bit, and if nothing new arrives for thirty seconds they throw the pile away, because the sender has clearly gone.

The budget

The limit is the whole encoded frame, not the payload. This is the single most important sentence in the chapter. 

  512 BYTE FRAME BUDGET

  ┌────────────────────────────────────────────────────────────┐
  │ 16 │  8 │  8 │ 13 │              467                        │
  └────┴────┴────┴────┴─────────────────────────────────────────┘
    │    │    │    │                  │
    │    │    │    │                  └─ fragment data
    │    │    │    └───────────────────── fragment header
    │    │    │                            streamID 8, index 2,
    │    │    │                            total 2, innerType 1
    │    │    └────────────────────────── recipientID (present on a DM
    │    │                                 fragment, omitted on a public one)
    │    └─────────────────────────────── senderID
    └──────────────────────────────────── v2 packet header

  NO SIGNATURE. Fragments are unsigned by design; the inner packet
  carries the authenticity and is re-verified after reassembly.

512 is not an MTU. It is the Bluetooth core specification's ceiling on the size of a single attribute value, and it holds regardless of what MTU was negotiated. Past it, Android truncates a write without response (which cannot exceed MTU minus 3) and iOS refuses. A truncated frame fails to decode on the far side, and nothing is reported at either end.

The 557 byte era

Airhop once budgeted 469 bytes of payload. Add a 16 byte header, an 8 byte sender ID and a 64 byte signature and the encoded frame is 557 bytes, 45 over the ceiling. Every fragment of every attachment was discarded before any handler saw it, in both directions, with no error anywhere. Live push-to-talk kept working throughout, because a voice burst is capped at 210 bytes and never enters this path, which is why the bug survived: the feature that looked most fragile was the one that was fine.

bitchat derives 469 data bytes from the same 512 byte budget because its fragment header is smaller. Being two bytes under is harmless: the chunk size is a sender-side choice and the receiver reassembles by index without needing to agree on it.

The fragment payload

  outer packet:  type = 0x20 (FRAGMENT), ttl 7, flags = 0 (UNSIGNED)
                 senderID   = our peer ID
                 recipientID = THE PARENT PACKET'S recipientID

  payload:
    [0..7]    streamID      8 bytes, random per original packet
    [8..9]    index         u16 BE, zero based
    [10..11]  total         u16 BE
    [12]      originalType  u8, the inner packet's type
    [13..]    data          up to 467 bytes of the encoded inner packet

  The "data" across all fragments, concatenated in index order, is the
  complete wire encoding of the original packet, as returned by
  encodePacket(). The receiver runs decodePacket() on the result.

Why a fragment carries its parent's recipientID

Addressed to nobody, bitchat classifies a DM's fragments as public. Three things then go wrong: it archives sealed private media in its gossip store, it re-offers that media to third parties, and it floods each fragment to every neighbour instead of sending it down the directed path. Carrying the parent's recipient keeps a private attachment private and keeps the traffic on one path.

Why fragments are unsigned

A per-fragment signature would spend 64 of the 512 bytes, roughly 12 percent of every transfer, to authenticate a piece that means nothing on its own. The inner packet is signed and re-verified after reassembly, so a forged fragment can only ever produce a packet that fails verification. bitchat sends signature: nil and neither side's fragment path inspects one, so this is also an interop requirement.

The consequence is that both halves of the assembly key (sender ID and stream ID) are attacker-choosable, and fragments skip the deduplicator. Every defence in the receive path exists because of that.

Sending: the paced queue

  sendAttachment(file, channel or peer)
     │
     ├─ compress the image to the quality setting, check the per-type cap
     │     photo 512 KiB · voice note 512 KiB · anything else 1 MiB
     │
     ├─ build the BitchatFilePacket TLV, then the outer packet, then SIGN it
     │
     ├─ encodePacket() -> ~500,000 bytes
     │
     ├─ fragmentPacket()
     │     total = ceil(len / 467)
     │     streamID = 8 random bytes
     │     refuse if total > 65,535
     │
     └─ hand the array to the PACED QUEUE

  PACED QUEUE
     one fragment every 25 ms   (directed, IF the path touches BLE)
     one fragment every 30 ms   (broadcast, to a room)
     │
     ├─ write refused?  back off 60 ms and retry the same fragment
     │                   give up after 250 consecutive refusals
     │
     └─ report progress to the transfer store every 250 ms

The 25 ms is not politeness, it is required: without it the radio drops fragments and the transfer never completes. The broadcast case uses 30 ms because each broadcast fragment is one radio write per connected peer. In a room of six, one fragment is six writes, so airtime cost grows with room size while the sender's clock does not.

A refused write is ordinary rather than fatal. The GATT queue fills up, especially while an announce, a prekey bundle and a gossip round are also in flight. So a refusal backs off and retries rather than tearing anything down, and only 250 consecutive refusals count as a dead transfer.

Receiving: assemblies

  fragment arrives

     │                                                        keep the assembly
     │
     ├─ store, bump byteCount, refresh updatedAt, report progress
     │
     └─ all `total` indices present?
           concatenate in index order
           decodePacket()
           routePacket() the inner packet, which re-verifies its signature

The idle timeout, not a total timeout

The 30 second timeout is measured from the last fragment that arrived, not from the first. That distinction is the whole point. A 512 KiB photo is about 1,120 fragments paced 25 ms apart, so it cannot arrive in under roughly 28 seconds; a 1 MiB file takes twice that. Timing out on total duration deleted the half-built file mid-transfer, and the fragments still arriving then started a fresh assembly that could never reach its total. The file was lost silently and permanently. Idle time is what actually means the sender is gone.

Every hostile case, and its answer

Fragments are unsigned and skip the deduplicator, so anyone in radio range can emit one claiming any sender and any stream. Each defence below is written against a specific attack.

AttackWhat it would doDefence
Truncation: inject a fragment declaring total = 3 into a ten fragment stream The assembly completes early and hands the receive path a truncated payload as the whole message. total and originalType are pinned from the first fragment accepted and never re-read. A conformant sender restates the same values on every fragment, so this refuses nothing legitimate.
Kill switch: inject one oversized fragment into a 90 percent complete transfer Deleting the stream on an over-ceiling fragment made one cheap packet a remote kill switch for somebody else's photo, with no error at either end. Refuse the fragment, keep the assembly. A genuinely oversized stream still cannot complete and ages out on the idle timeout like any stalled one.
Eviction primitive: with 128 assemblies in flight, send one fragment that will be rejected anyway Starting an assembly evicts the oldest slot, so a doomed fragment still costs somebody a transfer. The size check runs before the table is touched.
Decompression bomb in a fragment: a 25 byte fragment that inflates to megabytes One fragment can exceed the reassembly ceiling despite the 512 byte frame budget, because the outer packet may be DEFLATE compressed and the decoder inflates up to the sender-declared size. The declared size bounds inflation while it runs (chapter 09), and the fragment's data length is checked against the reassembly ceiling.
Memory exhaustion: open thousands of streams Unbounded table growth. 128 concurrent assemblies, oldest evicted. Plus the per-stream byte ceiling.
Relabelling: change originalType mid-transfer The UI shows a photo becoming a document, or vice versa. Progress reports the pinned type, not the arriving fragment's claim.
Forged content: reassemble into a packet claiming a trusted sender A photo attributed to a verified contact in a thread badged end to end encrypted. The reassembled inner packet goes back through routePacket, and FILE_TRANSFER is held to senderIsAuthentic: a signature checked against the key bound to the claimed sender. A missing key is a failed check, never a skipped one.

Relaying a fragment

A relay forwards fragments individually and never reassembles. Only the addressee reassembles. Three rules apply:

  • Time critical jitter. Fragments use the 8 to 25 ms relay window rather than the ordinary 10 to 220 ms, and the TTL is clamped to 5 in a dense mesh. A sustained stream at full depth in a busy graph would crowd out everything else.
  • The addressee stops relaying. A fragment addressed to us has nowhere further to go, so relaying it is pure cost, and for a file that cost is the whole file. Without this, the receiver re-fragmented every byte it had just been handed and pushed it back out over its other links: a photo arrives over WiFi and is then echoed over Bluetooth at 18 KiB/s, spending seconds of radio and both devices' battery on a copy for the sender.
  • Fragments inherit the parent's version and route, so a routed file crosses the mesh on the path its parent planned rather than falling back to flooding the moment it is split.

Pacing is per transport, and it was not always

The Wi-Fi fast path was paced for a radio it never touched

The 25 ms gap exists because the Bluetooth stack drops writes handed over faster than it can make them. The pacer had no idea which transport carried a fragment, so a 1 MiB file over WiFi Aware took the same 56 seconds Bluetooth takes, on a link two orders of magnitude faster.

It now asks one question through a callback into the mesh service: does anything on the path touch the Bluetooth radio. That covers channel broadcasts as well as directed sends. If the answer is a definite no, the gap goes to zero; absent an answer it stays on the Bluetooth timings, because a transfer slower than it needed to be is a nuisance and one paced faster than the radio can take drops fragments and never completes.

Fragment size does not change with it. The receiver reassembles by index, the next hop may be Bluetooth, and bitchat refuses an over-size frame as it decodes. 467 bytes is protocol and stays whatever carries it.

And a second drain loop, from clearing the timer too early

drainTimer is cleared before the transport is awaited, so a second transfer starting mid-write set a fresh timer and opened a parallel drain. Two loops shifting one queue hand the radio fragments at twice the spacing, which is precisely the loss the spacing exists to prevent, and a second transfer beginning during a first is entirely ordinary. A draining flag now covers the await and releases before the tail re-schedules; releasing later would swallow that schedule and stall the queue.

Why the file cap cannot be raised

bitchat-iOS refuses any packet whose declared expanded size passes maxFramedFileBytes, and it refuses it by returning nil with nothing logged. Raising Airhop's cap past that would leave sending, Android delivery and the local UI all working while every attachment to an iPhone silently stopped arriving, with no error at either end. bitchat-Android allows 10 MiB, so the ceiling is iOS's alone and there is no cross-platform number to raise to. conformance.test.ts reads maxPayloadBytes out of the vendored FileTransferLimits.swift and fails if Airhop's caps no longer fit under the ceiling it implies.

Alternatives

ApproachVerdict
L2CAP connection-oriented channels BLE 4.1 added credit-based flow-controlled channels that carry an MTU far above 512 with the stack handling segmentation. Genuinely better for bulk transfer. Not used because bitchat does not, and using it would create a path that only Airhop-to-Airhop links could take, which is a second transport to keep in sync for a case the WiFi fast path already covers better.
Application-level chunking above the packet Sending a file as N packets of 64 KiB each, with its own resume logic. This was Airhop's original plan and was dropped: bitchat enforces the size cap when it decodes, so chunks above the cap are rejected outright and interop breaks in both directions. One BitchatFilePacket per file, split by the fragment layer, is what both sides expect.
Forward error correction (fountain codes, Raptor) Encode 1,120 fragments into 1,300 symbols, any 1,120 of which reconstruct the file. Removes the need for retransmission entirely and is genuinely elegant for a lossy broadcast medium. Costs a 15 percent airtime overhead on every transfer, adds a dependency, and cannot be adopted unilaterally without breaking bitchat. A real option for an Airhop-only fast path, and nothing more.
Selective retransmission (the receiver asks for missing indices) bitchat's gossip sync has a fragmentIdFilter TLV (0x06) for exactly this, narrowing a sync request to specific stalled streams. Airhop neither emits nor reads it: a stalled reassembly recovers through the ordinary 15 second round instead. A peer that sends one receives a normal full response, so the omission is compatible in both directions.

Drills

  • Why is 467 the right number and 469 wrong for Airhop? Because the budget is the encoded frame, and Airhop's fragment header plus a recipientID leaves 467. bitchat's smaller header leaves 469 from the same 512. Either is fine as a sender-side choice, since the receiver reassembles by index. What is not fine is treating 469 as a payload budget and then adding a 64 byte signature, which is how the frame reached 557 and every attachment silently failed.
  • Why does an over-ceiling fragment not delete the assembly? Because that would make one cheap unsigned packet a remote kill switch. Both halves of the assembly key are observable on the air, so an attacker can aim a fragment at any transfer in progress and destroy a nearly complete photo with no error at either end. Refusing the fragment and keeping the assembly means a genuinely oversized stream simply cannot complete and ages out on the idle timeout, which is the correct outcome for both the attack and the honest case.
  • A user says a large file transfer "stops at 90 percent every time". Where do you look? First, whether the last fragments are being dropped by the radio: check whether the pacing is being honoured and whether the link is being shared with live voice. Second, whether the idle timeout is firing, which would mean a stall longer than 30 seconds. Third, whether the receiver is hitting the reassembly ceiling, which points at a size cap mismatch. Fourth, if the receiver is a bitchat iPhone, whether the file exceeds maxFramedFileBytes, in which case it is refused silently on arrival regardless of how many fragments landed.
  • Why does the receiver of a directed fragment not relay it? It has nowhere further to go, and relaying it means re-fragmenting every byte just received and pushing it back out over every other link. The measured effect was a photo arriving over WiFi and being echoed over Bluetooth at 18 KiB/s, spending seconds of radio time and both devices' battery on a copy for the sender. The rule is narrow on purpose: only the addressee stops, so middle nodes still relay and multi-hop is untouched, and only FRAGMENT is affected.
